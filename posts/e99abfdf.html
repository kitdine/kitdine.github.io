先看两个小现象，都出自后文那个可以直接跑的示例（Dubbo 3.3.7）。

第一个：向扩展加载器要名叫 dubbo 的协议，拿到的并不是 DubboProtocol，而是七层套娃。

org.apache.dubbo.rpc.protocol.InvokerCountWrapper
  org.apache.dubbo.rpc.protocol.ProtocolSerializationWrapper
    org.apache.dubbo.rpc.cluster.filter.ProtocolFilterWrapper
      org.apache.dubbo.rpc.protocol.ProtocolSecurityWrapper
        org.apache.dubbo.rpc.protocol.ProtocolListenerWrapper
          org.apache.dubbo.qos.protocol.QosProtocolWrapper
            org.apache.dubbo.rpc.protocol.dubbo.DubboProtocol

而且把同一个程序连跑 6 次，中间三层的顺序出现了 4 种排列。

第二个：消费端把超时设成 200 毫秒，调用一个要跑 500 毫秒的方法，什么别的都没配。结果调用方等了 604 毫秒才拿到异常，提供方把这个方法完整执行了 3 遍。

这两件事看着不相干，其实来自同一副骨架：配置统一成 URL，每一层能力都是按名字加载的 SPI 扩展，能力之间靠一层层包装 Invoker 拼起来。这篇沿着这条线读 Dubbo 3.3 的源码，最后回到这两个现象，并给出完整的示例代码。

文中源码均取自 apache/dubbo 的 3.3.7 标签（提交于 2026-10-26），这是写作时 Maven Central 上的最新版本，2026-11-07 发布。

一切都是 URL

Dubbo 内部几乎不传配置对象，传的是 org.apache.dubbo.common.URL。服务的地址、协议、超时、负载均衡策略、重试次数，最后都会压成一个类似这样的东西：

dubbo://10.0.0.1:20880/com.foo.DemoService?timeout=3000&loadbalance=random&retries=2

URL 的好处是格式固定、可以一路往下传。下一节会看到，“这次该用哪个实现” 也是从 URL 里读出来的。代价是配置项都变成了字符串键值，写错一个键不会有编译期提示。

ExtensionLoader：按名字找类，再一层层包

Dubbo 没有用 JDK 的 ServiceLoader，而是自己写了 ExtensionLoader。扩展点是一个标了 @SPI 的接口，实现类写在以接口全名命名的文件里，一行一个 名字=类名。加载器按三个目录扫描：META-INF/dubbo/internal/（Dubbo 自带）、META-INF/dubbo/（用户扩展）、META-INF/services/（兼容 JDK 的目录）。

比如负载均衡，dubbo-cluster 里的 META-INF/dubbo/internal/org.apache.dubbo.rpc.cluster.LoadBalance 就是六行：

random=org.apache.dubbo.rpc.cluster.loadbalance.RandomLoadBalance
roundrobin=org.apache.dubbo.rpc.cluster.loadbalance.RoundRobinLoadBalance
leastactive=org.apache.dubbo.rpc.cluster.loadbalance.LeastActiveLoadBalance
consistenthash=org.apache.dubbo.rpc.cluster.loadbalance.ConsistentHashLoadBalance
shortestresponse=org.apache.dubbo.rpc.cluster.loadbalance.ShortestResponseLoadBalance
adaptive=org.apache.dubbo.rpc.cluster.loadbalance.AdaptiveLoadBalance

区别不在懒不懒加载。JDK 的 ServiceLoader 也是按需的：文档写明，迭代到哪个提供者才去找、才去实例化哪个。区别在三件事：

  • 按名字取。 ServiceLoader 的配置文件里只有类名，想要某一个实现只能遍历着挑；ExtensionLoader 的每一行带名字，getExtension("roundrobin") 直接拿到那一个，名字还能从 URL 参数里来。
  • 依赖注入。 实例造出来以后，加载器会找它的 setter，把别的扩展注入进去。
  • 自动包装。 同一个扩展点下的 Wrapper 类会一层层套在实例外面，这是 Filter 链、Cluster 包装这些机制的基础。

这三件事都在 ExtensionLoader#createExtension 里，去掉异常处理后是这样：

// dubbo-common/.../extension/ExtensionLoader.java，3.3.7
T instance = (T) extensionInstances.get(clazz);
if (instance == null) {
    extensionInstances.putIfAbsent(clazz, createExtensionInstance(clazz));
    instance = (T) extensionInstances.get(clazz);
    instance = postProcessBeforeInitialization(instance, name);
    injectExtension(instance);              // 1. setter 注入别的扩展
    instance = postProcessAfterInitialization(instance, name);
}
if (wrap) {
    List<Class<?>> wrapperClassesList = new ArrayList<>();
    if (cachedWrapperClasses != null) {
        wrapperClassesList.addAll(cachedWrapperClasses);
        wrapperClassesList.sort(WrapperComparator.COMPARATOR);
        Collections.reverse(wrapperClassesList);
    }
    for (Class<?> wrapperClass : wrapperClassesList) {
        // 2. 用 @Wrapper 的 matches / mismatches 判断要不要包（省略）
        instance = (T) wrapperClass.getConstructor(type).newInstance(instance);
        injectExtension(instance);
    }
}
initExtension(instance);                    // 3. Lifecycle#initialize
return instance;

注入和初始化好理解，值得细看的是第二步的包装。

Wrapper 是按形状认出来的

配置文件里的类，有一些并不是独立的实现，而是包装类。加载器认包装类的方法很直接，看它有没有一个“参数就是扩展接口本身”的单参公开构造器：

// ExtensionLoader#isWrapperClass
protected boolean isWrapperClass(Class<?> clazz) {
    Constructor<?>[] constructors = clazz.getConstructors();
    for (Constructor<?> constructor : constructors) {
        if (constructor.getParameterTypes().length == 1 && constructor.getParameterTypes()[0] == type) {
            return true;
        }
    }
    return false;
}

只要满足这个形状，它就不再是一个能按名字取到的扩展，而会被自动套在每一个真实实现外面。看一眼 Protocol 的配置文件（3.3.7 里分散在多个模块）就知道有哪些：

配置名 类 @Activate(order) 做什么
invokercount InvokerCountWrapper Integer.MIN_VALUE + 1000 给引用端的 Invoker 加引用计数
serializationwrapper ProtocolSerializationWrapper 未写，按 0 导出时登记服务允许的序列化方式
filter ProtocolFilterWrapper 100 导出、引用时组装 Filter 链
securitywrapper ProtocolSecurityWrapper 200 登记接口类型，供反序列化安全检查
listener ProtocolListenerWrapper 200 触发导出、引用的监听器
qos QosProtocolWrapper 200 启动时顺带拉起 QoS 运维端口

所以 getExtension("dubbo") 拿到的是最外层的 InvokerCountWrapper，最里面才是 DubboProtocol。getExtension("registry") 也一样被整串包住，这就是为什么几乎每个 Wrapper 的 export 开头都有一句“如果是注册中心 URL 就直接往下传”：

// ProtocolFilterWrapper#export
if (UrlUtils.isRegistry(invoker.getUrl())) {
    return protocol.export(invoker);
}
FilterChainBuilder builder = getFilterChainBuilder(invoker.getUrl());
return protocol.export(builder.buildInvokerChain(invoker, SERVICE_FILTER_KEY, CommonConstants.PROVIDER));

这是一种很省事的 AOP：想给所有协议加一项能力，写一个带这种构造器的类、登记进配置文件就行，不用改任何协议实现。代价也在这里：Wrapper 默认包所有实现，不需要它的实现只能靠它自己判断后放行，或者在类上用 @Wrapper(mismatches = ...) 排除。

同一个 order 的 Wrapper，谁在外面说不准

包装顺序由 WrapperComparator 决定：先按 @Activate 的 order 升序排，再整体反转，然后从头开始一层层往外包。结果是 order 越小越靠外。InvokerCountWrapper 的 order 最小，所以在最外层。

问题出在三个 order 都是 200 的 Wrapper 上。比较器是这样写的：

// WrapperComparator#compare（节选）
int n1 = a1.order;
int n2 = a2.order;
// never return 0 even if n1 equals n2, otherwise, o1 and o2 will override each other in collection like HashSet
return n1 > n2 ? 1 : -1;

order 相等时它不返回 0，而是固定返回 -1，于是“谁在前”取决于排序前的输入顺序。而输入来自 cachedWrapperClasses，它是一个 ConcurrentHashSet，迭代顺序取决于 Class 对象的哈希值，也就是 JVM 每次启动时分配的身份哈希。开头那 6 次运行里，三层的排列（从外到内）分别是：

Qos      Security Listener
Security Listener Qos
Listener Security Qos
Qos      Security Listener
Security Qos      Listener
Security Qos      Listener

对 Dubbo 自带的这三个 Wrapper 来说，它们各干各的，顺序无所谓。但如果你自己写了一个 Protocol Wrapper，又恰好依赖它和某个内置 Wrapper 的先后（比如要在 Filter 链组装之后再做点事），就别用和别人相同的 order，否则本地测试通过、换一次启动就可能不对。同一套规则也用在别的扩展点上，比如 Cluster：ScopeClusterWrapper（@Wrapper(order = -1)）和 MockClusterWrapper（没写 order，按 0）就是这样套在 FailoverCluster 外面的，前者在外。

Adaptive：用哪个实现，等调用时看 URL

注入解决了“扩展之间互相引用”，但注入时还不知道要用哪个实现：同一个 ServiceConfig 里的 protocol 字段，这次导出可能走 registry，下次走 dubbo 或 tri。Dubbo 的做法是注入一个代理，代理在每次调用时从 URL 里读出名字，再去取真正的扩展。

接口方法上标 @Adaptive，ExtensionLoader 就会用 AdaptiveClassCodeGenerator 拼出一份 Java 源码，再用 Compiler 扩展（默认 javassist）编译成 Protocol$Adaptive。示例里把这份源码直接打印了出来，export 方法是这样的：

public org.apache.dubbo.rpc.Exporter export(org.apache.dubbo.rpc.Invoker arg0) throws org.apache.dubbo.rpc.RpcException {
if (arg0 == null) throw new IllegalArgumentException("org.apache.dubbo.rpc.Invoker argument == null");
if (arg0.getUrl() == null) throw new IllegalArgumentException("org.apache.dubbo.rpc.Invoker argument getUrl() == null");
org.apache.dubbo.common.URL url = arg0.getUrl();
String extName = ( url.getProtocol() == null ? "dubbo" : url.getProtocol() );
if(extName == null) throw new IllegalStateException("Failed to get extension (org.apache.dubbo.rpc.Protocol) name from url (" + url.toString() + ") use keys([protocol])");
ScopeModel scopeModel = ScopeModelUtil.getOrDefault(url.getScopeModel(), org.apache.dubbo.rpc.Protocol.class);
org.apache.dubbo.rpc.Protocol extension = (org.apache.dubbo.rpc.Protocol)scopeModel.getExtensionLoader(org.apache.dubbo.rpc.Protocol.class).getExtension(extName);
return extension.export(arg0);
}

Protocol 接口上写的是 @SPI(value = "dubbo", scope = ExtensionScope.FRAMEWORK)，所以 URL 的协议头为空时默认用 dubbo。对 LoadBalance 这种标了 @Adaptive("loadbalance") 的方法，生成的代码读的是 URL 上的 loadbalance 参数。

服务导出时“同一个 protocolSPI.export() 先进 RegistryProtocol、再进 DubboProtocol”，就是这么来的：

  1. ServiceConfig 把真正的 dubbo:// URL 作为属性塞进注册中心 URL，协议头是 registry://（接口级）或 service-discovery-registry://（应用级）。
  2. 第一次 export，Adaptive 读到 registry，取到包着 RegistryProtocol 的那串 Wrapper。各个 Wrapper 看到是注册中心 URL，直接放行。
  3. RegistryProtocol 取出里面的 dubbo:// URL，用同一个 Adaptive 再调一次 export。这次取到的是包着 DubboProtocol 的那串 Wrapper，ProtocolFilterWrapper 在这一步组好提供端的 Filter 链，最后 DubboProtocol 打开 Netty 端口。

Adaptive 带来的约束是：方法参数里必须能拿到 URL，要么本身就是 URL，要么参数对象有一个返回 URL 的无参 getter（比如 Invoker#getUrl()）。标了 @Adaptive 却找不到 URL 的方法，生成代码这一步就会抛 IllegalStateException；没标 @Adaptive 的方法，生成出来的实现直接抛 UnsupportedOperationException。这也是 Dubbo 很多接口方法签名里都带着 URL 或 Invoker 的原因。

Activate：一组同时生效的 Filter

Protocol、LoadBalance 这类扩展一次只用一个，Filter 不一样，一次要用一串。@Activate 就是给这种场景准备的：

@Activate(group = {CommonConstants.CONSUMER, CommonConstants.PROVIDER}, order = 10_000)
public class TraceFilter implements Filter { ... }

getActivateExtension(url, key, group) 按三件事筛选和排序：group 是否匹配当前一端（consumer 或 provider）；如果写了 value，URL 上是否有对应的参数；最后按 order 排序。URL 上写 -名字 可以去掉某个默认 Filter，比如 reference.setFilter("-trace")。

Filter 链在哪里组装，决定了它每次调用执行几次。3.x 的消费端有两种 Filter：

  • ClusterFilter：AbstractCluster#join 在集群 Invoker 外面套了一层 ClusterFilterInvoker，这一层在选址和重试之前，每次调用只走一次。ConsumerContextFilter、FutureFilter 在这里，Sentinel 的 Dubbo 3 适配器里 SentinelDubboConsumerFilter 也实现的是 ClusterFilter。
  • 普通 Filter（group=consumer）：由 ProtocolFilterWrapper#refer 套在每一个提供者的 Invoker 外面，选中哪个提供者就走哪个的链，每次重试都会再走一遍。

提供端只有一条链，由 ProtocolFilterWrapper#export 套在 AbstractProxyInvoker 外面。

拼起来：一次调用穿过多少层 Invoker

有了上面三样东西，一次同步调用在消费端的结构就是一串 Invoker 套 Invoker（以接口级注册中心、默认配置为例）：

业务接口代理（InvokerInvocationHandler）
└─ MigrationInvoker                 接口级 / 应用级地址迁移
   └─ ScopeClusterInvoker           ScopeClusterWrapper 套的，处理 injvm 本地调用
      └─ MockClusterInvoker         MockClusterWrapper 套的，处理 mock=
         └─ ClusterFilterInvoker    ClusterFilter 链，每次调用一次
            └─ FailoverClusterInvoker
                 list()   → Directory + RouterChain 得到候选提供者
                 select() → LoadBalance 选一个，重试时避开已调过的
                 └─ ReferenceCountInvokerWrapper   InvokerCountWrapper 套的
                    └─ 普通 Filter 链              ProtocolFilterWrapper 套的，每次尝试一次
                       └─ DubboInvoker → ExchangeClient → Netty

提供端反过来：Netty 收到请求，经过 Handler 装饰链派发到业务线程池，DubboProtocol 按服务键找到 Exporter，穿过提供端 Filter 链，最后由 javassist 生成的 Wrapper.invokeMethod 调到你的实现类上。

这套结构的好处是每一层都只认识 Invoker 接口：Mock、迁移、路由、重试、Filter 都可以独立替换和组合。坏处是排查问题时调用栈很深，而且“某个行为发生在哪一层”并不总是显而易见。开头的第二个现象就是一个例子。

回到那次超时：一次调用，提供方执行三次

示例里，消费端只配了 timeout=200，提供方的 slow(500) 睡 500 毫秒。输出是：

== 4. 默认 failover：一次超时，提供方执行了几次？==
    [cluster filter] slow
    [consumer filter] slow
    [provider filter] slow
    [provider] 第 1 次执行，线程 DubboServerHandler-…-thread-3
    [consumer filter] slow
    [provider filter] slow
    [provider] 第 2 次执行，线程 DubboServerHandler-…-thread-4
    [consumer filter] slow
    [provider filter] slow
    [provider] 第 3 次执行，线程 DubboServerHandler-…-thread-5
  消费端在 604 ms 后收到异常 RpcException
  Tried 3 times of the providers [127.0.0.1:46853] (1/1)
  提供方一共执行: 3 次

原因都在 FailoverClusterInvoker#doInvoke 里：

int len = calculateInvokeTimes(methodName);   // retries + 1，默认 retries=2
for (int i = 0; i < len; i++) {
    if (i > 0) {
        copyInvokers = list(invocation);       // 重试前重新取一次候选列表
    }
    Invoker<T> invoker = select(loadbalance, invocation, copyInvokers, invoked);
    invoked.add(invoker);
    try {
        return invokeWithContext(invoker, invocation);
    } catch (RpcException e) {
        if (e.isBiz()) {                       // 业务异常不重试
            throw e;
        }
        le = e;                                // 超时、网络错误：记下来，继续下一轮
    } catch (Throwable e) {
        le = new RpcException(e.getMessage(), e);
    }
}

几个容易踩的点：

  1. 默认就会重试。 cluster 默认是 failover，retries 默认是 2，所以一次调用最多发 3 次请求。
  2. 超时会重试，业务异常不会。 提供方方法里抛出的异常会随响应带回来，不会让这里抛 RpcException，所以不重试。超时、连接失败这类“框架层”的错误才会重试。偏偏超时最说明不了问题：请求很可能已经到了提供方，只是没在时限内回来。
  3. 超时是按次算的。 每次尝试都重新用满 200 毫秒，调用方最坏要等 (retries + 1) × timeout。示例里是 3 × 200 ≈ 604 毫秒。如果上游给这次调用的预算本来就是 300 毫秒，那后两次重试只是在浪费提供方的资源。
  4. 普通 Filter 每次尝试都执行。 输出里 [consumer filter] 出现了 3 次，[cluster filter] 只出现了 1 次。做调用量统计、限流、打点的 Filter，放在哪一层会直接影响数字。
  5. 只有一个提供者时，重试还是打在它身上。 select 会尽量避开已经调过的提供者，但候选只有一个时没得选。上面的 (1/1) 就是这个意思。

对写操作，正确的做法是显式关掉重试。示例第 5 步给 slowNoRetry 单独配了 retries=0：

== 5. 同样的方法，retries=0 ==
    [cluster filter] slowNoRetry
    [consumer filter] slowNoRetry
    [provider filter] slowNoRetry
    [provider] 第 1 次执行，线程 DubboServerHandler-…-thread-6
  消费端在 202 ms 后收到异常 RpcException
  Tried 1 times of the providers [127.0.0.1:46853] (1/1)
  提供方一共执行: 1 次

也可以把这类引用的 cluster 设成 failfast。更稳的做法是让写接口本身幂等（带请求号去重），这样重试就不再是风险。但“默认重试”这件事本身值得记住：在 Dubbo 里，一个没写 retries 的写接口，是默认允许被调三次的。

Greeter.java 和 GreeterImpl.java：

package demo;

public interface Greeter {
    String hello(String name);

    // 按 sleepMs 睡一会再返回，用来制造消费端超时
    String slow(int sleepMs);

    // 和 slow 一样，只是消费端把这个方法的 retries 配成了 0
    String slowNoRetry(int sleepMs);
}
package demo;

import java.util.concurrent.atomic.AtomicInteger;

public class GreeterImpl implements Greeter {
    static final AtomicInteger SLOW_CALLS = new AtomicInteger();

    @Override
    public String hello(String name) {
        return "hello " + name;
    }

    @Override
    public String slow(int sleepMs) {
        return sleep(sleepMs);
    }

    @Override
    public String slowNoRetry(int sleepMs) {
        return sleep(sleepMs);
    }

    private static String sleep(int sleepMs) {
        int n = SLOW_CALLS.incrementAndGet();
        System.out.printf("    [provider] 第 %d 次执行，线程 %s%n", n, Thread.currentThread().getName());
        try {
            Thread.sleep(sleepMs);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        return "done";
    }
}

两个 Filter。普通 Filter 两端都生效，ClusterFilter 只在消费端：

package demo;

import org.apache.dubbo.common.constants.CommonConstants;
import org.apache.dubbo.common.extension.Activate;
import org.apache.dubbo.rpc.Filter;
import org.apache.dubbo.rpc.Invocation;
import org.apache.dubbo.rpc.Invoker;
import org.apache.dubbo.rpc.Result;
import org.apache.dubbo.rpc.RpcException;

// 没有任何代码 new 它：写进 META-INF/dubbo/org.apache.dubbo.rpc.Filter，
// 再用 @Activate 声明在两端都生效，ProtocolFilterWrapper 组链时就会把它带上。
@Activate(group = {CommonConstants.CONSUMER, CommonConstants.PROVIDER}, order = 10_000)
public class TraceFilter implements Filter {
    @Override
    public Result invoke(Invoker<?> invoker, Invocation invocation) throws RpcException {
        System.out.printf("    [%s filter] %s%n", invoker.getUrl().getSide(), invocation.getMethodName());
        return invoker.invoke(invocation);
    }
}
package demo;

import org.apache.dubbo.common.constants.CommonConstants;
import org.apache.dubbo.common.extension.Activate;
import org.apache.dubbo.rpc.Invocation;
import org.apache.dubbo.rpc.Invoker;
import org.apache.dubbo.rpc.Result;
import org.apache.dubbo.rpc.RpcException;
import org.apache.dubbo.rpc.cluster.filter.ClusterFilter;

// ClusterFilter 套在集群 Invoker 外面，在选址和重试之前，每次调用只走一次
@Activate(group = CommonConstants.CONSUMER, order = 10_000)
public class OncePerCallFilter implements ClusterFilter {
    @Override
    public Result invoke(Invoker<?> invoker, Invocation invocation) throws RpcException {
        System.out.printf("    [cluster filter] %s%n", invocation.getMethodName());
        return invoker.invoke(invocation);
    }
}

Main.java：

package demo;

import java.lang.reflect.Field;
import java.net.ServerSocket;
import java.util.List;

import org.apache.dubbo.common.extension.AdaptiveClassCodeGenerator;
import org.apache.dubbo.config.ApplicationConfig;
import org.apache.dubbo.config.MethodConfig;
import org.apache.dubbo.config.ProtocolConfig;
import org.apache.dubbo.config.ReferenceConfig;
import org.apache.dubbo.config.RegistryConfig;
import org.apache.dubbo.config.ServiceConfig;
import org.apache.dubbo.config.bootstrap.DubboBootstrap;
import org.apache.dubbo.rpc.Protocol;
import org.apache.dubbo.rpc.model.ApplicationModel;

public class Main {
    public static void main(String[] args) throws Exception {
        System.setProperty("dubbo.application.logger", "slf4j"); // 日志交给 slf4j-nop，输出只留演示内容
        System.out.println("== 1. Protocol$Adaptive 的源码（运行时生成）==");
        String code = new AdaptiveClassCodeGenerator(Protocol.class, "dubbo").generate();
        int start = code.indexOf("public org.apache.dubbo.rpc.Exporter export");
        System.out.println(code.substring(start, code.indexOf("}\n", start) + 1));

        System.out.println("\n== 2. getExtension(\"dubbo\") 拿到的对象，一层层剥开 ==");
        Object p = ApplicationModel.defaultModel().getExtensionLoader(Protocol.class).getExtension("dubbo");
        for (int depth = 0; p != null; depth++) {
            System.out.println("  ".repeat(depth) + p.getClass().getName());
            p = innerProtocol(p);
        }

        int port = freePort();
        ServiceConfig<Greeter> service = new ServiceConfig<>();
        service.setInterface(Greeter.class);
        service.setRef(new GreeterImpl());

        ReferenceConfig<Greeter> reference = new ReferenceConfig<>();
        reference.setInterface(Greeter.class);
        reference.setUrl("dubbo://127.0.0.1:" + port); // 直连，不走注册中心
        reference.setTimeout(200);                      // 每次调用 200ms 超时
        MethodConfig noRetry = new MethodConfig();
        noRetry.setName("slowNoRetry");
        noRetry.setRetries(0);
        reference.setMethods(List.of(noRetry));

        ApplicationConfig app = new ApplicationConfig("wrapper-demo");
        app.setQosEnable(false);
        DubboBootstrap bootstrap = DubboBootstrap.getInstance()
                .application(app)
                .registry(new RegistryConfig(RegistryConfig.NO_AVAILABLE))
                .protocol(new ProtocolConfig("dubbo", port))
                .service(service)
                .reference(reference)
                .start();

        Greeter greeter = reference.get();
        System.out.println("\n== 3. 一次普通调用经过的 Filter ==");
        System.out.println("  result: " + greeter.hello("dubbo"));

        System.out.println("\n== 4. 默认 failover：一次超时，提供方执行了几次？==");
        GreeterImpl.SLOW_CALLS.set(0);
        callAndReport(() -> greeter.slow(500));
        Thread.sleep(1500); // 等提供方把睡眠跑完，计数才完整
        System.out.println("  提供方一共执行: " + GreeterImpl.SLOW_CALLS.get() + " 次");

        System.out.println("\n== 5. 同样的方法，retries=0 ==");
        GreeterImpl.SLOW_CALLS.set(0);
        callAndReport(() -> greeter.slowNoRetry(500));
        Thread.sleep(1500);
        System.out.println("  提供方一共执行: " + GreeterImpl.SLOW_CALLS.get() + " 次");

        bootstrap.stop();
    }

    private static void callAndReport(Runnable call) {
        long t0 = System.nanoTime();
        try {
            call.run();
        } catch (Exception e) {
            String msg = e.getMessage();
            int i = msg.indexOf("Tried ");
            System.out.printf("  消费端在 %d ms 后收到异常 %s%n  %s%n",
                    (System.nanoTime() - t0) / 1_000_000, e.getClass().getSimpleName(),
                    i >= 0 ? msg.substring(i, msg.indexOf(')', i) + 1) : msg.lines().findFirst().orElse(""));
        }
    }

    // Wrapper 都把被包装的 Protocol 存在一个 Protocol 类型的字段里，按类型找出来即可
    private static Object innerProtocol(Object wrapper) throws IllegalAccessException {
        for (Class<?> c = wrapper.getClass(); c != null; c = c.getSuperclass()) {
            for (Field f : c.getDeclaredFields()) {
                if (f.getType() == Protocol.class) {
                    f.setAccessible(true);
                    return f.get(wrapper);
                }
            }
        }
        return null;
    }

    private static int freePort() throws Exception {
        try (ServerSocket s = new ServerSocket(0)) {
            return s.getLocalPort();
        }
    }
}

运行：

mvn -q compile exec:java

第 2 步里三个 order=200 的 Wrapper 的顺序每次可能不同；第 4 步的 604 毫秒会有几毫秒浮动。AdaptiveClassCodeGenerator 是 Dubbo 内部用来生成代码的类，这里只是借它把源码打印出来看，业务代码里不要依赖它。

小结

  • Dubbo 的扩展机制有三种用法：按名字取单个实现，@Adaptive 生成代理在调用时按 URL 选实现，@Activate 按 group 和 order 取一组实现。三者都建立在 ExtensionLoader 上。
  • 有“以扩展接口为唯一参数的公开构造器”的类会被当成 Wrapper，自动包在每个实现外面。order 越小越靠外；order 相同的 Wrapper 之间没有确定顺序，每次启动都可能不同。
  • 一次调用是一串 Invoker 套 Invoker。ClusterFilter 在重试之外，每次调用一次；普通消费端 Filter 在重试之内，每次尝试一次。
  • 默认的 failover 会对超时重试两次，每次各自用满超时。非幂等的写接口要显式设 retries=0 或用 failfast，并且最好让接口本身能去重。
