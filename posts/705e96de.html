leastactive（最少活跃调用数）是 Dubbo 自带的几种负载均衡里最“聪明”的一个：哪个提供端手上的活少，就把请求给谁，慢的实例自然少拿，快的实例自然多拿。常见的做法是：一看到某个实例偶尔变慢，就把 loadbalance 从默认的 random 改成 leastactive，然后认为问题解决了。

下面是后文示例在 Dubbo 3.3.7 上的三段输出。三个提供端是三个独立的进程，p1 每次处理 10 毫秒，p2、p3 每次 100 毫秒；消费端 30 个线程一共发 3000 次请求，retries=0，其余都是默认配置。A 用 random，B 只把策略换成 leastactive，D 在 B 的基础上多配了一个 actives=1000：

B 和 A 几乎一模一样：三个提供端各拿三分之一，平均耗时都是 70 毫秒左右，正好是 (10+100+100)/3。leastactive 选节点时读的那个数（输出里的“RpcStatus 峰值”）从头到尾都是 0，而消费端自己数的在途请求，慢实例上最多压了二十多个。只有配了 actives 的 D，p1 才拿到八成以上的请求，平均耗时降到原来的四成左右。

也就是说，不配 actives，leastactive 在行为上就是 random。这个 actives 本身是一个限流参数，跟负载均衡看起来毫无关系。这篇把这件事从源码里理清楚：leastactive 到底读的是什么，谁在维护它，怎么打开，打开以后它平衡的是什么，以及打开以后要面对的三个坑。

文中源码取自 apache/dubbo 的 3.3.7 标签（提交 481d41c，2026-10-26），写作时这是 Maven Central 上的最新版本。Filter 链怎么拼起来、@Activate 怎么按 URL 激活扩展，在第一篇 Dubbo 文章里讲过，这里直接用结论。

leastactive 读的是哪个数

LeastActiveLoadBalance#doSelect 不长，去掉注释和权重细节，骨架是这样的（dubbo-cluster 模块）：

for (int i = 0; i < length; i++) {
    Invoker<T> invoker = invokers.get(i);
    int active = RpcStatus.getStatus(invoker.getUrl(), RpcUtils.getMethodName(invocation))
            .getActive();
    int afterWarmup = getWeight(invoker, invocation);   // 带预热折算的权重
    weights[i] = afterWarmup;
    if (leastActive == -1 || active < leastActive) {
        leastActive = active;                          // 找到更小的，重新开始收集
        leastCount = 1;
        leastIndexes[0] = i;
        // ...
    } else if (active == leastActive) {
        leastIndexes[leastCount++] = i;                // 并列最小的都收集起来
        // ...
    }
}
if (leastCount == 1) {
    return invokers.get(leastIndexes[0]);              // 只有一个最小的：直接返回，不看权重
}
// 有并列：在并列者之间按权重随机；权重都一样就均匀随机

它读的是 RpcStatus.getStatus(url, 方法名).getActive()。RpcStatus 是 dubbo-rpc-api 里的一个静态计数器，按 url.toIdentityString()（协议、地址、端口和接口路径）加方法名分桶，桶里有 active、total、failed、耗时等几个原子变量。active 就是“这个消费端发给这个提供端、这个方法、还没回来的请求数”。

选节点只有两条路：

  1. 某个提供端的 active 严格最小，直接选它，权重和预热都不参与；
  2. 有若干个并列最小，在它们之间按权重随机。

如果所有提供端的 active 永远是 0，那每一次都是“全体并列”，走第二条路：在全部提供端之间按权重随机。这跟 RandomLoadBalance 做的事情是一样的。

谁在维护这个数

在整个 3.3.7 的源码里搜 RpcStatus.beginCount 和 endCount，调用方只有两个过滤器：

  • ExecuteLimitFilter：提供端的并发限制，管的是提供端自己的执行数，跟消费端选节点无关；
  • ActiveLimitFilter：消费端的并发限制，invoke 里 beginCount，onResponse/onError 里 endCount。

LoadBalance 自己只读不写。所以消费端的 active 有没有人加减，完全取决于 ActiveLimitFilter 在不在过滤器链上。再看它的声明：

@Activate(group = CONSUMER, value = ACTIVES_KEY)   // ACTIVES_KEY = "actives"
public class ActiveLimitFilter implements Filter, Filter.Listener {

value = "actives" 的意思是：只有 URL 上带着 actives 这个参数，这个过滤器才会被激活。判断逻辑在 ExtensionLoader#isActive：

String realValue = url.getParameter(key);
if (StringUtils.isEmpty(realValue)) {
    realValue = url.getAnyMethodParameter(key);    // 任意一个方法上配了也算
}
if ((keyValue != null && keyValue.equals(realValue))
        || (keyValue == null && ConfigUtils.isNotEmpty(realValue))) {
    return true;
}

ConfigUtils.isNotEmpty 不只是判空：值为 false、0、null、N/A（不区分大小写）都当作没配。

把这几段连起来，就是开头 B 的结果：没配 actives，ActiveLimitFilter 根本不在链上，没有任何代码去加减 active，它一直是 0，leastactive 每次都在全体提供端之间按权重随机。示例的消费端里挂了一个探针过滤器，在每次调用进来时读一下 RpcStatus 里的 active，同时自己数一份真实的在途请求，输出里的“RpcStatus 峰值”和“在途峰值”就是这两个数的峰值（“平均在途”和“平均驻留”下一节再用）。A、B、C 三组里，真实在途最多二十多个，RpcStatus 一直是 0：

I 把九成六的请求给了 p1，比 leastactive 还激进：p1 被记为成功的平均耗时只有 p2 的十分之一左右，按“耗时 × (在途数 + 1)“的估法，p1 的在途数要比 p2 高出近十倍，估值才追得上 p2，所以 p1 的在途峰值被推到了 26。这个策略适不适合你，取决于快实例能不能扛住被这样集中，这里不展开。

为什么计数会跟限流绑在一起？源码里没有说明，我能看到的事实只有：维护 active 的唯一一段消费端代码是一个限流过滤器，它按 actives 参数激活；而 leastactive 和 shortestresponse 都默认有人在维护这个数。这是两个模块之间一个没有写在代码里的约定，配置里不会有任何报错或日志提醒你它没生效。

打开计数之后：它在平衡什么

D 组只多了一个 actives=1000，p1 拿到了八成多的请求。这个比例可以用利特尔定律粗略估出来，但要先说清它是估算，不是策略的保证。

leastactive 做的只是每次调用时的一次即时比较：挑当前在途数最少的提供端。它没有承诺任何长期的分配比例。不过在负载稳定、各实例时延也稳定的稳态下，这种“谁少给谁”的比较往往会让各提供端的时间平均在途数趋于接近。注意是时间平均，不是峰值：峰值相同推不出平均相同。所以示例里另外量了两样东西，都是在消费端的探针里测的：

  • 平均在途：每次调用在探针里驻留的时长之和 ÷ 这组压测的总时长，也就是在途数对时间的平均；
  • 平均驻留：同一个时长之和 ÷ 调用次数，即从请求进入探针到回调的平均时长。

D 组的结果是：

三个提供端的平均在途分别是 9.42、9.72、9.77，确实接近。对每个提供端套用利特尔定律 L = λW（平均在途 = 到达率 × 平均驻留），到达率 λ = L / W。如果把三者的平均在途近似看成相等，份额就近似和平均驻留的倒数成正比：

  • 按名义处理时间 10 毫秒和 100 毫秒估算，p1 约占 (1/10) / (1/10 + 1/100 + 1/100) ≈ 83%；
  • 按这组实测的平均驻留 11.45 毫秒、101.97 毫秒、101.81 毫秒 估算，p1 约占 81.6%。

这组实验里 p1 实际拿到 81.1%。如果把实测的平均在途也代进去，L / W 算出来的就是实际份额，这只说明探针的口径前后一致，不是额外的证据。

所以更准确的说法是：leastactive 每次挑这个消费端看到的在途数最少的提供端；在稳态、时延稳定时，它近似把各提供端的平均在途数拉平，流量份额于是近似按平均驻留时长的倒数分配。负载在变、时延在抖、或者并发太低（坑一）的时候，这个近似都会走样。即便如此，“份额向响应快的实例倾斜”这个方向，是后面三个坑的根源。

三种打开方式，各有副作用

既然开关是“URL 上有一个非空、非零的 actives”，能让它出现在 URL 上的配置都行。示例里试了三种。

一、在消费端的引用上配。 就是 D 组的 ReferenceConfig#setActives(1000)，对应 XML 的 <dubbo:reference actives="1000">、注解的 @DubboReference(actives = 1000)。只影响这一个引用。

二、只给某一个方法配。 E 组只给从来不调用的 other() 方法配了 actives=1000，work() 上什么都没配，结果 work() 的计数照样打开了：

每个提供端的在途数被卡在 5，30 个线程只有 15 个能同时发出去，平均耗时从 D 组的 28.7 毫秒 涨到 55.7 毫秒，多出来的是在 ActiveLimitFilter 里排队的时间。超过上限之后会发生什么，要分两层看。

第一层是 ActiveLimitFilter 自己（源码）。负载均衡已经选完了，线程在已经选中的那个提供端的 RpcStatus 对象上 wait，等待期间不会改选别的提供端。等多久取这个方法 URL 上的 timeout 参数：示例显式配了 5000 毫秒，那就是最多等约 5000 毫秒；URL 上取不到 timeout 时这里按 0 处理，wait(0) 不是有限等待，会一直等到有调用结束发出通知。等不到名额就抛 LIMIT_EXCEEDED_EXCEPTION。

第二层是集群。这个限流异常是一个非业务的 RpcException，FailoverClusterInvoker 只对业务异常直接抛出，其余的在还有重试次数时进入下一轮，重新调用负载均衡选提供端（尽量避开已经试过的）。默认 retries=2，所以“等待时不改选”不等于“整个调用不会换节点”。示例的 retries=0，没有这一层。

所以如果只是想让 leastactive 生效、不想限流，actives 要配得比“单个消费端对单个提供端、单个方法可能出现的最大并发”还大。如果是同步调用、每个线程同一时刻最多只有一个在途请求，一个简单的上界是这个消费端发起调用的线程总数，例如 Web 容器的最大工作线程数加上业务线程池的大小。异步调用、或者一个线程同时扇出多个调用时，这个上界不成立，要按实际可能的最大并发来估。示例是同步调用、30 个线程，用的是 1000。

打开以后的三个坑

坑一：它只知道自己这一个消费端

RpcStatus 是消费端进程里的静态 Map，计数只来自本进程发出的请求。两个消费端各自算各自的，互相看不见；提供端那边另有多少别的调用方在压它，leastactive 也不知道。

最极端的情况是单线程的消费端（G 组）：每次选节点时，自己上一个请求已经回来了，三个提供端的 active 都是 0，又回到全体并列、按权重随机：

leastactive 本身没有任何摘除坏实例的能力。用它的时候，要另外有东西负责把快速失败的实例拿掉：提供端的健康检查让故障实例及时从注册中心下线，或者在消费端按提供端维度做熔断。只靠 leastactive，一个快速失败的实例造成的影响会比在 random 下大得多。

坑三：新实例的预热被绕过了

Dubbo 的预热是靠权重实现的：AbstractLoadBalance#getWeight 用提供端 URL 上的启动时间戳算出已运行时长 uptime，在预热期 warmup（默认 10 分钟）内，权重按 uptime / warmup × weight 折算，最小为 1。刚启动的实例权重很低，在 random 下只拿到很少的流量，留时间给 JIT 编译、连接池和本地缓存热起来。

但在 leastactive 里，权重只在并列时起作用。M、N 两组三个提供端处理时间相同，p1、p2 的预热期设成 1 秒并且已经过去，p3 刚启动、预热期是默认的 10 分钟：

如果你的服务在冷启动时明显变慢，这其实会自我调节一部分：新实例慢，在途数就涨得快，分到的就少。但它调节的依据是“已经变慢了”，预热的本意是“在变慢之前就少给”。启动后需要一段时间才能达到正常性能的服务，换成 leastactive 时要把这一点考虑进去，比如让实例在启动阶段自己把缓存、连接池热好，再导出服务（ServiceConfig 的 delay 可以推迟导出）。

完整示例

一个 Maven 工程，6 个 Java 文件、1 个扩展配置文件、1 个日志配置和 1 个运行脚本。在 JDK 21 上用 Maven 3.9 跑过，maven.compiler.release 设为 17，JDK 17 及以上都可以。

和前几篇不同，这次用了注册中心：负载均衡要在多个提供端之间挑，提供端的启动时间戳（预热要用）和提供端侧配置也要经注册中心传给消费端。为了不依赖外部服务，ZkMain 用 Curator 的 curator-test 在本机起一个一次性的 ZooKeeper，数据目录在脚本建的临时目录里。每组实验都重新起一套 ZooKeeper 和提供端，每个用例单独起一个消费端进程，互不影响。

请在隔离的网络里运行。 ZooKeeper 的客户端端口设成只监听 127.0.0.1，但提供端做不到：Dubbo 3.3.7 会把 127. 开头的地址当成无效的绑定地址，改为监听 0.0.0.0（超时那篇里说过）。三个提供端会从 20880 起各占一个端口。请在没有外部网络的容器里跑（例如 docker run --network none，回环在容器内照样可用），或者确认所在机器的防火墙不放行这几个端口。运行时可以用 lsof -nP -iTCP -sTCP:LISTEN（Linux 和 macOS 都有）核对实际监听地址。

几处为了实验方便的做法：

  • 消费端 retries=0，每次调用只落到一个提供端，按返回值统计的份额才干净；业务异常本来也不触发重试。
  • 第 1 到 3 组的提供端把预热期设成 1 秒，并在启动后等 2 秒，让三个提供端的权重都是满的 100。默认的预热期是 10 分钟，如果不这样做，几个提供端启动时间差几秒，权重就会差一截，random 的份额会偏向先启动的那个，干扰比较。第 4 组专门看预热，按需设置。
  • 探针 ProbeFilter 排在 ActiveLimitFilter 里面，平均在途和平均驻留都是从请求进入探针到回调这一段，比 ActiveLimitFilter 计数的那一段略短；“平均在途”的分母是整组压测的墙钟时间，收尾时线程陆续退出，平均值会被略微拉低。
  • 开测前，消费端先反复调 name()，直到看见全部提供端。RpcStatus 按方法分桶，这些调用不影响 work() 的计数。
  • 每个用例结尾有断言（份额范围、RpcStatus 峰值是否为 0），不成立时消费端以 1 退出，脚本最后报“有断言失败”。随机分配的份额有波动，断言的区间留了余量：3000 次三选一，单个份额的标准差约 0.9 个百分点。
  • 慢、快、失败都是在提供端用 Thread.sleep 或直接抛异常模拟的，不占 CPU，所以 I 组 p1 被压到二十多个在途，平均驻留也只是 12.12 毫秒。真实服务被集中压过去时会变慢，比例会不一样。

ProviderMain.java：

package demo;

import java.nio.file.Files;
import java.nio.file.Path;

import org.apache.dubbo.config.ApplicationConfig;
import org.apache.dubbo.config.ProtocolConfig;
import org.apache.dubbo.config.RegistryConfig;
import org.apache.dubbo.config.ServiceConfig;
import org.apache.dubbo.config.bootstrap.DubboBootstrap;

/**
 * 用法：ProviderMain 工作目录 名字 延迟毫秒 ok|fail [warmup 毫秒] [提供端 actives]
 * fail 表示 work() 立刻抛异常，模拟"依赖挂了、快速失败"的实例。
 */
public class ProviderMain {
    public static void main(String[] args) throws Exception {
        Path dir = Path.of(args[0]);
        String name = args[1];
        long delayMs = Long.parseLong(args[2]);
        boolean fail = "fail".equals(args[3]);
        Integer warmup = args.length > 4 && !"-".equals(args[4]) ? Integer.valueOf(args[4]) : null;
        Integer actives = args.length > 5 && !"-".equals(args[5]) ? Integer.valueOf(args[5]) : null;

        EchoService impl = new EchoService() {
            @Override
            public String work() {
                if (fail) {
                    throw new IllegalStateException(name + " failed fast");
                }
                try {
                    Thread.sleep(delayMs);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
                return name;
            }

            @Override
            public String name() {
                return name;
            }

            @Override
            public String other() {
                return name;
            }
        };

        ServiceConfig<EchoService> service = new ServiceConfig<>();
        service.setInterface(EchoService.class);
        service.setRef(impl);
        if (warmup != null) {
            service.setWarmup(warmup);
        }
        if (actives != null) {
            service.setActives(actives);
        }

        ProtocolConfig protocol = new ProtocolConfig("dubbo", -1); // -1：从默认的 20880 起找第一个空闲端口
        protocol.setHost("127.0.0.1");

        ApplicationConfig app = new ApplicationConfig("la-provider-" + name);
        app.setQosEnable(false);

        String zk = Files.readString(dir.resolve("zk.addr")).trim();
        DubboBootstrap.getInstance()
                .application(app)
                .registry(new RegistryConfig("zookeeper://" + zk))
                .protocol(protocol)
                .service(service)
                .start();
        Files.writeString(dir.resolve(name + ".ready"), "ok");
        Thread.currentThread().join();
    }
}

/**
 * 消费端探针，挂在每个提供端 invoker 的过滤器链上（order 大，排在 ActiveLimitFilter 里面）。
 * 只看 work()，按提供端地址分开记：
 *  REAL_MAX：自己数的在途请求数（进来 +1，回来 -1）的峰值；

 *    时长之和 ÷ 压测总时长 = 时间平均在途数；时长之和 ÷ 次数 = 平均驻留时长。
 * 另外数一下回调走了哪条路：onResponse（其中结果带异常的单独数）还是 onError。
 */

public class ProbeFilter implements Filter, Filter.Listener {

    private static final String START = "probe.start";

    static final Map<String, AtomicInteger> INFLIGHT = new ConcurrentHashMap<>();
    static final Map<String, AtomicInteger> REAL_MAX = new ConcurrentHashMap<>();
    static final Map<String, AtomicInteger> SEEN_MAX = new ConcurrentHashMap<>();
    static final Map<String, LongAdder> BUSY_NANOS = new ConcurrentHashMap<>();
    static final Map<String, LongAdder> DONE = new ConcurrentHashMap<>();
    static final LongAdder ON_RESPONSE = new LongAdder();
    static final LongAdder ON_RESPONSE_WITH_EXCEPTION = new LongAdder();
    static final LongAdder ON_ERROR = new LongAdder();
    /** 提供端地址 -> 提供端 URL，事后用它去 RpcStatus 里查计数。 */
    static final Map<String, URL> URLS = new ConcurrentHashMap<>();
    /** 提供端地址 -> 名字，从 name() 的返回值里学到。 */
    static final Map<String, String> NAMES = new ConcurrentHashMap<>();
    /** 提供端 URL 的实现类：InstanceAddressURL 说明走的是应用级服务发现。 */
    static final Set<String> URL_TYPES = ConcurrentHashMap.newKeySet();

    @Override
    public Result invoke(Invoker<?> invoker, Invocation invocation) throws RpcException {
        if ("work".equals(invocation.getMethodName())) {
            String addr = invoker.getUrl().getAddress();
            URLS.putIfAbsent(addr, invoker.getUrl());
            URL_TYPES.add(invoker.getUrl().getClass().getSimpleName());
            int now = INFLIGHT.computeIfAbsent(addr, k -> new AtomicInteger()).incrementAndGet();
            REAL_MAX.computeIfAbsent(addr, k -> new AtomicInteger()).accumulateAndGet(now, Math::max);
            int seen = RpcStatus.getStatus(invoker.getUrl(), "work").getActive();
            SEEN_MAX.computeIfAbsent(addr, k -> new AtomicInteger()).accumulateAndGet(seen, Math::max);
            invocation.put(START, System.nanoTime());
        }
        return invoker.invoke(invocation);
    }

    @Override
    public void onResponse(Result r, Invoker<?> invoker, Invocation invocation) {
        if ("name".equals(invocation.getMethodName()) && r.getValue() instanceof String) {
            NAMES.put(invoker.getUrl().getAddress(), (String) r.getValue());
        }
        if ("work".equals(invocation.getMethodName())) {
            ON_RESPONSE.increment();
            if (r.hasException()) {
                ON_RESPONSE_WITH_EXCEPTION.increment();
            }
            done(invoker, invocation);
        }
    }

    @Override
    public void onError(Throwable t, Invoker<?> invoker, Invocation invocation) {
        if ("work".equals(invocation.getMethodName())) {
            ON_ERROR.increment();
            done(invoker, invocation);
        }
    }

    private static void done(Invoker<?> invoker, Invocation invocation) {
        String addr = invoker.getUrl().getAddress();
        INFLIGHT.get(addr).decrementAndGet();
        Object start = invocation.get(START);
        if (start instanceof Long) {
            BUSY_NANOS.computeIfAbsent(addr, k -> new LongAdder()).add(System.nanoTime() - (Long) start);
            DONE.computeIfAbsent(addr, k -> new LongAdder()).increment();
        }
    }
}

/**
 * 用法：ConsumerMain 工作目录 key=value ...
 *   label=A              这一组的名字，只用来打印
 *   lb=leastactive       负载均衡策略
 *   actives=N            消费端 reference 上的 actives（不写就是没配）
 *   other.actives=N      只给 other() 方法配 actives
 *   step=FORCE_INTERFACE 改用接口级服务发现（默认是 APPLICATION_FIRST，有应用级地址就用应用级）
 *   threads=30 calls=3000 providers=3
 *   expect=zero|counted  断言 RpcStatus 里的 active 峰值是否一直为 0
 *   min.p1=0.6 max.p3=0.1  断言某个提供端分到的请求占比
 * 任何一条断言不成立，进程以 1 退出。
 */
public class ConsumerMain {
    public static void main(String[] args) throws Exception {
        Path dir = Path.of(args[0]);
        Map<String, String> opt = new HashMap<>();
        for (int i = 1; i < args.length; i++) {
            String[] kv = args[i].split("=", 2);
            opt.put(kv[0], kv[1]);
        }
        String lb = opt.getOrDefault("lb", "leastactive");
        int threads = Integer.parseInt(opt.getOrDefault("threads", "30"));
        int calls = Integer.parseInt(opt.getOrDefault("calls", "3000"));
        int providers = Integer.parseInt(opt.getOrDefault("providers", "3"));

        if (opt.containsKey("step")) {
            System.setProperty("dubbo.application.migration.step", opt.get("step"));
        }

        ReferenceConfig<EchoService> ref = new ReferenceConfig<>();
        ref.setInterface(EchoService.class);
        ref.setLoadbalance(lb);
        ref.setRetries(0);      // 不重试，每次调用只落到一个提供端，计数才干净
        ref.setTimeout(5000);
        if (opt.containsKey("actives")) {
            ref.setActives(Integer.valueOf(opt.get("actives")));
        }
        if (opt.containsKey("other.actives")) {
            MethodConfig m = new MethodConfig();
            m.setName("other");
            m.setActives(Integer.valueOf(opt.get("other.actives")));
            ref.setMethods(List.of(m));
        }

        ApplicationConfig app = new ApplicationConfig("la-consumer");
        app.setQosEnable(false);
        String zk = Files.readString(dir.resolve("zk.addr")).trim();
        DubboBootstrap boot = DubboBootstrap.getInstance()
                .application(app)
                .registry(new RegistryConfig("zookeeper://" + zk))
                .reference(ref)
                .start();
        EchoService svc = ref.get();

        // 先用 name() 确认所有提供端都被发现了；work() 的计数不受影响（RpcStatus 按方法分开记）
        long deadline = System.currentTimeMillis() + 30_000;
        while (new TreeSet<>(ProbeFilter.NAMES.values()).size() < providers) {
            if (System.currentTimeMillis() > deadline) {
                throw new IllegalStateException("only discovered " + ProbeFilter.NAMES.values());
            }
            svc.name();
        }

        Map<String, LongAdder> served = new ConcurrentHashMap<>();
        LongAdder failures = new LongAdder();
        AtomicLong totalNanos = new AtomicLong();
        AtomicInteger left = new AtomicInteger(calls);
        List<Thread> workers = new ArrayList<>();
        long start = System.nanoTime();
        for (int t = 0; t < threads; t++) {
            Thread w = new Thread(() -> {
                while (left.getAndDecrement() > 0) {
                    long t0 = System.nanoTime();
                    String who;
                    try {
                        who = svc.work();
                    } catch (RuntimeException e) {
                        failures.increment();
                        String msg = String.valueOf(e.getMessage());
                        int at = msg.indexOf(" failed fast");
                        who = at > 0 ? msg.substring(msg.lastIndexOf(' ', at - 1) + 1, at) : "error";
                    }
                    totalNanos.addAndGet(System.nanoTime() - t0);
                    served.computeIfAbsent(who, k -> new LongAdder()).increment();
                }
            });
            workers.add(w);
            w.start();
        }
        for (Thread w : workers) {
            w.join();
        }
        double wallMs = (System.nanoTime() - start) / 1e6;

        Map<String, String> addrOf = new HashMap<>();
        ProbeFilter.NAMES.forEach((addr, name) -> addrOf.put(name, addr));
        Set<String> names = new TreeSet<>(ProbeFilter.NAMES.values());
        names.addAll(served.keySet());

        String settings = "lb=" + lb + " threads=" + threads + " calls=" + calls
                + (opt.containsKey("actives") ? " actives=" + opt.get("actives") : "")
                + (opt.containsKey("other.actives") ? " other.actives=" + opt.get("other.actives") : "")
                + (opt.containsKey("step") ? " step=" + opt.get("step") : "");
        System.out.println("[" + opt.getOrDefault("label", "?") + "] " + settings);
        Map<String, Double> share = new TreeMap<>();
        int seenMax = 0;
        long statusFailed = 0;
        for (String n : names) {
            long c = served.getOrDefault(n, new LongAdder()).sum();
            share.put(n, (double) c / calls);
            String addr = addrOf.get(n);
            int real = get(ProbeFilter.REAL_MAX, addr);
            int seen = get(ProbeFilter.SEEN_MAX, addr);
            seenMax = Math.max(seenMax, seen);
            long busy = addr == null || !ProbeFilter.BUSY_NANOS.containsKey(addr) ? 0 : ProbeFilter.BUSY_NANOS.get(addr).sum();
            long done = addr == null || !ProbeFilter.DONE.containsKey(addr) ? 0 : ProbeFilter.DONE.get(addr).sum();
            double avgInflight = busy / (wallMs * 1e6);              // 时间平均在途数
            double residenceMs = done == 0 ? 0 : busy / 1e6 / done;   // 平均驻留时长
            if (addr != null && ProbeFilter.URLS.containsKey(addr)) {
                statusFailed += RpcStatus.getStatus(ProbeFilter.URLS.get(addr), "work").getFailed();
            }
            System.out.printf("  %-3s %5d  %5.1f%%   在途峰值 %2d  平均在途 %5.2f  平均驻留 %6.2f ms   RpcStatus 峰值 %2d%n",
                    n, c, 100.0 * c / calls, real, avgInflight, residenceMs, seen);
        }
        System.out.println("  提供端 URL 类型 " + ProbeFilter.URL_TYPES);
        System.out.printf("  平均耗时 %.1f ms，总用时 %.0f ms，失败 %d%n",
                totalNanos.get() / 1e6 / calls, wallMs, failures.sum());
        System.out.printf("  回调：onResponse %d 次（其中结果带异常 %d 次），onError %d 次；RpcStatus 记为失败 %d 次%n",
                ProbeFilter.ON_RESPONSE.sum(), ProbeFilter.ON_RESPONSE_WITH_EXCEPTION.sum(),
                ProbeFilter.ON_ERROR.sum(), statusFailed);

        List<String> broken = new ArrayList<>();
        String expect = opt.get("expect");
        if ("zero".equals(expect) && seenMax != 0) {
            broken.add("RpcStatus 峰值应为 0，实际 " + seenMax);
        }
        if ("counted".equals(expect) && seenMax == 0) {
            broken.add("RpcStatus 峰值应大于 0，实际一直是 0");
        }
        for (Map.Entry<String, String> e : opt.entrySet()) {
            boolean min = e.getKey().startsWith("min.");
            boolean max = e.getKey().startsWith("max.");
            if (!min && !max) {
                continue;
            }
            String n = e.getKey().substring(4);
            double want = Double.parseDouble(e.getValue());
            double got = share.getOrDefault(n, 0.0);
            if ((min && got < want) || (max && got > want)) {
                broken.add(String.format("%s 占比 %.3f，要求 %s %s", n, got, min ? ">=" : "<=", e.getValue()));
            }
        }
        System.out.println(broken.isEmpty() ? "  断言通过" : "  断言失败：" + broken);
        boot.stop();
        System.exit(broken.isEmpty() ? 0 : 1);
    }

    private static int get(Map<String, AtomicInteger> m, String addr) {
        return addr == null || !m.containsKey(addr) ? 0 : m.get(addr).get();
    }
}

#!/bin/sh
# 在本机起一次性的 ZooKeeper 和若干提供端进程，逐组跑消费端。
# ZooKeeper 只监听 127.0.0.1；提供端会监听所有网卡（见正文），请在隔离的网络里运行。
# 临时文件放在 mktemp 建的私有目录里，退出时停掉所有子进程并删除。
set -eu
cd "$(dirname "$0")"

mvn -q -B package -DskipTests
mvn -q -B dependency:build-classpath -Dmdep.outputFile=target/cp.txt
CP="target/classes:$(cat target/cp.txt)"
JOPTS="-Xmx256m -Dstdout.encoding=UTF-8 -Ddubbo.service.shutdown.wait=1000"

ROOT=$(mktemp -d "${TMPDIR:-/tmp}/la-demo.XXXXXX")
PIDS=""      # 提供端进程
ZKPID=""
FAILED=0

stop_all() {  # 先停提供端（它们要去 ZooKeeper 注销自己），最后停 ZooKeeper
    for p in $PIDS; do kill "$p" 2>/dev/null || true; done
    for p in $PIDS; do wait "$p" 2>/dev/null || true; done
    if [ -n "$ZKPID" ]; then kill "$ZKPID" 2>/dev/null || true; wait "$ZKPID" 2>/dev/null || true; fi
    PIDS=""
    ZKPID=""
}
cleanup() { stop_all; rm -rf "$ROOT"; }
trap cleanup EXIT
trap 'exit 130' INT TERM

wait_file() {  # 等某个文件出现，最多 60 秒
    i=0
    while [ ! -f "$1" ]; do
        i=$((i + 1))
        if [ "$i" -gt 600 ]; then echo "timeout waiting for $1" >&2; exit 1; fi
        sleep 0.1
    done
}

group() {  # 每组一套全新的 ZooKeeper 和提供端，互不影响
    stop_all
    WORK="$ROOT/$1"
    mkdir -p "$WORK"
    echo
    echo "=== $2"
    java $JOPTS -cp "$CP" demo.ZkMain "$WORK" >"$WORK/zk.log" 2>&1 &
    ZKPID=$!
    wait_file "$WORK/zk.addr"
}

provider() {  # provider 名字 延迟ms ok|fail [warmup] [actives]
    java $JOPTS -cp "$CP" demo.ProviderMain "$WORK" "$@" >"$WORK/$1.log" 2>&1 &
    PIDS="$PIDS $!"
    wait_file "$WORK/$1.ready"
}

consumer() {
    if ! java $JOPTS -cp "$CP" demo.ConsumerMain "$WORK" "$@" 2>>"$WORK/consumer.err"; then FAILED=1; fi
}

小结

  • leastactive 读的是消费端 RpcStatus 里的在途请求数。唯一维护这个数的消费端代码是 ActiveLimitFilter，它只在 URL 上有非空、非零的 actives 时才激活。不配 actives，计数一直是 0，leastactive 每次都在全体提供端之间按权重随机，行为和 random 一样。shortestresponse 同理。
  • 打开的方式是让 URL 上出现 actives：消费端引用上配、任意一个方法上配（组合出来的行为，不建议依赖）、或者提供端配（会变成每个消费端的上限）。actives=0 不算。
  • actives 同时是一个硬上限。超过时线程在已选中的提供端上等待，等待中不改选；显式配了正的 timeout 时最多等约 timeout，URL 上取不到 timeout 时是 wait(0)，不是有限等待。等不到抛出的限流异常，在配了重试时会让集群层重新选提供端。只想打开计数的话，值要大于单个消费端对单个提供端、单个方法可能的最大并发；“线程数是上界”只适用于每个线程最多一个在途请求的同步调用。
  • 打开以后，leastactive 每次挑当前在途最少的提供端。稳态、时延稳定时，它近似把各提供端的时间平均在途数拉平，份额近似按平均驻留时长的倒数分配；这是估算，不是策略保证。shortestresponse 用的“成功”是过滤器的记账口径，业务异常也算成功。
  • 三个坑：计数只来自本进程，消费端多而单实例并发低时接近随机；快速失败（包括抛业务异常）的实例会吸走大部分流量，需要另外的健康检查或熔断把它拿掉；唯一最小值直接返回、不看权重，新实例的预热被绕过。
