多个实例同时启动，只允许一个去跑数据库迁移；定时任务部署了三份，同一时刻只该有一份在干活。手边已经有 PostgreSQL 的话，advisory lock 是最省事的选择：不建表，不引入别的组件，进程崩了锁也会随会话自动释放。

SELECT pg_advisory_lock(4242);   -- 拿不到就等
-- ... 只允许一个实例做的事 ...
SELECT pg_advisory_unlock(4242);

问题出在 Go 这一侧。会话级 advisory lock 记在数据库后端会话名下，也就是一条连接；而 Go 服务里几乎都用连接池，pool.Exec 每次可能借到不同的连接。两边对“谁持有锁”的理解不一样，就会出现锁解不掉、两个调用方同时进临界区、等锁的进程死了服务端还在排队这些情况。

这篇只讲这一件事：会话级 advisory lock 怎么和连接池配在一起。先把几个坑实测出来，再看等锁该用轮询还是交给服务端排队，最后给一个完整可运行的小包和测试。

测试环境：

  • PostgreSQL 19.0（2026-11-19 发布，当前最新版，源码编译），对照 PostgreSQL 16.15；
  • Go 1.27.4，pgx v5.13.0（2026-11-11 发布，当前最新版）；
  • 4 核 Intel Xeon 2.10GHz，Linux，客户端和数据库在同一台机器上，走 Unix socket。

下文的现象在 19.0 和 16.15 上结果一致（轮询的获得顺序本来就不固定，除外）；两个版本唯一看得到的差别是 19 默认打开了 log_lock_waits，后面会提到。

锁记在谁名下

PostgreSQL 有两种 advisory lock。官方文档（Advisory Locks）的说法是：

  • 会话级：拿到之后一直持有，直到显式解锁或会话结束。它不遵守事务语义：在事务里拿到的锁，事务回滚了锁还在；解锁也一样，所在事务后来失败了，解锁照样生效。同一个会话可以对同一个键重复加锁，每加一次就要解一次才真正释放。
  • 事务级（pg_advisory_xact_lock）：事务结束时自动释放，不能手动解。

会话级锁“进程崩了自动释放”的好处，正来自它绑在会话上。可连接池里的会话是共享的：同一条连接先后服务很多个请求，连接本身却活得很久。锁于是不跟着请求走，而是跟着那条被反复借还的连接走。

三个坑，实测

下面这个程序（完整代码在文末）依次演示三种情况，只用锁键 4242，不建表、不改数据。在 PostgreSQL 19.0 上的输出：

== 1. lock and unlock on different pooled connections
    server WARNING: you don't own a lock of type ExclusiveLock
    unlock returned false
    pg_locks: pid 28910 granted=true state=idle
== 2. two callers, one pooled connection
    caller A got lock: true, caller B got lock: true
== 3. waiter process killed (client_connection_check_interval=0)
    waiter process killed, its backend pid 28922
    +0s: backend 28922 is still waiting in the lock queue, state=active
    +3s: backend 28922 is still waiting in the lock queue, state=active
    after holder unlocks: backend 28922 is gone
== 3. waiter process killed (client_connection_check_interval=1s)
    waiter process killed, its backend pid 28930
    +0s: backend 28930 is still waiting in the lock queue, state=active
    +3s: backend 28930 is gone
    after holder unlocks: backend 28930 is gone

PostgreSQL 16.15 上逐行相同，只有 pid 不同。

坑 1：解锁落到了另一条连接上

pool.Exec(ctx, `SELECT pg_advisory_lock(4242)`)   // 借到连接 A，加锁，A 还回池里
// ... 此时 A 正被别的请求占着 ...
pool.Exec(ctx, `SELECT pg_advisory_unlock(4242)`) // 借到连接 B，B 没这把锁

pg_advisory_unlock 在当前会话没持有这把锁时返回 false，服务端同时发一条 WARNING（文档也是这么写的）。很多代码根本不看这个返回值，pgx 默认也不把 WARNING 打出来，所以调用方以为解锁成功了。

而锁还在连接 A 上：pg_locks 里能看到它被一个 state=idle 的后端持有。这条连接会带着锁留在池里，直到连接池把它关掉为止，其他实例在这之前都拿不到锁。pgxpool 默认会关掉存活超过 1 小时（MaxConnLifetime）或空闲超过 30 分钟（MaxConnIdleTime）的连接（pgxpool 源码里的 defaultMaxConnLifetime、defaultMaxConnIdleTime），但这不是锁泄漏时长的上限：这两个检查只在连接归还或空闲巡检时进行，一条被长期借着不还的连接，比如被某个长任务一直占着，就不会因此被关掉。

演示里为了稳定复现，在解锁前手动占住了连接 A。真实服务里不需要人为制造，并发请求多一点就会遇到。

坑 2：两个调用方同时“拿到”了锁

会话级锁可以被同一个会话重复获得。演示把连接池限制成 1 条连接，两个调用方依次 pg_try_advisory_lock，两次都返回 true。

真实场景是坑 1 的延续：某段代码直接在连接池上加锁，连接带着锁回到池里；另一个 goroutine 恰好借到这条连接，再去加同一把锁，立刻成功。服务端看来这只是同一个会话把计数加到了 2，没有任何冲突，两个 goroutine 却同时进了临界区。多实例互斥做好了，进程内的互斥反倒破了。

坑 3：等锁的进程死了，服务端还在排队

演示里父进程持锁，子进程阻塞在 pg_advisory_lock 上等；父进程在 pg_locks 里确认子进程的后端已经排在这把锁的队列里，再 kill -9 子进程，模拟发布时 Pod 被强制终止。

子进程已经不在了，它的后端却还在锁队列里，state=active。PostgreSQL 默认只在下一次读写 socket 时才发现客户端断开（client_connection_check_interval 的文档原话），而等锁的后端正睡在锁队列里，不碰 socket。它会一直排下去，直到持锁者放手，它先拿到锁，再去给客户端发结果，这时才发现对面没了。19.0 的日志把这个过程记得很清楚：

LOG:  process 15653 still waiting for ExclusiveLock on advisory lock [5,0,4242,1] after 1000.205 ms
DETAIL:  Process holding the lock: 15645. Wait queue: 15653.
LOG:  process 15653 acquired ExclusiveLock on advisory lock [5,0,4242,1] after 3103.133 ms
LOG:  could not send data to client: Broken pipe
FATAL:  connection to client lost

本机走 Unix socket，发送立刻失败，“死人”拿着锁的时间很短。跨网络时，如果客户端所在机器整个失联，内核要等 TCP 超时才会判定连接断开，这段时间里它可能真的占着锁。这一点我没有在本机复现，只是按机制推断。

把 client_connection_check_interval 设成 1 秒之后，后端会定期轮询 socket，3 秒内就退出了队列。日志里是 FATAL: connection to client lost，上下文是 waiting for ExclusiveLock on advisory lock。这个参数普通用户就能设，可以只在等锁时打开。

只是 ctx 超时的话，情况要好一些。pgx 的默认做法是给连接设截止时间、让读失败，然后关闭连接；关闭时还会异步发一个 CancelRequest（pgconn 的 asyncClose）。我在两个版本上都测过，ctx 超时后 2 秒内服务端的等待者就没了。但进程被杀、机器宕机时，这个 CancelRequest 根本没有机会发出去。

等锁：轮询，还是交给服务端排队

拿不到锁时有两种等法。

轮询：pg_try_advisory_lock 立即返回，拿不到就睡一会儿再试。我在一个 Go 服务的迁移代码里见过这种写法：每 200 ms 试一次，总共等 30 秒，超时后查 pg_locks 把持锁者写进错误信息。它借一条专用连接、整个过程都在这条连接上，解锁用了 context.WithoutCancel，这些都做对了。但轮询本身有两个代价。

一是不公平。谁赶上锁空出来之后的第一次轮询，谁就拿到，跟谁先来无关。下面的程序（文末有代码）让 6 个独立会话依次开始等同一把锁：阻塞方式下，每个会话都先在 pg_locks 里确认已经排进这把锁的队列（同库、同键、objsubid = 1），才启动下一个；轮询方式下，每个会话第一次尝试失败之后才启动下一个。持锁者放手后记录它们拿到锁的顺序，每种方式各跑 3 轮，任何 SQL 错误都会让这一轮失败，不会被记成“拿到”：

blocking round 1: [1 2 3 4 5 6]
blocking round 2: [1 2 3 4 5 6]
blocking round 3: [1 2 3 4 5 6]
polling  round 1: [4 1 2 3 5 6]
polling  round 2: [4 1 2 3 5 6]
polling  round 3: [4 5 2 3 1 6]

这个实验里，阻塞等待按排队顺序拿到了锁。这是锁管理器的常规行为：锁管理器的说明写着，新请求通常排到队尾，放锁时互相冲突的请求按到达顺序授予。但它不是无条件的保证，同一份说明也列了例外：已经持有同一对象上冲突锁的进程会插到冲突等待者前面，死锁检测也可能重排队列。所以准确的说法是：同一个键、各自独立的会话、都请求独占锁、排队顺序已经确认的情况下，本实验里它们按队列顺序获得。

轮询的顺序取决于各自的睡眠节拍正好落在哪儿：4 号最先拿到，最早来的 1 号前两轮排第二，第三轮排到了第五（同样的程序在 16.15 上三轮都是 [4 1 2 3 5 6]）。换个负载，顺序还会变。等的人一多、持锁时间一长，某个实例可能一直抢不到。

二是看不见。轮询的会话只在调用 pg_try_advisory_lock 的那一瞬间碰一下锁，失败了也不留痕迹，pg_locks 里永远查不到“谁在等”，pg_blocking_pids() 也帮不上忙。上面那段迁移代码给排队的会话预留了“waiting”这种状态，可如果其他实例也是轮询，它就永远不会出现。

阻塞等待：pg_advisory_lock 让后端进入锁队列，用 lock_timeout 限制最长等多久。文档说 lock_timeout 适用于等待“表、索引、行或其他数据库对象”上的锁，advisory lock 也在其中，超时报 SQLSTATE 55P03：

ERROR:  55P03: canceling statement due to lock timeout
CONTEXT:  waiting for ExclusiveLock on advisory lock [5,0,7,1]

排队的会话在 pg_locks 里是 granted = false，pg_blocking_pids() 能直接给出挡路的 pid。PostgreSQL 19 还把 log_lock_waits 的默认值改成了 on（19 的发布说明），等锁超过 deadlock_timeout（默认 1 秒）就会记一条日志，上面那段 “still waiting … Wait queue” 就是这么来的，16 上默认不记。

问题是 lock_timeout 怎么设才不污染连接池。直接 SET lock_timeout 会留在这条连接上，下一个借到它的请求莫名其妙地带着 30 秒的锁超时。办法是利用前面那条“会话级锁不遵守事务语义”：

BEGIN;
SELECT set_config('lock_timeout', '30000ms', true);                    -- 等价于 SET LOCAL
SELECT set_config('client_connection_check_interval', '1000ms', true);
SELECT pg_advisory_lock($1);
COMMIT;  -- 两个设置随事务结束，锁留下

事务只是给 SET LOCAL 圈出作用域，COMMIT 之后两个设置都恢复原值，锁还在。等锁超时的话，事务回滚，设置同样恢复。顺带一提，事务回滚时连不带 LOCAL 的设置也会撤销，所以只测失败路径发现不了设置泄漏，测试里要专门检查成功之后的情况，后面的测试就是这么做的。

诊断查询别漏掉 database

文档（pg_locks）说明了 bigint 键在 pg_locks 里怎么存：高 32 位在 classid，低 32 位在 objid，objsubid 为 1，可以用 (classid::bigint << 32) | objid::bigint 还原。两个 int4 的键 objsubid 是 2。同一页还写着：advisory lock 是按数据库隔离的，database 列有意义。

pg_locks 却会列出整个实例的锁。只按键过滤的话，同一个实例上另一个库里恰好用了同一个键的会话，也会被当成持锁者报出来。完整的过滤条件是：

locktype = 'advisory'
AND database = (SELECT oid FROM pg_database WHERE datname = current_database())
AND objsubid = 1
AND ((classid::bigint << 32) | objid::bigint) = $1

完整实现

把上面这些放到一起，得到一个不依赖任何业务代码的小包。先说清楚它保证什么：会话正常期间的协作互斥。锁连接一旦断开（网络、数据库重启、被 pg_terminate_backend），服务端立刻释放锁，别的实例可以进来；而本进程里的业务代码并不会因此自动停下。钉住连接只保证“加锁、解锁、临界区里的 SQL 在同一个会话上”，不等于给锁续了租。下面的“失锁”一节专门说这个。

设计要点：

  1. 钉住连接：Acquire 从池里借一条连接，拿到锁后连接一直由 Lock 占着，Release 时才归还。加锁、解锁一定在同一个会话上。
  2. 先查这条连接是不是已经持有这把锁：防的是坑 2。如果别处直接在池上加锁导致连接带锁回池，就销毁它，换一条，最多试 3 次。
  3. 等锁交给服务端：lock_timeout 和 client_connection_check_interval 都用 SET LOCAL 的方式只覆盖这一次等待；超时返回 ErrNotAcquired，错误里带上持锁者和排队者。两个时长都向上取整到毫秒：lock_timeout = 0 在 PostgreSQL 里表示不限时，如果直接用 Duration.Milliseconds()，500 µs 会被截成 0ms，一个本想“几乎不等”的调用反而会无限等下去。Wait 只限制服务端在锁队列里等多久，不是整个 Acquire 的预算：从池里借连接、网络往返还要靠调用方给 ctx 设 deadline。
  4. 解锁失败就销毁连接：pg_advisory_unlock 报错或返回 false 时，用 Hijack 把连接从池里摘下来关掉。会话结束，它持有的所有会话级锁都会释放。绝不把一条“可能还持锁”的连接还给连接池。pgxpool 的 Release 只会销毁已关闭、正忙或事务没结束的连接（源码），它不知道连接上有没有 advisory lock。
  5. 清理不受调用方 ctx 影响，但都有时限：等锁事务的回滚和 Release 里的解锁都用 context.WithoutCancel 再加 5 秒超时，请求被取消了也照样清理，但不会无限等；拿不到锁时查持锁者的诊断查询有 2 秒的独立时限。
  6. 其他错误一律销毁连接：比如等锁时 ctx 取消，这时连接状态不可信；销毁也能保证即便锁其实已经拿到，也随会话一起释放。
  7. 临界区的 SQL 走同一个会话，但受 Lock 的生命周期管着：Lock.Exec 在持锁连接上执行语句。它不把连接交给调用方：Release 之后再调用返回 ErrReleased，不会碰已经还给连接池、可能正被下一位借用者使用的连接。Exec、Check、Release 用一把互斥锁串起来，Release 会等进行中的 Exec 结束。之所以只给 Exec，是因为 pgx 的 Rows 和 Tx 都带 Conn()，一旦交出去，Release 之后它们仍然能摸到那条连接。
  8. 能检查锁还在不在：Check() 查 pg_locks 确认本会话仍持有这把锁，连接断了或锁被别处解掉都返回 ErrLost，Release 之后返回 ErrReleased。

pglock.go：

// Package pglock 把 PostgreSQL 会话级 advisory lock 和 pgxpool 安全地配在一起。
//
// 要点：
//   - 锁属于后端会话（一条连接），不属于 goroutine，所以加锁到解锁必须钉在同一条连接上；
//   - 等锁交给服务端的 lock_timeout，排队、可观测，超时后连接仍然可用；
//   - 等锁期间打开 client_connection_check_interval，客户端放弃后服务端能尽快退出等待队列；
//   - 解锁失败或返回 false 时销毁这条连接，绝不把可能还持锁的连接还给连接池。
//
// 它提供的是“会话正常期间”的协作互斥：锁连接一旦断开，服务端就会释放锁，
// 别的实例可以进来，而本进程里的业务代码并不会因此自动停下。见 Lock.Check。
package pglock

import (
	"context"
	"errors"
	"fmt"
	"hash/fnv"
	"strings"
	"sync"
	"time"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgconn"
	"github.com/jackc/pgx/v5/pgxpool"
)

// ErrNotAcquired 表示在等待时间内没拿到锁（被别的会话持有）。
var ErrNotAcquired = errors.New("pglock: lock is held by another session")

// ErrLost 表示锁已经不在这个会话上了（连接断开，或被别处解掉）。
var ErrLost = errors.New("pglock: lock lost")

// ErrReleased 表示 Lock 已经 Release，连接已经交还（或销毁），不能再用。
var ErrReleased = errors.New("pglock: lock already released")

const (
	cleanupTimeout  = 5 * time.Second // 回滚、解锁、关连接各自的上限
	diagnoseTimeout = 2 * time.Second // 拿不到锁时查持锁者的上限
)

// Options 控制加锁行为。
type Options struct {
	// Wait 是服务端在锁队列里等待的上限（lock_timeout）。0 表示只试一次，不等待。
	// 不足 1 ms 的正数向上取整为 1 ms（lock_timeout=0 在 PostgreSQL 里表示不限时）。
	// 它只限制服务端等锁，不是整个 Acquire 的预算：从池里借连接、网络往返等
	// 仍然要靠调用方给 ctx 设置 deadline。
	Wait time.Duration
	// CheckInterval 是等锁期间服务端检查客户端是否断开的间隔
	// （client_connection_check_interval）。0 表示用默认值 1s，负数表示不设置。
	// 不足 1 ms 的正数同样向上取整为 1 ms。
	CheckInterval time.Duration
}

// Lock 是一把钉在某条连接上的会话级 advisory lock。
// 它的方法可以并发调用：Exec、Check、Release 互斥执行，Release 会等进行中的调用结束。
type Lock struct {
	mu       sync.Mutex
	conn     *pgxpool.Conn
	raw      *pgx.Conn // 借到时取出的底层连接；只在 released 为 false 时使用
	key      int64
	released bool
	err      error
}

// Key 把一个名字稳定地映射成 bigint 锁键（FNV-1a 64 位）。
// 同一个数据库里的所有应用共用一个锁键空间，名字最好带上应用前缀。
func Key(name string) int64 {
	h := fnv.New64a()
	_, _ = h.Write([]byte(name))
	return int64(h.Sum64())
}

// Acquire 从连接池借一条连接，在这条连接上拿锁，成功后连接一直被 Lock 占着，
// 直到 Release。
func Acquire(ctx context.Context, pool *pgxpool.Pool, key int64, opts Options) (*Lock, error) {
	for attempt := 0; attempt < 3; attempt++ {
		conn, err := pool.Acquire(ctx)
		if err != nil {
			return nil, fmt.Errorf("pglock: acquire connection: %w", err)
		}
		// 防御：这条连接如果已经持有同一把锁（别处用连接池直接加锁后忘了解），
		// 再加一次只会让计数 +1，两个调用方会同时进入临界区。销毁它，换一条。
		held, err := heldBySelf(ctx, conn.Conn(), key)
		if err != nil {
			discard(conn)
			return nil, err
		}
		if held {
			discard(conn)
			continue
		}
		if err := lock(ctx, conn.Conn(), key, opts); err != nil {
			if errors.Is(err, ErrNotAcquired) {
				err = fmt.Errorf("%w (%s)", err, describeHolders(ctx, conn.Conn(), key))
				conn.Release()
				return nil, err
			}
			// 其他错误（包括 ctx 取消）：连接状态不可信，直接销毁。
			// 销毁会结束会话，即便锁其实已经拿到也会随之释放。
			discard(conn)
			return nil, err
		}
		return &Lock{conn: conn, raw: conn.Conn(), key: key}, nil
	}
	return nil, errors.New("pglock: pool keeps handing out connections that already hold the lock")
}

func lock(ctx context.Context, conn *pgx.Conn, key int64, opts Options) error {
	if opts.Wait <= 0 {
		var ok bool
		if err := conn.QueryRow(ctx, `SELECT pg_try_advisory_lock($1)`, key).Scan(&ok); err != nil {
			return fmt.Errorf("pglock: try lock: %w", err)
		}
		if !ok {
			return ErrNotAcquired
		}
		return nil
	}

	check := opts.CheckInterval
	if check == 0 {
		check = time.Second
	}
	// 用事务只是为了让 SET LOCAL 的作用域刚好覆盖这一次等锁：
	// 会话级 advisory lock 不遵守事务语义，COMMIT 之后锁仍然在。
	tx, err := conn.Begin(ctx)
	if err != nil {
		return fmt.Errorf("pglock: begin: %w", err)
	}
	defer func() {
		// 已提交时是空操作；调用方 ctx 取消后也要回滚，但不能无限等。
		rctx, cancel := context.WithTimeout(context.WithoutCancel(ctx), cleanupTimeout)
		defer cancel()
		_ = tx.Rollback(rctx)
	}()

	if _, err := tx.Exec(ctx, `SELECT set_config('lock_timeout', $1, true)`, ms(opts.Wait)); err != nil {
		return fmt.Errorf("pglock: set lock_timeout: %w", err)
	}
	if check > 0 {
		if _, err := tx.Exec(ctx, `SELECT set_config('client_connection_check_interval', $1, true)`, ms(check)); err != nil {
			return fmt.Errorf("pglock: set client_connection_check_interval: %w", err)
		}
	}
	if _, err := tx.Exec(ctx, `SELECT pg_advisory_lock($1)`, key); err != nil {
		var pgErr *pgconn.PgError
		if errors.As(err, &pgErr) && pgErr.Code == "55P03" { // lock_not_available
			return ErrNotAcquired
		}
		return fmt.Errorf("pglock: lock: %w", err)
	}
	if err := tx.Commit(ctx); err != nil {
		return fmt.Errorf("pglock: commit: %w", err)
	}
	return nil
}

// Exec 在持锁的那个会话上执行一条语句，用来做临界区里的数据库操作。
// 语句和锁同生共死：连接一断，锁和这条语句所在的事务一起没了。
// Release 之后调用返回 ErrReleased，不会碰已经交还给连接池的连接。
// 想在临界区里用事务，就在一条语句里写完，或者用多条 Exec 依次发 BEGIN … COMMIT，
// 并在 Release 之前结束事务（否则 Release 的解锁会失败，连接被销毁）。
func (l *Lock) Exec(ctx context.Context, sql string, args ...any) (pgconn.CommandTag, error) {
	l.mu.Lock()
	defer l.mu.Unlock()
	if l.released {
		return pgconn.CommandTag{}, ErrReleased
	}
	return l.raw.Exec(ctx, sql, args...)
}

// Check 确认锁仍由本会话持有。返回错误时（ErrLost 或 ErrReleased）应当停止临界区里的工作：
// 别的实例可能已经拿到了锁。长任务应在每一步之前调用它。
// 它只能缩小、不能消除“失锁后旧持有者还在干活”的窗口；
// 对外部系统的副作用仍需要幂等，或者让对方能拒绝旧持有者（比如携带递增的版本号）。
func (l *Lock) Check(ctx context.Context) error {
	l.mu.Lock()
	defer l.mu.Unlock()
	if l.released {
		return ErrReleased
	}
	held, err := heldBySelf(ctx, l.raw, l.key)
	if err != nil {
		return fmt.Errorf("%w: %v", ErrLost, err)
	}
	if !held {
		return ErrLost
	}
	return nil
}

// Release 解锁并把连接还给连接池；解锁失败时销毁连接。可以重复调用，返回第一次的结果。
func (l *Lock) Release(ctx context.Context) error {
	l.mu.Lock()
	defer l.mu.Unlock()
	if l.released {
		return l.err
	}
	l.released = true // 先标记：此后 Exec、Check 都不再碰这条连接

	ctx, cancel := context.WithTimeout(context.WithoutCancel(ctx), cleanupTimeout)
	defer cancel()
	var ok bool
	err := l.raw.QueryRow(ctx, `SELECT pg_advisory_unlock($1)`, l.key).Scan(&ok)
	switch {
	case err != nil:
		l.err = fmt.Errorf("pglock: unlock: %w", err)
	case !ok:
		l.err = fmt.Errorf("%w: unlock returned false, this session did not hold the lock", ErrLost)
	}
	if l.err != nil {
		discard(l.conn)
	} else {
		l.conn.Release()
	}
	l.conn, l.raw = nil, nil
	return l.err
}

// discard 把连接从连接池里摘下来并关闭。会话结束时它持有的所有会话级锁都会释放。
func discard(c *pgxpool.Conn) {
	ctx, cancel := context.WithTimeout(context.Background(), cleanupTimeout)
	defer cancel()
	_ = c.Hijack().Close(ctx)
}

// LockFilter 是在 pg_locks 里定位一把 bigint advisory lock 的完整条件，$1 是锁键。
const LockFilter = `locktype = 'advisory'
	  AND database = (SELECT oid FROM pg_database WHERE datname = current_database())
	  AND objsubid = 1
	  AND ((classid::bigint << 32) | objid::bigint) = $1`

func heldBySelf(ctx context.Context, conn *pgx.Conn, key int64) (bool, error) {
	var held bool
	err := conn.QueryRow(ctx, `SELECT EXISTS (
	    SELECT 1 FROM pg_locks
	    WHERE pid = pg_backend_pid() AND granted AND `+LockFilter+`)`, key).Scan(&held)
	if err != nil {
		return false, fmt.Errorf("pglock: check own locks: %w", err)
	}
	return held, nil
}

// describeHolders 列出持锁和排队的会话，供报错时排查。它有自己的短时限，
// 不会因为诊断把调用方拖住。
func describeHolders(ctx context.Context, conn *pgx.Conn, key int64) string {
	ctx, cancel := context.WithTimeout(ctx, diagnoseTimeout)
	defer cancel()
	rows, err := conn.Query(ctx, `
	    SELECT l.pid, l.granted, coalesce(a.application_name, ''),
	           coalesce(a.state, ''), coalesce(now() - a.state_change, interval '0')
	    FROM pg_locks l LEFT JOIN pg_stat_activity a USING (pid)
	    WHERE `+LockFilter+`
	    ORDER BY l.granted DESC, l.pid`, key)
	if err != nil {
		return "holders unavailable: " + err.Error()
	}
	defer rows.Close()
	var parts []string
	for rows.Next() {
		var pid int32
		var granted bool
		var app, state string
		var since time.Duration
		if err := rows.Scan(&pid, &granted, &app, &state, &since); err != nil {
			return "holders unavailable: " + err.Error()
		}
		role := "waiting"
		if granted {
			role = "holding"
		}
		parts = append(parts, fmt.Sprintf("pid %d %s app=%q state=%s for %s",
			pid, role, app, state, since.Round(time.Millisecond)))
	}
	if err := rows.Err(); err != nil {
		return "holders unavailable: " + err.Error()
	}
	if len(parts) == 0 {
		return "no holder visible (it may have just released)"
	}
	return strings.Join(parts, "; ")
}

// ms 把时长换成 PostgreSQL 的毫秒设置，向上取整，保证正数不会变成 0（0 表示不限时）。
func ms(d time.Duration) string {
	n := (d + time.Millisecond - 1) / time.Millisecond
	return fmt.Sprintf("%dms", n)
}

// waitQueued 等到这把锁上恰好有 n 个排队者（granted = false），最多等 5 秒。
// 查询出错直接失败，不把默认值当成结果。
func waitQueued(t *testing.T, obs *pgx.Conn, key int64, n int) {
	t.Helper()
	deadline := time.Now().Add(5 * time.Second)
	for {
		var got int
		if err := obs.QueryRow(context.Background(),
			`SELECT count(*) FROM pg_locks WHERE NOT granted AND `+LockFilter, key).Scan(&got); err != nil {
			t.Fatalf("query pg_locks: %v", err)
		}
		if got == n {
			return
		}
		if time.Now().After(deadline) {
			t.Fatalf("waited 5s for %d queued waiter(s), have %d", n, got)
		}
		time.Sleep(20 * time.Millisecond)
	}
}

				}

					}

			t.Fatalf("err = %v, want context.Canceled", err)
		}
	case <-time.After(5 * time.Second):

		t.Fatalf("holder should be unaffected: %v", err)
	}
}

演示程序

开头那段输出来自这个程序。它会持锁、拉起自己作为子进程去等锁，在 pg_locks 里确认子进程已排队后再 kill -9 掉它。所有 pg_locks 查询都用包里导出的完整过滤条件 LockFilter；找不到子进程的后端、或者查询失败，程序直接报错退出，不会把失败输出成“已退出”。kill 在 macOS 和 Linux 上行为一致。cmd/demo/main.go：

// 演示会话级 advisory lock 直接配连接池时的三个坑。
// 用法：DATABASE_URL=postgres://... go run ./cmd/demo
// 只会用到锁键 4242，不建表、不改数据；请指向一个测试库。
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"os"
	"os/exec"
	"time"

	"example.com/pglock"
	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgconn"
	"github.com/jackc/pgx/v5/pgxpool"
)

const key int64 = 4242

func main() {
	url := os.Getenv("DATABASE_URL")
	if url == "" {
		log.Fatal("set DATABASE_URL to a test database")
	}
	if len(os.Args) == 3 && os.Args[1] == "wait" {
		waitForever(url, os.Args[2])
		return
	}
	ctx := context.Background()

	leak(ctx, url)
	reentrant(ctx, url)
	killedWhileWaiting(ctx, url, "0")
	killedWhileWaiting(ctx, url, "1s")
}

func newPool(ctx context.Context, url string, maxConns int32) *pgxpool.Pool {
	cfg, err := pgxpool.ParseConfig(url)
	if err != nil {
		log.Fatal(err)
	}
	cfg.MaxConns = maxConns
	cfg.ConnConfig.OnNotice = func(_ *pgconn.PgConn, n *pgconn.Notice) {
		fmt.Printf("    server %s: %s\n", n.Severity, n.Message)
	}
	pool, err := pgxpool.NewWithConfig(ctx, cfg)
	if err != nil {
		log.Fatal(err)
	}
	return pool
}

// 坑 1：加锁和解锁落在连接池里的不同连接上。
func leak(ctx context.Context, url string) {
	fmt.Println("== 1. lock and unlock on different pooled connections")
	pool := newPool(ctx, url, 4)
	defer pool.Close()

	must(pool.Exec(ctx, `SELECT pg_advisory_lock($1)`, key))

	// 模拟并发：另一个请求此刻正占着刚才那条连接。
	busy, err := pool.Acquire(ctx)
	if err != nil {
		log.Fatal(err)
	}
	var ok bool
	if err := pool.QueryRow(ctx, `SELECT pg_advisory_unlock($1)`, key).Scan(&ok); err != nil {
		log.Fatal(err)
	}
	busy.Release()
	fmt.Printf("    unlock returned %v\n", ok)
	showHolders(ctx, url)
}

// 坑 2：同一会话可以重复加锁，两个调用方拿到同一条连接时都会“加锁成功”。
func reentrant(ctx context.Context, url string) {
	fmt.Println("== 2. two callers, one pooled connection")
	pool := newPool(ctx, url, 1)
	defer pool.Close()

	var a, b bool
	if err := pool.QueryRow(ctx, `SELECT pg_try_advisory_lock($1)`, key).Scan(&a); err != nil {
		log.Fatal(err)
	}
	if err := pool.QueryRow(ctx, `SELECT pg_try_advisory_lock($1)`, key).Scan(&b); err != nil {
		log.Fatal(err)
	}
	fmt.Printf("    caller A got lock: %v, caller B got lock: %v\n", a, b)
	must(pool.Exec(ctx, `SELECT pg_advisory_unlock_all()`))
}

// 坑 3：等锁的客户端进程被杀掉（比如发布时 Pod 被强制终止），服务端那个后端还在排队。
// 父进程持锁，再拉起自己作为子进程去等锁，确认它已排队后 kill -9 子进程。
func killedWhileWaiting(ctx context.Context, url string, check string) {
	fmt.Printf("== 3. waiter process killed (client_connection_check_interval=%s)\n", check)
	holder, err := pgx.Connect(ctx, url)
	if err != nil {
		log.Fatal(err)
	}
	defer holder.Close(ctx)
	must(holder.Exec(ctx, `SELECT pg_advisory_lock($1)`, key))

	self, err := os.Executable()
	if err != nil {
		log.Fatal(err)
	}
	child := exec.Command(self, "wait", check)
	child.Stdout = os.Stdout
	child.Stderr = os.Stderr
	if err := child.Start(); err != nil {
		log.Fatal(err)
	}
	// 等子进程的后端出现在这把锁的等待队列里，最多 5 秒。
	var pid int32
	deadline := time.Now().Add(5 * time.Second)
	for {
		err := holder.QueryRow(ctx, `SELECT pid FROM pg_locks
		    WHERE NOT granted AND `+pglock.LockFilter, key).Scan(&pid)
		if err == nil {
			break
		}
		if !errors.Is(err, pgx.ErrNoRows) {
			log.Fatalf("query pg_locks: %v", err)
		}
		if time.Now().After(deadline) {
			child.Process.Kill()
			log.Fatal("waiter backend never showed up in the lock queue")
		}
		time.Sleep(50 * time.Millisecond)
	}
	if err := child.Process.Kill(); err != nil {
		log.Fatal(err)
	}
	child.Wait()
	fmt.Printf("    waiter process killed, its backend pid %d\n", pid)

	for _, after := range []time.Duration{0, 3 * time.Second} {
		time.Sleep(after)
		fmt.Printf("    +%s: backend %d %s\n", after, pid, backendState(ctx, holder, pid))
	}
	must(holder.Exec(ctx, `SELECT pg_advisory_unlock($1)`, key))
	time.Sleep(200 * time.Millisecond)
	fmt.Printf("    after holder unlocks: backend %d %s\n", pid, backendState(ctx, holder, pid))
}

// 子进程：设置好检查间隔后阻塞等锁，直到被杀。
func waitForever(url, check string) {
	ctx := context.Background()
	conn, err := pgx.Connect(ctx, url)
	if err != nil {
		log.Fatal(err)
	}
	must(conn.Exec(ctx, `SELECT set_config('client_connection_check_interval', $1, false)`, check))
	_, err = conn.Exec(ctx, `SELECT pg_advisory_lock($1)`, key)
	log.Fatalf("waiter should have been killed while waiting, got err=%v", err)
}

// backendState 报告某个后端是否还在、在这把锁上是持有还是排队。查询失败直接退出，
// 不把失败当成“已退出”。
func backendState(ctx context.Context, conn *pgx.Conn, pid int32) string {
	var state string
	var granted *bool
	err := conn.QueryRow(ctx, `SELECT a.state,
	        (SELECT granted FROM pg_locks WHERE pid = a.pid AND `+pglock.LockFilter+`)
	    FROM pg_stat_activity a WHERE a.pid = $2`, key, pid).Scan(&state, &granted)
	switch {
	case errors.Is(err, pgx.ErrNoRows):
		return "is gone"
	case err != nil:
		log.Fatalf("query backend %d: %v", pid, err)
	case granted == nil:
		return "is alive, not on this lock, state=" + state
	case *granted:
		return "holds the lock, state=" + state
	}
	return "is still waiting in the lock queue, state=" + state
}

func showHolders(ctx context.Context, url string) {
	conn, err := pgx.Connect(ctx, url)
	if err != nil {
		log.Fatal(err)
	}
	defer conn.Close(ctx)
	rows, err := conn.Query(ctx, `SELECT l.pid, l.granted, a.state
	    FROM pg_locks l JOIN pg_stat_activity a USING (pid)
	    WHERE `+pglock.LockFilter, key)
	if err != nil {
		log.Fatal(err)
	}
	defer rows.Close()
	n := 0
	for rows.Next() {
		var pid int32
		var granted bool
		var state string
		if err := rows.Scan(&pid, &granted, &state); err != nil {
			log.Fatal(err)
		}
		n++
		fmt.Printf("    pg_locks: pid %d granted=%v state=%s\n", pid, granted, state)
	}
	if err := rows.Err(); err != nil {
		log.Fatal(err)
	}
	if n == 0 {
		fmt.Println("    pg_locks: nobody holds the lock")
	}
}

func must(_ pgconn.CommandTag, err error) {
	if err != nil {
		log.Fatal(err)
	}
}

// 对比两种等锁方式下的获得顺序：阻塞排队 vs 每 200ms 轮询一次。
// 用法：DATABASE_URL=postgres://... go run ./cmd/fifo
// 只会用到锁键 4343，不建表、不改数据；请指向一个测试库。
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"os"
	"sync"
	"time"

	"example.com/pglock"
	"github.com/jackc/pgx/v5"
)

const (
	key     int64 = 4343
	waiters       = 6
)

func main() {
	url := os.Getenv("DATABASE_URL")
	if url == "" {
		log.Fatal("set DATABASE_URL to a test database")
	}
	for _, mode := range []string{"blocking", "polling"} {
		for round := 1; round <= 3; round++ {
			order, err := run(url, mode)
			if err != nil {
				log.Fatalf("%s round %d: %v", mode, round, err)
			}
			fmt.Printf("%-8s round %d: %v\n", mode, round, order)
		}
	}
}

// run 让 1..6 号会话依次开始等锁，持锁者放手后记录它们拿到锁的顺序。
// 整轮最多 30 秒；任何 SQL 错误都让这一轮失败，不会被记成“拿到”。
func run(url, mode string) ([]int, error) {
	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
	defer cancel()

	holder, err := pgx.Connect(ctx, url)
	if err != nil {
		return nil, err
	}
	defer holder.Close(context.Background())
	if _, err := holder.Exec(ctx, `SELECT pg_advisory_lock($1)`, key); err != nil {
		return nil, err
	}

	var mu sync.Mutex
	var order []int
	var firstErr error
	fail := func(err error) {
		mu.Lock()
		if firstErr == nil {
			firstErr = err
		}
		mu.Unlock()
		cancel()
	}
	var wg sync.WaitGroup
	for i := 1; i <= waiters; i++ {
		conn, err := pgx.Connect(ctx, url)
		if err != nil {
			return nil, err
		}
		var pid int32
		if err := conn.QueryRow(ctx, `SELECT pg_backend_pid()`).Scan(&pid); err != nil {
			return nil, err
		}
		started := make(chan struct{})
		wg.Add(1)
		go func(i int, conn *pgx.Conn) {
			defer wg.Done()
			defer conn.Close(context.Background())
			if err := acquire(ctx, conn, mode, started); err != nil {
				fail(fmt.Errorf("waiter %d: %w", i, err))
				return
			}
			mu.Lock()
			order = append(order, i)
			mu.Unlock()
			time.Sleep(30 * time.Millisecond) // 临界区
			if _, err := conn.Exec(ctx, `SELECT pg_advisory_unlock($1)`, key); err != nil {
				fail(fmt.Errorf("waiter %d unlock: %w", i, err))
			}
		}(i, conn)

		// 确认 i 号已经在等，再启动 i+1 号。
		if mode == "blocking" {
			if err := waitQueued(ctx, holder, pid); err != nil {
				return nil, fmt.Errorf("waiter %d: %w", i, err)
			}
		} else {
			select {
			case <-started: // 第一次尝试已失败，进入轮询
			case <-ctx.Done():
				return nil, ctx.Err()
			}
		}
		time.Sleep(50 * time.Millisecond)
	}
	if _, err := holder.Exec(ctx, `SELECT pg_advisory_unlock($1)`, key); err != nil {
		return nil, err
	}
	wg.Wait()
	if firstErr != nil {
		return nil, firstErr
	}
	if len(order) != waiters {
		return nil, fmt.Errorf("only %d of %d waiters got the lock", len(order), waiters)
	}
	return order, nil
}

func acquire(ctx context.Context, conn *pgx.Conn, mode string, started chan<- struct{}) error {
	if mode == "blocking" {
		close(started)
		_, err := conn.Exec(ctx, `SELECT pg_advisory_lock($1)`, key)
		return err
	}
	for first := true; ; first = false {
		var ok bool
		if err := conn.QueryRow(ctx, `SELECT pg_try_advisory_lock($1)`, key).Scan(&ok); err != nil {
			return err
		}
		if ok {
			return nil
		}
		if first {
			close(started)
		}
		select {
		case <-time.After(200 * time.Millisecond):
		case <-ctx.Done():
			return ctx.Err()
		}
	}
}

// waitQueued 确认指定后端已在同库、同键、objsubid=1 的这把锁上排队。
func waitQueued(ctx context.Context, conn *pgx.Conn, pid int32) error {
	for {
		var queued bool
		err := conn.QueryRow(ctx, `SELECT EXISTS (SELECT 1 FROM pg_locks
		    WHERE pid = $2 AND NOT granted AND `+pglock.LockFilter+`)`, key, pid).Scan(&queued)
		if err != nil {
			return err
		}
		if queued {
			return nil
		}
		select {
		case <-time.After(10 * time.Millisecond):
		case <-ctx.Done():
			return errors.New("backend never showed up in the lock queue")
		}
	}
}

取舍

能放进一个事务就用事务级锁。 pg_advisory_xact_lock 在事务结束时自动释放，不可能泄漏到连接池，也就没有上面这些麻烦。它不适合的情况是：临界区要跨多个事务，比如迁移工具每个版本单独一个事务；或者里面有不能在事务块里执行的语句，比如 CREATE INDEX CONCURRENTLY（文档明确说它不能在事务块里执行）。这时只能用会话级锁，再按本文的办法钉住连接。

经过 PgBouncer 的事务池模式就别用会话级锁。 事务池模式下，同一个客户端连接的前后两个事务可能落在不同的服务端连接上。PgBouncer 的功能对照表里，会话级 advisory lock 在事务池模式下标的是 “Never”。

失锁之后旧持有者不会自己停。 锁连接断开时，服务端释放锁，新实例进来；旧实例的 Go 代码却可能还在跑，尤其是临界区的工作不在这条连接上（用了池里别的连接、调了外部 API、写了文件）时，它根本不会收到任何错误。临界区的 SQL 走 Lock.Exec 能让这部分工作和锁同生共死：连接一断，未提交的事务随之回滚。长任务在每一步之前调 Check()，发现 ErrLost 就停。这两样只能缩小窗口、不能消除它：Check 通过之后到下一步真正执行之间，锁仍可能丢。对外部系统的副作用要么做成幂等，要么让对方能拒绝旧持有者，比如每次拿锁后在库里把一个版本号加一，外部写入都带上它，对方只接受最新的版本。

一把锁占一条连接。 持锁期间这条连接不能干别的。如果临界区里还要用同一个池执行查询，而池已经被占满（极端情况是 MaxConns = 1），就会自己等自己，永远卡住。临界区里的数据库操作直接用 Lock.Exec，或者给连接池留出余量。

多一次查询换防御。 Acquire 每次都多查一次 pg_locks，检查连接是否已经带着锁。迁移、选主、定时任务这种低频锁，这点开销无所谓；如果每个请求都要加锁，可以去掉这一步，改在连接池层面兜底，比如在 pgxpool 的 AfterRelease 里执行 pg_advisory_unlock_all()，代价是每次归还连接都多一次往返。不要图省事换成 DISCARD ALL：它除了释放 advisory lock，还会删掉服务端的 prepared statement、重置会话设置等（文档），而 pgx 默认会缓存 prepared statement，客户端缓存和服务端状态就对不上了。

client_connection_check_interval 依赖操作系统。 文档说它依赖 Linux、macOS、illumos 和 BSD 系列提供的内核事件，其他平台不可用；源码里的检查函数在不支持的平台上会拒绝非零值。数据库跑在这类平台上时，把 Options.CheckInterval 设成负数跳过它。

锁键的命名空间是整个数据库共享的。 不同应用如果连同一个库，用的又是 1、2、42 这样的小整数，很容易撞上。示例里的 Key 用 FNV-1a 把带应用前缀的名字映射成 64 位整数，随机碰撞的概率可以忽略，但最好还是在团队里登记一下用了哪些名字。
