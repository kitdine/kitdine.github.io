下面这段代码能编译、能启动，平时调用一切正常：

@SentinelResource(value = "queryOrder", blockHandler = "queryOrderBlocked")
public Order queryOrder(String id) { ... }

// BlockException 也是 Exception，写宽一点应该没问题吧
public Order queryOrderBlocked(String id, Exception e) {
    return Order.EMPTY;
}

直到流量上来、规则真的拦下请求，调用方拿到的不是 Order.EMPTY，而是一个 UndeclaredThrowableException，catch (BlockException e) 接不住它。到了 Web 层，@ExceptionHandler(BlockException.class) 能不能接住，要看同一个 @ControllerAdvice 里有没有更宽的处理器、advice 之间谁的优先级高：它和常见的兜底 @ExceptionHandler(Exception.class) 写在同一个 advice 里时，兜底处理器会先把异常截走，接口返回 500。应用日志里没有一行和 Sentinel 有关的错误。

原因是 @SentinelResource 的 blockHandler / fallback 既不经过编译器检查，也不在启动时绑定，而是在第一次被拦、第一次失败时用反射按名字和参数表去找。参数类型必须逐个完全相同，Exception 不等于 BlockException。找不到时它不报错，只在 Sentinel 自己的 sentinel-record.log 里写一行 WARN，然后退到下一级处理，最后把 BlockException 原样抛出。

这篇把注解切面这条路径从头走一遍：handler 怎么找、找不到会怎样、异常怎么分进 fallback 和统计、exceptionsToIgnore 该放什么、为什么同类调用会让整个注解失效，以及两个随调用顺序变化的缓存坑。每个结论都用一个可独立运行的示例验证过：完整代码在文末，九组实验，每一项都有断言，结果不符合预期时进程以 1 退出。

版本：Sentinel 1.8.10（写这篇时 Maven Central 上最新的稳定版；主干 1.8.11-SNAPSHOT 里这部分代码和 1.8.10 相同），Spring Boot 4.2.0（Spring Framework 7.1.0，AspectJ weaver 1.9.27），JDK 21。用 Spring Cloud Alibaba 时，它的 SentinelAutoConfiguration 注册的也是同一个 SentinelResourceAspect；2025.1.0.0 依赖的 Sentinel 1.8.9 在注解模块上和 1.8.10 没有差别。

切面就是一个 try 包住两段代码

SentinelResourceAspect 的核心方法（1.8.10，省略了开头取注解的几行）：

Entry entry = null;
try {
    entry = SphU.entry(resourceName, resourceType, entryType, pjp.getArgs());
    return pjp.proceed();
} catch (BlockException ex) {
    return handleBlockException(pjp, annotation, ex);
} catch (Throwable ex) {
    Class<? extends Throwable>[] exceptionsToIgnore = annotation.exceptionsToIgnore();
    // The ignore list will be checked first.
    if (exceptionsToIgnore.length > 0 && exceptionBelongsTo(ex, exceptionsToIgnore)) {
        throw ex;
    }
    if (exceptionBelongsTo(ex, annotation.exceptionsToTrace())) {
        traceException(ex);
        return handleFallback(pjp, annotation, ex);
    }

    // No fallback function can handle the exception, so throw it out.
    throw ex;
} finally {
    if (entry != null) {
        entry.exit(1, pjp.getArgs());
    }
}

后面所有现象都来自这里的三个细节：

  1. SphU.entry 和 pjp.proceed()（也就是业务方法本身）在同一个 try 里。catch (BlockException ex) 不区分这个异常是当前资源的规则抛的，还是从业务方法里冒出来的。
  2. 业务异常先过 exceptionsToIgnore，再过 exceptionsToTrace（默认 {Throwable.class}）。两次判断都是 exceptionClass.isAssignableFrom(ex.getClass())，只看异常自己的类，不看 cause。
  3. traceException 在 handleFallback 之前。不管 fallback 兜没兜住，异常都已经记在这次 Entry 上，exit 时进统计、进熔断器。

handler 的查找分级进行。被拦（BlockException）时依次找 blockHandler、fallback、defaultFallback，都没有就原样抛出；业务异常时依次找 fallback、defaultFallback，都没有就原样抛出。这里的“没有”不只是没配，配了但签名不匹配也算没有。

签名：参数逐个完全相同

查找逻辑在 AbstractSentinelAspectSupport#findMethod，判断条件只有一处：

if (name.equals(method.getName()) && checkStatic(mustStatic, method)
    && returnType.isAssignableFrom(method.getReturnType())
    && Arrays.equals(parameterTypes, method.getParameterTypes())) {

参数表用 Arrays.equals 比较 Class 对象，没有任何“兼容”的余地；返回类型用 isAssignableFrom，handler 可以返回原方法返回类型的子类。各种 handler 期望的参数表：

handler 期望的参数表 在哪个类里找
blockHandler 原参数 + BlockException 默认目标类；配了 blockHandlerClass 就只看数组里的第一个类，方法必须是 static
fallback 原参数；找不到再试原参数 + Throwable 默认目标类；配了 fallbackClass 同理
defaultFallback 空参数；找不到再试只有一个 Throwable 同 fallback；方法上没写时用类上 @SentinelResource 的

当前类找不到时沿父类往上找，不看接口，所以接口里的 default 方法不算数。

实验一里带 sig. 前缀的资源都配了 count = 0 的 QPS 规则，每次调用都会被拦；fb. 前缀的几个没有规则，业务方法自己抛 IllegalStateException：

  S2 末参数写成 Exception                           抛出 UndeclaredThrowableException(cause FlowException)
  S3 末参数写成 FlowException                       抛出 UndeclaredThrowableException(cause FlowException)
  S4 原参数 long，handler 写 Long                   抛出 UndeclaredThrowableException(cause FlowException)
  S5 原返回 CharSequence，handler 返回 String        返回 blockHandler(FlowException)
  S6 原返回 int，handler 返回 Integer                抛出 UndeclaredThrowableException(cause FlowException)
  S7 blockHandlerClass 里的实例方法                  抛出 UndeclaredThrowableException(cause FlowException)
  S8 blockHandlerClass 里的 static 方法            返回 blockHandler(FlowException)
  S9 blockHandler 写错，但有 fallback               返回 fallback(FlowException)
  S10 private 的 blockHandler                   返回 blockHandler(FlowException)
  F1 fallback 末参数写成 Exception                  抛出 IllegalStateException

  F3 fallback 写错，另有 defaultFallback            返回 defaultFallback(IllegalStateException)

逐条看：

  • 最后一个参数只能写 BlockException。写成父类 Exception（S2）、写成子类 FlowException（S3）都找不到。想区分限流和熔断，在 handler 里用 instanceof。
  • 基本类型和包装类型不通用（S4、S6）。long 参数配 Long、int 返回值配 Integer，源码层面有自动装箱，在反射匹配里却是不同的 Class。
  • 返回类型可以更窄（S5）。原方法返回 CharSequence，handler 返回 String 能匹配。官方文档说返回类型“需要与原方法相匹配”，实际规则比这宽一点。
  • blockHandlerClass 里只认 static 方法（S7、S8）。文档写了这一条，但忘写 static 的后果和签名写错一样，是静默的。
  • blockHandler 写错会悄悄落到 fallback（S9），fallback 收到的是 FlowException。看上去也算兜住了，但 fallback 往往是为业务失败写的：打错误日志、触发报警、返回缓存数据。限流本来是正常的保护动作，现在每一次都被当成故障处理。
  • fallback 额外的那个参数必须正好是 Throwable（F1）。写成 Exception 两种参数表都对不上，业务异常原样抛出。文档的说法是“可以额外多一个 Throwable 类型的参数用于接收对应的异常”，这里的 Throwable 要按字面理解。
  • F2：只写原参数的 fallback 能匹配，但拿不到异常，排查问题时只知道走了降级，不知道为什么。

另外两处文档和代码不一致的地方。文档说 blockHandler 的访问范围需要是 public，代码从 1.8.2 起（#2163）调用前会 setAccessible(true)，private 也能用（S10）。文档说同时配了 fallback 和 defaultFallback 时只有 fallback 生效，准确地说是 fallback 找到了才只有它生效；fallback 签名写错时会接着去找 defaultFallback（F3），这时用的是通用的兜底逻辑，而你以为在用专门写的那个。

为什么调用方拿到的是 UndeclaredThrowableException

三级都找不到时，切面把 BlockException 原样抛出。它继承的是 Exception，是受检异常，而业务方法通常不会声明 throws BlockException。方法抛出了自己没声明的受检异常，Spring AOP 的代理会把它包成 java.lang.reflect.UndeclaredThrowableException。实验里用的是 CGLIB 代理（Spring Boot 的默认）；JDK 动态代理在 java.lang.reflect.Proxy 这一层也是同样的规则，见 UndeclaredThrowableException 的 Javadoc。

所以在 Java 代码里直接调用这个方法的地方，catch (BlockException e) 接不住它，要接得写 UndeclaredThrowableException，再看 getCause() 是不是 BlockException。

Spring MVC 的 @ExceptionHandler 不一样，它不只看最外层的异常。Spring Framework 的文档写得很清楚：异常可以匹配最外层，也可以匹配包装异常里的 cause，“As of 5.3, this can match at arbitrary cause levels”；同一个 controller 或 @ControllerAdvice 类里，最外层的匹配优先于 cause 的匹配；而在多个 advice 之间，“a cause match on a higher-priority @ControllerAdvice bean is preferred to any match (for example, root) on a lower-priority @ControllerAdvice bean”（文档，页面版本 7.1.0）。

实验七用同一个版本跑了一遍：五个接口都调用 S2 那个签名写错的方法，区别只在各自生效的处理器（每个 advice 用 assignableTypes 限定到一个接口，M4、M5 的两个 advice 用 @Order 排优先级）：

  M1 没有任何 @ExceptionHandler                    HTTP 500
  M2 只有 BlockException 处理器                     HTTP 429 BlockException 处理器(参数实际是 FlowException)
  M3 同一个 advice 里还有 Exception 处理器              HTTP 500 Exception 处理器(参数实际是 UndeclaredThrowableException)
  M4 Exception 处理器在优先级更高的 advice               HTTP 500 Exception 处理器(参数实际是 UndeclaredThrowableException)
  M5 BlockException 处理器在优先级更高的 advice          HTTP 429 BlockException 处理器(参数实际是 FlowException)
  • 只有 BlockException 处理器时（M2），它能接住被包装的异常，而且方法参数拿到的是 cause 本身（FlowException），不是外面那层。
  • 同一个 advice 里还有 Exception 处理器时（M3），最外层的 UndeclaredThrowableException 直接匹配上 Exception，BlockException 处理器不会被用到。很多项目的全局异常处理正是这样写的。
  • 分在两个 advice 里时，谁的优先级高谁赢（M4、M5）。想让限流在 Web 层稳定地变成 429，BlockException 处理器要放在一个优先级比所有宽泛处理器都高的 advice 里。
  • 什么都没写时（M1），Spring Boot 默认的错误处理返回 500。

这些规则能补救一部分，但补救的只是 HTTP 响应。blockHandler 里的降级逻辑照样没有执行，非 Web 的调用方（定时任务、消息消费者、RPC 提供端）也用不上这套机制。更好的办法是让签名一开始就写对，后面“启动时校验”一节给了一个做法。

只在第一次触发时解析，找不到只写一行 WARN

解析结果缓存在 ResourceMetadataRegistry 的三个静态 Map 里，找不到也会缓存一个“不存在”的占位。所以每个 handler 在一个 JVM 里只解析一次，也只写一次日志。日志写进 sentinel-record.log（默认目录 ~/logs/csp/，可以用 csp.sentinel.log.dir 改），不进应用自己的日志。

更麻烦的是，解析发生在故障路径上：签名写错的 blockHandler 只有在规则第一次真的拦下请求时才会被发现，正是你最需要它的时候。

异常怎么分流

实验二的几个资源都没有流控规则，业务方法按参数抛出不同的异常：

  E1 默认 + IllegalStateException                返回 fallback(IllegalStateException)
  E1 默认 + BadRequestException                  返回 fallback(BadRequestException)
  E1 默认 + OutOfMemoryError                     返回 fallback(OutOfMemoryError)
  E1 ex.default 记录的异常数                         异常 3
  E2 ignore + BadRequestException              抛出 BadRequestException
  E2 ignore + 子类 MissingParamException         抛出 MissingParamException
  E2 ignore + 被包了一层的 BadRequestException       返回 fallback(IllegalStateException)
  E2 ignore + IllegalStateException            返回 fallback(IllegalStateException)
  E2 ex.ignore 记录的异常数                          异常 2
  E3 traceIo + UncheckedIOException            返回 fallback(UncheckedIOException)
  E3 traceIo + IllegalStateException           抛出 IllegalStateException
  E3 ex.traceIo 记录的异常数                         异常 1
  E4 fallback 遇到 Error 原样抛出                    抛出 OutOfMemoryError
  E4 普通异常照常兜底                                  返回 fallback(IllegalStateException)
  E4 ex.rethrowError 记录的异常数                    异常 2

  • 默认连 Error 也进 fallback（E1）。exceptionsToTrace 的默认值是 {Throwable.class}，业务方法抛出的 OutOfMemoryError 被 fallback 变成了一个普通的返回值，调用方拿着降级结果继续往下跑。注意 E1 里的 OutOfMemoryError 是代码自己 new 出来抛的，只验证了注解怎么给 Error 分流；真实的堆耗尽时 fallback 能不能执行、执行之后应用处在什么状态，这里没有验证。如果 fallback 只想处理异常，就在里面把 Error 原样抛出（E4）。异常在调 fallback 之前就记过了，E4 的两次失败都在统计里，熔断不受影响。不要为此把 Error 放进 exceptionsToIgnore，那样它就不进统计了。

  • exceptionsToIgnore 按继承匹配，但只看异常自己的类（E2）。子类 MissingParamException 也被忽略；IllegalStateException 里包着一个 BadRequestException 就不算，照样进 fallback、照样记异常。习惯把异常包一层再抛的代码，要忽略的是外面那一层。

  • 被忽略的异常原样抛给调用方，不进 fallback，也不记异常（E2 只记了两次，都是没被忽略的那两次）。对熔断器来说，这次请求的 Entry 上没有 error，就是一次正常完成的请求：异常数不算它，异常比例的分母反而算它。ExceptionCircuitBreaker#onRequestComplete 里是这样记的：

    if (error != null) {
    counter.getErrorCount().add(1);
}
counter.getTotalCount().add(1);

  • 自己写了 exceptionsToTrace，它就成了白名单（E3）。只追踪 IO 类异常时，IllegalStateException 既不记、也不进 fallback，直接抛出。

fallback 兜住了，熔断照样算

实验三的两个资源都配了“统计窗口内异常数大于 2 就熔断 30 秒”的规则。先用空 id 调 5 次（参数错误），再用正常 id 调 1 次：

  B1 默认：5 次空 id，再 1 次正常 id
      第 1 次                                    返回 fallback(BadRequestException)
      第 2 次                                    返回 fallback(BadRequestException)
      第 3 次                                    返回 fallback(BadRequestException)
      第 4 次                                    返回 blockHandler(DegradeException)
      第 5 次                                    返回 blockHandler(DegradeException)
      第 6 次                                    返回 blockHandler(DegradeException)
  B2 忽略 BadRequestException：同样 6 次
      第 1 次                                    抛出 BadRequestException
      第 2 次                                    抛出 BadRequestException
      第 3 次                                    抛出 BadRequestException
      第 4 次                                    抛出 BadRequestException
      第 5 次                                    抛出 BadRequestException
      第 6 次                                    返回 ok:42

默认配置下，前三次走 fallback，调用方看到的都是正常返回值。第三次之后异常数 3 > 2，熔断器打开；第 4、5 次连同那次参数正确的请求都被 DegradeException 拦下，进了 blockHandler。接下来 30 秒，这个资源上的所有请求都拿到降级结果，起因只是某个调用方在传空参数。

把 BadRequestException 放进 exceptionsToIgnore 之后，参数错误原样抛给调用方，熔断器不受影响，正常请求照常返回。

这就是 exceptionsToIgnore 该放什么的答案：放“调用方的错”，比如参数校验失败、资源不存在、无权限、被业务规则拒绝（余额不足之类）。这些异常恰恰说明被保护的依赖是健康的。代价是它们不再进 fallback，要由调用方或全局异常处理来接；通常本来就该这样，参数错误不应该被降级成一个默认值。反过来，超时、连接失败、下游 5xx 这类“依赖出了问题”的异常要留在统计里，熔断才有意义。

嵌套资源：下游被拦，上游的 handler 在响应

这是第一个细节的后果。实验四里 OuterService 的两个方法都标了资源，自己没有任何规则，各自调用 InnerService 的一个资源；inner 的两个资源配了 count = 0，而且没写任何 handler：

  N1 下游声明 throws BlockException                返回 outer.blockHandler(FlowException 来自 inner.declared)
  N1 outer.declared 通过/拦截/异常                   通过 1 / 拦截 0 / 异常 0
  N1 inner.declared 通过/拦截/异常                   通过 0 / 拦截 1 / 异常 0
  N2 下游没声明                                     返回 outer.fallback(UndeclaredThrowableException)
  N2 outer.undeclared 通过/拦截/异常                 通过 1 / 拦截 0 / 异常 1
  N2 inner.undeclared 通过/拦截/异常                 通过 0 / 拦截 1 / 异常 0
  • N1，下游声明了 throws BlockException。FlowException 原样穿过代理，被 outer 切面的 catch (BlockException ex) 接住，于是 outer 的 blockHandler 被调用了，尽管 outer 自己没有任何规则。统计上 outer 是“通过 1、拦截 0、异常 0”，一次成功的调用。看监控会以为 outer 从来没被限流，日志里却全是 outer 的限流处理。
  • N2，下游没声明。代理把 FlowException 包成 UndeclaredThrowableException，outer 的切面把它当成业务异常：记一次异常，进 fallback。下游的限流在上游变成了故障。outer 上要是配了异常数或异常比例的熔断规则，下游一限流，上游就跟着熔断。

处理办法：

  1. 每个资源配自己的 blockHandler，不让 BlockException 往上冒。只有这样，返回值和两边的统计才都是对的。
  2. 上游 handler 里先看清楚是谁被拦了。BlockException#getRule() 带着触发它的那条规则，N1 里 e.getRule().getResource() 是 inner.declared，不是 outer 自己。
  3. 在上游 fallback 里拆 UndeclaredThrowableException 只能改返回值：异常在调 fallback 之前已经记到 outer 上了。

代理的边界

实验五里 self.target 配了 count = 0：

  P1 同类里 this.target()                         返回 biz
  P1 self.target 节点是否存在                        false
  P2 通过代理调用 target()                           返回 blockHandler(FlowException)
  P2 self.target 节点是否存在                        true
  P3 fallback 方法自己也标了 @SentinelResource        返回 fallback
  P3 self.fallbackResource 节点是否存在              false
  • 同类里的 this.target() 不经过代理，切面根本没执行（P1）。没有 Entry，连资源节点都没有创建，ClusterBuilderSlot.getClusterNode("self.target") 返回 null。规则形同虚设，blockHandler 也不会被调用。这和 @Transactional 的同类调用失效是同一个原因，但更难察觉：事务失效时数据迟早会出问题，限流失效平时什么症状都没有，Sentinel 里压根没有这个资源。官方文档里“注解方式埋点不支持 private 方法”也是同一个原因，CGLIB 生成的子类覆盖不了 private 方法。
  • 通过代理调用就正常了（P2）。示例用 ObjectProvider<SelfCallService> 拿到容器里的代理对象。其他做法还有：把资源方法挪到另一个 bean（最清楚）；用 @Lazy 注入自己；AopContext.currentProxy()，需要 @EnableAspectJAutoProxy(exposeProxy = true)；或者改用 AspectJ 编译期、加载期织入，不走代理。示例只验证了 ObjectProvider 这一种。
  • handler 本身是用反射在原始对象（pjp.getTarget()）上调用的，同样不经过代理（P3）。fallback 上标的 @SentinelResource 没有生效，资源节点不存在。照同样的道理，标在 handler 上的 @Transactional、@Async、@Cacheable 也不会生效；示例只验证了 @SentinelResource，其余几个是同一机制的推论。

两个随调用顺序变化的缓存坑

ResourceMetadataRegistry 用两种键缓存解析结果：

private static String getKey(Class<?> clazz, String name) {
    return String.format("%s:%s", clazz.getCanonicalName(), name);
}

private static String getKey(Class<?> clazz, String name, Class<?>[] parameterTypes) {
    return String.format(
            "%s:%s;%s",
            clazz.getCanonicalName(),
            name,
            Arrays.stream(parameterTypes).map(Class::getCanonicalName).collect(Collectors.joining(","))
    );
}

defaultFallback 用的是第一种，键里只有类名和方法名；可解析时又要拿当前方法的返回类型做 isAssignableFrom 匹配。同一个类里返回类型不同的方法共用一个 defaultFallback 时，谁先失败，谁决定缓存里放什么。实验六里 ReportServiceA 和 ReportServiceB 的代码完全相同：类上配了 defaultFallback = "df"，df 返回 String，title() 返回 String，count() 返回 Integer；两个类的区别只是调用顺序：

  D1 A 先调 title()（返回 String）                   返回 defaultFallback
  D1 A 再调 count()（返回 Integer）                  抛出 ClassCastException
  D2 B 先调 count()（返回 Integer）                  抛出 IllegalStateException
  D2 B 再调 title()（返回 String）                   抛出 IllegalStateException
  D3 C 先调 title(id)（返回 String）                 返回 fallback
  D3 C 再调 count(id)（返回 Integer）                抛出 ClassCastException
  • D1：title() 先失败，解析出 String df(Throwable) 并缓存。count() 再失败时直接拿缓存里的方法调用，String 被当成 Integer 返回，代理里的强制转换抛出 ClassCastException。
  • D2：count() 先失败，按 Integer 找不到，缓存了“不存在”。之后 title() 失败，读到的也是“不存在”，原本能匹配的 defaultFallback 不再使用，异常原样抛出。

生产环境里哪个方法先失败没法预知，同一份代码重启一次，行为就可能不一样。

fallback 和 blockHandler 用第二种键，有参数类型（1.8.8 修过同名不同参的问题，#3395），但同样没有返回类型。D3 里 ReportServiceC 的两个方法参数相同、返回类型不同，共用一个返回 String 的 fallback，结果和 D1 一样。严格地说，D3 里 count 的 fallback 本来就配错了，只不过它不会表现为“找不到”，而是 ClassCastException。

结论：类级别的 defaultFallback 只用在所有方法返回同一种类型的类上，比如都返回统一的结果包装类。

启动时校验

既然 Sentinel 要等到出事时才解析，那就在启动时或测试里按同样的规则自己解析一遍。示例里的 HandlerValidator 照着 1.8.10 的 findMethod 写成：遍历容器里的每个 bean，用 AopUtils.getTargetClass 拿到代理背后的类，检查每个 @SentinelResource 方法的 blockHandler、fallback 和 defaultFallback。实验九的结果：

    ReportServiceC#count: fallback fb 不匹配，要求 Integer (String) 或 Integer (String, Throwable)

    SignatureService#fbToDefault: fallback fbToDefaultFallback 不匹配，要求 String (String) 或 String (String, Throwable)

  发现的问题数                                       11

前面实验里故意写错的 11 处全部找了出来，包括 D1 那种单独看能用、换个调用顺序就坏的情况。它对每个方法单独比较 defaultFallback 和这个方法的返回类型，不受调用顺序影响。

它的局限也要说清楚：

  • 它复制了 Sentinel 的匹配规则。升级 Sentinel 时要看一下 AbstractSentinelAspectSupport 有没有变。
  • 它查不出同类调用和嵌套资源的问题。那是调用方式的问题，不是声明的问题。
  • 示例里是在实验跑完之后才调用它。放进项目时，可以写成一个启动整个容器的测试，也可以在容器启动完成后执行、发现问题就让启动失败；这两种接法示例里都没有写。

另一个办法是做一次限流演练：在测试环境给每个资源推一条 count = 0 的规则，挨个调一遍。它能顺带发现同类调用（资源节点不出现），但要覆盖所有资源和所有异常分支，成本高得多。

package demo;

import com.alibaba.csp.sentinel.annotation.SentinelResource;
import com.alibaba.csp.sentinel.slots.block.BlockException;
import java.lang.reflect.Method;
import java.lang.reflect.Modifier;
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;
import java.util.stream.Collectors;

/**
 * 按 Sentinel 1.8.10 AbstractSentinelAspectSupport 的匹配规则，在启动时把每个
 * blockHandler / fallback / defaultFallback 解析一遍。Sentinel 自己要等到第一次
 * 被拦、第一次失败时才解析，找不到只在 sentinel-record.log 里写一行 WARN。
 */
public final class HandlerValidator {

    private HandlerValidator() {}

    public static List<String> validate(Class<?> type) {
        List<String> problems = new ArrayList<>();
        SentinelResource onClass = type.getAnnotation(SentinelResource.class);
        for (Method m : annotatedMethods(type)) {
            SentinelResource a = m.getAnnotation(SentinelResource.class);
            if (a == null) {
                continue;
            }
            String where = type.getSimpleName() + "#" + m.getName();
            Class<?>[] params = m.getParameterTypes();

            if (!a.blockHandler().isEmpty()) {
                boolean mustStatic = a.blockHandlerClass().length > 0;
                Class<?> location = mustStatic ? a.blockHandlerClass()[0] : type;
                if (find(location, a.blockHandler(), mustStatic, m.getReturnType(), append(params, BlockException.class)) == null) {
                    problems.add(where + ": blockHandler " + a.blockHandler() + " 不匹配，要求 "
                        + describe(mustStatic, m.getReturnType(), append(params, BlockException.class)));
                }
            }

            boolean fallbackFound = false;
            if (!a.fallback().isEmpty()) {
                boolean mustStatic = a.fallbackClass().length > 0;
                Class<?> location = mustStatic ? a.fallbackClass()[0] : type;
                fallbackFound = find(location, a.fallback(), mustStatic, m.getReturnType(), params) != null
                    || find(location, a.fallback(), mustStatic, m.getReturnType(), append(params, Throwable.class)) != null;
                if (!fallbackFound) {
                    problems.add(where + ": fallback " + a.fallback() + " 不匹配，要求 "
                        + describe(mustStatic, m.getReturnType(), params) + " 或 "
                        + describe(mustStatic, m.getReturnType(), append(params, Throwable.class)));
                }
            }

            // fallback 找不到时才会用 defaultFallback；方法上没写就看类上的
            String df = a.defaultFallback();
            Class<?>[] dfClass = a.fallbackClass();
            if (df.isEmpty() && onClass != null) {
                df = onClass.defaultFallback();
                if (dfClass.length == 0) {
                    dfClass = onClass.fallbackClass();
                }
            }
            if (!fallbackFound && !df.isEmpty()) {
                boolean mustStatic = dfClass.length > 0;
                Class<?> location = mustStatic ? dfClass[0] : type;
                if (find(location, df, mustStatic, m.getReturnType()) == null
                    && find(location, df, mustStatic, m.getReturnType(), Throwable.class) == null) {
                    problems.add(where + ": defaultFallback " + df + " 不匹配，要求 "
                        + describe(mustStatic, m.getReturnType()) + " 或 "
                        + describe(mustStatic, m.getReturnType(), Throwable.class));
                }
            }
        }
        problems.sort(null);
        return problems;
    }

    /** 切点按方法上的注解匹配，父类里声明的方法也会被拦，所以沿父类往上收集。 */
    private static List<Method> annotatedMethods(Class<?> type) {
        List<Method> out = new ArrayList<>();
        for (Class<?> c = type; c != null && c != Object.class; c = c.getSuperclass()) {
            for (Method m : c.getDeclaredMethods()) {
                if (m.isAnnotationPresent(SentinelResource.class)) {
                    out.add(m);
                }
            }
        }
        return out;
    }

    /** 和 Sentinel 的 findMethod 一样：当前类找不到就沿父类往上找，不看接口。 */
    private static Method find(Class<?> c, String name, boolean mustStatic, Class<?> returnType, Class<?>... params) {
        for (; c != null && c != Object.class; c = c.getSuperclass()) {
            for (Method m : c.getDeclaredMethods()) {
                if (m.getName().equals(name)
                    && (!mustStatic || Modifier.isStatic(m.getModifiers()))
                    && returnType.isAssignableFrom(m.getReturnType())
                    && Arrays.equals(params, m.getParameterTypes())) {
                    return m;
                }
            }
        }
        return null;
    }

    private static Class<?>[] append(Class<?>[] params, Class<?> last) {
        Class<?>[] out = Arrays.copyOf(params, params.length + 1);
        out[params.length] = last;
        return out;
    }

    private static String describe(boolean mustStatic, Class<?> ret, Class<?>... params) {
        return (mustStatic ? "static " : "") + ret.getSimpleName() + " ("
            + Arrays.stream(params).map(Class::getSimpleName).collect(Collectors.joining(", ")) + ")";
    }
}

import com.alibaba.csp.sentinel.slots.block.BlockException;
import org.springframework.core.annotation.Order;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.bind.annotation.RestControllerAdvice;

/**
 * 实验九：五个接口都调用 SignatureService#exParam（blockHandler 签名写错，
 * 调用方拿到 UndeclaredThrowableException，cause 是 FlowException），
 * 区别只在各自生效的 @ExceptionHandler。每个 advice 用 assignableTypes 限定到一个接口。
 */
abstract class BaseController {
    private final SignatureService sig;
    BaseController(SignatureService sig) { this.sig = sig; }
    String call() { return sig.exParam("42"); }
}

@RestController
class NoAdviceController extends BaseController {
    NoAdviceController(SignatureService sig) { super(sig); }
    @GetMapping("/mvc/none") String get() { return call(); }
}

@RestController
class BlockOnlyController extends BaseController {
    BlockOnlyController(SignatureService sig) { super(sig); }
    @GetMapping("/mvc/block-only") String get() { return call(); }
}

@RestController
class BlockAndGenericController extends BaseController {
    BlockAndGenericController(SignatureService sig) { super(sig); }
    @GetMapping("/mvc/block-and-generic") String get() { return call(); }
}

@RestController
class GenericFirstController extends BaseController {
    GenericFirstController(SignatureService sig) { super(sig); }
    @GetMapping("/mvc/generic-first") String get() { return call(); }
}

@RestController
class BlockFirstController extends BaseController {
    BlockFirstController(SignatureService sig) { super(sig); }
    @GetMapping("/mvc/block-first") String get() { return call(); }
}

final class Responses {
    private Responses() {}

    static ResponseEntity<String> block(BlockException e) {
        return ResponseEntity.status(429).body("BlockException 处理器(参数实际是 " + e.getClass().getSimpleName() + ")");
    }

    static ResponseEntity<String> generic(Exception e) {
        return ResponseEntity.status(500).body("Exception 处理器(参数实际是 " + e.getClass().getSimpleName() + ")");
    }
}

// M2：只有 BlockException 处理器
@RestControllerAdvice(assignableTypes = BlockOnlyController.class)
class BlockOnlyAdvice {
    @ExceptionHandler(BlockException.class)
    ResponseEntity<String> onBlock(BlockException e) { return Responses.block(e); }
}

// M3：同一个 advice 里同时有 BlockException 和 Exception 处理器
@RestControllerAdvice(assignableTypes = BlockAndGenericController.class)
class BlockAndGenericAdvice {
    @ExceptionHandler(BlockException.class)
    ResponseEntity<String> onBlock(BlockException e) { return Responses.block(e); }

    @ExceptionHandler(Exception.class)
    ResponseEntity<String> onAny(Exception e) { return Responses.generic(e); }
}

// M4：两个 advice，Exception 处理器所在的优先级更高
@Order(1)
@RestControllerAdvice(assignableTypes = GenericFirstController.class)
class GenericFirstGenericAdvice {
    @ExceptionHandler(Exception.class)
    ResponseEntity<String> onAny(Exception e) { return Responses.generic(e); }
}

@Order(2)
@RestControllerAdvice(assignableTypes = GenericFirstController.class)
class GenericFirstBlockAdvice {
    @ExceptionHandler(BlockException.class)
    ResponseEntity<String> onBlock(BlockException e) { return Responses.block(e); }
}

// M5：两个 advice，BlockException 处理器所在的优先级更高
@Order(1)
@RestControllerAdvice(assignableTypes = BlockFirstController.class)
class BlockFirstBlockAdvice {
    @ExceptionHandler(BlockException.class)
    ResponseEntity<String> onBlock(BlockException e) { return Responses.block(e); }
}

@Order(2)
@RestControllerAdvice(assignableTypes = BlockFirstController.class)
class BlockFirstGenericAdvice {
    @ExceptionHandler(Exception.class)
    ResponseEntity<String> onAny(Exception e) { return Responses.generic(e); }
}

小结

  • blockHandler、fallback、defaultFallback 都在第一次触发时按名字和参数表反射查找，参数逐个完全相同才算找到，找不到只在 sentinel-record.log 写一行 WARN，而这个文件里还混着正常配置留下的同样的 WARN。
  • blockHandler 的最后一个参数只能是 BlockException，fallback 额外的参数只能是 Throwable，基本类型和包装类型不通用，blockHandlerClass / fallbackClass 里只认 static。
  • 三级都找不到时 BlockException 原样抛出；它是受检异常，过代理就变成 UndeclaredThrowableException，Java 调用方的 catch (BlockException) 接不住。Spring MVC 的 @ExceptionHandler(BlockException.class) 能按 cause 匹配到它，但会输给同一个 advice 里的 Exception 处理器和优先级更高的 advice，而且 blockHandler 的降级逻辑照样没执行。
  • 默认连 Error 也进 fallback；fallback 兜住的异常照样计入熔断。“调用方的错”放进 exceptionsToIgnore，它按继承匹配，但不看 cause。
  • 切面的 catch (BlockException) 同时包住了业务方法：下游的限流会触发上游的 blockHandler，或者被上游记成异常。每个资源配自己的 handler。
  • 同类调用不经过代理，资源根本不存在；handler 也是在原始对象上反射调用的，标在它上面的注解都不生效。
  • defaultFallback 的缓存键里没有返回类型，返回类型不同的方法共用一个时，行为取决于谁先失败。
  • 签名问题可以在启动时按同样的规则提前检查出来。
