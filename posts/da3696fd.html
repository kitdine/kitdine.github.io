三台提供者，消费端接了 Sentinel 的 Dubbo 3 适配器，Dubbo 的重试保持默认。做两个小实验：

  • 给消费端的方法资源配 QPS 5 的限流，三台都在超时，10 个调用在 100 毫秒内依次发起。Sentinel 放行 5 个、拦下 5 个，提供者那边却一共执行了 15 次。
  • 只让其中一台每次超时，消费端配“异常比例超过 30% 就熔断”。顺序调 30 次，有 15 次请求打到坏的那台并且全部超时，Sentinel 记下的异常是 0，熔断器一次都没开。

换成慢调用比例熔断，结果又反过来：第 5 次调用熔断器就打开了，后面 25 次全被拒绝，另外两台好好的机器也一起没了流量。

三个结果都能稳定复现，代码在文末。原因是同一个：适配器的消费端 Filter 实现的是 ClusterFilter，挂在 failover 重试循环的外面。Sentinel 在消费端看到的是“一次调用”，不是“一次请求”。默认 retries=2，一次调用最多尝试三次，它只记一个 entry，而且只记最后的结局。

前一篇 Sentinel 文章 讲了一次 entry 怎么走完 Slot 链，Dubbo 的骨架那篇 讲了 ClusterFilter 和普通 Filter 分别在哪一层。这篇只看两者接上之后的一件事：统计的粒度变了，限流和熔断规则的含义也跟着变了。

本文对照的是 sentinel-apache-dubbo3-adapter 1.8.10 和 Dubbo 3.3.7，都是写作时 Maven Central 上的最新稳定版。

适配器挂在哪一层

适配器的 jar 里有两个 Dubbo 扩展配置文件：

# META-INF/dubbo/org.apache.dubbo.rpc.Filter
sentinel.dubbo.provider.filter=com.alibaba.csp.sentinel.adapter.dubbo3.SentinelDubboProviderFilter
dubbo.application.context.name.filter=com.alibaba.csp.sentinel.adapter.dubbo3.DubboAppContextFilter

# META-INF/dubbo/org.apache.dubbo.rpc.cluster.filter.ClusterFilter
sentinel.dubbo.consumer.filter=com.alibaba.csp.sentinel.adapter.dubbo3.SentinelDubboConsumerFilter

提供端的 SentinelDubboProviderFilter 是普通 Filter，消费端的 SentinelDubboConsumerFilter 是 ClusterFilter：

@Activate(group = CONSUMER)
public class SentinelDubboConsumerFilter extends BaseSentinelDubboFilter implements ClusterFilter {

Dubbo 3 在消费端组两条链。AbstractCluster#join 在集群 Invoker（默认 FailoverClusterInvoker）外面套一层 ClusterFilterInvoker，里面是所有 group=consumer 的 ClusterFilter；ProtocolFilterWrapper#refer 则给每一个提供者的 Invoker 套上普通 Filter 链。放在一起看（省略了 Mock、作用域选择等与本文无关的几层）：

业务代码调用代理
└─ ClusterFilterInvoker
   └─ SentinelDubboConsumerFilter        ← 消费端的 entry 在这里，一次调用一次
      └─ FailoverClusterInvoker          for i in 0..retries（默认 retries=2，共 3 次）
         └─ 选中的那台提供者的 Filter 链    ← 普通消费端 Filter，每次尝试一次
            └─ DubboInvoker ── 网络 ── 提供端 Filter 链
                                        └─ SentinelDubboProviderFilter ← 每次尝试在提供端一次

所以同一次调用，在三个位置会被数出三种结果：消费端适配器数调用，普通消费端 Filter 数尝试，提供端适配器数到达提供端的请求。

这不是某个版本的偶然。Maven Central 上 sentinel-apache-dubbo3-adapter 的每个版本，从最早的 1.8.5 到 1.8.10，消费端都注册在 ClusterFilter 里。给 Dubbo 2.7 用的 sentinel-apache-dubbo-adapter 则只有一个 org.apache.dubbo.rpc.Filter 文件，消费端 Filter 是普通 Filter，按尝试计数。从 2.7 适配器迁到 3 适配器，规则一条没改，含义已经变了。

一次调用，各层各记几笔

先看最直接的情况：三台都超时（提供者睡 300ms，消费端超时 200ms），调用一次。示例在消费端另加了一个按机器计数的普通 Filter（后文会讲），三个位置的计数是这样的：

== 1. 三台都超时，调用一次 ==
  调用方: 697 ms 后 失败 Tried 3 times of the providers [127.0.0.1:43341, 127.0.0.1:45191, 127.0.0.1:45635] (3/3)
  消费端适配器资源: 通过 1, 异常 1, 平均 RT 637 ms
  尝试级资源(按机器, 3 台合计): 通过 3, 异常 3
  提供端适配器资源(3 台在同一进程, 合计): 通过 3
  提供者实际执行: A=1 B=1 C=1

消费端适配器的逻辑很直白，同步调用时：

interfaceEntry = SphU.entry(interfaceResourceName, ResourceTypeConstants.COMMON_RPC, EntryType.OUT);
methodEntry = SphU.entry(methodResourceName, ResourceTypeConstants.COMMON_RPC, EntryType.OUT,
    invocation.getArguments());
Result result = invoker.invoke(invocation);   // 这里面是整个 failover 循环
if (result.hasException()) {
    Tracer.traceEntry(result.getException(), interfaceEntry);
    Tracer.traceEntry(result.getException(), methodEntry);
}
return result;
// catch (RpcException e) 里同样 traceEntry 后再抛；finally 里两个 entry 依次 exit

invoker.invoke 包住了整个重试循环，所以：

  • 通过数是 1。 不管里面尝试了几次。
  • 异常数是 0 或 1，只看结局。 三次都失败，FailoverClusterInvoker 最后抛出一个 RpcException，记一次异常；前两次失败、第三次成功，Sentinel 看到的是一次成功。
  • RT 是全程。 637ms 是三次各约 200ms 的超时，加上重新选址和发请求的开销；单次尝试的 RT 只有 200ms 出头。

什么时候会重试，要看 FailoverClusterInvoker 拿到的是什么：

  • 正常返回的 Result：不重试，直接交回去。提供者方法里抛出的业务异常随响应带回来，就装在这个 Result 里。
  • 抛出的业务 RpcException：不重试，直接往外抛。
  • 抛出的其他 RpcException（超时、连接失败等）以及其他 Throwable：重试，后者先包成 RpcException。

所以“尝试几次”只在第三种情况下和“调用几次”分家，而超时恰恰是生产上最常见的那一种。

“有没有重试”和“谁记异常”是两件事。再看一次业务异常的调用，提供者每次都抛 IllegalStateException：

== 2. 提供者抛业务异常，调用一次 ==
  调用方: 失败 IllegalStateException
  提供者实际执行: 1 次
  消费端适配器资源: 通过 1, 异常 1
  尝试级资源(按机器, 3 台合计): 通过 1, 异常 0
  提供端适配器资源: 通过 1, 异常 1

没有重试，三处都只数到 1 次。但异常计数不同：官方适配器在两端都会把 Result 里的业务异常 trace 到 entry 上，所以记 1；示例里按尝试计数的 Filter 是有意不记业务异常的（理由后文讲），所以记 0。拿两层的异常数做对比时，得先知道各自记的是什么。

每种规则因此变成了什么意思

QPS 限流：限住的是调用，不是尝试

开头的第一个实验，消费端方法资源配 QPS 5，三台都超时，10 个调用在 100 毫秒内依次发起：

== 3. 消费端限流 QPS=5，三台都超时，10 个调用在 100ms 内依次发起 ==
  消费端适配器资源: 通过 5, 被限流 5
  尝试级资源(3 台合计): 15 次尝试; 提供者实际执行: 15 次
  尝试次数 = 通过数 x 3 ? true

被放行的 5 个调用各重试了两次，一共 15 次尝试，在这个本机实验里每次都送达了提供者。消费端 QPS 规则数的是调用：这一批被放行的 M 个调用，最多会产生 M × (retries + 1) 次尝试。

示例里 10 个调用的发起时刻错开了 10 毫秒，这是有意的。Sentinel 默认的 QPS 检查（DefaultController）先读窗口里已通过的数量，判断通过后由 StatisticSlot 再加一，读和加不是原子的预留。真正同时进来的调用可能一起读到“还没满”，放行数就会超过 5。错开之后检查基本是串行的，放行数才稳定；示例同时打印了“尝试次数 = 通过数 × 3”：三台都超时的前提下，放行数变了，这个关系也照样成立。

这个 M × 3 只是一批调用的上限，不是下游每秒请求数的上限：

  • 重试会落到后面的时间窗里，而那时消费端的 QPS 额度已经按新窗口重新算了；
  • 每个消费者实例各有一份本地额度，十个实例就是十份；
  • 再加上前面说的并发检查不原子。

放大发生的时机也不对。下游健康时几乎不重试，调用数约等于尝试数；下游开始超时，每个调用都变成三次尝试。限流本该在下游最脆弱的时候兜住它，这时它放进去的请求反而最多。

把阈值除以 3 能把单批最坏的放大压回原来的量级，算是一种保守的做法，代价是正常时只用了三分之一的额度。但它解决不了上面列的跨窗口和多实例问题。真要约束下游收到多少请求，得在提供端限流，或者用明确的全局预算（比如 Sentinel 的集群流控），而不是靠某个客户端上的一条本地规则。

被限流的调用倒是不会触发重试。适配器在重试循环外面，BlockException 由 fallback 处理，默认的 DefaultDubboFallback 把它包进 Result 返回，根本走不到 failover。这是挂在外层的好处之一。

并发线程数限流：外层恰好是对的

线程数在 entry 时加一、exit 时减一，统计的是“有多少个调用方线程正卡在这次调用里”。重试期间线程一直被占着，外层的 entry 正好覆盖了全程。如果目的是保护调用方自己的线程池不被一个慢下游拖垮，这条规则放在适配器的资源上是合适的。

异常比例熔断：一台坏了，看不见

第二个实验，A 每次超时，B、C 正常，负载均衡用轮询：

== 4. 只有 A 超时，消费端异常比例熔断(>30%)，顺序调用 30 次 ==
  调用方: 30 次中失败 0 次; 耗时超过 150ms 的: 前 10 次 5 次, 后 20 次 10 次
  消费端适配器资源: 通过 30, 异常 0, 被熔断 0
  打到 A 的尝试: 15 次, 全部超时 15 次

一半的调用先打到 A，等满 200ms 超时，再换到 B 或 C 成功。调用方没有看到失败，Sentinel 也就一笔异常都没记。只要这些调用一直能被重试救回来，也没有别的会计入异常的情况（比如业务异常、三台同时失败），这条熔断规则就不会打开。代价全落在耗时上：每隔一次调用就多等 200ms，而且这会一直持续下去。（轮询加上 failover 重选，A 恰好每隔一次被选中一次；换成默认的随机负载均衡，比例会在三分之一上下浮动。）

反过来，三台都坏的时候，三次超时只记一次异常。熔断器的 minRequestAmount 数的是调用，攒够 5 次调用，背后是 15 次超时的尝试。

慢调用比例熔断：一台坏了，整个接口一起停

同样只有 A 超时，把规则换成“RT 超过 100ms 的调用占比超过 20% 就熔断”：

== 5. 只有 A 超时，消费端慢调用比例熔断(RT>100ms 占 >20%)，顺序调用 30 次 ==
    [熔断器] 第 5 次调用时 消费端适配器资源: CLOSED -> OPEN
  调用方: 30 次中失败 25 次; 耗时超过 150ms 的: 前 10 次 3 次, 后 20 次 0 次
  消费端适配器资源: 通过 5, 被熔断 25
  这 30 次里 A/B/C 各被调用: 3/3/2

打到 A 的调用全程 RT 都超过 200ms，被算成慢调用；前 5 次里有 3 次慢，比例 60%，凑够最小请求数立刻熔断。熔断的对象是整个方法资源，它不认识机器，于是 B、C 的流量也被一并切断。30 次调用失败 25 次，比不熔断还糟：不熔断的话这 30 次都能成功，只是一半慢一些。

两种熔断一个看不见、一个反应过度，根子是同一个：资源的粒度是“所有机器上的这个方法”，故障的粒度却是“某一台机器”，中间还隔着一层会把单次失败吞掉、把耗时累加起来的重试。

怎么应对

想让消费端规则数的就是尝试：关掉这些方法的重试

给这些方法设 retries=0，或者把 cluster 设成 failfast，一次调用就至多一次传输尝试，适配器数到的调用数就是尝试数的上限。这仍然不等于提供端收到的请求数：连接失败、请求没写出去时，提供端可能根本没收到。写接口本来就该这么配（Dubbo 那篇 讲过默认重试对写接口的风险）。

代价是失去了 failover 对偶发错误的兜底：一次网络抖动就直接报给调用方。读接口要不要这么做，看你更在意放大还是单次成功率。

想按机器判断健康：自己加一层按尝试计数的 Filter

另一条路是在重试循环里面再接一次 Sentinel。普通的消费端 Filter 套在每台提供者的 Invoker 外，每次尝试都会经过，资源名里带上提供者地址，就成了“一台机器一个资源”：

@Activate(group = CommonConstants.CONSUMER)
public class AttemptSentinelFilter implements Filter {
    @Override
    public Result invoke(Invoker<?> invoker, Invocation invocation) throws RpcException {
        if (RpcUtils.getInvokeMode(invoker.getUrl(), invocation) != InvokeMode.SYNC) {
            return invoker.invoke(invocation);       // 示例只处理同步调用
        }
        Entry entry;
        try {
            entry = SphU.entry("attempt:" + invoker.getUrl().getAddress() + ":"
                    + invoker.getInterface().getName() + ":" + invocation.getMethodName(),
                    ResourceTypeConstants.COMMON_RPC, EntryType.OUT);
        } catch (BlockException e) {
            throw new RpcException(RpcException.LIMIT_EXCEEDED_EXCEPTION, "blocked by sentinel", e);
        }
        try {
            return invoker.invoke(invocation);        // 正常返回的 Result 不记，哪怕装着业务异常
        } catch (RpcException e) {
            if (!e.isBiz()) {
                Tracer.traceEntry(e, entry);
            }
            throw e;
        } catch (RuntimeException | Error e) {
            Tracer.traceEntry(e, entry);
            throw e;
        } finally {
            entry.exit();
        }
    }
}

（完整版在文末，这里省掉了注释。）给每台机器的资源各配一条“异常比例超过 50%、最少 3 次”的熔断规则，还是只有 A 坏：

== 6. 只有 A 超时，按机器熔断(异常比例>50%)，顺序调用 30 次 ==
    [熔断器] 第 5 次调用时 机器 A 的资源: CLOSED -> OPEN
  调用方: 30 次中失败 0 次; 耗时超过 150ms 的: 前 10 次 3 次, 后 20 次 0 次
  打到 A 的尝试: 放行 3 次(全部超时 3 次), 在 A 上被熔断 12 次
  这 30 次里 A/B/C 各执行: 3/15/15

A 吃了 3 次超时之后熔断，之后轮询再选中 A，尝试在 entry 处就被拒绝，failover 立刻换到下一台，不用再等 200ms。调用方 30 次全部成功，后 20 次没有一次慢的；B、C 照常接流量。

这个 Filter 有三处是刻意这么写的：

  1. 被拒绝时抛非业务的 RpcException。 failover 会对它重试，于是“这台被熔断”会被当成“这台失败”，马上换下一台。如果学适配器返回一个带异常的 Result，failover 会把它当成正常返回的业务结果，原样交给调用方，换台就不会发生。
  2. 只记会让 failover 换台的失败。 抛出的非业务 RpcException 和其他运行时异常记为这台机器失败，正好对应 failover 会重试的那两种情况。正常返回的 Result 不记，哪怕里面装着业务异常；抛出的业务 RpcException 也不记。业务异常说明请求到了提供者、提供者也正常处理了，这台机器是健康的。把它记成机器的失败，会因为某个参数总是校验不过而熔断掉一台好机器。这一点和官方适配器不同，上面的业务异常对照里两层异常数一个是 1、一个是 0，就是这个原因。
  3. 只处理同步调用。 异步调用时 invoker.invoke 返回的 Result 还没完成，在 finally 里 exit 量不到真实结果。要支持异步，得像官方适配器那样改用 SphU.asyncEntry，在 whenCompleteWithContext 回调里记异常和 exit。

这条路的代价也要算清楚：

  • 资源数量是“机器数 × 方法数”。 Sentinel 对资源数有硬上限 6000（Constants.MAX_SLOT_CHAIN_SIZE）。CtSph#lookProcessChain 发现超限时返回 null，之后新资源的 entry 直接放行，不做任何规则检查，也不报错。按机器拆资源，很容易在不知不觉中碰到这条线。
  • 机器下线后资源不会消失。 容器环境里 IP 经常变，旧地址的资源和统计节点会一直留在内存里，同样占着上面那 6000 个名额。
  • 规则要按资源名配。 机器是动态的，规则没法提前写死。一种做法是监听实例列表的变化去生成和删除规则；另一种是 1.8.10 里的 DefaultCircuitBreakerRuleManager：加载一条资源名为 * 的熔断规则，它会作用于所有没有单独配置熔断规则的资源，但“所有”包括应用里其他的 Web、RPC 资源，不想覆盖的要用 addExcludedResource 一个个排除。
  • 半开探测要付一次超时。 熔断时长到了以后，下一次选中 A 的尝试会被放过去探测；A 还没好，就再等一次超时，然后重新熔断。按机器熔断的成本是每个熔断周期一次超时，而不是每次调用一次。
  • 被拒绝的尝试占用重试次数。 retries=2 时一次调用最多三次尝试，被熔断的机器每被选中一次就用掉一次。按 failover 的逻辑，三台都熔断时，调用会在三次立即拒绝后快速失败。

两层并用，各管各的

两层的计数含义不同，规则也就该分开放：

想保护的东西 放在哪一层 合适的规则
调用方自己的线程池 适配器的资源（按调用） 并发线程数
调用方对上游承诺的耗时 适配器的资源（按调用） 慢调用比例，接受它会整体熔断
下游的总容量 提供端，或明确的全局预算 提供端 QPS 限流、集群流控；消费端单条规则保证不了
某一台机器坏了 按尝试计数、按机器拆分的资源 异常比例或异常数熔断

消费端适配器上的 QPS 规则仍然有用，它限制的是“这个实例每秒发起多少次调用”，只是不要把它当成下游容量的保证。

适配器挂在外层并没有错：它让资源和业务代码里的一次方法调用一一对应，被拒绝的调用不会消耗重试，线程数统计覆盖全程，每次调用也只付两个 entry 的开销。源码里没有注释说明当初为什么这样选，但只要知道它数的是调用，规则就能配对。容易出问题的是把它当成“下游收到了多少请求”或“哪台机器坏了”来用。

完整示例

一个 Maven 工程，四个 Java 文件、一个扩展配置文件。在 JDK 21、Maven 3.9 上跑过，maven.compiler.release 设为 17，JDK 17 及以上都可以。不需要注册中心：同一个服务在三个端口上暴露，当作三台提供者，消费端直连 127.0.0.1 上的这三个端口。

注意监听地址。 消费端连的是回环地址，不代表提供端只监听回环。Dubbo 3.3.7 把 127. 开头的地址当作无效的绑定地址（NetUtils#isInvalidLocalHost），AbstractServer 拿到的绑定地址只要是 127. 开头就改绑 0.0.0.0；用 DUBBO_IP_TO_BIND 指定 127.0.0.1 则会在启动时直接报错。示例运行期间，三个端口在本机所有网卡上都能连。第 0 步会用本机的非回环地址去连这三个端口，把实际情况打印出来。请只在隔离的网络里跑这个示例，比如没有对外网卡的容器或虚拟机，或者入站连接被防火墙挡住的机器。

GreeterImpl.java。Dubbo 3 要求同一组 group、接口、版本只能有一个 ServiceConfig（否则启动时报 “Found multiple ServiceConfigs with unique service name”），所以这里只有一个实现、暴露在三个端口上，按收到请求的本地端口区分是哪台“机器”：

package demo;

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;

import org.apache.dubbo.rpc.RpcContext;

// 同一个实现暴露在三个端口上，每个端口当作一台机器。
// Dubbo 不允许同一接口有两个 ServiceConfig，所以按收到请求的本地端口区分"哪台"。
public class GreeterImpl implements Greeter {
    static final class Machine {
        final String name;
        volatile int delayMs; // 超过消费端超时（200ms），这台就是"坏的"
        final AtomicInteger executed = new AtomicInteger();

        Machine(String name) {
            this.name = name;
        }
    }

    static final Map<Integer, Machine> MACHINES = new ConcurrentHashMap<>();

    @Override public String step1(String s) { return work(s); }
    @Override public String step2(String s) {
        work(s);
        throw new IllegalStateException("业务校验不通过"); // 随响应带回消费端的业务异常
    }
    @Override public String step3(String s) { return work(s); }
    @Override public String step4(String s) { return work(s); }
    @Override public String step5(String s) { return work(s); }
    @Override public String step6(String s) { return work(s); }

    private String work(String s) {
        Machine m = MACHINES.get(RpcContext.getServiceContext().getLocalPort());
        m.executed.incrementAndGet();
        if (m.delayMs > 0) {
            try {
                Thread.sleep(m.delayMs);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }
        return m.name + ":" + s;
    }
}

AttemptSentinelFilter.java，正文里那个 Filter 的完整版：

package demo;

import org.apache.dubbo.common.constants.CommonConstants;
import org.apache.dubbo.common.extension.Activate;
import org.apache.dubbo.rpc.Filter;
import org.apache.dubbo.rpc.InvokeMode;
import org.apache.dubbo.rpc.Invocation;
import org.apache.dubbo.rpc.Invoker;
import org.apache.dubbo.rpc.Result;
import org.apache.dubbo.rpc.RpcException;
import org.apache.dubbo.rpc.support.RpcUtils;

import com.alibaba.csp.sentinel.Entry;
import com.alibaba.csp.sentinel.EntryType;
import com.alibaba.csp.sentinel.ResourceTypeConstants;
import com.alibaba.csp.sentinel.SphU;
import com.alibaba.csp.sentinel.Tracer;
import com.alibaba.csp.sentinel.slots.block.BlockException;

// 普通 Filter：ProtocolFilterWrapper 把它套在每个提供者的 Invoker 外面，
// 位于 failover 的重试循环之内，所以每次尝试都会走一遍。
// 资源名带上提供者地址，一台机器一个资源，统计和熔断都按机器算。
@Activate(group = CommonConstants.CONSUMER)
public class AttemptSentinelFilter implements Filter {
    static String resourceName(String address, String service, String method) {
        return "attempt:" + address + ":" + service + ":" + method;
    }

    @Override
    public Result invoke(Invoker<?> invoker, Invocation invocation) throws RpcException {
        // 只处理同步调用。异步调用在这里拿到的 Result 还没完成，
        // 要像官方适配器那样用 SphU.asyncEntry，并在 whenCompleteWithContext 里 exit。
        if (RpcUtils.getInvokeMode(invoker.getUrl(), invocation) != InvokeMode.SYNC) {
            return invoker.invoke(invocation);
        }
        Entry entry;
        try {
            entry = SphU.entry(resourceName(invoker.getUrl().getAddress(), invoker.getInterface().getName(),
                    invocation.getMethodName()),
                    ResourceTypeConstants.COMMON_RPC, EntryType.OUT);
        } catch (BlockException e) {
            // 抛非业务的 RpcException：failover 会把它当成这台机器失败，换下一台重试，
            // 而且不用等超时。返回带异常的 Result 则会被当成业务结果直接交给调用方。
            throw new RpcException(RpcException.LIMIT_EXCEEDED_EXCEPTION,
                    "blocked by sentinel: " + invoker.getUrl().getAddress(), e);
        }
        try {
            // 正常返回的 Result 不记，哪怕里面装着业务异常：请求到了提供者、也被正常处理了，
            // 说明这台机器是好的。官方适配器会把 Result 里的业务异常记下来，这里刻意不同。
            return invoker.invoke(invocation);
        } catch (RpcException e) {
            // 抛出的非业务 RpcException（超时、连接失败等）记为这台机器失败。
            // 抛出的业务 RpcException 不记，failover 也不会对它重试。
            if (!e.isBiz()) {
                Tracer.traceEntry(e, entry);
            }
            throw e;
        } catch (RuntimeException | Error e) {
            // 其他抛出的异常，failover 会包成 RpcException 再重试，这里同样记为这台失败。
            Tracer.traceEntry(e, entry);
            throw e;
        } finally {
            entry.exit();
        }
    }
}

import org.apache.dubbo.config.ApplicationConfig;

import com.alibaba.csp.sentinel.node.ClusterNode;

import com.alibaba.csp.sentinel.slots.block.degrade.DegradeRule;

import com.alibaba.csp.sentinel.slots.clusterbuilder.ClusterBuilderSlot;

public class Main {
    static final int TIMEOUT_MS = 200;
    static final int BAD_DELAY_MS = 300; // 比超时长，这台提供者每次都会超时

    static final List<GreeterImpl.Machine> machines = new ArrayList<>();
    static final List<String> addresses = new ArrayList<>();
    static volatile int callNo; // 熔断器状态变化时，打印当时是第几次调用

    public static void main(String[] args) throws Exception {
        System.setProperty("dubbo.application.logger", "slf4j");          // Dubbo 日志交给 slf4j-nop
        System.setProperty("csp.sentinel.dubbo.resource.use.prefix", "true"); // 两端资源名加前缀，免得同进程里混在一起
        System.setProperty("project.name", "retry-demo");

        // 三个"提供者" A、B、C：一个服务暴露在三个端口上
        DubboBootstrap bootstrap = DubboBootstrap.getInstance();
        ApplicationConfig app = new ApplicationConfig("retry-demo");
        app.setQosEnable(false);
        bootstrap.application(app).registry(new RegistryConfig(RegistryConfig.NO_AVAILABLE));
        ServiceConfig<Greeter> service = new ServiceConfig<>();
        service.setInterface(Greeter.class);
        service.setRef(new GreeterImpl());
        List<ProtocolConfig> protocols = new ArrayList<>();
        StringBuilder urls = new StringBuilder();
        for (String name : List.of("A", "B", "C")) {
            int port = freePort();
            ProtocolConfig protocol = new ProtocolConfig("dubbo", port);
            protocol.setId("dubbo-" + name);
            protocols.add(protocol);
            GreeterImpl.Machine m = new GreeterImpl.Machine(name);
            GreeterImpl.MACHINES.put(port, m);
            machines.add(m);
            addresses.add("127.0.0.1:" + port);
            urls.append(urls.length() == 0 ? "" : ";").append("dubbo://127.0.0.1:").append(port);
        }
        service.setProtocols(protocols);
        bootstrap.protocols(protocols).service(service);

        // 消费端直连三台：默认 failover、retries=2，一次调用最多尝试 3 次
        ReferenceConfig<Greeter> reference = new ReferenceConfig<>();
        reference.setInterface(Greeter.class);
        reference.setUrl(urls.toString());
        reference.setTimeout(TIMEOUT_MS);
        reference.setLoadbalance("roundrobin"); // 轮询，结果比随机稳定，便于对照
        bootstrap.reference(reference).start();
        Greeter greeter = reference.get();

        EventObserverRegistry.getInstance().addStateChangeObserver("print", (prev, next, rule, snapshot) ->
                System.out.printf("    [熔断器] 第 %d 次调用时 %s: %s -> %s%n",
                        callNo, shortName(rule.getResource()), prev, next));

        reportListening();
        step1(greeter);
        step2(greeter);
        step3(greeter);
        step4(greeter);
        step5(greeter);
        step6(greeter);
        bootstrap.stop();
    }

    // 0. 提供者实际监听在哪。消费端写的是 127.0.0.1，但 Dubbo 3.3.7 把 127.x 当作无效的绑定地址，
    //    服务端改绑 0.0.0.0。这里用本机的非回环地址去连三个端口，确认它们对外是否可连。
    static void reportListening() {
        String other = null;
        try {
            for (NetworkInterface nif : Collections.list(NetworkInterface.getNetworkInterfaces())) {
                if (!nif.isUp() || nif.isLoopback()) {
                    continue;
                }
                for (InetAddress addr : Collections.list(nif.getInetAddresses())) {
                    if (addr instanceof Inet4Address) {
                        other = addr.getHostAddress();
                        break;
                    }
                }
                if (other != null) {
                    break;
                }
            }
        } catch (Exception ignored) {
            // 取不到网卡信息就当没有非回环地址
        }
        if (other == null) {
            System.out.println("== 0. 本机没有非回环 IPv4 地址，跳过监听检查 ==\n");
            return;
        }
        int reachable = 0;
        for (String address : addresses) {
            int port = Integer.parseInt(address.substring(address.indexOf(':') + 1));
            try (Socket socket = new Socket()) {
                socket.connect(new InetSocketAddress(other, port), 500);
                reachable++;
            } catch (Exception ignored) {
                // 连不上说明这个端口没有对这块网卡开放
            }
        }
        System.out.printf("== 0. 用本机的非回环地址连三个提供者端口: %d/3 能连上 ==%n%n", reachable);
    }

    // 1. 三台都超时：一次调用，各层各记了几笔
    static void step1(Greeter greeter) throws Exception {
        System.out.println("== 1. 三台都超时，调用一次 ==");
        setDelays(BAD_DELAY_MS, BAD_DELAY_MS, BAD_DELAY_MS);
        long t0 = System.nanoTime();
        String outcome = call(greeter::step1, "x");
        long ms = (System.nanoTime() - t0) / 1_000_000;
        ClusterNode consumer = consumerNode("step1");
        double rt = consumer.avgRt(); // avgRt 是秒级窗口，调用一结束就读
        Thread.sleep(BAD_DELAY_MS + 200); // 等提供者把睡眠跑完，提供端的 exit 才记上
        System.out.printf("  调用方: %d ms 后 %s%n", ms, outcome);
        System.out.printf("  消费端适配器资源: 通过 %d, 异常 %d, 平均 RT %.0f ms%n",
                consumer.totalPass(), consumer.totalException(), rt);
        long[] attempt = attemptTotals("step1");
        long attempts = attempt[0], attemptErrors = attempt[1];
        System.out.printf("  尝试级资源(按机器, 3 台合计): 通过 %d, 异常 %d%n", attempts, attemptErrors);
        ClusterNode provider = ClusterBuilderSlot.getClusterNode("dubbo:provider:demo.Greeter:step1(java.lang.String)");
        System.out.printf("  提供端适配器资源(3 台在同一进程, 合计): 通过 %d%n", provider.totalPass());
        System.out.printf("  提供者实际执行: %s%n", executed());
    }

    // 2. 业务异常：failover 不重试，两层各记多少
    static void step2(Greeter greeter) throws Exception {
        System.out.println("\n== 2. 提供者抛业务异常，调用一次 ==");
        setDelays(0, 0, 0);
        int before = totalExecuted();
        String outcome = call(greeter::step2, "x");
        Thread.sleep(100);
        ClusterNode consumer = consumerNode("step2");
        long[] attempt = attemptTotals("step2");
        long attempts = attempt[0], attemptErrors = attempt[1];
        ClusterNode provider = ClusterBuilderSlot.getClusterNode("dubbo:provider:demo.Greeter:step2(java.lang.String)");
        System.out.printf("  调用方: %s%n", outcome);
        System.out.printf("  提供者实际执行: %d 次%n", totalExecuted() - before);
        System.out.printf("  消费端适配器资源: 通过 %d, 异常 %d%n", consumer.totalPass(), consumer.totalException());
        System.out.printf("  尝试级资源(按机器, 3 台合计): 通过 %d, 异常 %d%n", attempts, attemptErrors);
        System.out.printf("  提供端适配器资源: 通过 %d, 异常 %d%n", provider.totalPass(), provider.totalException());
    }

    // 3. 消费端限流 QPS=5，三台都超时，10 个调用在 100ms 内依次发起
    static void step3(Greeter greeter) throws Exception {
        System.out.println("\n== 3. 消费端限流 QPS=5，三台都超时，10 个调用在 100ms 内依次发起 ==");
        setDelays(BAD_DELAY_MS, BAD_DELAY_MS, BAD_DELAY_MS);
        FlowRule rule = new FlowRule(consumerResource("step3"));
        rule.setGrade(RuleConstant.FLOW_GRADE_QPS);
        rule.setCount(5);
        FlowRuleManager.loadRules(List.of(rule));
        int before = totalExecuted();

        // 每个调用占着一个线程等超时，所以要多线程；但发起时刻错开 10ms。
        // Sentinel 的 QPS 检查是"先读当前计数、通过后再加一"，不是原子预留，
        // 真正同时进来的调用可能一起通过，放行数会超过 5。错开后检查基本是串行的。
        ExecutorService pool = Executors.newFixedThreadPool(10);
        CountDownLatch done = new CountDownLatch(10);
        for (int i = 0; i < 10; i++) {
            pool.execute(() -> {
                try {
                    call(greeter::step3, "x");
                } finally {
                    done.countDown();
                }
            });
            Thread.sleep(10);
        }
        done.await();
        pool.shutdown();
        Thread.sleep(BAD_DELAY_MS + 200);

        ClusterNode consumer = consumerNode("step3");
        long passed = consumer.totalPass();
        long attempts = attemptTotals("step3")[0];
        int executed = totalExecuted() - before;
        System.out.printf("  消费端适配器资源: 通过 %d, 被限流 %d%n", passed, consumer.blockRequest());
        System.out.printf("  尝试级资源(3 台合计): %d 次尝试; 提供者实际执行: %d 次%n", attempts, executed);
        System.out.printf("  尝试次数 = 通过数 x 3 ? %s%n", attempts == passed * 3);
    }

    // 4. 只有 A 坏，消费端配异常比例熔断
    static void step4(Greeter greeter) throws Exception {
        System.out.println("\n== 4. 只有 A 超时，消费端异常比例熔断(>30%)，顺序调用 30 次 ==");
        setDelays(BAD_DELAY_MS, 0, 0);
        DegradeRule rule = new DegradeRule(consumerResource("step4"));
        rule.setGrade(RuleConstant.DEGRADE_GRADE_EXCEPTION_RATIO);
        rule.setCount(0.3);
        rule.setMinRequestAmount(5);
        rule.setStatIntervalMs(10_000);
        rule.setTimeWindow(10);
        DegradeRuleManager.loadRules(List.of(rule));
        waitForFreshWindow(10_000);
        runSequential(greeter::step4, 30);
        ClusterNode consumer = consumerNode("step4");
        ClusterNode a = attemptNode(addresses.get(0), "step4");
        System.out.printf("  消费端适配器资源: 通过 %d, 异常 %d, 被熔断 %d%n",
                consumer.totalPass(), consumer.totalException(), consumer.blockRequest());
        System.out.printf("  打到 A 的尝试: %d 次, 全部超时 %d 次%n", a.totalPass(), a.totalException());
    }

    // 5. 只有 A 坏，消费端配慢调用比例熔断
    static void step5(Greeter greeter) throws Exception {
        System.out.println("\n== 5. 只有 A 超时，消费端慢调用比例熔断(RT>100ms 占 >20%)，顺序调用 30 次 ==");
        setDelays(BAD_DELAY_MS, 0, 0);
        DegradeRule rule = new DegradeRule(consumerResource("step5"));
        rule.setGrade(RuleConstant.DEGRADE_GRADE_RT);
        rule.setCount(100);                 // 超过 100ms 算慢调用
        rule.setSlowRatioThreshold(0.2);
        rule.setMinRequestAmount(5);
        rule.setStatIntervalMs(10_000);
        rule.setTimeWindow(10);
        DegradeRuleManager.loadRules(List.of(rule));
        int[] before = executedArray();
        waitForFreshWindow(10_000);
        runSequential(greeter::step5, 30);
        int[] after = executedArray();
        ClusterNode consumer = consumerNode("step5");
        System.out.printf("  消费端适配器资源: 通过 %d, 被熔断 %d%n", consumer.totalPass(), consumer.blockRequest());
        System.out.printf("  这 30 次里 A/B/C 各被调用: %d/%d/%d%n",
                after[0] - before[0], after[1] - before[1], after[2] - before[2]);
    }

    // 6. 只有 A 坏，熔断规则配在"每台机器一个资源"上
    static void step6(Greeter greeter) throws Exception {
        System.out.println("\n== 6. 只有 A 超时，按机器熔断(异常比例>50%)，顺序调用 30 次 ==");
        setDelays(BAD_DELAY_MS, 0, 0);
        List<DegradeRule> rules = new ArrayList<>();
        for (String address : addresses) {
            DegradeRule rule = new DegradeRule(attemptResource(address, "step6"));
            rule.setGrade(RuleConstant.DEGRADE_GRADE_EXCEPTION_RATIO);
            rule.setCount(0.5);
            rule.setMinRequestAmount(3);
            rule.setStatIntervalMs(10_000);
            rule.setTimeWindow(10);
            rules.add(rule);
        }
        DegradeRuleManager.loadRules(rules);
        int[] before = executedArray();
        waitForFreshWindow(10_000);
        runSequential(greeter::step6, 30);
        int[] after = executedArray();
        ClusterNode a = attemptNode(addresses.get(0), "step6");
        System.out.printf("  打到 A 的尝试: 放行 %d 次(全部超时 %d 次), 在 A 上被熔断 %d 次%n",
                a.totalPass(), a.totalException(), a.blockRequest());
        System.out.printf("  这 30 次里 A/B/C 各执行: %d/%d/%d%n",
                after[0] - before[0], after[1] - before[1], after[2] - before[2]);
    }

    // 熔断器的统计是一个长 statIntervalMs 的单桶窗口，桶的起点对齐到这个长度的整数倍。
    // 实验中途跨过边界，计数会清零，熔断器打开的时刻就会变。所以每个熔断实验都从刚过边界时开始，
    // 30 次调用在 10 秒内跑完。
    static void waitForFreshWindow(long intervalMs) throws InterruptedException {
        long now = System.currentTimeMillis();
        Thread.sleep(intervalMs - now % intervalMs + 50);
    }

    static void runSequential(Function<String, String> method, int n) {
        int failed = 0, slowFirst10 = 0, slowRest = 0;
        for (int i = 1; i <= n; i++) {
            callNo = i;
            long t0 = System.nanoTime();
            String outcome = call(method, "x");
            long ms = (System.nanoTime() - t0) / 1_000_000;
            if (!outcome.startsWith("成功")) {
                failed++;
            }
            if (ms > 150) {
                if (i <= 10) slowFirst10++; else slowRest++;
            }
        }
        System.out.printf("  调用方: %d 次中失败 %d 次; 耗时超过 150ms 的: 前 10 次 %d 次, 后 %d 次 %d 次%n",
                n, failed, slowFirst10, n - 10, slowRest);
    }

    static String call(Function<String, String> method, String arg) {
        try {
            return "成功 " + method.apply(arg);
        } catch (Exception e) {
            String msg = String.valueOf(e.getMessage());
            int i = msg.indexOf("Tried ");
            String detail = i >= 0 ? msg.substring(i, msg.indexOf(')', i) + 1) : e.getClass().getSimpleName();
            return "失败 " + detail;
        }
    }

    static String consumerResource(String method) {
        return "dubbo:consumer:demo.Greeter:" + method + "(java.lang.String)";
    }

    static String attemptResource(String address, String method) {
        return AttemptSentinelFilter.resourceName(address, Greeter.class.getName(), method);
    }

    static ClusterNode consumerNode(String method) {
        return ClusterBuilderSlot.getClusterNode(consumerResource(method));
    }

    static ClusterNode attemptNode(String address, String method) {
        return ClusterBuilderSlot.getClusterNode(attemptResource(address, method));
    }

    // 三台机器的尝试级资源合计 {通过, 异常}。没被选中过的机器还没有统计节点。
    static long[] attemptTotals(String method) {
        long pass = 0, exception = 0;
        for (String address : addresses) {
            ClusterNode n = attemptNode(address, method);
            if (n != null) {
                pass += n.totalPass();
                exception += n.totalException();
            }
        }
        return new long[] {pass, exception};
    }

    static String shortName(String resource) {
        for (int i = 0; i < addresses.size(); i++) {
            if (resource.contains(addresses.get(i))) {
                return "机器 " + machines.get(i).name + " 的资源";
            }
        }
        return "消费端适配器资源";
    }

    static void setDelays(int... delays) {
        for (int i = 0; i < delays.length; i++) {
            machines.get(i).delayMs = delays[i];
        }
    }

    static int[] executedArray() {
        return machines.stream().mapToInt(g -> g.executed.get()).toArray();
    }

    static int totalExecuted() {
        return machines.stream().mapToInt(g -> g.executed.get()).sum();
    }

    static String executed() {
        StringBuilder sb = new StringBuilder();
        for (GreeterImpl.Machine g : machines) {
            sb.append(g.name).append('=').append(g.executed.get()).append(' ');
        }
        return sb.toString().trim();
    }

    static int freePort() throws Exception {
        try (ServerSocket s = new ServerSocket(0)) {
            return s.getLocalPort();
        }
    }
}

几点说明：

  • 端口每次随机，RT 会有几毫秒到几十毫秒的浮动，其余计数在本机连续跑了四次都一样。第 3 步的放行数依赖发起时刻错开，换到很慢或很忙的机器上可能不同，但“尝试次数 = 通过数 × 3”应当仍然成立。输出里有中文，终端需要是 UTF-8。
  • Sentinel 会在 ~/logs/csp/ 下写日志文件，不影响结果。
  • 示例开启了 csp.sentinel.dubbo.resource.use.prefix，消费端和提供端的资源名分别带上 dubbo:consumer:、dubbo:provider: 前缀。不开的话两端资源名相同，在同一进程里会合并成一个统计节点。实际部署中两端通常不在一个进程，但同一个应用既调用又提供同一接口时也会遇到这个问题。
  • 第 4 到 6 步开始前会等到下一个 10 秒整点之后。熔断器的统计窗口是一个长 statIntervalMs 的单桶，桶的起点对齐到 10 秒的整数倍（前一篇讲过，这是按绝对时间对齐的固定窗口），实验中途跨过边界，计数会清零，熔断器打开的时刻就会往后推。不对齐的话，第 5 步偶尔会在第 7 次调用才打开。
  • 读计数用的是 ClusterNode 的 totalPass()、totalException()、blockRequest()，它们是分钟级窗口；avgRt() 是秒级窗口，所以示例在调用一结束就读。

小结

  • Sentinel 1.8.10 的 Dubbo 3 适配器，消费端 Filter 是 ClusterFilter，挂在 failover 重试循环外面；提供端 Filter 是普通 Filter。Dubbo 2.7 适配器的消费端则是普通 Filter，按尝试计数，迁移时规则含义会悄悄改变。
  • 一次调用不管尝试几次，消费端只记一个 entry，异常只看最终结局，RT 是全程累加。正常返回的 Result（包括装在里面的业务异常）和抛出的业务 RpcException 不重试；超时这类框架错误才重试，调用数和尝试数在这里分家。
  • 消费端 QPS 限流限的是调用：一批放行的 M 个调用最多产生 M × (retries + 1) 次尝试，下游超时时放大最严重。它不是下游请求数的保证，重试跨窗口、多实例各有额度、检查也不是原子的；约束下游要靠提供端限流或全局预算。
  • 一台机器坏了：只要重试总能救回来，异常比例熔断就看不见它；慢调用比例熔断被累加的 RT 触发，把整个接口连同好机器一起熔断。
  • 要让调用数就是尝试数的上限，就给这些方法关掉重试；要按机器判断健康，就在重试循环里加一层按地址拆资源的普通 Filter，被拒绝时抛非业务 RpcException 让 failover 换台，只记会让 failover 换台的失败，并留意 6000 个资源的上限。
