同样是抛一个业务异常，消费端拿到了三种完全不同的东西：

  • 用例 6 最符合直觉：消费端原样拿到 BizException，错误码和消息都在。
  • 用例 5 拿到的是一个 java.lang.RuntimeException，原来的类型、错误码都没了，消息是一大段 5012 个字符的文本，提供端埋在 cause 里的一条“内部 SQL”也跟着到了消费端。
  • 用例 4 最糟糕：消费端拿到的是 RpcException，而且被标成网络异常；按默认的 retries=2，提供端把这个方法执行了 3 次。如果它是一个扣库存、发券之类的写操作，一次业务上的“不行”就变成了三次真实的执行。

差别全在两处：提供端默认启用的 ExceptionFilter 怎么判定这个异常，以及 Dubbo 3.2 起默认开启的序列化白名单肯不肯放行它。这篇把两者的规则、它们为什么这么设计、叠在一起以后会出什么问题、以及怎么让业务异常稳定地到达消费端讲清楚。

下文的源码和实测都基于 Dubbo 3.3.7（写作时 Maven Central 上的最新版本），dubbo 协议，hessian2 序列化，默认的 Failover 集群容错。示例在两端都显式固定了 hessian2，并且在提供端逐个请求核对了实际用的序列化方式。后文关于重试和失败形态的结论都限定在这个组合里：换成 triple 协议、别的序列化、别的集群容错策略，表现可能不同，本文没有验证。

异常先变成数据，再交给 ExceptionFilter

先看业务异常在提供端的路径。业务方法被 Dubbo 生成的 Wrapper 反射调用，抛出的异常被包在 InvocationTargetException 里，AbstractProxyInvoker 接住它，不再往上抛，而是把真正的异常塞进一个 AppResponse 里当作结果返回：

// AbstractProxyInvoker#invoke（3.3.7，节选）
} catch (InvocationTargetException e) {
    ...
    return AsyncRpcResult.newDefaultAsyncResult(null, e.getTargetException(), invocation);
}

返回 CompletableFuture 的异步方法也一样，异常完成时同样落进 AppResponse。所以对提供端的过滤器链来说，业务异常不是一个“抛出来的异常”，而是“一个带着异常的结果”，过滤器要在 onResponse 里看它、改它。之后编码器把整个 AppResponse 连同里面的 Throwable 一起序列化发回去，消费端解码后由 AppResponse#recreate() 把异常从代理方法里重新抛出来。

这也解释了总览那篇里提到的“业务异常不会触发重试”：异常是作为结果回来的，集群层的 FailoverClusterInvoker 看到的是一次成功的调用，异常直到代理层才被抛出。记住这一点，后面会看到它在什么情况下失效。

ExceptionFilter 标着 @Activate(group = CommonConstants.PROVIDER)，每个提供端默认都有它。它的 invoke 什么也不做，直接往下传，所有逻辑都在 onResponse 里。

判定规则：一串“消费端认不认识这个类”的猜测

下面是 3.3.7 里 ExceptionFilter#onResponse 的主体，日志参数和外层的 try/catch 做了省略，注释是我加的：

if (appResponse.hasException() && GenericService.class != invoker.getInterface()) {
    Throwable exception = appResponse.getException();

    // ① 受检异常：原样返回
    if (!(exception instanceof RuntimeException) && (exception instanceof Exception)) {
        return;
    }
    // ② 方法签名里声明过的：原样返回（注意是 equals，不是 isAssignableFrom）
    Method method = invoker.getInterface()
            .getMethod(RpcUtils.getMethodName(invocation), invocation.getParameterTypes());
    for (Class<?> exceptionClass : method.getExceptionTypes()) {
        if (exception.getClass().equals(exceptionClass)) {
            return;
        }
    }
    // ③ 走到这里先打一条 ERROR，带完整堆栈
    logger.error(..., "Got unchecked and undeclared exception which called by ...", exception);

    // ④ 异常类和接口类来自同一个 jar：原样返回
    String serviceFile = ReflectUtils.getCodeBase(invoker.getInterface());
    String exceptionFile = ReflectUtils.getCodeBase(exception.getClass());
    if (serviceFile == null || exceptionFile == null || serviceFile.equals(exceptionFile)) {
        return;
    }
    // ⑤ JDK 的异常：原样返回
    String className = exception.getClass().getName();
    if (className.startsWith("java.") || className.startsWith("javax.") || className.startsWith("jakarta.")) {
        return;
    }
    // ⑥ Dubbo 自己的 RpcException（含子类）：原样返回
    if (exception instanceof RpcException) {
        return;
    }
    // ⑦ 其余：整个异常转成字符串，包进一个新的 RuntimeException
    appResponse.setException(new RuntimeException(StringUtils.toString(exception)));
}

逐条看：

  1. 最外层的条件：只处理带异常的结果；提供端自己实现 GenericService（泛化实现）时整段跳过。
  2. ① 受检异常原样返回。 判断条件是“是 Exception 但不是 RuntimeException”，所以 Error 不算，Error 的子类会继续往下走。
  3. ② 签名里声明过的原样返回。 比较用的是 equals：签名里写 throws StockException，实际抛出它的子类 FrozenStockException，不算声明过。（反射找不到这个方法时，省略掉的 catch 里也是直接原样返回。）
  4. ③ ERROR 日志打在 ④⑤⑥ 之前。只要一个非受检异常没在签名里精确声明，不管后面是原样返回还是被包装，提供端都会打一条带完整堆栈的 ERROR。业务里用 RuntimeException 子类做参数校验、状态校验的项目，提供端日志会被这条刷满。
  5. ④ 同一个 jar 原样返回。 ReflectUtils.getCodeBase 取的是类的 ProtectionDomain → CodeSource → getLocation().getFile()，也就是“这个类是从哪个 jar 或目录加载的”。异常类和接口类来自同一处就放行；任何一边取不到位置（比如由启动类加载器加载的类）也放行。
  6. ⑤ JDK 异常原样返回，按类名前缀判断。3.2.0 的源码里只有 java. 和 javax.，3.2.20 和 3.3.0 里已经加上了 jakarta.。
  7. ⑥ RpcException 及其子类原样返回。
  8. ⑦ 其余的包装。 不是把原异常设成 cause，而是用 StringUtils.toString 把它连同堆栈打印成一个字符串，当作新 RuntimeException 的消息。

把 ①②④⑤⑥ 放在一起看，设计意图就很清楚了：每一条都是在猜”消费端的 classpath 上有没有这个类“。受检异常必须写在接口签名里，接口在 API jar 里，消费端一定依赖了 API jar，所以有；签名里声明的同理；和接口同一个 jar 的，消费端引了 API jar 也就有；JDK 的人人都有；RpcException 是 Dubbo 自己的。猜不准的，就退回到一个绝对安全的形式：RuntimeException 加一个字符串，任何一端都能反序列化。类注释里也是这么写的：“Wrap the exception not introduced in API package into RuntimeException”。

这套规则相当稳定。我对照了 2.7.23、3.1.11、3.2.0 和 3.3.7 的源码，除了 ⑤ 多了 jakarta. 前缀，判定逻辑没有变过。

第一行是 StringUtils.toString 自己写的“类名: 消息”，第二行起是 printStackTrace 的输出，所以类名和消息出现了两遍。对消费端来说，这意味着：

  • 类型没了。 catch (BizException e) 接不住它，getCode() 也没了，错误码只剩消息文本里的一个片段。
  • cause 没了，但 cause 的文本还在。 getCause() 是 null，原来的 cause 变成了消息里的 Caused by: 几行。
  • 堆栈是提供端的。 这个 RuntimeException 是在提供端的 ExceptionFilter 里 new 出来的，它的堆栈随着序列化一起过来，所以消费端看到的栈顶是 ExceptionFilter.onResponse(ExceptionFilter.java:113)，跟消费端自己的代码毫无关系。
  • 消息很大，而且泄露实现细节。 这个示例的调用栈很浅，消息也有 5012 个字符；真实的服务里叠上 Spring、AOP、各种过滤器，几十 KB 很常见。提供端的包名、类名、行号、用了哪些框架，全都原样交给了调用方。cause 的消息也在里面：示例在提供端所有不该公开的内容里埋了一个合成标记 SECRET-7f3a（用例 5 里它在 cause 的消息里，代表一条 SQL），消费端把拿到的异常的每一层类名、消息、堆栈都拼起来检查，用例 5、9、10 都能找到它。

为什么不直接把原异常设成 cause？因为 cause 里的类同样可能是消费端没有的，设成 cause 只是把问题往下挪了一层。不包装会怎样，我临时改过一次代码观察：去掉 plain 那组服务的 ExceptionFilter，并且把两端的序列化检查都调成 WARN（否则下一节说的白名单会先把它拦住），再抛那个只有提供端才有的异常类。消费端拿到的是 RpcException，原因是 Response data error, expect Throwable, but get class java.util.HashMap，提供端执行了 3 次。消费端解码时找不到这个类，hessian2 只能把它读成一个 HashMap，而这个位置要求的是 Throwable，于是整个响应解码失败。这就是 ⑦ 要防的情况：包装成字符串虽然丢了信息，至少保证了消费端能拿到“出错了”。

调低序列化检查只是为了看清这个现象，后文的可复制示例里不提供这种运行方式，也不建议在任何能被别人访问的网络里这么跑。

三者都被放行了，最后却都死在了序列化上。原因是 Dubbo 从 3.2.0 起把序列化检查的默认模式改成了 STRICT（3.1.11 的源码里默认还是 WARN），只有白名单里的类才能被序列化和反序列化。白名单由三部分组成：

  1. Dubbo 自带的 security/serialize.allowlist。里面列了基本类型、常用集合、java.time 的几个类，以及一部分 java.lang 下的异常：IllegalArgumentException、IllegalStateException、NullPointerException、RuntimeException 都在，UnsupportedOperationException、ArithmeticException、ClassCastException、ConcurrentModificationException 不在。
  2. 从服务接口推导出来的类。SerializeSecurityConfigurator#registerInterface 会遍历接口的每个方法，把参数类型、返回类型、签名里声明的异常类型，以及这些类的父类、接口、字段类型加进白名单。默认只加精确的类名，不按包名放行。
  3. 应用自己在 classpath 的 security/serialize.allowlist 文件或系统属性里额外配置的类。

注意第 2 部分只会向上找父类，不会向下找子类：声明了 StockException，FrozenStockException 依然不在白名单里。而 ExceptionFilter ④⑤ 放行的，恰恰是“消费端有这个类、但契约里没写它”的异常。

更关键的是，hessian2 在写出时也会查白名单。Hessian2SerializerFactory#getDefaultSerializer 在为一个类创建序列化器之前，先用同一个检查器“预检”一遍。于是失败发生在提供端编码响应的时候：

  1. 提供端 ExchangeCodec 编码 AppResponse 失败，打一条 Fail to encode response，改为给消费端回一个 BAD_RESPONSE 状态的响应，里面只有错误信息；
  2. 消费端把它当成 RemotingException，AbstractInvoker 把它转换成 RpcException，错误码是 NETWORK_EXCEPTION；
  3. FailoverClusterInvoker 只对 isBiz() 的 RpcException 直接抛出，其余的（包括网络异常）都会重试，默认 retries=2，一共三次；
  4. 每一次重试，业务方法都真实地执行一遍，ExceptionFilter 也打一遍 ERROR。

所以上一节说的“业务异常不会触发重试”，前提是这个异常能被序列化。一旦提供端编码响应失败，它在消费端看来就是一次网络故障，被重试，被监控当成网络错误统计。这条重试路径我只在本文的组合里验证过：dubbo 协议、hessian2、Failover、失败发生在提供端编码响应的时候。失败发生在别处（比如消费端解码）、换了协议或集群容错策略，要单独看。

原来的异常也没有消失，而是变成了 RpcException 消息里的一段文本：ExchangeCodec 回的错误信息是 "Failed to send response: " + res + ", cause: " + StringUtils.toString(t)，res 的 toString 里带着原异常的类名和消息，后面还跟着提供端序列化失败时的完整堆栈。所以用例 3、4、8 的消费端同样能找到 SECRET-7f3a。

讽刺的是，被 ⑦ 包装成 RuntimeException 的那些反而没事，因为 java.lang.RuntimeException 在白名单里。两套机制对“安全”的定义不一样：ExceptionFilter 看的是“消费端有没有这个类”，白名单看的是“契约里有没有写这个类”。前者是 2.x 时代的规则，后者是 3.2 为了防反序列化漏洞加上的，3.3.7 的 ExceptionFilter 并没有跟着白名单调整。

精确声明了，也不等于发得出去

两者都放行的，是签名里精确声明的异常和白名单里列出的那部分 JDK 异常。但白名单检查的不是“顶层是什么类”，而是序列化器实际写出去的整个对象图：异常的 cause、suppressed、堆栈元素、子类上加的字段，每一个对象的类都要过一遍。示例里最后两个用例抛的都是签名里声明过的 StockException，只是 cause 不同：

  • 用例 11 的 cause 是 IllegalStateException，在 Dubbo 的内置清单里，所以整个异常连同 cause 一起到了消费端。cause 的消息（这里是一个内网地址和标记）也一起到了。

返回值也一样。接口推导只覆盖签名里能看到的类型和它们的字段类型，运行时实际放进去的子类、装在 Object 或泛型集合里的对象都不在其中，返回一个业务 DTO 同样会在编码时被检查。白名单的完整机制可以参考 Dubbo 官方文档的类检查机制一节。

白名单本身还有不少可调的地方（ApplicationConfig 上的 serializeCheckStatus、autoTrustSerializeClass、trustSerializeClassLevel 等），系列后面会专门写一篇，这里只说一句：把检查调回 WARN 确实能让这些异常通过，但那是拿反序列化安全换来的，不建议当成解决办法。

怎么让业务异常稳定地到达消费端

问题的根源是两套规则只在一处达成一致：签名里精确声明、并且整个对象图都在白名单里的异常。所以办法也围绕这一点。

办法一：把业务异常写进契约

用一个扁平的业务异常类（错误码加消息，不要搞一层层子类），放在提供端和消费端都依赖的 jar 里，在接口方法上声明 throws BizException。示例里用例 6 就是这种写法，没有 ERROR 日志，类型、错误码、消息都在。

这个办法的约束也来自上面的规则：

  • 必须声明精确的类。 声明父类、抛子类，② 不认，白名单也不认。所以业务异常最好就是一个类，用错误码区分情况，而不是 OrderClosedException、StockFrozenException 这样的继承体系。
  • 每个方法都要声明。 没声明的方法抛同一个 BizException，就回到了规则 ④⑦：BizException 在公共 jar 里就被包装（示例用例 5），在 API jar 里就被放行再看白名单。
  • 不要往里塞 cause。 声明过的异常是原样序列化的，cause 要么让整个响应发不出去（用例 12），要么把内部信息带给调用方（用例 11）。需要排查的上下文写进提供端日志。

办法二：不用异常表达业务失败

返回一个带错误码的结果对象（比如 Result<T>），业务上的“不行”不再走异常通道，异常只留给真正的意外。这样 ExceptionFilter 和白名单都不会碰到业务失败，代价是接口签名和调用方代码都更啰嗦，调用方也可能忘了检查错误码。很多团队的 RPC 规范直接这么定，就是为了绕开这一节讲的所有问题。

办法三：换掉 ExceptionFilter

已经有一大批子类、改签名成本太高的项目，可以在提供端用自己的过滤器替换内置的那个。示例里的 BizExceptionFilter 做三件事：

  1. BizException 及其所有子类，不管来自哪个 jar，都重新 new 一个 BizException，只带错误码和消息这两个约定可以公开的字段，不带堆栈、cause 和子类上的其他字段，不打 ERROR。前提是团队约定 BizException 的消息就是写给调用方看的；
  2. 签名里精确声明过的其他异常，原样返回，和内置规则一致。这个分支不做任何清理，堆栈、cause、字段都原样序列化；
  3. 其余所有异常：完整异常只写进提供端的 ERROR 日志，消费端只拿到固定的错误码 INTERNAL_ERROR、一句通用的消息和一个用来对日志的编号，原来的类名和消息都不给。

这几条不是靠看输出确认的。消费端对第 2 组的用例 1 到 10 逐个断言：异常类型必须是预期的那个，BizException 的错误码必须对，BizException 不能带堆栈，拿到的异常每一层里都不能有 SECRET-7f3a，提供端必须正好执行 1 次，请求必须是 hessian2。调用正常返回、拿到连接失败之类的无关异常、出现标记、多执行或没执行，都算失败；只要有一条失败，消费端就抛 AssertionError，进程以非 0 状态退出。我把示例改坏了几种方式，确认断言真的会失败：

  • 过滤器把原始消息拼进公开消息里：用例 3、4、7、8、9、10 报“出现了 SECRET-7f3a”；
  • 让 providerOnly 正常返回：报“正常返回了，应该抛 BizException”；
  • 让第 2 组的引用指向一个不存在的分组（模拟连到了错误的服务）：每个用例都报拿到了 RpcException、提供端执行 0 次；
  • 删掉下面说的白名单文件：用例 3 到 10 报拿到了 RpcException、提供端执行 3 次；
  • 提供端没启动：消费端启动时就连接失败退出。

用例 11、12 走的是第 2 个分支，过滤器原样放行，所以结果和内置过滤器一样：一个把 cause 带给了调用方，一个编码失败、执行 3 次。这是有意保留的：过滤器没法替签名的作者决定一个声明过的异常该带什么出去。真要让它们也受保护，要么按办法一把签名里的异常收敛成 BizException（它会先进第 1 个分支被重新构造），要么去掉第 2 个分支，代价是声明过的受检异常也会被换掉，调用方 catch 不到原类型。

几点需要说明：

  • BizException 必须在白名单里。 第 1、3 个分支返回的都是它。示例里 common 模块带了一个 security/serialize.allowlist，只有一行 demo.common.BizException，提供端和消费端都依赖 common，两个进程各自加载它。它是必要的：上面最后一种改坏的方式就是把接口上唯一声明 BizException 的那个方法改成不声明、再删掉这个文件。
  • JDK 异常也被统一成了 INTERNAL_ERROR。 这是有意的：没写进签名的异常不是契约的一部分，消费端不应该按它的类型做分支。如果某个 JDK 异常确实是契约的一部分，就把它写进签名。
  • 消费端看不到提供端的堆栈和原始消息了。 只清掉堆栈是不够的：常见的写法是给消费端一个“类名: 消息”、不带堆栈的异常，可消息里的 SQL、路径、业务数据照样出去。现在完整异常只在提供端的 ERROR 日志里，排查靠那个编号（真实项目里用链路 ID）把两边串起来。
  • 它只在提供端生效。 所有提供端都要部署这个过滤器；老版本的提供端依然按内置规则处理。

不管用哪种办法

  • 写操作把 retries 设成 0，但别把它当成“只执行一次”。 本文的问题之所以从“拿错了异常”升级成“执行了三次”，是默认重试放大的。总览那篇已经说过默认重试会让提供端执行三次，这里又多了一个触发它的路径：在 dubbo 协议、hessian2、Failover 的组合下，提供端编码响应失败会被当成网络异常重试。retries=0 只是去掉了框架这一层的重试：超时以后提供端可能已经执行完了，连接在响应回来之前断了也一样，调用方自己的重试、消息队列的重投也都还在。扣库存、发券这类有副作用的操作，仍然要靠业务上的幂等（请求号去重、状态机校验）来兜底。
  • 用真实的序列化测一遍契约。 签名里写了什么，不代表运行时发得出去：cause、字段、DTO 里装的子类都要过白名单。像示例这样两个进程各自启动、走真实网络和序列化跑一遍，比单元测试里直接调实现类可靠。
  • 消费端不要解析 RuntimeException 的消息。 它的格式取决于提供端用了哪条规则、用的什么过滤器、堆栈有多深，不是一个可以依赖的接口。

完整示例

一个 Maven 多模块工程，在 JDK 21 上用 Maven 3.9 跑过，maven.compiler.release 设为 17，JDK 17 及以上都可以。不需要注册中心，提供端和消费端是两个独立启动的进程，classpath 各不相同，消费端用 127.0.0.1 直连。四个模块各有分工：

  • common：公共 jar，放业务异常基类 BizException、一个 Error 子类、白名单文件，以及一个只为实验统计日志用的 LogCounter；
  • api：接口和四个异常，依赖 common；另有一个只为实验服务的 ProbeService；
  • provider：服务实现、只有提供端才有的两个异常类、BizExceptionFilter、一个记录序列化方式的 ProbeFilter 和提供端的 main；
  • consumer：消费端的 main，只依赖 api 和 Dubbo，classpath 上没有 provider 里的任何类。

请在隔离的网络里运行。 消费端连的是回环地址，但这不限制提供端监听在哪：Dubbo 3.3.7 会把 127. 开头的地址当成无效的绑定地址，改为监听 0.0.0.0（上一篇里说过）。请在没有外部网络的容器里跑（例如 docker run --network none，回环在容器内照样可用），或者确认所在机器的防火墙不放行 20880 端口。运行时可以用 lsof -nP -iTCP -sTCP:LISTEN（Linux 和 macOS 都有）核对实际监听地址。

几处为了实验方便的做法：

  • 同一个实现导出两次，用 group 区分：plain 用内置的 ExceptionFilter，tuned 换成 BizExceptionFilter。
  • 两端都把序列化固定成 hessian2：提供端在 ProtocolConfig 上设 serialization 和 preferSerialization，消费端在引用的参数里设同样的两个值。dubbo 协议由消费端决定请求用哪种序列化，提供端按请求头里的 id 解码，响应也沿用这个 id（DubboCodecSupport#getResponseSerialization）。ProbeFilter 在提供端读出每个请求实际的序列化方式，输出里的 x-application/hessian2 就是它报的。我还试过只把消费端改成 fastjson2，提供端直接拒绝解码请求，说明两端确实只走 hessian2。
  • 消费端引用没有改 retries，保持默认值，这样才能看到重试的效果；超时设成 3 秒，免得机器慢时误报超时。
  • 两个进程的 Dubbo 日志都改走 java.util.logging，只收集 WARNING 及以上的日志并按来源计数，不打印正文。每个用例跑完，消费端调一次 ProbeService#drain，把提供端那边的执行次数、序列化方式和日志计数取回来一起打印。DefaultSerializeClassChecker 对同一个类只告警一次，重试三次也只记一条。
  • 提供端在不该公开的内容里埋了合成标记 SECRET-7f3a，消费端检查拿到的异常（包括每一层 cause 和 suppressed 的类名、消息、堆栈）里有没有它。第 1 组只打印结果，第 2 组的用例 1 到 10 还要过断言，失败时消费端以非 0 状态退出（Maven 显示 BUILD FAILURE）。

package demo.common;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.logging.Handler;
import java.util.logging.Level;
import java.util.logging.LogRecord;
import java.util.logging.Logger;

// 只为实验服务：把 Dubbo 的日志改走 java.util.logging，只收 WARNING 及以上，按来源计数，不打印正文
public final class LogCounter {
    private static final List<LogRecord> LOGS = new ArrayList<>();

    private LogCounter() {}

    /** 必须在 Dubbo 的任何类初始化之前调用。 */
    public static void install() {
        System.setProperty("dubbo.application.logger", "jdk");
        Logger root = Logger.getLogger("");
        for (Handler h : root.getHandlers()) {
            root.removeHandler(h);
        }
        root.addHandler(new Handler() {
            @Override
            public void publish(LogRecord r) {
                if (r.getLevel().intValue() >= Level.WARNING.intValue()) {
                    synchronized (LOGS) {
                        LOGS.add(r);
                    }
                }
            }

            @Override
            public void flush() {}

            @Override
            public void close() {}
        });
    }

    /** 返回自上次调用以来的日志计数，然后清零。 */
    public static String drain() {
        Map<String, Integer> counts = new LinkedHashMap<>();
        synchronized (LOGS) {
            for (LogRecord r : LOGS) {
                String name = r.getLoggerName();
                String key = name.substring(name.lastIndexOf('.') + 1) + " "
                        + (r.getLevel() == Level.SEVERE ? "ERROR" : "WARN");
                counts.merge(key, 1, Integer::sum);
            }
            LOGS.clear();
        }
        if (counts.isEmpty()) {
            return "没有告警日志";
        }
        StringBuilder sb = new StringBuilder("日志 ");
        counts.forEach((k, v) -> sb.append(k).append(" ×").append(v).append("  "));
        return sb.toString().stripTrailing();
    }
}

package demo.provider;

import java.lang.reflect.Method;
import java.util.concurrent.atomic.AtomicLong;

import org.apache.dubbo.common.logger.Logger;
import org.apache.dubbo.common.logger.LoggerFactory;
import org.apache.dubbo.rpc.Filter;
import org.apache.dubbo.rpc.Invocation;
import org.apache.dubbo.rpc.Invoker;
import org.apache.dubbo.rpc.Result;
import org.apache.dubbo.rpc.RpcException;
import org.apache.dubbo.rpc.service.GenericService;
import org.apache.dubbo.rpc.support.RpcUtils;

import demo.common.BizException;

/**
 * 替换内置的 ExceptionFilter（配置成 filter="-exception,bizException"）。
 * 1. BizException 及其子类：重新 new 一个 BizException，只带错误码和消息这两个约定可以公开的字段，
 *    不带堆栈、cause 和子类上的其他字段，不打 ERROR。前提是团队约定 BizException 的消息就是写给调用方看的。
 * 2. 方法签名里精确声明的其他异常：原样返回，和内置规则一致。这个分支不做任何清理：
 *    堆栈、cause、字段都会原样序列化，能不能发出去、会带出去什么，由声明它的人负责。
 * 3. 其余异常：完整异常只写进提供端日志，消费端只拿到固定的错误码 INTERNAL_ERROR、
 *    一句通用的消息和一个用来对日志的编号，类名和原始消息都不给。
 */
public class BizExceptionFilter implements Filter, Filter.Listener {
    private static final Logger log = LoggerFactory.getLogger(BizExceptionFilter.class);
    // 真实项目里用链路 ID；示例用自增编号，好让两次运行的输出一致
    private static final AtomicLong ERROR_NO = new AtomicLong();

    @Override
    public Result invoke(Invoker<?> invoker, Invocation invocation) throws RpcException {
        return invoker.invoke(invocation);
    }

    @Override
    public void onResponse(Result result, Invoker<?> invoker, Invocation invocation) {
        if (!result.hasException() || invoker.getInterface() == GenericService.class) {
            return;
        }
        Throwable e = result.getException();
        if (e instanceof BizException) {
            BizException biz = (BizException) e;
            result.setException(publicError(biz.getCode(), biz.getMessage()));
            return;
        }
        if (declared(invoker, invocation, e)) {
            return;
        }
        String errorNo = String.format("E%04d", ERROR_NO.incrementAndGet());
        log.error("Unexpected exception " + errorNo + " in " + invoker.getInterface().getName()
                + "#" + RpcUtils.getMethodName(invocation), e);
        result.setException(publicError("INTERNAL_ERROR", "服务内部错误（编号 " + errorNo + "）"));
    }

    @Override
    public void onError(Throwable t, Invoker<?> invoker, Invocation invocation) {
        log.error("Failed to invoke " + invoker.getInterface().getName() + "#" + RpcUtils.getMethodName(invocation), t);
    }

    private static BizException publicError(String code, String message) {
        BizException e = new BizException(code, message);
        e.setStackTrace(new StackTraceElement[0]);
        return e;
    }

    private static boolean declared(Invoker<?> invoker, Invocation invocation, Throwable e) {
        try {
            Method m = invoker.getInterface()
                    .getMethod(RpcUtils.getMethodName(invocation), invocation.getParameterTypes());
            for (Class<?> declared : m.getExceptionTypes()) {
                if (declared == e.getClass()) {
                    return true;
                }
            }
        } catch (NoSuchMethodException ignored) {
            // 找不到方法就按"没声明"处理
        }
        return false;
    }
}

package demo.provider;

import java.util.Set;
import java.util.TreeSet;

import org.apache.dubbo.remoting.transport.CodecSupport;
import org.apache.dubbo.rpc.Filter;
import org.apache.dubbo.rpc.Invocation;
import org.apache.dubbo.rpc.Invoker;
import org.apache.dubbo.rpc.Result;
import org.apache.dubbo.rpc.RpcException;

// 只为实验服务：记下每个请求实际是用哪种序列化解码的。dubbo 协议的响应沿用请求的序列化方式编码。
public class ProbeFilter implements Filter {
    private static final Set<String> SEEN = new TreeSet<>();

    @Override
    public Result invoke(Invoker<?> invoker, Invocation invocation) throws RpcException {
        Object id = invocation.get("serialization_id"); // 解码请求时放进去的，值是请求头里的序列化 id
        String name = id == null ? "未知" : CodecSupport.getSerializationById((Byte) id).getContentType();
        synchronized (SEEN) {
            SEEN.add(name);
        }
        return invoker.invoke(invocation);
    }

    static String drain() {
        synchronized (SEEN) {
            String s = SEEN.isEmpty() ? "（没有收到请求）" : String.join("、", SEEN);
            SEEN.clear();
            return s;
        }
    }
}

    static <T> ServiceConfig<T> service(Class<T> type, T ref, String group, String filter) {
        ServiceConfig<T> s = new ServiceConfig<>();
        s.setInterface(type);
        s.setRef(ref);
        if (group != null) {
            s.setGroup(group);
        }
        if (filter != null) {
            s.setFilter(filter);
        }
        return s;
    }

public class ConsumerMain {
    // 提供端在不该公开的内容里埋的合成标记（见 OrderServiceImpl.SECRET），消费端不依赖提供端的代码，所以这里再写一遍

    // 换成 BizExceptionFilter 以后消费端应该拿到什么：异常类型，以及 BizException 的错误码（其他类型为 null）

    // thrown 为 null 表示调用正常返回
    record Outcome(Throwable thrown, Map<String, String> provider) {}

    static Outcome run(OrderService orders, ProbeService probe, Case c, int no) throws InterruptedException {
        Throwable thrown = null;
        String seen;
        try {
            c.call().apply(orders);
            seen = "正常返回";
        } catch (Throwable e) {
            thrown = e;
            seen = describe(e);
        }
        Thread.sleep(200); // 等两边的 IO 线程把日志写完
        Map<String, String> provider = probe.drain();
        boolean leaked = thrown != null && everything(thrown).contains(SECRET);
        System.out.printf("%n%2d %s%n   抛出    %s%n   拿到    %s%n   提供端  执行 %s 次，请求按 %s 解码，%s%n   消费端  %s，%s%n",
                no, c.method(), c.thrown(), seen,
                provider.get("calls"), provider.get("serialization"), provider.get("logs"), LogCounter.drain(),
                leaked ? "拿到的异常里出现了提供端的 " + SECRET : "拿到的异常里没有 " + SECRET);
        return new Outcome(thrown, provider);
    }

    // 正常返回、类型或错误码不对（包括连接失败之类的无关异常）、带了堆栈、出现标记、执行次数不是 1、
    // 序列化不是 hessian2，任何一条都算失败
    static List<String> check(int no, Case c, Outcome o) {
        List<String> errors = new ArrayList<>();
        Expect x = c.tuned();
        Throwable e = o.thrown();
        if (e == null) {
            errors.add("正常返回了，应该抛 " + x.type().getName());
        } else {
            if (e.getClass() != x.type()) {
                errors.add("拿到 " + e.getClass().getName() + "，应该是 " + x.type().getName());
            } else if (x.code() != null && !x.code().equals(((BizException) e).getCode())) {
                errors.add("错误码是 " + ((BizException) e).getCode() + "，应该是 " + x.code());
            }
            if (e instanceof BizException && e.getStackTrace().length > 0) {
                errors.add("BizException 带了 " + e.getStackTrace().length + " 帧堆栈");
            }
            if (everything(e).contains(SECRET)) {
                errors.add("拿到的异常里出现了 " + SECRET);
            }
        }
        if (!"1".equals(o.provider().get("calls"))) {
            errors.add("提供端执行了 " + o.provider().get("calls") + " 次，应该是 1 次");
        }
        if (!HESSIAN2.equals(o.provider().get("serialization"))) {
            errors.add("请求的序列化是 " + o.provider().get("serialization") + "，应该是 " + HESSIAN2);
        }
        List<String> out = new ArrayList<>();
        for (String err : errors) {
            out.add("失败：用例 " + no + " " + c.method() + "，" + err);
        }
        return out;
    }

    static String describe(Throwable e) {
        String msg = String.valueOf(e.getMessage());
        if (e instanceof RpcException) {
            RpcException rpc = (RpcException) e;
            String kind = "isNetwork=" + rpc.isNetwork() + "，isBiz=" + rpc.isBiz();
            Matcher m = Pattern.compile("Serialized class (\\S+) is not in allow list").matcher(msg);
            if (m.find()) {
                return "RpcException（" + kind + "）：提供端编码响应时 " + m.group(1) + " 不在白名单里";
            }
            return "RpcException（" + kind + "）：" + msg.lines().findFirst().orElse("");
        }
        if (e instanceof BizException) {
            BizException b = (BizException) e;
            return e.getClass().getName() + "，code=" + b.getCode() + "，message=" + msg
                    + "，堆栈 " + e.getStackTrace().length + " 帧，cause=" + e.getCause();
        }
        if (e.getClass() == RuntimeException.class) {
            return "java.lang.RuntimeException，message " + msg.length() + " 个字符，第一行是「"
                    + msg.lines().findFirst().orElse("") + "」，cause=" + e.getCause()
                    + (e.getStackTrace().length > 0 ? "，栈顶 " + e.getStackTrace()[0] : "，没有堆栈");
        }
        return e.getClass().getName() + "：" + msg + "，cause=" + e.getCause();
    }

    // 消费端能从这个异常上读到的所有文本：每一层（cause、suppressed）的类名、消息和堆栈
    static String everything(Throwable e) {
        StringBuilder sb = new StringBuilder();
        List<Throwable> todo = new ArrayList<>(List.of(e));
        for (int i = 0; i < todo.size() && i < 50; i++) {
            Throwable t = todo.get(i);
            sb.append(t).append('\n');
            for (StackTraceElement s : t.getStackTrace()) {
                sb.append(s).append('\n');
            }
            if (t.getCause() != null && t.getCause() != t) {
                todo.add(t.getCause());
            }
            todo.addAll(List.of(t.getSuppressed()));
        }
        return sb.toString();
    }

    static <T> ReferenceConfig<T> reference(Class<T> type, String group, int port) {
        ReferenceConfig<T> r = new ReferenceConfig<>();
        r.setInterface(type);
        if (group != null) {
            r.setGroup(group);
        }
        r.setUrl("dubbo://127.0.0.1:" + port);
        // 消费端决定请求用哪种序列化，提供端按请求头里的 id 解码，响应也用同一种。这里固定成 hessian2。
        r.setParameters(Map.of("serialization", "hessian2", "prefer.serialization", "hessian2"));
        r.setTimeout(3000); // retries 保持默认
        return r;
    }
}

小结

  • 业务异常在提供端不是被抛出去的，而是作为 AppResponse 里的结果，经过 ExceptionFilter#onResponse 判定后，序列化到消费端，再从代理方法里抛出。
  • ExceptionFilter 原样返回五种异常：受检异常、签名里精确声明的、和接口同一个 jar 的、JDK 的、RpcException；其余的连同堆栈转成字符串，包进新的 RuntimeException。每条规则都是在猜“消费端有没有这个类”。没精确声明的非受检异常都会在提供端打一条带堆栈的 ERROR。
  • 被包装后，类型、错误码、cause 都没了，消息里是提供端的完整堆栈和 cause 的消息，又大又泄露实现细节。
  • 3.2 起序列化检查默认 STRICT，白名单只认接口签名里出现的类和一份内置清单，而且 hessian2 在提供端写出时就会检查整个对象图。被 ④⑤ 放行、却不在白名单里的异常，或者声明过、但 cause 不在白名单里的异常，会在提供端编码失败；在 dubbo 协议、hessian2、Failover 的组合下，消费端拿到被标成网络异常的 RpcException，按默认重试，业务方法执行三次，原异常的类名和消息还会出现在这个 RpcException 的消息里。
  • 规则 ④ 看的是类从哪个 jar 或目录加载，同一份代码，多模块运行和打成一个 jar 的结果不同；shade 打包还要记得合并 security/serialize.allowlist。
  • 让业务异常稳定到达消费端：用一个扁平、不带 cause 的业务异常类并精确声明在签名里；或者用返回值表达业务失败；已有大量异常子类的，换掉 ExceptionFilter，业务异常只回错误码和消息，其余异常只回固定错误码和对日志用的编号，完整异常留在提供端日志里。
  • 写操作把 retries 设成 0，但它不等于只执行一次，有副作用的操作仍要做幂等。
