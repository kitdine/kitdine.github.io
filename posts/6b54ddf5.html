Go 里怎么取消一个卡在 WebSocket 读上的 goroutine

订阅一个 WebSocket 推送流，通常会写一个后台 goroutine 循环读消息，再给调用方一个 context.Context 用来停掉它。很多人第一版会这么写：

// NaiveReadLoop 是常见的错误写法：只在两次读之间检查 ctx。
// 一旦阻塞在 ReadMessage 里，取消就传不进去。
func NaiveReadLoop(ctx context.Context, conn *websocket.Conn, out chan<- []byte) error {
	for {
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}
		_, data, err := conn.ReadMessage()
		if err != nil {
			return err
		}
		out <- data
	}
}

看上去每轮都检查了 ctx，实际上调用方取消之后，这个 goroutine 多半还活着，连接也还开着。服务端一直不推数据时，它会在 ReadMessage 里一直等下去。页面关了、订阅换了、进程准备优雅退出，它都不走。

这篇只讲一件事：怎么让一个阻塞在网络读上的 goroutine 真正响应取消。顺着这个问题，会碰到另外几个绕不开的坑：对端半开时永远读不到错误，消费者慢下来时读循环卡在发送上，以及退出时等一个卡在写里的 goroutine。最后给出一个完整可运行的小包和测试，基于 gorilla/websocket v1.5.3。

为什么 ctx 传不进去

ctx 本身不会打断任何东西。它只是一个会在取消时关闭的 channel，必须有代码去 select 它才有用。上面那段代码只在两次读之间看一眼 ctx.Done()，而 goroutine 大部分时间都停在 ReadMessage 里面，那时没有任何代码在看 ctx。

Go 也没有从外面中断另一个 goroutine 的办法。一个卡在 net.Conn.Read 上的 goroutine，只有三种情况会醒：

  1. 数据到了；
  2. 读截止时间到了；
  3. 连接被关闭了。

后两条在 net.Conn 的文档里写得很直接：Close 会让 “Any blocked Read or Write operations will be unblocked and return errors”；截止时间是 “an absolute time after which I/O operations fail instead of blocking”。gorilla/websocket 的 ReadMessage 没有 ctx 参数，底下就是对 net.Conn 的读，所以想让取消生效，只能在取消发生时去动连接本身：要么关掉它，要么把截止时间拨到现在。

这一点不靠讲道理，后面的测试 TestNaiveLoopIgnoresCancel 会直接证明：取消之后 300 毫秒，朴素写法依然没有返回，只有关掉连接它才出来。

关连接，还是把截止时间拨到过去

两种办法都能把读打断，代价不一样。

把截止时间设到过去，读会立即以超时错误返回，连接本身不关。标准库 net/http 就用了这一招：服务端在后台读连接时，如果要中止这次读，会调用 SetReadDeadline(aLongTimeAgo)，其中 aLongTimeAgo = time.Unix(1, 0)，等读返回后再把截止时间清零，连接继续复用（见 Go 1.26.4 源码 net/http/server.go 的 abortPendingRead，常量定义在 net/http/http.go）。这适合裸 TCP 或你自己掌握协议状态的场景：只是想暂停一次读，不想丢连接。

但在 WebSocket 上，这条路走不通。gorilla/websocket 的 SetReadDeadline 文档写明：“After a read has timed out, the websocket connection state is corrupt and all future reads will return an error.”。一次读超时之后连接就废了，打断读和关连接的效果一样，不如直接 Close，意图更清楚，也不会留下一个看似还开着、实则不能用的连接。

所以对 WebSocket 来说，取消等于关连接。剩下要解决的是：谁来关，什么时候关，关了之后怎么收尾。

还有一个前提要确认：在读 goroutine 正阻塞在 ReadMessage 时，另一个 goroutine 去调 Close 安全吗？gorilla/websocket 文档的 Concurrency 一节规定，连接只支持一个并发读者和一个并发写者，但 “The Close and WriteControl methods can be called concurrently with all other methods.”。Close 和 WriteControl 是专门放开的例外，这两样后面都要用到。

完整代码

一个独立的小包 wsread。go.mod：

module example.com/wsread

go 1.21

require github.com/gorilla/websocket v1.5.3

context.AfterFunc 是 Go 1.21 加入的，所以最低版本写 1.21。下面的代码和测试在 Go 1.24.7（linux/amd64）上跑过。

wsread.go：

// Package wsread 演示怎么让阻塞在 WebSocket 读上的 goroutine 响应 context 取消。
package wsread

import (
	"context"
	"errors"
	"net"
	"time"

	"github.com/gorilla/websocket"
)

// Options 控制保活和投递参数。零值字段使用默认值。
type Options struct {
	PongWait    time.Duration // 多久收不到任何数据（含 pong）就认为连接已死，默认 60s
	PingPeriod  time.Duration // 多久发一次 ping，必须满足 0 < PingPeriod < PongWait，默认 PongWait 的九成
	SendTimeout time.Duration // 一条消息最多等消费者多久，默认 10s
}

var (
	// ErrDeadPeer 表示在 PongWait 内没有收到对端任何数据。
	ErrDeadPeer = errors.New("wsread: peer stopped responding")
	// ErrSlowConsumer 表示一条消息在 SendTimeout 内没有被消费者取走。
	ErrSlowConsumer = errors.New("wsread: consumer did not keep up")
	// ErrBadOptions 表示参数无法满足 0 < PingPeriod < PongWait。
	ErrBadOptions = errors.New("wsread: need 0 < PingPeriod < PongWait")
)

func (o Options) normalize() (Options, error) {
	if o.PongWait <= 0 {
		o.PongWait = 60 * time.Second
	}
	if o.PingPeriod <= 0 || o.PingPeriod >= o.PongWait {
		// 不写成 PongWait*9/10：PongWait 很大时乘法会溢出。
		o.PingPeriod = o.PongWait - o.PongWait/10
	}
	if o.SendTimeout <= 0 {
		o.SendTimeout = 10 * time.Second
	}
	// PongWait 只有几纳秒时，上面算出来的值等于 PongWait，留不出任何余量。
	if o.PingPeriod <= 0 || o.PingPeriod >= o.PongWait {
		return o, ErrBadOptions
	}
	return o, nil
}

// ReadLoop 持续读消息并发到 out，直到出现下面任意一种情况：
//   - ctx 被取消：返回 ctx.Err()
//   - 对端正常关闭：返回 nil
//   - 对端超过 PongWait 没有任何数据：返回 ErrDeadPeer
//   - 消费者超过 SendTimeout 没有取走消息：返回 ErrSlowConsumer
//   - 其他读错误：原样返回
//
// ReadLoop 返回时连接一定已经关闭，它启动的 goroutine 和回调也都已结束。
func ReadLoop(ctx context.Context, conn *websocket.Conn, out chan<- []byte, opt Options) error {
	opt, err := opt.normalize()
	if err != nil {
		_ = conn.Close()
		return err
	}

	// 1. 取消时关闭连接，把阻塞中的 ReadMessage 打断。
	//    Close 可以和读方法并发调用（gorilla/websocket 文档的 Concurrency 一节）。
	closedByCancel := make(chan struct{})
	stop := context.AfterFunc(ctx, func() {
		_ = conn.Close()
		close(closedByCancel)
	})

	// 2. 读超时 + pong 续期：对端半开时不会永远卡住。
	_ = conn.SetReadDeadline(time.Now().Add(opt.PongWait))
	conn.SetPongHandler(func(string) error {
		return conn.SetReadDeadline(time.Now().Add(opt.PongWait))
	})

	// 3. 单独的 goroutine 定时发 ping。WriteControl 也可以和其他方法并发调用。
	pingDone := make(chan struct{})
	readDone := make(chan struct{})
	go func() {
		defer close(pingDone)
		t := time.NewTicker(opt.PingPeriod)
		defer t.Stop()
		for {
			select {
			case <-readDone:
				return
			case <-t.C:
				deadline := time.Now().Add(opt.PingPeriod)
				if err := conn.WriteControl(websocket.PingMessage, nil, deadline); err != nil {
					return // 连接坏了，读那边很快也会出错
				}
			}
		}
	}()

	// 4. 收尾顺序：先通知 ping 停下，再关连接把可能卡在写里的 ping 叫醒，最后才等它退出。
	//    反过来先等 ping，最坏要等到它的写截止时间。
	defer func() {
		close(readDone)
		_ = conn.Close()
		<-pingDone
		// stop 返回 false 说明回调已经开始跑了；它不会等回调结束，所以自己等。
		if !stop() {
			<-closedByCancel
		}
	}()

	for {
		_, data, err := conn.ReadMessage()
		if err != nil {
			return classify(ctx, err)
		}
		if err := deliver(ctx, out, data, opt.SendTimeout); err != nil {
			return err
		}
		// 投递期间没人读连接，pong 只是堆在缓冲区里没被处理。
		// 从这里重新开始计时，否则一次慢投递会被误判成对端死了。
		_ = conn.SetReadDeadline(time.Now().Add(opt.PongWait))
	}
}

// deliver 把一条消息交给消费者，最多等 limit。
// 读截止时间管不到 channel 发送，所以这里需要自己的上限。
func deliver(ctx context.Context, out chan<- []byte, data []byte, limit time.Duration) error {
	select { // 快路径：消费者跟得上时不创建 timer
	case out <- data:
		return nil
	default:
	}
	t := time.NewTimer(limit)
	defer t.Stop()
	select {
	case out <- data:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	case <-t.C:
		return ErrSlowConsumer
	}
}

// classify 把读错误翻译成调用方关心的几种结果。顺序很重要：
// 先看 ctx，因为是我们自己关的连接，底层错误只是取消的副作用。
func classify(ctx context.Context, err error) error {
	if ctxErr := ctx.Err(); ctxErr != nil {
		return ctxErr
	}
	if websocket.IsCloseError(err, websocket.CloseNormalClosure, websocket.CloseGoingAway) {
		return nil
	}
	var ne net.Error
	if errors.As(err, &ne) && ne.Timeout() {
		return ErrDeadPeer
	}
	return err
}

// NaiveReadLoop 是常见的错误写法：只在两次读之间检查 ctx。
// 一旦阻塞在 ReadMessage 里，取消就传不进去。
func NaiveReadLoop(ctx context.Context, conn *websocket.Conn, out chan<- []byte) error {
	for {
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}
		_, data, err := conn.ReadMessage()
		if err != nil {
			return err
		}
		out <- data
	}
}

逐段拆开

1. 用 context.AfterFunc 在取消时关连接

context.AfterFunc(ctx, f) 会在 ctx 被取消后，在一个新的 goroutine 里调用 f；如果 ctx 已经取消，就立刻调用。它返回一个 stop 函数，用来解除这个关联。

在 Go 1.21 以前，同样的事要手写一个看门 goroutine：

done := make(chan struct{})
defer close(done)
go func() {
	select {
	case <-ctx.Done():
		_ = conn.Close()
	case <-done: // 读循环自己结束了，看门的也该走
	}
}()

这里最容易漏的是 case <-done。没有它，读循环因为对端断开而正常退出后，看门 goroutine 还在等 ctx；如果调用方传的是 context.Background()，它永远等不到，每建一个连接就泄漏一个 goroutine。AfterFunc 把这件事做对了：对标准库派生出来的 ctx，它只是登记一个回调，没取消时不额外占 goroutine；传 context.Background() 时回调永远不会触发，也不留任何东西；stop() 之后回调不会再跑。

stop 的语义有一个细节值得留意。它的文档说：返回 true 表示成功阻止了回调；返回 false 表示回调已经开始，或者早已被停掉；并且 “The stop function does not wait for f to complete before returning.”。也就是说，如果取消和读循环退出几乎同时发生，ReadLoop 返回时 Close 可能还在另一个 goroutine 里跑。关一个已经关掉的连接本身无害，但这会让 “函数返回时一切都已收拾干净” 这句话不成立，测试里数 goroutine 时也会多出偶发的一个。所以代码里让回调在结束时关一个 channel，stop() 返回 false 时等它关闭。我们只调一次 stop，所以这里的 false 只可能是回调已经开始。

2. 先看 ctx，再看错误

连接被我们关掉之后，ReadMessage 返回的错误长这样（在上面的环境里实测）：

*net.OpError: read tcp 127.0.0.1:51526->127.0.0.1:35695: use of closed network connection

它满足 errors.Is(err, net.ErrClosed)。但对调用方来说，这只是 “我取消了” 的副作用，不是故障。如果原样返回，调用方的日志里就会在每次正常退订时多一条错误，监控上也分不清是自己停的还是网断了。

所以 classify 的第一步是看 ctx.Err()：只要 ctx 已经取消，就返回 context.Canceled（或 DeadlineExceeded），不管底层报的是什么。之后才区分：

  • 对端发了正常关闭帧（1000 或 1001）：返回 nil；
  • 读超时：返回 ErrDeadPeer，下一节解释它从哪来；
  • 其他：原样返回，交给调用方决定要不要重连。

顺序反过来就会出错。比如先判断 net.ErrClosed，那 “被我们关掉” 和 “被别的代码误关” 就混在了一起。

3. 只会取消还不够：对端半开

假设没人取消，服务端也一直不发数据，而中间某台设备丢掉了这条 TCP 连接，或者对端机器直接断电。本地内核没有收到 FIN 或 RST，连接在本地看来还开着，ReadMessage 会一直阻塞。没有读截止时间时，这个 goroutine 永远不会醒。取消能救它，前提是有人会取消；后台长连接往往没有。

解决办法是 WebSocket 自带的 ping/pong：

  • 读截止时间设为 “现在 + PongWait”；
  • 每收到一个 pong（以及每收到一条数据）就把截止时间往后推；
  • 另一个 goroutine 每隔 PingPeriod 发一个 ping。

PingPeriod 必须小于 PongWait，而且要小出足够的余量：ping 发出去之后，pong 要经过一个往返时间才能回来，回来之后还要等读循环被调度、真正读到它，截止时间才会被推后。这两段时间加起来要落在 PongWait - PingPeriod 之内，否则对端明明活着，也会因为 pong 晚到一点而被判死。

gorilla/websocket 自带的 chat 示例用的是 pongWait = 60 * time.Second、pingPeriod = (pongWait * 9) / 10，也就是留出 6 秒余量。这里的默认值取同样的比例，但写成 PongWait - PongWait/10：PongWait 是调用方传进来的，接近 math.MaxInt64 时先乘 9 会溢出，得到一个毫无意义的值。另一头也有问题：PongWait 只有 1 纳秒时，PongWait*9/10 截断成 0，交给 time.NewTicker 会 panic（它要求间隔大于 0）；换成减法也只会得到等于 PongWait 的值，留不出任何余量。所以 normalize 在算完默认值之后再校验一次 0 < PingPeriod < PongWait，不满足就返回 ErrBadOptions，ReadLoop 直接关连接退出。

这两个数还要按你的场景调：中间有代理或负载均衡时，ping 间隔要比它们的空闲超时短，否则连接会被中间设备先掐掉；链路抖动大时，余量要放宽。

这里有三个坑：

pong 处理函数里设零值。 SetReadDeadline(time.Time{}) 的含义是 “不超时”，文档原话是 “A zero value for t means reads will not time out.”。在 pong 回调里写零值，等于每收到一个 pong 就把超时关掉，保活形同虚设。必须写 time.Now().Add(PongWait)。

pong 只在读的时候才会被处理。 文档说 pong 处理函数 “is called from the NextReader, ReadMessage and message reader Read methods”。我们的读循环一直在读，所以没问题。但反过来也意味着：对端如果从不读连接，它的默认 ping 处理函数就不会运行，也就不会回 pong。测试里正是用 “服务端既不读也不写” 来模拟半开连接的。

发 ping 的 goroutine 不能随便写。 连接只允许一个并发写者。这里用的是 WriteControl，它在允许并发的例外名单里，所以和别处的写不冲突。如果你在 ping goroutine 里改用 WriteMessage，又在别处发业务消息，就需要自己加锁或把所有写集中到一个 goroutine。

超时之后 ReadMessage 返回的错误满足 net.Error 且 Timeout() 为真，classify 据此返回 ErrDeadPeer。这时连接状态已经损坏，正好也该退出。

4. 往外发：取消之外还要有上限

读到数据后，out <- data 也是一个可能永远阻塞的点。

最直接的情况是调用方取消订阅后不再读 out。只要这里 select 上 ctx.Done()，取消就能把它叫醒。这和第一节是同一个问题的另一面：每一个可能阻塞的地方，都要有一条能被唤醒的路。

但光靠取消不够。调用方没有取消，只是处理变慢了，或者它自己卡在别处，读循环就会停在发送上。整个连接只有这一个读 goroutine，它停下来，pong 和关闭帧就没人处理了：pong 回调和关闭处理都只在读的时候运行。读截止时间也帮不上忙，SetReadDeadline 只作用于网络读，管不到 channel 发送。结果是对端已经走了，这边也不知道，goroutine 挂着，连接也挂着。

所以 deliver 给投递设了一个明确上限 SendTimeout，超时返回 ErrSlowConsumer，随后 ReadLoop 关连接退出。单独用一个错误值，是为了让调用方分得清两种完全不同的故障：ErrDeadPeer 说明网络或对端出了问题，应该重连；ErrSlowConsumer 说明自己的下游处理不过来，立刻重连只会更快地再次堆积，应该先看下游。

实现上有两个细节：

  • 先走一次非阻塞发送。 消费者跟得上时直接成功，不创建 timer。只有真的要等，才 time.NewTimer，并在返回时 Stop。
  • 投递完成后再续读截止时间。 投递期间没人读连接，对端的 pong 即使到了也只是躺在缓冲区里，截止时间不会被推后。如果续期放在投递之前，一次超过 PongWait 的慢投递结束后，下一次网络读会直接撞上已经过期的截止时间，把一个活着的对端误判成 ErrDeadPeer。放在投递之后，计时就从 “重新开始听” 的那一刻算起。

SendTimeout 的默认值 10 秒只是一个起点，应该按下游一条消息最慢的正常处理时间来定。如果宁可丢消息也不想断连接，可以换一种策略：超时后丢掉这条并计数，继续读。那是另一种取舍，但无论选哪种，都不能没有上限。

5. 返回前把自己起的东西收干净，顺序要对

ReadLoop 自己起了 ping goroutine，就负责等它退出。加上第 1 节对 AfterFunc 回调的等待，调用方可以放心地认为：函数返回后，这个连接相关的东西都已经结束，可以立即重连，不会和旧连接的 goroutine 交叠。

收尾放在一个 defer 里，顺序是：

  1. close(readDone)，通知 ping goroutine 停下；
  2. conn.Close()，关连接；
  3. <-pingDone，等 ping goroutine 真正退出；
  4. 处理 AfterFunc 的 stop。

第 2 步必须在第 3 步之前。ping goroutine 可能正卡在 WriteControl 里，比如对端不读、TCP 发送缓冲已满。这时它看不到 readDone，只有两种情况会让它出来：写截止时间到期，或者连接被关闭。如果先等它再关连接，一次普通的退出最坏要等满写截止时间，按默认参数是 54 秒。先关连接，被阻塞的写立刻返回错误，ping goroutine 随即退出。Close 可以和写方法并发调用，这一点前面已经确认过。

这个顺序很容易写反，因为 “先停后台任务，再释放资源” 听起来更自然。区别在于这里的后台任务正阻塞在这个资源上，只有释放资源才能让它停下。

var upgrader = websocket.Upgrader{}

// newServer 起一个本地 WebSocket 服务端，handler 决定服务端怎么表现。
func newServer(t *testing.T, handler func(*websocket.Conn)) string {
	t.Helper()
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		c, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}
		defer c.Close()
		handler(c)
	}))
	t.Cleanup(srv.Close)
	return "ws" + strings.TrimPrefix(srv.URL, "http")
}

func dial(t *testing.T, url string) *websocket.Conn {
	t.Helper()
	c, _, err := websocket.DefaultDialer.Dial(url, nil)
	if err != nil {
		t.Fatal(err)
	}
	return c
}

// 服务端持续读（这样默认的 ping 处理器会回 pong），但一条数据也不发。
func silentButAlive(c *websocket.Conn) {
	for {
		if _, _, err := c.ReadMessage(); err != nil {
			return
		}
	}
}

func run(ctx context.Context, conn *websocket.Conn, out chan []byte, opt Options) <-chan error {
	errc := make(chan error, 1)
	go func() { errc <- ReadLoop(ctx, conn, out, opt) }()
	return errc
}

func wait(t *testing.T, errc <-chan error, within time.Duration) error {
	t.Helper()
	select {
	case err := <-errc:
		return err
	case <-time.After(within):
		t.Fatalf("ReadLoop 在 %v 内没有返回", within)
		return nil
	}
}

// 消费者慢于 PongWait 但在 SendTimeout 之内：不能误判成对端死了。
func TestSlowButWithinLimitIsNotDeadPeer(t *testing.T) {
	conn := dial(t, newServer(t, func(c *websocket.Conn) {
		_ = c.WriteMessage(websocket.TextMessage, []byte("1"))
		// 隔一会儿再发第二条，让它不在客户端第一次读的缓冲里，
		// 客户端必须在投递完第一条之后再碰一次网络读。
		time.Sleep(300 * time.Millisecond)
		_ = c.WriteMessage(websocket.TextMessage, []byte("2"))
		silentButAlive(c)
	}))
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()
	out := make(chan []byte)
	errc := run(ctx, conn, out, Options{
		PongWait: 200 * time.Millisecond, PingPeriod: 50 * time.Millisecond, SendTimeout: 2 * time.Second,
	})

	for _, want := range []string{"1", "2"} {
		time.Sleep(400 * time.Millisecond) // 每条都比 PongWait 慢一倍才去取
		select {
		case got := <-out:
			if string(got) != want {
				t.Fatalf("want %q, got %q", want, got)
			}
		case err := <-errc:
			t.Fatalf("连接不该断，got %v", err)
		}
	}
}

// stuckWriteConn 在 stuck 打开后让每次写都卡住，直到连接被关闭。
// 真实连接会在写截止时间到期时返回，这里把「等到截止时间」放大成「一直等」。
type stuckWriteConn struct {
	net.Conn
	stuck     atomic.Bool
	blocked   chan struct{} // 第一次卡住时关闭
	closed    chan struct{}
	blockOnce sync.Once
	closeOnce sync.Once
}

func (c *stuckWriteConn) Write(p []byte) (int, error) {
	if !c.stuck.Load() {
		return c.Conn.Write(p)
	}
	c.blockOnce.Do(func() { close(c.blocked) })
	<-c.closed
	return 0, net.ErrClosed
}

func (c *stuckWriteConn) Close() error {
	c.closeOnce.Do(func() { close(c.closed) })
	return c.Conn.Close()
}

// ping 卡在写里时，对端断开：ReadLoop 要立即返回，而不是等 ping 的写结束。
func TestStuckPingDoesNotBlockExit(t *testing.T) {
	drop := make(chan struct{})
	url := newServer(t, func(*websocket.Conn) { <-drop }) // 收到信号就直接断 TCP
	var wrapped *stuckWriteConn
	dialer := websocket.Dialer{NetDialContext: func(ctx context.Context, network, addr string) (net.Conn, error) {
		c, err := (&net.Dialer{}).DialContext(ctx, network, addr)
		if err != nil {
			return nil, err
		}
		wrapped = &stuckWriteConn{Conn: c, blocked: make(chan struct{}), closed: make(chan struct{})}
		return wrapped, nil
	}}
	conn, _, err := dialer.Dial(url, nil)
	if err != nil {
		t.Fatal(err)
	}
	wrapped.stuck.Store(true) // 握手完成后再让写卡住

	errc := run(context.Background(), conn, make(chan []byte), Options{PongWait: 10 * time.Second, PingPeriod: 20 * time.Millisecond})
	select {
	case <-wrapped.blocked:
	case <-time.After(time.Second):
		t.Fatal("ping 没有进入写")
	}
	close(drop)
	if err := wait(t, errc, time.Second); err == nil || errors.Is(err, ErrDeadPeer) {
		t.Fatalf("want 连接断开的错误, got %v", err)
	}
}

func TestOptionsNormalize(t *testing.T) {
	cases := []struct {
		name    string
		in      Options
		wantErr bool
	}{
		{"零值用默认", Options{}, false},
		{"极大 PongWait 不溢出", Options{PongWait: math.MaxInt64}, false},
		{"PingPeriod 等于 PongWait 时改用默认", Options{PongWait: time.Second, PingPeriod: time.Second}, false},
		{"负数 PingPeriod", Options{PongWait: time.Second, PingPeriod: -1}, false},
		{"负数 PongWait", Options{PongWait: -5}, false},
		{"10ns 还能留出余量", Options{PongWait: 10}, false},
		{"1ns 无解", Options{PongWait: 1}, true},
		{"2ns 无解", Options{PongWait: 2}, true},
	}
	for _, tc := range cases {
		t.Run(tc.name, func(t *testing.T) {
			got, err := tc.in.normalize()
			if tc.wantErr {
				if !errors.Is(err, ErrBadOptions) {
					t.Fatalf("want ErrBadOptions, got %v", err)
				}
				return
			}
			if err != nil {
				t.Fatal(err)
			}
			if !(0 < got.PingPeriod && got.PingPeriod < got.PongWait) || got.SendTimeout <= 0 {
				t.Fatalf("参数不满足约束：%+v", got)
			}
			time.NewTicker(got.PingPeriod).Stop() // 不能 panic
		})
	}
}

func TestNoGoroutineLeak(t *testing.T) {
	url := newServer(t, silentButAlive)
	before := runtime.NumGoroutine()

	for i := 0; i < 50; i++ {
		conn := dial(t, url)
		ctx, cancel := context.WithCancel(context.Background())
		errc := run(ctx, conn, make(chan []byte), Options{PingPeriod: time.Millisecond, PongWait: time.Second})
		cancel()
		wait(t, errc, time.Second)
	}

	// 服务端那一侧的 goroutine 也需要一点时间退出。
	deadline := time.Now().Add(2 * time.Second)
	for runtime.NumGoroutine() > before+2 && time.Now().Before(deadline) {
		time.Sleep(10 * time.Millisecond)
	}
	if n := runtime.NumGoroutine(); n > before+2 {
		t.Fatalf("goroutine 从 %d 涨到了 %d", before, n)
	}
}

各个用例对应的是正文里的一个结论：

用例 服务端表现 证明什么
TestCancelWhileBlockedInRead 只读不写 阻塞在读上时，取消能在 1 秒内让函数返回 context.Canceled
TestCancelWhileConsumerIsGone 发一条后沉默，客户端没人消费 卡在 channel 发送上时，取消同样有效
TestSlowConsumerWithoutCancel 发一条后沉默，客户端没人消费，也不取消 在 SendTimeout 后返回 ErrSlowConsumer，服务端看到连接被关闭
TestSlowButWithinLimitIsNotDeadPeer 隔 300 毫秒发两条 消费者每条都慢于 PongWait、但在 SendTimeout 之内时，不会被误判为对端已死
TestStuckPingDoesNotBlockExit 等 ping 卡在写里之后直接断开 TCP 退出时先关连接再等 ping，1 秒内返回
TestOptionsNormalize / TestBadOptionsClosesConn 无 / 只读不写 极端参数不溢出、不让 ticker panic；无解的参数返回 ErrBadOptions 并关连接
TestKeepaliveKeepsQuietConnectionOpen 只读不写 没有业务数据时，pong 在持续续期，连接不会被误判为死
TestDeadPeerIsDetected 不读也不写 收不到 pong 时，在 PongWait 后返回 ErrDeadPeer
TestNormalCloseReturnsNil 发一条后发正常关闭帧 正常关闭不当成错误，之前的数据不丢
TestNoGoroutineLeak 只读不写 50 次建连和取消之后，goroutine 数回到原来的水平
TestNaiveLoopIgnoresCancel 只读不写 朴素写法在取消后 300 毫秒仍未返回

运行：

go mod tidy
go vet ./...
go test -race -count=10 ./...

在 Go 1.24.7、linux/amd64、4 核 Intel Xeon 2.10GHz 的环境里，-race -count=10 全部通过。用例里的时间（50 毫秒、300 毫秒、1 秒等）只是给调度留余量，不是性能数字；在很慢的 CI 机器上如果偶发失败，先放宽这些等待时间。

其中三个用例是专门的回归测试，在旧写法上会失败：把收尾顺序改回 “先等 ping 再关连接”，TestStuckPingDoesNotBlockExit 超时失败；去掉 SendTimeout 分支，TestSlowConsumerWithoutCancel 超时失败；把续读截止时间挪回投递之前，TestSlowButWithinLimitIsNotDeadPeer 得到 ErrDeadPeer。

TestStuckPingDoesNotBlockExit 需要让 ping 稳定地卡在写里。真实环境里要填满 TCP 发送缓冲才能做到，既慢又不稳定。这里通过 Dialer.NetDialContext 换上一个包装过的 net.Conn：握手完成后，它的每次写都阻塞到连接被关闭为止。真实连接会在写截止时间到期时返回，这个包装把 “等到截止时间” 放大成了 “一直等”，旧写法因此会确定地挂住，而不是偶尔慢一点。

TestNoGoroutineLeak 允许比基线多 2 个，是给 httptest 服务端那一侧的连接 goroutine 留的余量。它们在客户端关连接后才会陆续退出，所以测试会轮询最多 2 秒。更严格的做法是用 go.uber.org/goleak，它会在测试结束时检查是否还有多余的 goroutine；这里为了示例零额外依赖，用了 runtime.NumGoroutine。

和其他做法比

换一个带 ctx 的库。 coder/websocket（原 nhooyr.io/websocket）的读方法直接接收 ctx，文档说 “The passed context will also bound the reader.”。看它 v1.8.15 的源码，conn.go 里的 setupReadTimeout 正是用 context.AfterFunc 在 ctx 结束时调用 c.close() 关掉整个连接。也就是说，它做的事和本文一样，只是替你封装好了。这带来一个容易忽视的后果：给一次读传一个带超时的 ctx，超时了关的是整条连接，不是只放弃这一次读。想要 “每条消息最多等 5 秒，等不到就继续等下一条” 的语义，这两个库都不提供，要在应用层用心跳或业务超时去表达。

周期性超时再检查 ctx。 比如每次读都设 1 秒截止时间，超时了就看一眼 ctx，没取消就继续读。对裸 net.Conn，只要你自己能处理读到一半的数据，这是可行的，代价是取消最多延迟 1 秒，外加空闲时每秒一次唤醒。对 gorilla/websocket 不可行：第一次超时后连接就坏了。

给订阅者一个单独的 Close channel。 有些 API 在 ctx 之外再给一个 Close channel，让调用方主动退订。两套机制都要接到每个阻塞点上，很容易漏掉一处。更省心的做法是在入口处把它们合成一个：用 context.WithCancel 派生一个 ctx，Close 时调用 cancel，内部只认 ctx。

什么都不做，依赖进程退出。 对命令行小工具无所谓，对长期运行的服务不行。每次退订泄漏一个 goroutine 和一个文件描述符，几天后就会以 “too many open files” 或内存缓慢上涨的形式出现，而且很难从现象倒推到这里。

小结

  • Go 不能从外面中断一个 goroutine。阻塞在网络读上的 goroutine，只能靠数据到达、截止时间到期或连接关闭来唤醒，ctx 必须被翻译成其中一种。
  • 对 gorilla/websocket，读超时后连接就不可再用，所以取消就是关连接。用 context.AfterFunc 做这件事，比手写看门 goroutine 少一个泄漏点；要严格收尾，记得 stop 不等回调结束。
  • 取消之后的读错误是副作用，先看 ctx.Err() 再分类，调用方才分得清 “我停的” 和 “它断的”。
  • 只靠取消不够。读截止时间加 ping/pong 续期，才能发现半开连接；pong 回调里写零值会让保活失效。
  • 每个可能阻塞的点都要能被唤醒：网络读靠关连接，channel 发送除了 select 上 ctx，还要有自己的超时，否则一个慢消费者会让读循环停下、保活跟着失效。
  • 收尾时先关连接、再等自己起的 goroutine 退出。它们可能正阻塞在这个连接上，反过来等，最坏要等满写截止时间。
