一条最常见的调用链：客户端调服务 A，超时 300 毫秒；A 先干 200 毫秒自己的活，再去调服务 B。客户端在 300 毫秒时放弃了，A 和 B 会怎样？

下面是后文示例在 Dubbo 3.3.7 上没有打开超时倒计时（场景 1）时的输出。为了排除重试的干扰，客户端调 A、A 调 B 的两个引用都显式设了 retries=0，其余是默认配置。client、front（A）、back（B）三个角色在同一个进程里，时间轴是同一个起点；-> 开头的行是 front 每次向 back 发起尝试：

== 1. 没开倒计时（两个引用都是 retries=0）：客户端 300ms 超时，front 干 200ms 再连调两次 back(400) ==
    0 ms  client 发出请求
    3 ms  front  开始，收到 _TO=null，没有倒计时
  204 ms  front  -> 发起对 back.work 的一次尝试
  212 ms  back   第 1 次执行 work(400)，收到 _TO=null，没有倒计时
  303 ms  client 放弃：TIMEOUT_EXCEPTION，尝试 1 次
  613 ms  back   第 1 次执行跑完
  618 ms  front  调下游成功，等了 414 ms
  618 ms  front  -> 发起对 back.work 的一次尝试
  621 ms  back   第 2 次执行 work(400)，收到 _TO=null，没有倒计时
 1022 ms  back   第 2 次执行跑完
 1026 ms  front  调下游成功，等了 407 ms
 1027 ms  front  返回，线程中断标志=false
WARN DefaultFuture -  [DUBBO] The timeout response finally returned at 2026-11-26 02:24:41.784, response status is 90
  back 一共执行了 2 次

客户端 303 毫秒放弃时，第一个 B 调用已经在 212 毫秒开始执行。它没有被打断，一直跑到 613 毫秒；A 等它回来以后，在 618 毫秒又发出第二个 B 调用，这时客户端早就不要结果了。A 一直干到 1027 毫秒，线程也没有被中断。更出乎意料的是，提供端一条超时日志都没有，唯一的告警出现在消费端，说一个超时的响应“终于回来了”。

很多人印象里，Dubbo 提供端有个 TimeoutFilter 会处理超时。它确实在，也确实默认启用，但在 3.3 里它做的事比想象中少得多：只在一种特定条件下打一行日志。这篇顺着一次调用把超时的来龙去脉理清楚：消费端怎么计时、超时怎么传到下一跳、提供端的 TimeoutFilter 到底做了什么，以及打开“超时倒计时”以后仍然存在的几个坑。

文中源码取自 apache/dubbo 的 3.3.7 标签（提交 481d41c，2026-10-26），写作时这是 Maven Central 上的最新版本。只讨论默认的 dubbo 协议，tri 协议用 grpc-timeout 头传超时，链路不同，这里不展开。Filter 链和默认重试的来历在上一篇 Dubbo 文章里讲过，这里直接用结论。

消费端的超时只管“我等多久”

消费端的超时值在 DubboInvoker.doInvoke 里确定，真正干活的是 RpcUtils.calculateTimeout：

// RpcUtils.java（3.3.7）
public static int calculateTimeout(URL url, Invocation invocation, String methodName, long defaultTimeout) {
    Object countdown = RpcContext.getClientAttachment().getObjectAttachment(TIME_COUNTDOWN_KEY);
    int timeout = (int) defaultTimeout;
    if (countdown == null) {
        if (url != null) {
            timeout = (int) RpcUtils.getTimeout(
                    url, methodName, RpcContext.getClientAttachment(), invocation, defaultTimeout);
            if (url.getMethodParameter(methodName, ENABLE_TIMEOUT_COUNTDOWN_KEY, false)) {
                // pass timeout to remote server
                invocation.setObjectAttachment(TIMEOUT_ATTACHMENT_KEY, timeout);
            }
        }
    } else {
        TimeoutCountDown timeoutCountDown = (TimeoutCountDown) countdown;
        timeout = (int) timeoutCountDown.timeRemaining(TimeUnit.MILLISECONDS);
        // pass timeout to remote server
        invocation.setObjectAttachment(TIMEOUT_ATTACHMENT_KEY, timeout);
    }

    invocation.getObjectAttachments().remove(TIME_COUNTDOWN_KEY);
    return timeout;
}

先看 countdown == null 这一支，也就是调用链的第一跳。超时值按这个顺序取：RpcContext.getClientAttachment() 里的 timeout（代码里临时给单次调用设超时就是走这里）、调用附件里的 timeout、URL 上方法级再到接口级的 timeout 参数，都没有就用默认的 1000 毫秒。

拿到这个数以后，DubboInvoker 把请求写出去，同时创建一个 DefaultFuture，按请求 id 放进一个全局 Map，并在一个时间轮上挂一个检查任务。这个时间轮的刻度是 30 毫秒：

// DefaultFuture.java（3.3.7）
private static final GlobalResourceInitializer<Timer> TIME_OUT_TIMER = new GlobalResourceInitializer<>(
        () -> new HashedWheelTimer(new NamedThreadFactory("dubbo-future-timeout", true), 30, TimeUnit.MILLISECONDS),
        DefaultFuture::destroy);

刻度决定了检查的粒度，但不是延迟的上界：除了刻度，线程调度、GC 停顿和时间轮线程处理到期任务本身都可能让超时触发得更晚。这次在本机测到的是 302、303 毫秒。到点后 DefaultFuture 以超时异常结束，调用方拿到 RpcException，错误码 TIMEOUT_EXCEPTION。

关键在于：这一切只发生在消费端。没有任何“取消”消息发给提供端。消费端只是不再等了，提供端那边该干什么还干什么。等提供端的响应真的回来，全局 Map 里已经找不到这个请求 id，解码时打出开头看到的那条 The timeout response finally returned，响应被丢掉。日志里的 status is 90 是消费端因为找不到原请求、解码失败给响应打上的 CLIENT_ERROR，不是提供端返回的状态。

还有一个容易误会的细节。DubboInvoker 每次都会把算出来的超时塞进请求附件：

invocation.setAttachment(TIMEOUT_KEY, String.valueOf(timeout));

看起来提供端是知道超时的。但提供端第一个 Filter ContextFilter 起倒计时只读 _TO（或小写的 _to），不看 timeout；这两个键还都在它“不往业务上下文里带”的名单上。_TO 只在上面代码的两个地方写入：要么方法上配了 enable-timeout-countdown=true（默认 false），要么当前已经处在一条倒计时链里。示例第 1 步两个条件都不满足，所以 front 和 back 都打印 收到 _TO=null。

提供端：ContextFilter 起表，TimeoutFilter 看表

提供端收到 _TO 后，ContextFilter（order 是 Integer.MIN_VALUE，最先执行）用它创建一个倒计时，放进服务端上下文：

// ContextFilter.java（3.3.7）
long timeout = RpcUtils.getTimeout(invocation, -1);   // 读 _TO，没有就是 -1
if (timeout != -1) {
    // pass to next hop
    RpcContext.getServerAttachment()
            .setObjectAttachment(
                    TIME_COUNTDOWN_KEY, TimeoutCountDown.newCountDown(timeout, TimeUnit.MILLISECONDS));
}

TimeoutCountDown 很简单：构造时记下 System.nanoTime() + timeout 作为截止点，之后 isExpired()、timeRemaining() 都拿当前的 nanoTime 和它比。注意它是一个相对时长，从提供端执行到这一行才开始计。这一点后面会变成一个坑。

然后是 TimeoutFilter，3.3.7 里它的全部逻辑（省略了 logger 字段，换行略有调整）：

// TimeoutFilter.java（3.3.7）
@Activate(group = CommonConstants.PROVIDER)
public class TimeoutFilter implements Filter, Filter.Listener {

    @Override
    public Result invoke(Invoker<?> invoker, Invocation invocation) throws RpcException {
        return invoker.invoke(invocation);
    }

    @Override
    public void onResponse(Result appResponse, Invoker<?> invoker, Invocation invocation) {
        Object obj = RpcContext.getServerAttachment().getObjectAttachment(TIME_COUNTDOWN_KEY);
        if (obj != null) {
            TimeoutCountDown countDown = (TimeoutCountDown) obj;
            if (countDown.isExpired()) {
                if (logger.isWarnEnabled()) {
                    logger.warn(PROXY_TIMEOUT_REQUEST, "", "",
                            "invoke timed out. method: " + RpcUtils.getMethodName(invocation) + " url is "
                                    + invoker.getUrl() + ", invoke elapsed " + countDown.elapsedMillis() + " ms.");
                }
            }
        }
    }

    @Override
    public void onError(Throwable t, Invoker<?> invoker, Invocation invocation) {}
}

invoke 原样放行。onResponse 在业务方法已经执行完之后才被调用，如果有倒计时且已过期，打一行 WARN。没有倒计时，什么也不做。它既不中断线程，也不改结果。这就是开头“提供端一条超时日志都没有”的原因：没开倒计时，TimeoutFilter 根本无事可做。

这个 Filter 在几个大版本里的行为并不一样，按各版本标签的源码：

版本 判断依据 超时后做什么
2.6.x、2.7.0 ~ 2.7.6 业务耗时和提供端 URL 上的 timeout 比 打日志
2.7.7 ~ 2.7.x 末版、3.0.x、3.1.0 ~ 3.1.6 倒计时（_TO） 清空结果 AppResponse.clear()，再打日志
3.1.7 起（含 3.2、3.3） 倒计时（_TO） 只打日志

中间那段版本里，过期的调用会把业务好不容易算出来的结果清掉，返回一个空响应；3.1.7 起去掉了这一步。另一个变化在判断依据上：从 2.7.6 及更早版本升上来的应用会发现提供端的超时告警“消失了”：以前只要提供端自己配了 timeout 就会比较，现在必须由消费端发来 _TO。

为什么不干脆中断业务线程？源码里没有写理由，下面是我的理解。Thread.interrupt() 只在 sleep、wait、可中断 IO 这些阻塞点上起作用，一个在做 CPU 计算或者在不可中断 IO 上阻塞的线程根本不理它。反过来，在 NIO 通道上阻塞的线程被中断，通道会被直接关掉（ClosedByInterruptException），如果那是连接池里的一条连接，伤的是后续请求。更根本的是，框架不知道业务做到了哪一步：数据库已经写了一半、消息已经发出去，这时候打断只会留下更难收拾的中间状态。所以 Dubbo 选择不替业务做“停下来”这个决定，只负责把“还剩多少时间”告诉业务。

打开倒计时：预算一跳一跳往下传

把消费端的方法配成 enable-timeout-countdown=true，再跑同样的调用：

== 2. 开了倒计时：同样的调用 ==
    0 ms  client 发出请求
    3 ms  front  开始，收到 _TO=300，倒计时还剩 299 ms
  204 ms  front  -> 发起对 back.work 的一次尝试
  207 ms  back   第 1 次执行 work(400)，收到 _TO=98，倒计时还剩 97 ms
  302 ms  client 放弃：TIMEOUT_EXCEPTION，尝试 1 次
  304 ms  front  调下游失败，等了 100 ms，TIMEOUT_EXCEPTION，尝试 1 次
  308 ms  front  调下游失败，等了 3 ms，TIMEOUT_TERMINATE（No time left，未发请求）
  308 ms  front  返回，线程中断标志=false
WARN TimeoutFilter -  [DUBBO] invoke timed out. method: withBudget url is dubbo://…/demo.Front?…, invoke elapsed 306 ms.
WARN DefaultFuture -  [DUBBO] The timeout response finally returned at 2026-11-26 02:24:42.870, response status is 90
  608 ms  back   第 1 次执行跑完
WARN TimeoutFilter -  [DUBBO] invoke timed out. method: work url is dubbo://…/demo.Back?…, invoke elapsed 401 ms.
WARN DefaultFuture -  [DUBBO] The timeout response finally returned at 2026-11-26 02:24:43.171, response status is 90
  back 一共执行了 1 次

逐行看发生了什么：

  1. 客户端发出 _TO=300，front 收到后起表，开始时还剩 299 毫秒。
  2. front 干完 200 毫秒的活去调 back。这次 back 收到的是 _TO=98：front 这一跳的超时不再是引用上配的 1000 毫秒，而是倒计时的余额。这就是 calculateTimeout 的 else 分支。
  3. front 等了 100 毫秒就放弃了 back，几乎和客户端同时。
  4. front 第二次调 back，几毫秒就失败了，错误码 TIMEOUT_TERMINATE，请求根本没有发出去，back 只执行了 1 次。
  5. 两个 TimeoutFilter 都打了日志：front 用了 306 毫秒，back 用了 401 毫秒。

第 2 步和第 4 步来自消费端的 ConsumerContextFilter。它是一个 ClusterFilter，在选址和重试之外，每次调用执行一次：

// ConsumerContextFilter.java（3.3.7）
Object countDown = RpcContext.getServerAttachment().getObjectAttachment(TIME_COUNTDOWN_KEY);
if (countDown != null) {
    String methodName = RpcUtils.getMethodName(invocation);
    // When the client has enabled the timeout-countdown function,
    // the subsequent calls launched by the Server side will be enabled by default,
    // and support to turn off the function on a node to get rid of the timeout control.
    if (invoker.getUrl().getMethodParameter(methodName, ENABLE_TIMEOUT_COUNTDOWN_KEY, true)) {
        context.setObjectAttachment(TIME_COUNTDOWN_KEY, countDown);

        TimeoutCountDown timeoutCountDown = (TimeoutCountDown) countDown;
        if (timeoutCountDown.isExpired()) {
            return AsyncRpcResult.newDefaultAsyncResult(
                    new RpcException(
                            RpcException.TIMEOUT_TERMINATE,
                            "No time left for making the following call: " + invocation.getServiceName() + "."
                                    + RpcUtils.getMethodName(invocation) + ", terminate directly."),
                    invocation);
        }
    }
}

它从服务端上下文里取出本次请求带来的倒计时，放进客户端上下文，后面的 calculateTimeout 就会用余额作为超时，并把余额作为新的 _TO 继续往下传。如果已经过期，直接返回失败，连网络都不碰。DubboInvoker 里还有一道同样的检查（算出来的超时 <= 0 就终止）。注意这里开关的默认值是 true：链路第一跳要显式打开，之后的每一跳默认跟随，想在某一跳摆脱它需要显式写 false。

顺带一提重试。示例里的 back 另外暴露了一个 retried 方法，front 引用它时在方法级配了 retries=2（MethodConfig.setRetries(2)，见完整示例里 Main.java 的 backRef），其他和第 2 步一样。为了看清重试循环转了几圈，示例注册了一个普通的消费端 Filter（AttemptFilter），它在重试循环之内，每次尝试打一行 ->：

== 2b. 开了倒计时，front 调的 back.retried 配了 retries=2 ==
    0 ms  client 发出请求
    2 ms  front  开始，收到 _TO=300，倒计时还剩 299 ms
  203 ms  front  -> 发起对 back.retried 的一次尝试
  206 ms  back   第 1 次执行 retried(400)，收到 _TO=98，倒计时还剩 97 ms
  302 ms  client 放弃：TIMEOUT_EXCEPTION，尝试 1 次
  303 ms  front  -> 发起对 back.retried 的一次尝试
  304 ms  front  调下游失败，等了 101 ms，code=0（No time left，未发请求）
WARN TimeoutFilter -  [DUBBO] invoke timed out. method: retriedWithBudget url is dubbo://…/demo.Front?…, invoke elapsed 302 ms.
  607 ms  back   第 1 次执行跑完
WARN TimeoutFilter -  [DUBBO] invoke timed out. method: retried url is dubbo://…/demo.Back?…, invoke elapsed 401 ms.
WARN DefaultFuture -  [DUBBO] The timeout response finally returned at 2026-11-26 02:24:44.473, response status is 90
  back 一共执行了 1 次

要分开看两件事。重试循环本身还在执行：303 毫秒出现了第二行 ->，FailoverClusterInvoker 确实发起了第二次尝试。但这次尝试在 DubboInvoker 里发现余额已经不够，没有往网络上写请求，back 只执行了 1 次；也没有第三次尝试。从源码看，DubboInvoker 把这种终止包成一个带异常的结果返回，而 FailoverClusterInvoker 只在捕获到异常时才换下一次尝试，所以循环在第二次就结束了。异常也和单次调用不一样：front 最后拿到的错误码是 0（UNKNOWN_EXCEPTION），原因链里是 No time left，消息里没有 Tried N times，所以 isTimeout() 是 false。按错误码判断超时的代码，在开了倒计时的链路上要把 TIMEOUT_TERMINATE（8）和这种情况一起考虑。我没有逐行追这里错误码的来路，以上是 3.3.7 上的实测结果。

这种短路只对链路的后续跳有效。第一跳的消费端手里没有倒计时，走的是 countdown == null 分支，每次重试都重新用满配置的超时、重新发一个满额的 _TO。上一篇里第一跳最坏要等 (retries + 1) × timeout 的说法依然成立；不过这是 RPC 等待预算的估算，不是严格的墙钟上限，选址、重试之间的处理和上面说的计时器延迟都会再加一点。

还要看清倒计时没有改变什么：back 收到的预算只有 98 毫秒，它照样把 400 毫秒睡完，608 毫秒才结束，TimeoutFilter 也只是在结束后补一句日志。倒计时让链路上还没开始的调用不再白跑，但已经在跑的那一跳照旧跑完。想让它也提前收手，得业务自己来，后文会讲。

开了倒计时之后的三个坑

坑一：上游的预算会盖过下游自己的超时

front 调 back 的 quick 方法，引用上专门给它配了 100 毫秒超时，可能是因为这个依赖偶尔会卡，宁可快速失败走降级。back 这次要执行 400 毫秒，客户端给 front 的超时是 3000 毫秒。

== 3a. 没开倒计时：客户端 3000ms，front 调 back.quick(400)，quick 自己配了 100ms ==
    0 ms  client 发出请求
    2 ms  front  开始，收到 _TO=null，没有倒计时
    3 ms  front  -> 发起对 back.quick 的一次尝试
    5 ms  back   第 1 次执行 quick(400)，收到 _TO=null，没有倒计时
  104 ms  front  调下游失败，等了 101 ms，TIMEOUT_EXCEPTION，尝试 1 次
  106 ms  client 拿到结果 front-degraded
  405 ms  back   第 1 次执行跑完
WARN DefaultFuture -  [DUBBO] The timeout response finally returned at 2026-11-26 02:24:45.574, response status is 90
  back 一共执行了 1 次

没开倒计时（3a），100 毫秒的配置生效，front 很快走了降级。开了倒计时（3b），back 收到 _TO=2998，front 老老实实等了 405 毫秒：引用上配的 100 毫秒被完全忽略了。回去看 calculateTimeout，else 分支里只有余额，没有和 URL 上的配置取较小值。

也就是说，倒计时语义是“上游说还剩多少就等多少”，不是“不超过上游剩余时间”。下游为保护自己而配的短超时，在上游预算宽松时会悄悄失效。想保住它，只能在这个方法上关掉倒计时：

== 3c. 开了倒计时，但 front 调的是 back.capped(400)：100ms，并在这个方法上关掉倒计时 ==
    0 ms  client 发出请求
    3 ms  front  开始，收到 _TO=3000，倒计时还剩 2999 ms
    3 ms  front  -> 发起对 back.capped 的一次尝试
    5 ms  back   第 1 次执行 capped(400)，收到 _TO=null，没有倒计时
  104 ms  front  调下游失败，等了 101 ms，TIMEOUT_EXCEPTION，尝试 1 次
  107 ms  client 拿到结果 front-degraded
  405 ms  back   第 1 次执行跑完
WARN DefaultFuture -  [DUBBO] The timeout response finally returned at 2026-11-26 02:24:47.701, response status is 90
  back 一共执行了 1 次

capped 方法配了 enable-timeout-countdown=false，100 毫秒又回来了。代价是倒计时在这一跳断开：back 收到 _TO=null，它再往下的调用又回到各自的配置。这是一个只能二选一的开关，没有“取两者较小值”的选项。

坑二：表是在提供端拿到线程之后才开始走的

TimeoutCountDown 是相对时长，在提供端的 ContextFilter 里才开始计。请求在网络上传输、在提供端线程池队列里排队的时间，都不会从预算里扣掉。下面把 front 的业务线程数设成 1、队列设成 10，客户端同时发两个各要 250 毫秒的请求：

== 4. 排队的时间不算数：front 只有 1 个线程，客户端同时发两个 step(250) ==
    1 ms  client1 发出请求
    1 ms  client2 发出请求
    3 ms  front  开始处理，此时消费端已经等了 2 ms，收到 _TO=300，倒计时还剩 299 ms
  254 ms  front  处理完
  255 ms  front  开始处理，此时消费端已经等了 253 ms，收到 _TO=300，倒计时还剩 299 ms
  256 ms  client1 拿到结果 step-ok
  303 ms  client2 放弃：TIMEOUT_EXCEPTION，尝试 1 次
  505 ms  front  处理完
WARN DefaultFuture -  [DUBBO] The timeout response finally returned at 2026-11-26 02:24:48.708, response status is 90

第二个请求在队列里等了 253 毫秒才拿到线程，此时客户端只剩不到 50 毫秒，但 front 看到的倒计时仍然是满的 299 毫秒。它又干了 250 毫秒，客户端早在 303 毫秒时就放弃了。更糟的是，这次调用在 front 自己的倒计时里只用了 250 毫秒左右，没有过期，TimeoutFilter 连日志都不打。提供端监控看起来一切正常，客户端看到的却是超时。

传相对时长而不是绝对截止时间，是一个有道理的取舍：绝对时间依赖各台机器的时钟一致，时钟偏差几十毫秒就能让预算整个失真；相对时长只用本机的单调时钟（nanoTime），不受时钟同步影响。gRPC 的 grpc-timeout 头也是相对时长。代价就是传输和排队时间被“偷”走了。应对办法只能是留余量，以及盯住提供端线程池的排队情况。线程池满或排队长的时候，倒计时给出的余额是偏乐观的。

坑三：换个线程，倒计时就丢了

倒计时放在 RpcContext 的服务端上下文里，而 RpcContext 是线程本地变量。业务代码一旦把下游调用挪到另一个线程池里，比如用 CompletableFuture.supplyAsync 并行调几个服务，那个线程里就没有倒计时：

== 5a. 开了倒计时，但 front 换到业务线程池去调 back(400) ==
    0 ms  client 发出请求
    2 ms  front  开始，收到 _TO=300，倒计时还剩 299 ms
  206 ms  front  -> 发起对 back.work 的一次尝试
  208 ms  back   第 1 次执行 work(400)，收到 _TO=null，没有倒计时
  302 ms  client 放弃：TIMEOUT_EXCEPTION，尝试 1 次
  609 ms  back   第 1 次执行跑完
  611 ms  front  调下游成功，等了 405 ms
WARN TimeoutFilter -  [DUBBO] invoke timed out. method: hop url is dubbo://…/demo.Front?…, invoke elapsed 609 ms.
WARN DefaultFuture -  [DUBBO] The timeout response finally returned at 2026-11-26 02:24:49.619, response status is 90
  back 一共执行了 1 次

back 收到 _TO=null，front 用引用上的 1000 毫秒去等，一直等到 back 跑完。

Dubbo 自己的异步提供端写法会把上下文带过去：RpcContext.startAsync() 在调用的那一刻保存当前线程的 RpcContext，新线程里调 signalContextSwitch() 恢复，倒计时也在其中。这种写法要保证响应一定被结束：任务提交被线程池拒绝、或者任务里任何一步抛异常，都要用失败结束它，否则客户端只能等到超时。3.3.7 的 AsyncContext.write 收到一个 Throwable 就以失败结束，所以可以这样写：

AsyncContext ctx = RpcContext.startAsync();    // 保存当前线程的 RpcContext
Runnable task = () -> {
    Object result;
    try {
        ctx.signalContextSwitch();              // 在新线程里恢复，倒计时也跟着过来
        result = back.work(400);
    } catch (Throwable t) {
        result = t;                             // 失败也要交回去
    }
    try {
        ctx.write(result);                      // 只调一次，write 自己抛异常也不重写
    } finally {
        ctx.resetContext();                     // 清掉工作线程上恢复的上下文
    }
};
try {
    pool.execute(task);
} catch (RejectedExecutionException e) {
    ctx.write(e);                               // 任务不会跑了，在当前线程以失败结束
}
return null;                                    // 方法本身的返回值不再使用
== 5b. 同上，用 RpcContext.startAsync() 把上下文带过去 ==
    0 ms  client 发出请求
    2 ms  front  开始，收到 _TO=300，倒计时还剩 299 ms
  204 ms  front  -> 发起对 back.work 的一次尝试
  207 ms  back   第 1 次执行 work(400)，收到 _TO=97，倒计时还剩 96 ms
  301 ms  client 放弃：TIMEOUT_EXCEPTION，尝试 1 次
  303 ms  front  调下游失败，等了 98 ms，TIMEOUT_EXCEPTION，尝试 1 次
WARN TimeoutFilter -  [DUBBO] invoke timed out. method: hopAsync url is dubbo://…/demo.Front?…, invoke elapsed 301 ms.
  608 ms  back   第 1 次执行跑完
WARN TimeoutFilter -  [DUBBO] invoke timed out. method: work url is dubbo://…/demo.Back?…, invoke elapsed 401 ms.
WARN DefaultFuture -  [DUBBO] The timeout response finally returned at 2026-11-26 02:24:50.719, response status is 90
  back 一共执行了 1 次

预算回来了。结果和计算放在 try 里、write 放在外面，是为了让“算结果失败”和“交结果失败”分开：前者以失败结束响应，后者说明响应已经结束或者通道出了问题，不应该再写第二次。

如果不想改成异步提供端，也可以在原线程里先取出 TimeoutCountDown，到新线程里把余额设成那一次调用的 timeout。这里有两个容易漏的地方。第一，先判断余额够不够：已经用完了就别再发请求，直接降级（示例里的判断是 <= 0，实际可以换成下游最少需要的时间）。第二，RpcContext.getClientAttachment() 也是线程本地的，线程池的线程会被复用，设进去的值不清掉，就会被这个线程上的下一次调用拿去当超时，而那时它早已过期。所以要在 finally 里还原：

TimeoutCountDown cd = (TimeoutCountDown) RpcContext.getServerAttachment()
        .getObjectAttachment("timeout-countdown");   // 在原线程里取
// ……下面在新线程里执行
if (cd == null) {
    return back.work(400);                      // 没有预算，按引用自己的配置
}
long left = cd.timeRemaining(MILLISECONDS);
if (left <= 0) {
    return "front-degraded";                   // 余额不够，不发请求
}
RpcContextAttachment attachment = RpcContext.getClientAttachment();
Object previous = attachment.getObjectAttachment("timeout");
attachment.setObjectAttachment("timeout", (int) Math.min(left, Integer.MAX_VALUE));
try {
    return back.work(400);
} finally {
    if (previous == null) {
        attachment.removeAttachment("timeout");
    } else {
        attachment.setObjectAttachment("timeout", previous);
    }
}
== 5c. 同上，手动把余额设成那次调用的 timeout ==
    0 ms  client 发出请求
    3 ms  front  开始，收到 _TO=300，倒计时还剩 299 ms
  204 ms  front  -> 发起对 back.work 的一次尝试
  207 ms  back   第 1 次执行 work(400)，收到 _TO=null，没有倒计时
  302 ms  client 放弃：TIMEOUT_EXCEPTION，尝试 1 次
  304 ms  front  调下游失败，等了 99 ms，TIMEOUT_EXCEPTION，尝试 1 次
WARN TimeoutFilter -  [DUBBO] invoke timed out. method: hopManual url is dubbo://…/demo.Front?…, invoke elapsed 301 ms.
  607 ms  back   第 1 次执行跑完
WARN DefaultFuture -  [DUBBO] The timeout response finally returned at 2026-11-26 02:24:51.822, response status is 90
  back 一共执行了 1 次

front 这一跳只等了 99 毫秒，但 back 收到的是 _TO=null：这种做法只限住这一跳的等待，不会产生 _TO，倒计时不会继续往下传，除非那个引用自己也打开了 enable-timeout-countdown。

让业务自己看表

倒计时真正有用的地方，是业务代码可以读到它，自己决定什么时候收手。front 有 10 项活要干，每项 50 毫秒，客户端只给 300 毫秒。每干一项之前看一眼余额，不够再干一项就把已经做完的部分先返回：

TimeoutCountDown cd = (TimeoutCountDown) RpcContext.getServerAttachment()
        .getObjectAttachment("timeout-countdown");
for (int i = 0; i < items; i++) {
    // 留 30ms 余量给回包和调度延迟；这是本例的经验值，不是上界
    if (cd != null && cd.timeRemaining(MILLISECONDS) < perItemMs + 30) {
        return "partial " + done + "/" + items;
    }
    doOneItem();
    done++;
}
== 6. front 自己看预算：10 项活、每项 50ms，客户端 300ms ==
    0 ms  client 发出请求
    2 ms  front  开始，收到 _TO=300，倒计时还剩 299 ms
  254 ms  front  只剩 48 ms，不够再做一项，先把做完的 5 项返回
  260 ms  client 拿到结果 partial 5/10
  back 一共执行了 0 次

客户端在 260 毫秒拿到了一个部分结果，而不是在 300 毫秒拿到超时异常。数据库查询、批量处理、循环调下游，都可以用同样的思路把余额换算成自己的上限。

两点提醒。timeout-countdown 这个键名和 TimeoutCountDown 类都在 Dubbo 的公开包里，但官方没有把它们写成稳定的业务 API，最好包成一个自己的工具方法，升级时只改一处。另外 cd 可能是 null：消费端没开倒计时、或者经过了一次线程切换，都拿不到它，代码要能在没有预算的情况下照常工作。

完整示例

一个 Maven 工程，七个 Java 文件加一个扩展配置文件，在 JDK 21 上用 Maven 3.9 跑过，maven.compiler.release 设为 17，JDK 17 及以上都可以。不需要注册中心，三个角色在同一个进程里，front 和 back 各占一个端口，客户端用 127.0.0.1 直连。

请在隔离的网络里运行。 客户端连的是回环地址，但这不限制提供端监听在哪。Dubbo 3.3.7 的 NetUtils.isInvalidLocalHost 把 127. 开头的地址当成无效的绑定地址，AbstractServer 遇到它就改成监听 0.0.0.0；ProtocolConfig.setHost("127.0.0.1") 和 -DDUBBO_IP_TO_BIND=127.0.0.1 都绕不过去（后者会直接报错）。我在容器里跑的时候，两个端口确实都监听在 0.0.0.0。所以请在没有外部网络的容器里跑（例如 docker run --network none，回环在容器内照样可用），或者确认所在机器的防火墙不放行这两个随机端口。运行时可以用 lsof -nP -iTCP -sTCP:LISTEN（Linux 和 macOS 都有）核对实际监听地址。

FrontImpl.java：

package demo;

import static java.util.concurrent.TimeUnit.MILLISECONDS;

import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.RejectedExecutionException;

import org.apache.dubbo.rpc.AsyncContext;
import org.apache.dubbo.rpc.RpcContext;
import org.apache.dubbo.rpc.RpcContextAttachment;
import org.apache.dubbo.rpc.RpcException;
import org.apache.dubbo.rpc.TimeoutCountDown;

public class FrontImpl implements Front {
    static volatile Back back; // 启动后注入
    private static final ExecutorService POOL = Executors.newCachedThreadPool(r -> {
        Thread t = new Thread(r, "biz-pool");
        t.setDaemon(true);
        return t;
    });

    @Override
    public String noBudget(int workMs, int backMs) {
        return twoCalls(workMs, backMs);
    }

    @Override
    public String withBudget(int workMs, int backMs) {
        return twoCalls(workMs, backMs);
    }

    @Override
    public String retriedWithBudget(int workMs, int backMs) {
        T.log("front", "开始，%s", T.seen());
        T.sleep(workMs);
        long t0 = System.nanoTime();
        try {
            back.retried(backMs);
            T.log("front", "调下游成功，等了 %d ms", (System.nanoTime() - t0) / 1_000_000);
        } catch (RpcException e) {
            T.log("front", "调下游失败，等了 %d ms，%s", (System.nanoTime() - t0) / 1_000_000, T.describe(e));
        }
        return "front-ok";
    }

    // 先干 workMs 的活，再连着调两次下游
    private String twoCalls(int workMs, int backMs) {
        T.log("front", "开始，%s", T.seen());
        T.sleep(workMs);
        callBack(false, backMs);
        callBack(false, backMs);
        T.log("front", "返回，线程中断标志=%s", Thread.currentThread().isInterrupted());
        return "front-ok";
    }

    @Override
    public String quickNoBudget(int backMs) {
        T.log("front", "开始，%s", T.seen());
        return callBack(true, backMs);
    }

    @Override
    public String quickWithBudget(int backMs) {
        T.log("front", "开始，%s", T.seen());
        return callBack(true, backMs);
    }

    @Override
    public String cappedWithBudget(int backMs) {
        T.log("front", "开始，%s", T.seen());
        long t0 = System.nanoTime();
        try {
            String r = back.capped(backMs);
            T.log("front", "调下游成功，等了 %d ms", (System.nanoTime() - t0) / 1_000_000);
            return r;
        } catch (RpcException e) {
            T.log("front", "调下游失败，等了 %d ms，%s", (System.nanoTime() - t0) / 1_000_000, T.describe(e));
            return "front-degraded";
        }
    }

    @Override
    public String step(int ms, long sentAtNanos) {
        long waited = (System.nanoTime() - sentAtNanos) / 1_000_000;
        T.log("front", "开始处理，此时消费端已经等了 %d ms，%s", waited, T.seen());
        T.sleep(ms);
        T.log("front", "处理完");
        return "step-ok";
    }

    @Override
    public String hop(int workMs, int backMs) {
        T.log("front", "开始，%s", T.seen());
        T.sleep(workMs);
        // 换到业务线程池里调下游：RpcContext 是线程本地的，倒计时留在了原线程
        return CompletableFuture.supplyAsync(() -> callBack(false, backMs), POOL).join();
    }

    @Override
    public String hopAsync(int workMs, int backMs) {
        T.log("front", "开始，%s", T.seen());
        T.sleep(workMs);
        AsyncContext ctx = RpcContext.startAsync(); // 这一刻把当前线程的 RpcContext 存下来
        Runnable task = () -> {
            Object result;
            try {
                ctx.signalContextSwitch();         // 在新线程里恢复，倒计时也跟着过来
                result = callBack(false, backMs);
            } catch (Throwable t) {
                result = t;                        // write 收到异常就以失败结束
            }
            try {
                ctx.write(result);                 // 只写一次；write 自己抛异常也不再重写
            } finally {
                ctx.resetContext();                // 清掉工作线程上恢复的上下文
            }
        };
        try {
            POOL.execute(task);
        } catch (RejectedExecutionException e) {
            ctx.write(e);                          // 提交被拒，任务不会跑，在当前线程结束响应
        }
        return null; // 真正的返回值由 ctx.write 给出
    }

    @Override
    public String hopManual(int workMs, int backMs) {
        T.log("front", "开始，%s", T.seen());
        T.sleep(workMs);
        TimeoutCountDown cd = T.countdown();       // 在原线程里取出倒计时
        return CompletableFuture.supplyAsync(() -> callWithBudget(cd, backMs), POOL).join();
    }

    // 用倒计时余额给这一次调用单独设超时，用完把线程上的附件恢复原样
    private String callWithBudget(TimeoutCountDown cd, int backMs) {
        if (cd == null) {
            return callBack(false, backMs);        // 没有预算，按引用自己的配置
        }
        long left = cd.timeRemaining(MILLISECONDS);
        if (left <= 0) {
            T.log("front", "余额 %d ms，不再调下游", left);
            return "front-degraded";
        }
        RpcContextAttachment attachment = RpcContext.getClientAttachment();
        Object previous = attachment.getObjectAttachment("timeout");
        attachment.setObjectAttachment("timeout", (int) Math.min(left, Integer.MAX_VALUE));
        try {
            return callBack(false, backMs);
        } finally {
            if (previous == null) {
                attachment.removeAttachment("timeout");
            } else {
                attachment.setObjectAttachment("timeout", previous);
            }
        }
    }

    @Override
    public String batch(int items, int perItemMs) {
        TimeoutCountDown cd = T.countdown();
        T.log("front", "开始，%s", T.seen());
        int done = 0;
        for (int i = 0; i < items; i++) {
            // 留 30ms 余量给回包和调度延迟；这是本例的经验值，不是上界
            if (cd != null && cd.timeRemaining(MILLISECONDS) < perItemMs + 30) {
                T.log("front", "只剩 %d ms，不够再做一项，先把做完的 %d 项返回", cd.timeRemaining(MILLISECONDS), done);
                return "partial " + done + "/" + items;
            }
            T.sleep(perItemMs);
            done++;
        }
        return "all " + done + "/" + items;
    }

    private String callBack(boolean quick, int ms) {
        long t0 = System.nanoTime();
        try {
            String r = quick ? back.quick(ms) : back.work(ms);
            T.log("front", "调下游成功，等了 %d ms", (System.nanoTime() - t0) / 1_000_000);
            return r;
        } catch (RpcException e) {
            T.log("front", "调下游失败，等了 %d ms，%s", (System.nanoTime() - t0) / 1_000_000, T.describe(e));
            return "front-degraded";
        }
    }
}

package demo;

import java.util.concurrent.atomic.AtomicInteger;

public class BackImpl implements Back {
    static final AtomicInteger RUNS = new AtomicInteger();

    @Override
    public String work(int ms) {
        return run("work", ms);
    }

    @Override
    public String quick(int ms) {
        return run("quick", ms);
    }

    @Override
    public String capped(int ms) {
        return run("capped", ms);
    }

    @Override
    public String retried(int ms) {
        return run("retried", ms);
    }

    private String run(String name, int ms) {
        int n = RUNS.incrementAndGet();
        T.log("back", "第 %d 次执行 %s(%d)，%s", n, name, ms, T.seen());
        T.sleep(ms);
        T.log("back", "第 %d 次执行跑完", n);
        return "back-ok";
    }
}

import static java.util.concurrent.TimeUnit.MILLISECONDS;

/** 时间线打印和几个小工具。所有角色在同一个进程里，共用一个起点。 */
final class T {
    private static volatile long epoch = System.nanoTime();
    static volatile boolean muted; // 预热时不打印

    static void reset() {
        epoch = System.nanoTime();
    }

    static long now() {
        return (System.nanoTime() - epoch) / 1_000_000;
    }

    static void log(String who, String fmt, Object... args) {
        if (muted) {
            return;
        }
        System.out.printf("%5d ms  %-6s %s%n", now(), who, String.format(fmt, args));
    }

    /** 提供端 ContextFilter 根据 _TO 放进服务端上下文的倒计时，没有就是 null。 */
    static TimeoutCountDown countdown() {
        return (TimeoutCountDown) RpcContext.getServerAttachment().getObjectAttachment("timeout-countdown");
    }

    /** 当前这次服务端调用收到了什么：_TO 附件和倒计时余额。 */
    static String seen() {
        Invocation inv = RpcContext.getServiceContext().getInvocation();
        Object to = inv == null ? null : inv.getObjectAttachment("_TO");
        TimeoutCountDown cd = countdown();
        return "收到 _TO=" + to + (cd == null ? "，没有倒计时" : "，倒计时还剩 " + cd.timeRemaining(MILLISECONDS) + " ms");
    }

    static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            log("", "!! 线程被中断");
            Thread.currentThread().interrupt();
        }
    }

    static String describe(RpcException e) {
        String code = switch (e.getCode()) {
            case RpcException.TIMEOUT_EXCEPTION -> "TIMEOUT_EXCEPTION";
            case RpcException.TIMEOUT_TERMINATE -> "TIMEOUT_TERMINATE";
            default -> "code=" + e.getCode();
        };
        String msg = String.valueOf(e.getMessage());
        StringBuilder sb = new StringBuilder(code);
        String tried = between(msg, "Tried ", " times");      // 集群层包装过的异常带着尝试次数
        if (tried != null) {
            sb.append("，尝试 ").append(tried).append(" 次");
        }
        String used = between(msg, "timeout: ", " ms");       // 等待超时的异常里带着这次用的超时值
        if (used != null) {
            sb.append("（本次超时 ").append(used).append(" ms）");
        } else if (msg.contains("No time left")) {             // 没时间了，请求没有发出
            sb.append("（No time left，未发请求）");
        }
        return sb.toString();
    }

    // 找不到分隔符就返回 null，不让日志处理本身抛异常
    private static String between(String s, String start, String end) {
        int i = s.indexOf(start);
        if (i < 0) {
            return null;
        }
        int j = s.indexOf(end, i + start.length());
        return j < 0 ? null : s.substring(i + start.length(), j);
    }

    private T() {}
}

AttemptFilter.java，每次尝试打一行，用来看重试循环转了几圈：

package demo;

import org.apache.dubbo.common.constants.CommonConstants;
import org.apache.dubbo.common.extension.Activate;
import org.apache.dubbo.rpc.Filter;
import org.apache.dubbo.rpc.Invocation;
import org.apache.dubbo.rpc.Invoker;
import org.apache.dubbo.rpc.Result;
import org.apache.dubbo.rpc.RpcException;

/** 普通消费端 Filter 在重试循环之内，每次尝试都会经过；只打印 front 调 back 的尝试。 */
@Activate(group = CommonConstants.CONSUMER)
public class AttemptFilter implements Filter {
    @Override
    public Result invoke(Invoker<?> invoker, Invocation invocation) throws RpcException {
        if (invoker.getInterface() == Back.class) {
            T.log("front", "-> 发起对 back.%s 的一次尝试", invocation.getMethodName());
        }
        return invoker.invoke(invocation);
    }
}

package demo;

import java.net.ServerSocket;
import java.util.List;
import java.util.Map;
import java.util.concurrent.CompletableFuture;
import java.util.function.Supplier;

import org.apache.dubbo.config.ApplicationConfig;
import org.apache.dubbo.config.MethodConfig;
import org.apache.dubbo.config.ProtocolConfig;
import org.apache.dubbo.config.ReferenceConfig;
import org.apache.dubbo.config.RegistryConfig;
import org.apache.dubbo.config.ServiceConfig;
import org.apache.dubbo.config.bootstrap.DubboBootstrap;
import org.apache.dubbo.rpc.RpcException;

public class Main {
    public static void main(String[] args) throws Exception {
        // 只放出两类日志：提供端 TimeoutFilter 的告警，和消费端"超时的响应终于回来了"的告警
        System.setProperty("org.slf4j.simpleLogger.logFile", "System.out");
        System.setProperty("org.slf4j.simpleLogger.defaultLogLevel", "off");
        System.setProperty("org.slf4j.simpleLogger.showThreadName", "false");
        System.setProperty("org.slf4j.simpleLogger.showShortLogName", "true");
        System.setProperty("org.slf4j.simpleLogger.log.org.apache.dubbo.rpc.filter.TimeoutFilter", "warn");
        System.setProperty("org.slf4j.simpleLogger.log.org.apache.dubbo.remoting.exchange.support.DefaultFuture", "warn");
        System.setProperty("dubbo.application.logger", "slf4j");

        // front 一个端口、只有 1 个业务线程（排队实验要用），back 另一个端口。
        // 注意：Dubbo 会把 127.x 当成无效的绑定地址，改为监听 0.0.0.0，所以请在隔离的网络里运行。
        ProtocolConfig frontProto = new ProtocolConfig("dubbo", freePort());
        frontProto.setId("front-proto");
        frontProto.setThreads(1);
        frontProto.setQueues(10);
        ProtocolConfig backProto = new ProtocolConfig("dubbo", freePort());
        backProto.setId("back-proto");

        ServiceConfig<Front> frontService = new ServiceConfig<>();
        frontService.setInterface(Front.class);
        frontService.setRef(new FrontImpl());
        frontService.setProtocol(frontProto);
        ServiceConfig<Back> backService = new ServiceConfig<>();
        backService.setInterface(Back.class);
        backService.setRef(new BackImpl());
        backService.setProtocol(backProto);

        // front 调 back 的引用：work 1000ms 超时，quick 100ms 超时，都不重试
        ReferenceConfig<Back> backRef = new ReferenceConfig<>();
        backRef.setInterface(Back.class);
        backRef.setUrl("dubbo://127.0.0.1:" + backProto.getPort());
        backRef.setTimeout(1000);
        backRef.setRetries(0);
        MethodConfig retried = method("retried", 1000, null);
        retried.setRetries(2);
        backRef.setMethods(List.of(method("quick", 100, null), method("capped", 100, "false"), retried));

        // 客户端调 front 的引用：默认 300ms 超时、不重试、开倒计时；个别方法单独配
        ReferenceConfig<Front> frontRef = new ReferenceConfig<>();
        frontRef.setInterface(Front.class);
        frontRef.setUrl("dubbo://127.0.0.1:" + frontProto.getPort());
        frontRef.setTimeout(300);
        frontRef.setRetries(0);
        frontRef.setParameters(Map.of("enable-timeout-countdown", "true"));
        frontRef.setMethods(List.of(
                method("noBudget", null, "false"),
                method("quickNoBudget", 3000, "false"),
                method("quickWithBudget", 3000, null),
                method("cappedWithBudget", 3000, null)));

        ApplicationConfig app = new ApplicationConfig("deadline-demo");
        app.setQosEnable(false);
        DubboBootstrap bootstrap = DubboBootstrap.getInstance()
                .application(app)
                .registry(new RegistryConfig(RegistryConfig.NO_AVAILABLE))
                .protocols(List.of(frontProto, backProto))
                .services(List.of(frontService, backService))
                .references(List.of(backRef, frontRef))
                .start();
        FrontImpl.back = backRef.get();
        Front front = frontRef.get();
        T.muted = true;
        front.step(0, System.nanoTime()); // 预热连接，不计入
        Thread.sleep(300);
        T.muted = false;

        System.out.println("\n== 1. 没开倒计时（两个引用都是 retries=0）：客户端 300ms 超时，front 干 200ms 再连调两次 back(400) ==");
        run(() -> front.noBudget(200, 400), 1500);

        System.out.println("\n== 2. 开了倒计时：同样的调用 ==");
        run(() -> front.withBudget(200, 400), 1000);
        System.out.println("\n== 2b. 开了倒计时，front 调的 back.retried 配了 retries=2 ==");
        run(() -> front.retriedWithBudget(200, 400), 1000);

        System.out.println("\n== 3a. 没开倒计时：客户端 3000ms，front 调 back.quick(400)，quick 自己配了 100ms ==");
        run(() -> front.quickNoBudget(400), 800);
        System.out.println("\n== 3b. 开了倒计时：同上 ==");
        run(() -> front.quickWithBudget(400), 800);
        System.out.println("\n== 3c. 开了倒计时，但 front 调的是 back.capped(400)：100ms，并在这个方法上关掉倒计时 ==");
        run(() -> front.cappedWithBudget(400), 800);

        System.out.println("\n== 4. 排队的时间不算数：front 只有 1 个线程，客户端同时发两个 step(250) ==");
        BackImpl.RUNS.set(0);
        T.reset();
        CompletableFuture<Void> a = CompletableFuture.runAsync(() -> call("client1", () -> front.step(250, System.nanoTime())));
        CompletableFuture<Void> b = CompletableFuture.runAsync(() -> call("client2", () -> front.step(250, System.nanoTime())));
        CompletableFuture.allOf(a, b).join();
        Thread.sleep(500);

        System.out.println("\n== 5a. 开了倒计时，但 front 换到业务线程池去调 back(400) ==");
        run(() -> front.hop(200, 400), 800);
        System.out.println("\n== 5b. 同上，用 RpcContext.startAsync() 把上下文带过去 ==");
        run(() -> front.hopAsync(200, 400), 800);
        System.out.println("\n== 5c. 同上，手动把余额设成那次调用的 timeout ==");
        run(() -> front.hopManual(200, 400), 800);

        System.out.println("\n== 6. front 自己看预算：10 项活、每项 50ms，客户端 300ms ==");
        run(() -> front.batch(10, 50), 600);

        bootstrap.stop();
    }

    private static void run(Supplier<String> s, long settleMs) throws InterruptedException {
        BackImpl.RUNS.set(0);
        T.reset();
        call("client", s);
        Thread.sleep(settleMs); // 等提供端把活干完，时间线才完整
        System.out.println("  back 一共执行了 " + BackImpl.RUNS.get() + " 次");
    }

    private static void call(String who, Supplier<String> s) {
        T.log(who, "发出请求");
        try {
            T.log(who, "拿到结果 %s", s.get());
        } catch (RpcException e) {
            T.log(who, "放弃：%s", T.describe(e));
        }
    }

    private static MethodConfig method(String name, Integer timeout, String countdown) {
        MethodConfig m = new MethodConfig();
        m.setName(name);
        if (timeout != null) {
            m.setTimeout(timeout);
        }
        if (countdown != null) {
            m.setParameters(Map.of("enable-timeout-countdown", countdown));
        }
        return m;
    }

    private static int freePort() throws Exception {
        try (ServerSocket s = new ServerSocket(0)) {
            return s.getLocalPort();
        }
    }
}

小结

  • 消费端的超时只决定“我等多久”。到点后消费端单方面放弃，不会通知提供端，提供端照常执行，结果回来时被丢弃。
  • 提供端的 TimeoutFilter 从 3.1.7 起只做一件事：业务执行完之后，如果倒计时已过期，打一行 WARN。没有倒计时它什么也不做，所以默认配置下提供端看不到任何超时日志。
  • 倒计时要在链路第一跳的消费端用 enable-timeout-countdown=true 打开，之后每一跳默认跟随。它让后续的下游调用用余额当超时，余额用完直接终止、不发请求，后续跳的重试也随之短路。
  • 倒计时不会打断已经在跑的那一跳；它的余额会盖过下游引用上自己配的更短超时；它从提供端拿到线程才开始计，排队时间不算；换线程会丢失，要用 RpcContext.startAsync() 或手动带过去。
  • 真正让提供端少干无用功的，是业务代码自己读倒计时、在合适的位置收手。
