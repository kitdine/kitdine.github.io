Sentinel 1.8 的一次 entry：Slot 链做判断，两格滑动窗口记账

给一个资源配上“每秒最多 10 次”的限流规则，然后做个小实验：在某一刻连打 15 次，隔 535 毫秒再连打 15 次。按字面理解，一秒之内最多放行 10 次，结果却是两波各放行 10 次，0.5 秒多一点放过了 20 个请求。

再配一条“异常比例超过 50% 就熔断”的规则，让业务代码每次都抛异常，并且在 catch 里老老实实调了 Tracer.traceEntry。20 次请求全部失败，熔断器一次都没打开。

两个结果都可以稳定复现，代码在文末。它们都不是 bug，而是 Sentinel 两个核心设计的直接后果：每个资源一条 Slot 责任链，规则判断在 entry 时做，统计有一部分在 exit 时才记；限流看的是资源节点上默认只有两格的滑动窗口，熔断器则各自另记一份单桶的统计。这篇顺着一次 SphU.entry 读下去，把这两件事讲清楚。

源码取自 alibaba/Sentinel 的 1.8.10 标签（提交于 2026-05-21），这是写作时 Maven Central 上 sentinel-core 的最新稳定版。仓库里另有一个 2023 年 2 月发布的 2.0.0-alpha 预览版，本文不涉及。

资源、Entry，和第一次调用时才发生的初始化

Sentinel 里被保护的东西叫资源，就是一个字符串名字。一次受保护的调用是一对 entry 和 exit：

Entry entry = null;
try {
    entry = SphU.entry("createOrder");   // 被拒绝时抛 BlockException 的子类
    // 业务逻辑
} catch (BlockException e) {
    // 被限流、熔断、系统保护或授权规则拦下
} finally {
    if (entry != null) {
        entry.exit();
    }
}

Sentinel 没有显式的启动方法。SphU.entry 第一次被调用时会访问 Env.sph，触发 Env 的静态初始化：

public class Env {

    public static final Sph sph = new CtSph();

    static {
        // If init fails, the process will exit.
        InitExecutor.doInit();
    }

}

InitExecutor.doInit() 用 CAS 保证只跑一次，通过 SPI 加载所有 InitFunc 并按顺序执行。接了控制台的应用，命令中心（默认端口 8719）和心跳都是在这里启动的。所以一个刚启动、还没有流量的应用，在控制台里是看不到的。这是用 Sentinel 最常见的困惑之一，不是配置错了。

每个资源一条 Slot 链

CtSph#entryWithPriority 拿到当前线程的 Context（没有就进一个名叫 sentinel_default_context 的默认上下文），然后为资源找它的处理链：

// CtSph#lookProcessChain，1.8.10
ProcessorSlotChain chain = chainMap.get(resourceWrapper);
if (chain == null) {
    synchronized (LOCK) {
        chain = chainMap.get(resourceWrapper);
        if (chain == null) {
            // Entry size limit.
            if (chainMap.size() >= Constants.MAX_SLOT_CHAIN_SIZE) {
                return null;
            }
            chain = SlotChainProvider.newSlotChain();
            Map<ResourceWrapper, ProcessorSlotChain> newMap = new HashMap<ResourceWrapper, ProcessorSlotChain>(
                chainMap.size() + 1);
            newMap.putAll(chainMap);
            newMap.put(resourceWrapper, chain);
            chainMap = newMap;
        }
    }
}
return chain;

读路径完全无锁，只有第一次见到一个资源时才加锁，并且用“复制一份新 Map 再替换引用”的方式写入。代价是每新增一个资源都要复制整张表，所以资源的数量是有上限的：MAX_SLOT_CHAIN_SIZE 是 6000。超过之后 lookProcessChain 返回 null，entryWithPriority 看到 null 就直接放行，不做任何规则检查，也不报错。

这一点要特别小心。如果资源名里拼进了用户 ID、订单号或者完整 URL，资源数会一直涨，涨过 6000 以后的新资源静默地不受保护。Sentinel 在这里的原则是“自己出问题时一律放行”，保护组件不能成为故障点，但前提是你知道它放行了。

链的内容由 META-INF/services 里登记的 ProcessorSlot 按 @Spi(order) 排出来。示例的第一步把一条新链从头走到尾打印出来，sentinel-core 1.8.10 里是 9 个：

order Slot 做什么
-10000 NodeSelectorSlot 按 Context 名为资源建 DefaultNode，搭出调用树
-9000 ClusterBuilderSlot 建资源级的 ClusterNode，以及按来源区分的 origin 节点
-8000 LogSlot 记录被拦下的请求
-7000 StatisticSlot 先让后面的 Slot 判断，再按结果计数
-6000 AuthoritySlot 来源黑白名单
-5000 SystemSlot 系统自适应保护，只管入口流量
-2000 FlowSlot 流量控制
-1500 DefaultCircuitBreakerSlot 资源没配熔断规则时，按全局默认规则熔断（1.8.7 起）
-1000 DegradeSlot 熔断降级

引入 sentinel-parameter-flow-control 后还会多一个 order 为 -3000 的 ParamFlowSlot，做热点参数限流。要加自己的 Slot，继承 AbstractLinkedProcessorSlot、标上 @Spi(order = ...)、登记到同一个 services 文件即可。

整条链分成两段：前面的 Slot 负责“建节点、记账”，后面的 Slot 负责“拿账本做判断”。两段的交界处是 StatisticSlot。

StatisticSlot：先放行，后计数

StatisticSlot 排在所有规则 Slot 前面，但它做的第一件事是把请求交给后面：

// StatisticSlot#entry（节选），1.8.10
try {
    // Do some checking.
    fireEntry(context, resourceWrapper, node, count, prioritized, args);

    // Request passed, add thread count and pass count.
    node.increaseThreadNum();
    node.addPassRequest(count);
    // ……origin 节点、全局入口节点同样计数，再触发 onPass 回调
} catch (PriorityWaitException ex) {
    node.increaseThreadNum();
    // ……
} catch (BlockException e) {
    // Blocked, set block exception to current entry.
    context.getCurEntry().setBlockError(e);

    // Add block count.
    node.increaseBlockQps(count);
    // ……
    throw e;
}

fireEntry 返回或抛异常时，后面所有规则都已经判完了，所以 StatisticSlot 一个位置就能知道这个请求是通过还是被拦，分别记到“通过数”或“拦截数”上。反过来，规则 Slot 读到的永远是本次请求之前的统计：FlowSlot 判断时，当前这个请求还没被算进 QPS 里。

响应时间和成功数在 exit 时记。这里要分清两个“方向”：entry.exit() 退出的是 Entry 调用栈（嵌套的 entry 要从里往外逐个 exit），而在一个 Entry 内部，CtEntry 仍然从链头调 chain.exit，每个 Slot 的 exit 做完自己的事再用 fireExit 交给 next.exit，方向和 entry 时一样是往后传。StatisticSlot#exit 先算出 RT、加成功数、减线程数，再往后传；排在它后面的熔断 Slot 随后在 exit 里更新自己的统计，这一点后面会用到。

两套节点：资源 × 入口，和资源总量

node.addPassRequest 里的 node 是 NodeSelectorSlot 建的 DefaultNode。Sentinel 为同一个资源维护了好几份统计：

节点 维度 谁在用
DefaultNode 资源 × Context 名 链路限流（STRATEGY_CHAIN）
ClusterNode 资源 默认的限流看它（熔断器不看，见后文）
origin 节点 资源 × 调用来源 按来源限流（规则的 limitApp 写具体应用名时）
Constants.ENTRY_NODE 全局入口流量 系统自适应保护

同一个资源从两个入口进来，会有两个 DefaultNode，它们共享一个 ClusterNode。DefaultNode#addPassRequest 在给自己计数的同时也加到 ClusterNode 上。

这些节点都继承自 StatisticNode，统计最终都落在它持有的两个滑动窗口里。

LeapArray：一个按时间取模的环形数组

StatisticNode 里有两个窗口：

// StatisticNode，1.8.10
private transient volatile Metric rollingCounterInSecond = new ArrayMetric(SampleCountProperty.SAMPLE_COUNT,
    IntervalProperty.INTERVAL);
private transient Metric rollingCounterInMinute = new ArrayMetric(60, 60 * 1000, false);

秒级窗口默认 1000 毫秒、2 个桶，每桶 500 毫秒，QPS 限流读的就是它。分钟级窗口 60 个桶、每桶 1 秒，给指标日志和控制台的实时监控用。熔断器不读这两个窗口，它们有自己的统计，放到熔断一节再说。

窗口本身是 LeapArray：一个固定长度的 AtomicReferenceArray<WindowWrap<T>>，每个元素是一个桶，记着桶的起始时间和桶里的数据（MetricBucket，内部是一组 LongAdder，按通过、拦截、异常、成功、RT 等事件分别计数）。找当前桶的逻辑是整个统计的核心：

// LeapArray#currentWindow，1.8.10（注释为笔者所加）
int idx = calculateTimeIdx(timeMillis);              // (time / 桶宽) % 桶数
long windowStart = calculateWindowStart(timeMillis); // time - time % 桶宽

while (true) {
    WindowWrap<T> old = array.get(idx);
    if (old == null) {
        // 1. 这个位置还没有桶：CAS 放一个新的，失败就让出 CPU 再试
        WindowWrap<T> window = new WindowWrap<T>(windowLengthInMs, windowStart, newEmptyBucket(timeMillis));
        if (array.compareAndSet(idx, null, window)) {
            return window;
        } else {
            Thread.yield();
        }
    } else if (windowStart == old.windowStart()) {
        // 2. 正是当前桶：直接返回，绝大多数请求走这里，没有锁
        return old;
    } else if (windowStart > old.windowStart()) {
        // 3. 这个位置上是一圈之前的旧桶：抢到锁的线程原地重置，抢不到的让出 CPU
        if (updateLock.tryLock()) {
            try {
                return resetWindowTo(old, windowStart);
            } finally {
                updateLock.unlock();
            }
        } else {
            Thread.yield();
        }
    } else if (windowStart < old.windowStart()) {
        // 4. 时间倒退（比如时钟回拨）：给一个不进数组的临时桶
        return new WindowWrap<T>(windowLengthInMs, windowStart, newEmptyBucket(timeMillis));
    }
}

几个值得学的地方：

  • 惰性清理。 过期的桶不会被后台线程清零，而是下一个落到同一位置的请求顺手重置。桶对象从头到尾复用，热路径上不分配内存，也不需要定时任务。
  • 锁只在换桶时出现，而且不阻塞。 用 tryLock，抢不到就 yield 后重试，重试时多半已经命中分支 2。
  • 计数用 LongAdder。 高并发写会分散到多个 Cell 上，避免所有线程 CAS 同一个 AtomicLong。

读的时候，values() 遍历整个数组，跳过“已经落后一整个窗口”的桶：

public boolean isWindowDeprecated(long time, WindowWrap<T> windowWrap) {
    return time - windowWrap.windowStart() > intervalInMs;
}

QPS 就是剩下这些桶的通过数之和除以窗口秒数。DefaultController（默认的“快速失败”效果）拿它加上本次申请数，和阈值比：

// DefaultController#canPass（节选）
int curCount = avgUsedTokens(node);   // QPS 模式下就是 (int) node.passQps()
if (curCount + acquireCount > count) {
    // ……优先级请求可以借用下一个桶的配额，这里略
    return false;
}
return true;

只有两个桶，窗口其实时长时短

开头那 20 个请求，就出在 isWindowDeprecated 和“只有两个桶”的组合上。

设桶宽 500 毫秒，某个桶从时刻 0 开始。在 470 毫秒时打第一波，它们落在桶 [0, 500) 里，放行 10 个，后 5 个被拦。之后：

  • 在 605 毫秒打第二波（间隔 135 毫秒）。当前桶是 [500, 1000)，另一个桶是 [0, 500)，605 - 0 = 605，没有超过 1000，仍然有效。窗口里已有 10 个，第二波全部被拦。
  • 在 1005 毫秒打第二波（间隔 535 毫秒）。当前桶是 [1000, 1500)，它和 [0, 500) 是数组里的同一个位置，旧桶被重置；另一个桶 [500, 1000) 是空的。窗口里是 0，第二波再放行 10 个。

也就是说，在时刻 t，两格窗口实际统计的是“上一个桶的起点到 t”这段时间，长度在 500 到 1000 毫秒之间来回变。第一波请求如果恰好打在一个桶的末尾，它只会被记住 500 多毫秒。最坏情况下，0.5 秒多一点的时间里可以通过两倍阈值的请求。

示例第二步就是这个实验，换成 10 个桶（每桶 100 毫秒）再跑一遍做对照，连跑三次结果相同：

== 2. 阈值 10 QPS，两波突发 ==
   2 个桶，间隔 135 ms：第一波放行 10，第二波放行  0，合计 10
   2 个桶，间隔 535 ms：第一波放行 10，第二波放行 10，合计 20
  10 个桶，间隔 535 ms：第一波放行 10，第二波放行  0，合计 10
  10 个桶，间隔 935 ms：第一波放行 10，第二波放行 10，合计 20

10 个桶时，窗口长度在 900 到 1000 毫秒之间，边界误差缩小到一个桶宽，但没有消失：间隔 935 毫秒时同样放过了 20 个。滑动窗口计数法本来就是近似，桶数只决定近似得有多粗。

为什么默认只用两个桶？这是在性能和精度之间的取舍。每次判断都要遍历整个数组求和，桶越多，每个请求的开销越大；而一个限流组件放在每次调用的热路径上，这点开销会被放大成全站的开销。对于“挡住持续的过载”这个主要目标，两个桶足够；它挡不住的，是阈值附近、跨桶边界的短时突发。

如果这种突发对你很重要，有两条路：

  1. 调大桶数。 SampleCountProperty.updateSampleCount(n)，n 必须能整除 1000。这是全局设置，会重置所有 ClusterNode 的统计，而且对每个资源都增加了求和的开销。它只改节点上的秒级窗口，熔断器的统计窗口不受影响。
  2. 换控制效果。 把规则的 controlBehavior 设为匀速排队（CONTROL_BEHAVIOR_RATE_LIMITER，实现类是 ThrottlingController）。它不看窗口里的计数，而是按 1000 / 阈值 毫秒的固定间隔放行，排不上的等待，等太久的拒绝。适合“能等、怕突发”的场景，比如消费消息。

熔断只在 exit 时记账

再看开头的第二个现象。熔断器在 entry 时检查状态，CLOSED 直接放行；OPEN 时如果重试计时已到，就在这次 entry 上把状态切到 HALF_OPEN，放这一个请求过去探测：

// AbstractCircuitBreaker#tryPass，1.8.10
if (currentState.get() == State.CLOSED) {
    return true;
}
if (currentState.get() == State.OPEN) {
    // For half-open state we allow a request for probing.
    return retryTimeoutArrived() && fromOpenToHalfOpen(context);
}
return false;

这次请求成功还是失败、要不要因此打开或关闭熔断，则要等请求结束：DegradeSlot#exit 对每个熔断器调 onRequestComplete，记下结果，再按结果决定后续状态：

// ExceptionCircuitBreaker#onRequestComplete，1.8.10
Entry entry = context.getCurEntry();
if (entry == null) {
    return;
}
Throwable error = entry.getError();
SimpleErrorCounter counter = stat.currentWindow().value();
if (error != null) {
    counter.getErrorCount().add(1);
}
counter.getTotalCount().add(1);

handleStateChangeWhenThresholdExceeded(error);

先注意 stat：它不是资源的 ClusterNode，而是这个熔断器自己的 LeapArray。ExceptionCircuitBreaker 和 ResponseTimeCircuitBreaker 的构造器都是这样建统计的：

// ExceptionCircuitBreaker，1.8.10；ResponseTimeCircuitBreaker 同理
public ExceptionCircuitBreaker(DegradeRule rule) {
    this(rule, new SimpleErrorCounterLeapArray(1, rule.getStatIntervalMs()));
}

每条熔断规则一份，只有 1 个桶，桶宽就是规则的 statIntervalMs（默认 1000 毫秒）。所以熔断的统计和限流是两套：前面调大 SampleCountProperty 的桶数，只改变 QPS 限流看到的窗口，不会让熔断器的统计变平滑；想改熔断的统计时长，改的是规则上的 statIntervalMs。单桶也意味着它是固定窗口：时间每跨过一个 statIntervalMs 的整数倍，计数就整体清零，不会像两格窗口那样还带着上一个桶。

再看判断本身。它判断“这次失败没有”，只看 entry.getError()。业务代码抛出的异常 Sentinel 是看不见的，必须有人在 exit 之前把异常记到 Entry 上，这就是 Tracer.traceEntry(t, entry) 的作用。框架适配器（Dubbo、Spring MVC 等）和 @SentinelResource 切面会替你做这件事，手写 SphU.entry 时要自己做。

问题在于顺序。Java 的 try-with-resources 会在执行 catch 块之前关闭资源，而 Entry 实现了 AutoCloseable，close() 就是 exit()。于是这样写：

try (Entry entry = SphU.entry(resource)) {
    callDownstream();
} catch (BlockException ex) {
    // 被拦
} catch (Exception ex) {
    Tracer.traceEntry(ex, entry);   // 太晚了：entry 已经 exit 过了
}

catch 运行时熔断器已经把这次请求记成了“成功”，traceEntry 写进去的异常没有人再读。示例第三步对比了三种写法，规则是“10 秒内至少 5 个请求、异常比例超过 50% 就熔断 10 秒”：

== 3. 异常比例熔断：不调 Tracer 会怎样 ==
  no-trace 20 次请求全部抛异常：业务代码执行 20 次，被熔断 0 次
  traced   20 次请求全部抛异常：业务代码执行 5 次，被熔断 15 次
  twr      20 次请求全部抛异常：业务代码执行 20 次，被熔断 0 次

只有在 finally 里手动 exit、并在此之前调 Tracer 的写法（traced）真正触发了熔断：前 5 次凑够最小请求数、异常比例 100%，第 5 次结束时熔断器打开，后 15 次直接被拒。想用 try-with-resources，就把 Tracer.traceEntry 放进 try 块内部，在异常抛出前调用。

熔断打开后，过了 timeWindow，下一个请求会把状态从 OPEN 切到 HALF_OPEN，作为探测请求放行。这里有个细节：探测请求可能被链上后面的其他规则拦下，那样它永远不会正常结束，熔断器就会一直卡在半开。1.8.10 的 fromOpenToHalfOpen 用 entry.whenTerminate 挂了个钩子处理这种情况，源码注释里写明是 issue #1638 的临时解法：

entry.whenTerminate(new BiConsumer<Context, Entry>() {
    @Override
    public void accept(Context context, Entry entry) {
        if (entry.getBlockError() != null) {
            // Fallback to OPEN due to detecting request is blocked
            currentState.compareAndSet(State.HALF_OPEN, State.OPEN);
            notifyObservers(State.HALF_OPEN, State.OPEN, 1.0d);
        }
    }
});

完整示例

只依赖 sentinel-core，不需要控制台。在 JDK 21 上用 Maven 3.9 跑过，maven.compiler.release 设为 17。Sentinel 默认把日志写到用户目录下的 logs/csp/，启动时会在终端打几行 INFO，不影响结果。

package demo;

import java.util.List;

import com.alibaba.csp.sentinel.Entry;
import com.alibaba.csp.sentinel.SphU;
import com.alibaba.csp.sentinel.Tracer;
import com.alibaba.csp.sentinel.node.SampleCountProperty;
import com.alibaba.csp.sentinel.slotchain.AbstractLinkedProcessorSlot;
import com.alibaba.csp.sentinel.slotchain.SlotChainProvider;
import com.alibaba.csp.sentinel.slots.block.BlockException;
import com.alibaba.csp.sentinel.slots.block.RuleConstant;
import com.alibaba.csp.sentinel.slots.block.degrade.DegradeRule;
import com.alibaba.csp.sentinel.slots.block.degrade.DegradeRuleManager;
import com.alibaba.csp.sentinel.slots.block.flow.FlowRule;
import com.alibaba.csp.sentinel.slots.block.flow.FlowRuleManager;

public class Main {
    public static void main(String[] args) throws Exception {
        System.out.println("== 1. 每个资源一条的 Slot 链，按顺序 ==");
        for (AbstractLinkedProcessorSlot<?> s = SlotChainProvider.newSlotChain().getNext(); s != null; s = s.getNext()) {
            System.out.println("  " + s.getClass().getSimpleName());
        }

        System.out.println("\n== 2. 阈值 10 QPS，两波突发 ==");
        burst("w2-135", 2, 135);   // 默认：1 秒窗口切 2 个桶
        burst("w2-535", 2, 535);
        burst("w10-535", 10, 535); // 同样 1 秒窗口切 10 个桶
        burst("w10-935", 10, 935);

        System.out.println("\n== 3. 异常比例熔断：不调 Tracer 会怎样 ==");
        errors("no-trace", false);
        errors("traced", true);
        errorsWithResources("twr");
    }

    // 第一波打在某个 500ms 段结束前 30ms，隔 gapMs 再打第二波，每波 15 个
    static void burst(String resource, int sampleCount, long gapMs) throws Exception {
        SampleCountProperty.updateSampleCount(sampleCount);
        FlowRule rule = new FlowRule(resource).setGrade(RuleConstant.FLOW_GRADE_QPS).setCount(10);
        FlowRuleManager.loadRules(List.of(rule));

        long t0 = sleepUntilPhase(500, 470);
        int first = fire(resource, 15);
        Thread.sleep(Math.max(0, t0 + gapMs - System.currentTimeMillis()));
        int second = fire(resource, 15);
        System.out.printf("  %2d 个桶，间隔 %d ms：第一波放行 %2d，第二波放行 %2d，合计 %2d%n",
                sampleCount, gapMs, first, second, first + second);
    }

    static int fire(String resource, int n) {
        int passed = 0;
        for (int i = 0; i < n; i++) {
            try (Entry e = SphU.entry(resource)) {
                passed++;
            } catch (BlockException ex) {
                // 被限流
            }
        }
        return passed;
    }

    // 睡到 System.currentTimeMillis() % period == phase 的时刻
    static long sleepUntilPhase(long period, long phase) throws InterruptedException {
        long now = System.currentTimeMillis();
        long target = now - now % period + phase;
        if (target <= now + 5) target += period;
        Thread.sleep(target - now);
        while (System.currentTimeMillis() < target) Thread.onSpinWait();
        return System.currentTimeMillis();
    }

    static void loadRatioRule(String resource) {
        DegradeRule rule = new DegradeRule(resource)
                .setGrade(RuleConstant.DEGRADE_GRADE_EXCEPTION_RATIO)
                .setCount(0.5)            // 异常比例超过 50%
                .setMinRequestAmount(5)
                .setStatIntervalMs(10_000)
                .setTimeWindow(10);       // 熔断 10 秒
        DegradeRuleManager.loadRules(List.of(rule));
    }

    static void errors(String resource, boolean trace) {
        loadRatioRule(resource);
        int calls = 0, blocked = 0;
        for (int i = 0; i < 20; i++) {
            Entry entry = null;
            try {
                entry = SphU.entry(resource);
                calls++;
                throw new IllegalStateException("下游挂了");
            } catch (BlockException ex) {
                blocked++;
            } catch (IllegalStateException ex) {
                if (trace) Tracer.traceEntry(ex, entry);
            } finally {
                if (entry != null) entry.exit();
            }
        }
        System.out.printf("  %-8s 20 次请求全部抛异常：业务代码执行 %d 次，被熔断 %d 次%n", resource, calls, blocked);
    }

    // try-with-resources 写法：catch 运行时 entry 已经 exit 了，Tracer 记不进去
    static void errorsWithResources(String resource) {
        loadRatioRule(resource);
        int calls = 0, blocked = 0;
        for (int i = 0; i < 20; i++) {
            Entry outer = null;
            try (Entry entry = SphU.entry(resource)) {
                outer = entry;
                calls++;
                throw new IllegalStateException("下游挂了");
            } catch (BlockException ex) {
                blocked++;
            } catch (IllegalStateException ex) {
                Tracer.traceEntry(ex, outer);
            }
        }
        System.out.printf("  %-8s 20 次请求全部抛异常：业务代码执行 %d 次，被熔断 %d 次%n", resource, calls, blocked);
    }
}

运行：

mvn -q compile exec:java

第二步依赖墙上时钟对齐桶边界：第一波的 15 个请求要在 30 毫秒内打完，第二波要准时开始。在负载很高的机器上，个别轮次可能偏一个桶，多跑几次即可。

小结

  • Sentinel 在第一次 SphU.entry 时才初始化，没流量的应用在控制台里看不到。
  • 每个资源一条 Slot 链，创建时复制整张表，上限 6000 个资源；超过后新资源直接放行、不报错。资源名里不要拼动态的 ID。
  • StatisticSlot 先把请求交给后面的规则，再按结果计数。规则看到的永远是本次请求之前的统计。
  • 秒级统计是 2 个桶的环形数组，惰性重置、无锁读、LongAdder 计数。代价是窗口实际长度在 500 到 1000 毫秒之间变化，跨桶边界时 0.5 秒多一点就能放过两倍阈值。要更平滑，调大桶数或改用匀速排队。
  • 熔断器不读资源节点的窗口，每条规则有自己的单桶统计，长度是规则的 statIntervalMs，调桶数影响不到它。它在 exit 时才统计，只认 entry.getError()。手写 SphU.entry 时必须在 exit 之前调 Tracer.traceEntry；try-with-resources 的 catch 已经在 exit 之后了。
