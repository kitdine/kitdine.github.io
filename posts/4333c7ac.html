存密码哈希时，很多人会把迭代次数写成代码里的一个常量。过两年想调高，才发现库里几万条记录都是按旧参数算的：只改常量，老用户全都登录不上；不改，安全参数就永远停在当年。

这个问题的解法很小，只有两件事：把参数和哈希写在同一个字符串里，以及在用户登录成功时按新参数重新派生。但真要落地，格式怎么定、旧记录怎么解析、升级写回时会不会踩到并发和回滚，都有讲究。这篇用 Go 1.24 起标准库自带的 crypto/pbkdf2 写一个完整可运行的小包，把这些细节一次讲清楚。

为什么要把参数写进哈希串

PBKDF2 的结果取决于四样东西：密码、盐、迭代次数、输出长度。少了任何一样，同一个密码就算不出同一个结果。参数如果只存在代码里，就会遇到三个问题：

  • 没法渐进升级。 校验只能用“当前”的参数，旧记录全部失效，只能停机批量迁移。可数据库里只有哈希、没有明文，批量迁移根本做不到。
  • 没法混存多种算法。 将来想从 PBKDF2 换到 Argon2id，过渡期两种记录会同时存在，代码必须知道每一条是怎么算的。
  • 记录不能自证。 拿到一条记录，你说不清它是哪一年、按什么参数生成的，也没法统计“还有多少用户停在弱参数上”。

把参数写进字符串，每条记录就自带说明书。这不是新发明：bcrypt 的 $2b$12$... 里，12 就是成本因子，所以 bcrypt 天生可以升级。PBKDF2 只是一个函数，没有规定存储格式，这一步得自己做。

格式怎么设计

我参照 PHC 字符串格式，它是密码哈希竞赛（Argon2 就是在这次竞赛中胜出的）之后整理出来的通用规范：

$pbkdf2-sha256$i=600000$<盐>$<密钥>

几个设计点：

  • 开头的算法名就是版本号。 换算法时只换这一段，比如 Argon2id 的记录长这样：$argon2id$v=19$m=19456,t=2,p=1$<盐>$<密钥>。校验代码先看算法名再分支。
  • 参数写成 名=值。 以后加参数（比如换成 SHA-512 时要区分）不会和旧格式冲突，读的人也一眼能看懂。
  • 盐和密钥用不带 = 填充的标准 base64。 $ 不在 base64 字母表里，所以拿它分隔不会有歧义。
  • 数字只有一种写法。 PHC 要求十进制不带符号、没有前导零。Go 的 strconv.Atoi 会接受 +600000 和 0600000，同一个值就有了多种写法，所以下面的代码自己解析。
  • 写入和解析共用一组边界。 迭代次数必须在 1000（RFC 8018 建议的下限）到一千万之间，写入时越界直接报错，解析时越界当作损坏。哈希串来自数据库，数据库也可能被误写或被篡改；没有上限的话，一条 i=2000000000 的记录就能让一次登录卡上几分钟。两边共用同一个检查函数，代码就写不出自己读不了的记录。反过来，它也会拒绝范围外的历史记录，比如早年按 500 次迭代存下的，上线前要先盘点，后文“回滚”一节会讲。
  • 新记录用 16 字节盐，旧记录放宽到 8 字节。 8 字节是 RFC 8018 的最低建议，放宽只是为了兼容历史数据，这些记录在下次登录时会被换成 16 字节盐。这个放宽和 FIPS 模式冲突，后面单独说。

完整代码

整个包一百多行，放进任意目录加一个 go.mod（go 1.24 或更新）就能编译：

// Package pwhash 用 PBKDF2-HMAC-SHA256 存储密码，参数和哈希写在同一个字符串里。
package pwhash

import (
	"crypto/pbkdf2"
	"crypto/rand"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/base64"
	"errors"
	"fmt"
	"strings"
)

const (
	id      = "pbkdf2-sha256"
	saltLen = 16 // 新记录的盐长度
	keyLen  = 32 // 新记录的密钥长度

	// 写入和解析共用的边界：写不出自己读不了的记录。
	minIterations = 1_000      // RFC 8018 建议的下限
	maxIterations = 10_000_000 // 超过这个数的记录一律当作损坏

	minSaltLen = 8 // 只为兼容旧记录，见文中 FIPS 一节
	minKeyLen  = 16
	maxKeyLen  = 64
)

var (
	ErrMalformed   = errors.New("pwhash: malformed hash")
	ErrUnsupported = errors.New("pwhash: unsupported algorithm")
	ErrBadConfig   = errors.New("pwhash: iterations out of range")

	b64       = base64.RawStdEncoding // 标准字母表，不带 '=' 填充
	dummySalt = make([]byte, saltLen)
)

func validIterations(n int) bool { return n >= minIterations && n <= maxIterations }

// Hasher 保存新记录使用的迭代次数，用 New 创建。
type Hasher struct {
	iterations int
}

// New 在启动时检查配置，迭代次数越界直接报错。
func New(iterations int) (Hasher, error) {
	if !validIterations(iterations) {
		return Hasher{}, ErrBadConfig
	}
	return Hasher{iterations: iterations}, nil
}

// Hash 生成 "$pbkdf2-sha256$i=600000$<salt>$<key>"。
func (h Hasher) Hash(password string) (string, error) {
	return hashWith(password, h.iterations)
}

func hashWith(password string, iter int) (string, error) {
	if !validIterations(iter) {
		return "", ErrBadConfig // 在派生之前拒绝
	}
	salt := make([]byte, saltLen)
	if _, err := rand.Read(salt); err != nil {
		return "", err
	}
	key, err := pbkdf2.Key(sha256.New, password, salt, iter, keyLen)
	if err != nil {
		return "", err
	}
	return fmt.Sprintf("$%s$i=%d$%s$%s", id, iter,
		b64.EncodeToString(salt), b64.EncodeToString(key)), nil
}

// Verify 按记录里写的参数校验。ok 为 true 且 upgraded 非空时，
// 调用方应当用 upgraded 替换原记录。
func (h Hasher) Verify(password, encoded string) (ok bool, upgraded string, err error) {
	if !validIterations(h.iterations) {
		return false, "", ErrBadConfig
	}
	r, err := parse(encoded)
	if err != nil {
		return false, "", err
	}
	got, err := pbkdf2.Key(sha256.New, password, r.salt, r.iter, len(r.key))
	if err != nil {
		return false, "", err
	}
	if subtle.ConstantTimeCompare(got, r.key) != 1 {
		return false, "", nil
	}
	if r.iter >= h.iterations && len(r.salt) >= saltLen && len(r.key) >= keyLen {
		return true, "", nil
	}
	// 只升不降：迭代次数取记录和当前配置中较高的那个。
	upgraded, err = hashWith(password, max(r.iter, h.iterations))
	if err != nil {
		return true, "", nil // 密码是对的，升级失败下次再说
	}
	return true, upgraded, nil
}

// Dummy 在用户不存在时调用，按当前配置派生一次，什么也不返回。
// 它只能缩小一部分耗时差：存在的用户按记录里的参数校验，
// 新旧成本并存、或者顺带升级时，两条路径的耗时并不相同。
func (h Hasher) Dummy(password string) {
	if validIterations(h.iterations) {
		_, _ = pbkdf2.Key(sha256.New, password, dummySalt, h.iterations, keyLen)
	}
}

type record struct {
	iter      int
	salt, key []byte
}

func parse(s string) (record, error) {
	f := strings.Split(s, "$") // 以 '$' 开头，所以 f[0] 是空串
	if len(f) < 2 || f[0] != "" {
		return record{}, ErrMalformed
	}
	if f[1] != id {
		return record{}, ErrUnsupported
	}
	if len(f) != 5 || !strings.HasPrefix(f[2], "i=") {
		return record{}, ErrMalformed
	}
	iter, ok := parseDecimal(f[2][len("i="):])
	if !ok || !validIterations(iter) {
		return record{}, ErrMalformed
	}
	salt, err1 := b64.DecodeString(f[3])
	key, err2 := b64.DecodeString(f[4])
	if err1 != nil || err2 != nil || len(salt) < minSaltLen ||
		len(key) < minKeyLen || len(key) > maxKeyLen {
		return record{}, ErrMalformed
	}
	return record{iter, salt, key}, nil
}

// parseDecimal 只接受不带符号、没有前导零的十进制，这是 PHC 格式的要求。
// strconv.Atoi 会接受 "+600000" 和 "0600000"，同一个值就有了多种写法。
func parseDecimal(s string) (int, bool) {
	if s == "" || len(s) > 9 || (len(s) > 1 && s[0] == '0') {
		return 0, false
	}
	n := 0
	for i := 0; i < len(s); i++ {
		if s[i] < '0' || s[i] > '9' {
			return 0, false
		}
		n = n*10 + int(s[i]-'0')
	}
	return n, true
}

几个地方值得多看一眼：

Verify 只认记录里的参数。 盐、迭代次数和密钥长度都从字符串里来，和 Hasher 的配置无关。配置只影响两件事：新写入的记录用多少次，以及判断旧记录要不要升级。

升级只升不降。 假设你把迭代次数从 21 万提到 60 万，上线后发现登录太慢，又回滚到旧版本。这时库里已经有 60 万次的记录，回滚后的代码不能把它们改回 21 万。所以有两层保护：一是只有记录的参数比当前配置弱时才升级；二是升级时迭代次数取“记录”和“当前配置”中较高的那个。第二层容易漏：一条 60 万次、但盐只有 8 字节的旧记录，会因为盐太短触发升级，如果直接按回滚后的 21 万次重写，迭代次数就被悄悄降下来了。

Verify 直接返回升级后的记录。 调用方不用再自己调 Hash，也就不会在这一步用错参数。升级派生如果失败，只是不返回新记录，不影响这次登录。

配置在用之前就检查。 New 在启动时拒绝越界的迭代次数；即使有人绕过 New 用了零值的 Hasher，Hash 和 Verify 也会在派生之前返回 ErrBadConfig，而不是写出一条 i=0 的记录。

比较用 subtle.ConstantTimeCompare。 bytes.Equal 碰到第一个不同的字节就返回，耗时会泄露“前面对上了几个字节”。对 PBKDF2 的输出来说这个风险很小，因为攻击者控制不了派生结果，但常数时间比较没有成本，应该成为习惯。

接到登录流程里

Verify 返回的 upgraded 要在登录处理里用掉：

func (s *Service) Login(ctx context.Context, name, password string) (*User, error) {
	u, err := s.users.FindByName(ctx, name)
	if errors.Is(err, ErrNotFound) {
		s.hasher.Dummy(password) // 用户不存在时也派生一次，缩小耗时差
		return nil, ErrInvalidCredentials
	}
	if err != nil {
		return nil, err
	}
	ok, upgraded, err := s.hasher.Verify(password, u.PasswordHash)
	if err != nil {
		s.log.Warn("unreadable password hash", "user", u.ID, "err", err)
		return nil, ErrInvalidCredentials
	}
	if !ok {
		return nil, ErrInvalidCredentials
	}
	if upgraded != "" {
		// 只有记录仍是刚才校验的那一条时才覆盖，失败也不影响本次登录
		_ = s.users.ReplacePasswordHash(ctx, u.ID, u.PasswordHash, upgraded)
	}
	return u, nil
}

ReplacePasswordHash 对应一条带条件的更新：

UPDATE users
SET password_hash = $3
WHERE id = $1 AND password_hash = $2;

升级时的坑

只能在登录成功时升级。 只有这一刻服务端手里有明文密码。改常量本身不会动任何已有记录：活跃用户会在下次登录时自然迁到新参数，长期不登录的会一直停在旧参数。因为参数写在记录里，可以直接查出还有多少人停在弱参数上，过一段时间对这部分账号要求重置密码。

并发：别把刚改的密码覆盖掉。 设想用户在手机上用旧密码登录，同一时刻在电脑上改了密码。登录请求读到的是旧哈希，校验通过、算好新哈希，再写回去时，如果用的是无条件的 UPDATE ... WHERE id = $1，就会把刚改的新密码覆盖成旧密码。上面的 AND password_hash = $2 就是为这个准备的：记录已经变了，这次升级就什么也不做。两个旧密码登录同时升级则没关系，两次写入都合法，后到的那次条件不成立，自然跳过。

条件更新只防覆盖，不防旧密码登录成功。 上面那次用旧密码的登录，在改密之前读到旧哈希并校验通过，条件更新虽然什么也没写，示例里的 Login 仍然会返回成功，调用方照样会给它签发会话。如果业务要求“改密之后，旧密码不能再换来新会话”，就要在签发会话的那一刻再核对一次凭据版本，比如用户表上的密码版本号或修改时间，和登录开始时读到的值不一致就拒绝。这属于会话系统的设计，本文不展开，只是要知道条件更新管不到这一层。

回滚：先能读，再去写。 换算法比调参数更容易出事。如果新版本开始写 $argon2id$... 的记录，上线后又回滚，旧代码不认识这个前缀，这些用户就登录不上了。稳妥的做法是分两次发布：第一次只加上“能校验新格式”，确认没有回滚需要之后，第二次再开始“用新格式写”。调迭代次数时，回滚的保证同样有边界：只在新旧两个版本都能解析的格式和参数范围内成立。 本文的解析器只接受 1000 到一千万次迭代、8 字节以上的盐。新版本只要写出的记录还在旧版本的范围里，回滚后照样能校验，加上只升不降的规则，也不会把参数降回去；但如果新版本把上限提高并写出了超过一千万次的记录，旧版本就会把它当作损坏，这部分用户在回滚后登录不上。所以放宽解析范围也要按“先能读，再去写”分两次发布。

同样的问题也出在第一次上线这个解析器的时候。库里如果有低于 1000 次迭代、盐短于 8 字节，或者根本不是这个格式的历史记录，它们会被直接拒绝，照抄示例就会把这些老用户锁在门外。上线前先盘点。参数写在记录里，所以用一条查询就能看到分布，比如在 PostgreSQL 里：

SELECT split_part(password_hash, '$', 2) AS alg,
       split_part(password_hash, '$', 3) AS params,
       count(*)
FROM users
GROUP BY 1, 2
ORDER BY 3 DESC;

盐的长度不好在 SQL 里判断，可以写个一次性的小程序，对每条记录调用 parse，统计被拒绝的原因。范围外的记录有两种处理：一是临时放宽对应的下限，让这些记录还能校验，并在登录时升级到新参数，等它们清空后再收紧；二是直接要求这些账号重置密码。哪种都行，关键是在上线之前做完。

用户不存在时也要花时间，但别指望完全一样。 如果用户名不存在时立刻返回，而存在时要算上百毫秒 PBKDF2，攻击者光看响应时间就能枚举出哪些用户名注册过。Dummy 让不存在的用户也按当前配置派生一次，能把最明显的差距抹掉，但只能缩小一部分：存在的用户按记录里的参数校验，库里新旧成本并存时，有的账号比 Dummy 快，有的比它慢；顺带升级的那次登录还要多派生一次。真要防枚举，还得靠限流和统一的错误信息。

密码哈希本身是攻击面。 每次登录都要消耗上百毫秒的 CPU，登录接口很容易被刷成拒绝服务。慢哈希必须配合限流，按账号和来源 IP 一起限。

升级写回失败不能影响登录。 写回只是顺手的优化，失败了下次登录再试，不应该因此让用户登录失败。

测试

测试覆盖升级、回滚不降级、错误密码和各种坏记录：

package pwhash

import (
	"crypto/pbkdf2"
	"crypto/sha256"
	"errors"
	"fmt"
	"strings"
	"testing"
)

// 测试里用很小的迭代次数，只为了跑得快。
func mustNew(t *testing.T, iter int) Hasher {
	t.Helper()
	h, err := New(iter)
	if err != nil {
		t.Fatal(err)
	}
	return h
}

// legacy 手工造一条旧记录，盐的长度和迭代次数都可以指定。
func legacy(password string, iter, saltBytes int) string {
	salt := make([]byte, saltBytes)
	key, _ := pbkdf2.Key(sha256.New, password, salt, iter, keyLen)
	return fmt.Sprintf("$%s$i=%d$%s$%s", id, iter, b64.EncodeToString(salt), b64.EncodeToString(key))
}

func TestRoundTrip(t *testing.T) {
	h := mustNew(t, 2_000)
	enc, err := h.Hash("correct horse")
	if err != nil || !strings.HasPrefix(enc, "$pbkdf2-sha256$i=2000$") {
		t.Fatalf("enc=%q err=%v", enc, err)
	}
	ok, upgraded, err := h.Verify("correct horse", enc)
	if !ok || upgraded != "" || err != nil {
		t.Fatalf("ok=%v upgraded=%q err=%v", ok, upgraded, err)
	}
}

func TestUpgradeOnLogin(t *testing.T) {
	old, _ := mustNew(t, 1_000).Hash("correct horse")
	cur := mustNew(t, 2_000)

	ok, upgraded, err := cur.Verify("correct horse", old)
	if !ok || err != nil || !strings.HasPrefix(upgraded, "$pbkdf2-sha256$i=2000$") {
		t.Fatalf("旧记录: ok=%v upgraded=%q err=%v", ok, upgraded, err)
	}
	ok, again, err := cur.Verify("correct horse", upgraded)
	if !ok || again != "" || err != nil {
		t.Fatalf("升级后: ok=%v upgraded=%q err=%v", ok, again, err)
	}
}

func TestRollbackDoesNotDowngrade(t *testing.T) {
	enc, _ := mustNew(t, 2_000).Hash("correct horse")
	ok, upgraded, err := mustNew(t, 1_000).Verify("correct horse", enc) // 代码回滚到旧配置
	if !ok || upgraded != "" || err != nil {
		t.Fatalf("回滚: ok=%v upgraded=%q err=%v", ok, upgraded, err)
	}
}

func TestUpgradeKeepsHigherIterations(t *testing.T) {
	enc := legacy("correct horse", 4_000, 8) // 迭代次数比当前配置高，但盐只有 8 字节
	ok, upgraded, err := mustNew(t, 2_000).Verify("correct horse", enc)
	if !ok || err != nil {
		t.Fatalf("ok=%v err=%v", ok, err)
	}
	r, err := parse(upgraded)
	if err != nil || r.iter != 4_000 || len(r.salt) != saltLen {
		t.Fatalf("upgraded=%q iter=%d salt=%d err=%v", upgraded, r.iter, len(r.salt), err)
	}
}

func TestWrongPassword(t *testing.T) {
	h := mustNew(t, 2_000)
	enc, _ := h.Hash("correct horse")
	if ok, upgraded, err := h.Verify("wrong horse", enc); ok || upgraded != "" || err != nil {
		t.Fatalf("ok=%v upgraded=%q err=%v", ok, upgraded, err)
	}
}

func TestInvalidConfig(t *testing.T) {
	for _, n := range []int{0, 999, maxIterations + 1} {
		if _, err := New(n); !errors.Is(err, ErrBadConfig) {
			t.Errorf("New(%d): err=%v", n, err)
		}
	}
	var zero Hasher // 没经过 New 的零值
	if _, err := zero.Hash("x"); !errors.Is(err, ErrBadConfig) {
		t.Errorf("Hash: err=%v", err)
	}
	enc := legacy("x", 1_000, saltLen)
	if _, _, err := zero.Verify("x", enc); !errors.Is(err, ErrBadConfig) {
		t.Errorf("Verify: err=%v", err)
	}
}

func TestRejectsBadRecords(t *testing.T) {
	const salt = "AAAAAAAAAAAAAAAAAAAAAA"                     // 16 字节
	const key = "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA" // 32 字节
	cases := []struct {
		name, in string
		want     error
	}{
		{"空串", "", ErrMalformed},
		{"缺少开头的 $", "pbkdf2-sha256$i=1000$" + salt + "$" + key, ErrMalformed},
		{"别的算法", "$argon2id$v=19$m=19456,t=2,p=1$" + salt + "$" + key, ErrUnsupported},
		{"前导零", "$pbkdf2-sha256$i=01000$" + salt + "$" + key, ErrMalformed},
		{"带符号", "$pbkdf2-sha256$i=+1000$" + salt + "$" + key, ErrMalformed},
		{"迭代次数过小", "$pbkdf2-sha256$i=999$" + salt + "$" + key, ErrMalformed},
		{"迭代次数过大", "$pbkdf2-sha256$i=20000000$" + salt + "$" + key, ErrMalformed},
		{"盐太短", "$pbkdf2-sha256$i=1000$AAAA$" + key, ErrMalformed},
		{"base64 带填充", "$pbkdf2-sha256$i=1000$" + salt + "==$" + key, ErrMalformed},
	}
	h := mustNew(t, 2_000)
	for _, c := range cases {
		if _, _, err := h.Verify("x", c.in); !errors.Is(err, c.want) {
			t.Errorf("%s: err=%v, want %v", c.name, err, c.want)
		}
	}
}

为了让测试跑得快，这里只用了 1000 到 4000 次迭代，逻辑和 60 万次完全一样。在包目录下执行 go test ./... 即可。

我也确认了这些测试确实能拦住错误：把升级时的 max(r.iter, h.iterations) 改成 h.iterations，TestUpgradeKeepsHigherIterations 会失败；去掉 hashWith 开头的边界检查，TestInvalidConfig 会失败。

参数取多少

这里要把两件事分开说：

  • 文中出现的 21 万次只是“历史记录里的旧参数”，用来演示升级，不是推荐值。
  • 新项目请以 OWASP 密码存储备忘单为准。 我在 2026 年 11 月查阅时，它对 PBKDF2-HMAC-SHA256 的建议是至少 60 万次。

这个建议值会随着硬件进步而上调，这也正是要把参数写进记录、并在登录时升级的原因。

和 bcrypt、Argon2id 怎么选

PBKDF2-HMAC-SHA256 bcrypt Argon2id
Go 里在哪 标准库 crypto/pbkdf2 golang.org/x/crypto/bcrypt golang.org/x/crypto/argon2
抗显卡破解 弱，只耗 CPU 中，占用少量内存 强，可配置大量内存
存储格式 要自己定 自带 $2b$成本$... 通常用 PHC 格式
主要限制 需要很高的迭代次数 密码有 72 字节上限 内存参数要按机器调
OWASP 建议 60 万次（需要 FIPS 时） 成本 10 以上（遗留系统） 首选，19 MiB、2 轮、1 线程起

我的取舍是这样的：

  • 新项目、没有合规要求：选 Argon2id。 它让每次猜测都要占用一大块内存，显卡和专用芯片上的并行优势会被大幅削弱，OWASP 也把它列为首选。代价是多一个 x/crypto 依赖，内存参数要考虑并发登录时的峰值。
  • 有 FIPS-140 要求：OWASP 推荐 PBKDF2-HMAC-SHA256。 但选对算法只是前提，不等于合规，下一节细说。
  • 已经在用 bcrypt：可以继续用。 它自带成本因子，本来就能按本文的方式升级。要注意的是 72 字节限制：x/crypto/bcrypt 遇到更长的密码会直接返回 ErrPasswordTooLong，接口层要提前处理。
  • 想要零依赖：PBKDF2 用标准库就够了。 本文的例子就属于这种情况。

不管选哪个，本文的格式和升级流程都通用：换算法就是换一个前缀，Verify 里多一个分支，对旧算法的记录校验通过后一律返回新算法生成的 upgraded。

FIPS：选对算法不等于合规

OWASP 在有 FIPS-140 要求时推荐 PBKDF2-HMAC-SHA256，这句话说的是“算法选哪个”。合规本身还要看你用的是不是经过验证的密码模块、以什么模式运行、参数是否满足相关标准，这些要按你所在组织的合规要求逐项确认，不是换个函数就能达成的。

具体到 Go：Go 1.24 起带了 FIPS 140-3 模式。用 GODEBUG=fips140=only 运行时，crypto/pbkdf2 会直接拒绝短于 16 字节的盐和短于 112 位的密钥（见 Go 1.24.7 的源码）。这和上面示例的兼容策略冲突：解析器为了兼容旧记录接受 8–15 字节的盐，可这些记录在 fips140=only 下根本算不出结果。我实际试了一下，一条 8 字节盐的旧记录，在普通模式下能正常校验并升级，在 fips140=only 下 Verify 返回的是 crypto/pbkdf2: use of salts shorter than 128 bits is not allowed in FIPS 140-only mode，用户就登录不上了。

所以兼容的边界是：

  • 不开 FIPS-only 模式时，8–15 字节盐的旧记录可以校验，并在登录时升级成 16 字节盐。
  • 要开 FIPS-only 模式，先查出盐短于 16 字节的记录，让这些用户在普通模式下完成一次登录升级，或者直接要求重置密码；清干净之后再把 minSaltLen 提到 16，再切换模式。顺序反过来，这部分用户会直接被锁在门外。

为什么不自己写 PBKDF2

PBKDF2 本身不复杂，用 hmac 三十行就能写完，但朴素写法通常每一轮都 hmac.New 一次。HMAC 有内外两层，每层都要先压缩一个由 key 填充出来的块；标准库会把这两个中间状态缓存下来，每轮只压缩真正变化的部分，计算量少一半左右，也省掉了每轮的内存分配。

另外，HMAC 的 key 超过 64 字节时会先被哈希一遍。朴素写法每轮重建 HMAC，这一步也会每轮重做，用户提交超长密码就能让校验慢得离谱，Django 在 2013 年就因类似原因出过拒绝服务漏洞。标准库只在开头做一次。

为了看差距，我做了一个单机测量。下面是完整的 bench_test.go，和前面的包放在同一个目录里。对照组是一个每轮 hmac.New 的朴素实现，先用一条测试确认它和标准库输出一致，再比速度：

package pwhash

import (
	"bytes"
	"crypto/hmac"
	"crypto/pbkdf2"
	"crypto/sha256"
	"testing"
)

var (
	benchPW   = "correct horse battery staple" // 28 字节
	benchSalt = []byte("0123456789abcdef")     // 16 字节
)

// naivePBKDF2 每轮重新 hmac.New，只算第一块（正好 32 字节），作为对照组。
func naivePBKDF2(pw, salt []byte, iter int) []byte {
	mac := func(data []byte) []byte {
		m := hmac.New(sha256.New, pw)
		m.Write(data)
		return m.Sum(nil)
	}
	u := mac(append(append([]byte{}, salt...), 0, 0, 0, 1))
	t := append([]byte{}, u...)
	for i := 1; i < iter; i++ {
		u = mac(u)
		for j := range t {
			t[j] ^= u[j]
		}
	}
	return t
}

// 先确认对照组算得对，否则比速度没有意义。
func TestNaiveMatchesStdlib(t *testing.T) {
	for _, iter := range []int{1, 2, 4096} {
		want, err := pbkdf2.Key(sha256.New, benchPW, benchSalt, iter, 32)
		if err != nil {
			t.Fatal(err)
		}
		if got := naivePBKDF2([]byte(benchPW), benchSalt, iter); !bytes.Equal(got, want) {
			t.Fatalf("iter=%d: 输出不一致", iter)
		}
	}
}

func BenchmarkNaive210k(b *testing.B) {
	for b.Loop() {
		naivePBKDF2([]byte(benchPW), benchSalt, 210_000)
	}
}

func BenchmarkStdlib210k(b *testing.B) {
	for b.Loop() {
		_, _ = pbkdf2.Key(sha256.New, benchPW, benchSalt, 210_000, 32)
	}
}

func BenchmarkStdlib600k(b *testing.B) {
	for b.Loop() {
		_, _ = pbkdf2.Key(sha256.New, benchPW, benchSalt, 600_000, 32)
	}
}

三次运行的结果（每次 20 轮取平均）：

实现 迭代次数 每次耗时
朴素实现 21 万 147–156 ms
crypto/pbkdf2 21 万 44–46 ms
crypto/pbkdf2 60 万 125–129 ms

这些数字只代表这一台机器、这一次运行。云主机的耗时本身有波动，我在同一台机器上早些时候跑过一次，三组数字都比这次低一些。在这台机器上观察到的是：同样的迭代次数，标准库快三倍多；标准库跑 60 万次的耗时比朴素实现跑 21 万次还略短。换了硬件和 Go 版本，倍率未必一样，要用自己的机器重跑。

服务端慢并不会让破解更难，攻击者本来就用自己优化过的实现，甚至用显卡。朴素实现多花的 CPU 是白花的；换成标准库，同样的登录耗时就能用上推荐参数。

小结

  • 把算法和参数写进哈希串，校验只认记录里的参数。
  • 登录成功时发现参数比当前弱，就重新派生，用带条件的更新写回。
  • 升级只升不降，迭代次数取记录和当前配置中较高的那个；换算法先发布“能读”，再发布“去写”。
  • 写入和解析共用参数边界，配置在派生之前检查。
  • PBKDF2 直接用 crypto/pbkdf2；没有合规要求的新项目，优先考虑 Argon2id；要开 FIPS-only 模式，先清掉短盐的旧记录。
