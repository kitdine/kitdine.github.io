只追加、按时间写入的表（GPS 轨迹、监控采样、日志），时间列上建一个 BRIN 索引几乎是标准做法。下面这张演示表 604.8 万行、442 MB，collected_at 上的 BRIN 索引只有 32 kB，同一列上的 B-tree 是 67 MB。刚建好时查任意 10 分钟，只读 128 个数据页，1.4 到 2.3 毫秒。

然后让它像线上一样继续写一天，再查最近 10 分钟：

Bitmap Heap Scan on positions (actual rows=3000 loops=1)
  Recheck Cond: (collected_at >= '2026-11-15 23:50:00+00'::timestamp with time zone)
  Rows Removed by Index Recheck: 423368
  Heap Blocks: lossy=3985
Execution Time: 39.719 ms

要 3000 行，读了 3985 个页、扔掉 42 万行。更意外的是查一周前的 10 分钟，也从 128 页变成了 4113 页。索引没坏，数据也是按时间顺序写的，问题出在新写入的页还没有 “摘要”。这篇讲清楚 BRIN 什么时候才给新数据做摘要、几种补救办法各自的代价，最后给一个可以直接用的维护程序。

文中数字都来自我在 PostgreSQL 16.15（Ubuntu 24.04 的发行版包）上跑的实验，机器是 4 核 Intel Xeon 2.10GHz，shared_buffers=1GB，数据全在缓存里（EXPLAIN 里都是 shared hit）。脚本在 “完整代码” 一节，复制就能重跑。

BRIN 存的是什么

BRIN 把表按物理顺序切成 “块范围”（block range），每个范围默认 128 个页（pages_per_range 的默认值，见 CREATE INDEX 文档），每个范围在索引里只存一条摘要。对默认的 minmax 操作符类来说，摘要就是这个范围里 collected_at 的最小值和最大值。另有一个 revmap，按范围编号记着每条摘要在索引里的位置。

查询时，BRIN 逐个范围看摘要：区间和查询条件可能有交集，就把这 128 个页整块交给 Bitmap Heap Scan，再逐行复查条件。所以 EXPLAIN 里总是 lossy，总有 Rows Removed by Index Recheck。数据按时间顺序写入时，每个范围的 min/max 很窄，一次查询只命中一两个范围，于是 32 kB 的索引就能把 442 MB 的表裁到 1 MB 左右。

关键在于没有摘要的范围。PostgreSQL 16 源码 src/backend/access/brin/brin.c 里 bringetbitmap 的注释写得很直白：revmap 里读到无效指针，说明这个范围没有汇总，“Pages in those ranges need to be returned regardless of scan keys”。没有摘要的范围对任何查询都算命中。开头那一天的新数据有 32 个范围没摘要，共 3985 页，所以查最近 10 分钟要读 3985 页，查一周前的 10 分钟要读 128 + 3985 = 4113 页。

新页什么时候才有摘要

BRIN 文档的 Index Maintenance 一节 说明了规则：

  • 建索引时，所有已有的页都会被汇总，包括表尾页数不足 128 的那个范围。
  • 插入的行落在一个已经有摘要的范围里，摘要会随之更新。
  • 插入时开出的新页如果落在最后一个已汇总范围之外，这个范围不会自动得到摘要，要等以后某次汇总。

触发汇总的途径有三类：VACUUM（手动或 autovacuum）、索引上开了 autosummarize 时由 autovacuum 顺带执行、手动调用 brin_summarize_new_values / brin_summarize_range。它们的行为并不一样，下面逐个看。

VACUUM：跳过页数不足 128 的最后一个范围

先分清两个容易混的概念。表在磁盘上有若干已分配的页；纯追加写入时，新行总是写进最后一个已分配页，写不下才分配下一页。所以对纯追加表来说，最后一个已分配页所在的范围 才是还在接收写入的当前范围，下文的 “尾巴” 都指它。

文档说 VACUUM 时 “all existing unsummarized page ranges are summarized”，但源码里 brinvacuumcleanup 调用 brinsummarize 时传的 include_partial 是 false。brinsummarize 里对应的判断是 startBlk + pagesPerRange > heapNumBlocks 时停下，也就是只看这个范围的 128 个页是否都已分配，不足 128 页才跳过。brinsummarize 的注释解释了区分：brin_summarize_new_values 通常在批量导入完成后调用，所以连尾部一起汇总；VACUUM 是 “arbitrarily-scheduled maintenance”，就不汇总尾部。

这里有个边界：表恰好有 128 页时，范围 0 的 128 个页都已分配，VACUUM 会汇总它；可第 128 页（编号 127）可能刚分配、几乎是空的，接下来的追加写入还会落在范围 0。也就是说，“页数够一个范围” 不等于 “这个范围不再接收插入”。下文 “完整代码” 里的边界测试构造的就是这种情况。

实验里，追加一天数据后表有 60561 页，即 473 个页数够 128 的范围，加一个只有 17 页的尾巴。执行 VACUUM positions 后，474 个范围里 473 个有了摘要，剩下的正是那个尾巴。最近 10 分钟的查询变成 145 页（前一个范围 128 页加尾巴 17 页），2.1 毫秒。再调用一次 brin_summarize_new_values，返回 1，尾巴也有了摘要。

至于为什么要区分，后面 “写放大” 一节会用数字说明。

只靠 autovacuum 不够

PostgreSQL 13 起，只插入不更新的表也会因为插入量触发 autovacuum（12 的配置文档里还没有 autovacuum_vacuum_insert_threshold，13 开始有）。触发条件见 Routine Vacuuming 文档：

vacuum insert threshold = vacuum base insert threshold + vacuum insert scale factor * number of tuples

两个参数的默认值是 1000 和 0.2（autovacuum 参数文档），也就是表里新插入的行数超过总行数的 20% 才会 VACUUM。代入演示表（每天 43.2 万行）：

  • 存了 14 天、604.8 万行时，要再插 1000 + 0.2 × 6,048,000 ≈ 121 万行，约 2.8 天的数据，才会触发一次。
  • 存满一年（约 1.58 亿行）时，阈值是 3154 万行，约 73 天。

阈值随表变大而线性增长。表越老，没摘要的尾巴可以越长，最坏时每个查询都要多扫将近整张表的 20%。调小表级的 autovacuum_vacuum_insert_scale_factor 可以缓解，但那是为了汇总 BRIN 去频繁 VACUUM 整张表，代价不成比例。

autosummarize：只补上一个范围，请求放在内存里

autosummarize 是 PostgreSQL 10 加的索引存储参数，默认关闭。源码 brininsert 里的逻辑是：开了 autosummarize，且这一行是写进新范围第一个页的第一个位置的行，并且前一个范围还没有摘要，就调用 AutoVacuumRequestWork 请求 autovacuum 去汇总前一个范围。请求会 “fulfilled the next time an autovacuum worker finishes running in the same database”，而 autovacuum 访问每个数据库的间隔是 autovacuum_naptime，默认 1 分钟。

由此有三点要注意：

  1. 它永远不汇总当前正在写的那个范围，只在跨进下一个范围时补上一个。
  2. 请求放在共享内存的固定数组里。autovacuum.c 里 NUM_WORKITEMS 是 256，整个实例共用。满了就丢弃，日志里留一句 request for BRIN range summarization for index ... was not recorded；实例重启时队列里没处理的请求也跟着没了。
  3. **它依赖 autovacuum 在运行。**全局 autovacuum = off 时，请求只在队列里排着，不会被执行。表级的 autovacuum_enabled = off 不影响，文档说汇总会发生 “regardless of whether the table itself is processed by autovacuum”。

我用一张关掉了表级 autovacuum、索引开了 autosummarize 的表验证了这三点（autovacuum_naptime 调成 2 秒以便观察）：

步骤 范围数 有摘要 没摘要
写入 3 小时数据，6 秒后 4 3 1（当前尾巴）
全局关闭 autovacuum 后重启实例，再写 3 小时 8 3 5
重新打开 autovacuum 并重启，等 8 秒 8 3 5
再写 3 小时，6 秒后 12 7 5
运行下文的维护程序一次 12 11 1（当前尾巴）

第二段写入时请求了 4 次汇总，因为 autovacuum 没开而一直排着，重启后就没了，之后也不会有人再提起它们。正常运行时 autosummarize 很及时，但它是 “尽力而为”，需要一个兜底。

写放大：为什么不总是把尾巴也汇总

既然 brin_summarize_new_values 连尾巴都能汇总，定期调它不就好了？问题在 “已有摘要的范围插入时摘要会更新” 这一条。准确地说，brininsert 会先看新值是否已在摘要的 min/max 之内：在里面就什么也不做，在外面才扩张摘要、改写索引元组、写一条 WAL。时序数据的时间单调递增，于是落在已汇总尾巴里、把最大值往后推的那些行，每一行都要改写一次摘要。尾巴没摘要时，插入只查一下 revmap 就走。

改写多频繁，取决于有多少行带着新的时间戳。下面的批量测试里 5 辆车每秒共用一个时间戳，每秒只有第一行扩张最大值，大约五行改写一次；单行测试里每行时间都不同，每行都改写。

我写了 300 万行（每条 INSERT 写 300 行，相当于 5 辆车 1 分钟的数据，共 1 万条 INSERT），对比三种策略，每种跑 4 遍：

策略 耗时 WAL
A：从不汇总 2.48 ～ 2.89 秒 207 MB
B：每 5 条 INSERT 调一次 brin_summarize_new_values 3.53 ～ 3.79 秒 247 MB
C：同样频率，只汇总尾巴之前的范围 2.92 ～ 3.29 秒 207 MB

B 比 A 慢约 35%，多写 40 MB WAL；C 和 A 的 WAL 完全一样，耗时多出的零点几秒应该是那 2000 次汇总调用本身的开销。把脚本改成每条 INSERT 只写一行、共 30 万行、每 1000 行汇总一次，差距更明显：WAL 从 22 MB 涨到 41 MB，耗时从 0.82 ～ 0.95 秒涨到 1.12 ～ 1.26 秒（各跑 3 遍）。

这就是 VACUUM 和 autosummarize 都尽量不碰尾巴的道理（VACUUM 在上面 “恰好 128 页” 的边界上会碰）。对追加写的时序表，尾巴留着不汇总，代价是每个查询最多多读一个范围（128 页、1 MB）；汇总了尾巴，代价是之后每个新时间戳的第一行都要多改一次索引。前者有上限，后者随写入量增长。

推荐做法

  1. 索引开 autosummarize = on，它负责日常的及时汇总，且不碰尾巴：

    ALTER INDEX positions_at_brin SET (autosummarize = on);

  2. 再跑一个定期任务兜底，只汇总最后一个已分配页所在范围之前的范围，补上丢失的请求。表有 N 页时最后一页是第 N-1 页，要汇总的是第 0 到第 (N-1)/128-1 个范围。这比 VACUUM 的判断严格，和 autosummarize 的时机一致：第 129 页分配出来之后，范围 0 才算不再接收追加写入。PostgreSQL 没有直接提供这样的函数，但 brin_summarize_range(index, 块号) 只处理一个范围，对已有摘要的范围什么也不做，循环调用就行。我测了在 474 个范围全都有摘要时扫一遍，耗时 0.7 ～ 1.5 毫秒，每次从头扫也负担得起。

  3. 间隔按 “多久写完一个范围” 来定。演示表每天约写 4037 页，即 31.5 个范围，大约 46 分钟写完一个。autosummarize 正常时兜底任务几乎总是无事可做，5 到 15 分钟一次足够；写入量大一百倍时，一分钟就会写完两个范围，兜底间隔要相应缩短。

  4. 如果最新几分钟数据的查询延迟比写入吞吐更重要，而且写入量不大，可以连尾巴一起汇总（下面程序的 -include-tail），心里清楚它的写放大：每个新时间戳的第一行都要改写一次摘要。

汇总的开销本身不大：一整天 32 个范围、约 4000 页，brin_summarize_new_values 实测 48 ～ 68 毫秒。

另外两个坑：权限和锁

必须是表的属主。brin_summarize_range 的源码注释写着 “User must own the index (comparable to privileges needed for VACUUM)”。很多部署里建表的迁移账号和应用账号不是同一个，应用账号调用会得到：

ERROR: must be owner of index positions_at_brin (SQLSTATE 42501)

索引的属主不能单独设置。ALTER INDEX 文档 写明 “An index cannot have an owner different from its table’s owner”，ALTER INDEX ... OWNER TO 只给一个警告，什么也不改（我在 16.15 上试过，提示去改表的属主）。所以 “索引属主” 就是表的属主。

属主检查认的是 “有属主角色的权限”，下面三种做法我都在 16.15 上试过：

  • 维护任务直接用表的属主角色连库。
  • 建一个专门的维护登录角色，GRANT 表属主角色 TO 维护角色。默认 INHERIT TRUE 时它直接继承属主权限，调用成功。
  • 如果既有权限设计里成员关系是 WITH INHERIT FALSE，就先 SET ROLE 表属主角色 再调用；不切换会得到上面那个错误。

前文实验用的是超级用户，只是因为观察工具依赖 pageinspect。生产环境的维护任务不需要也不该用超级用户，给一个有表属主权限的角色就够了。

**它在表上拿 SHARE UPDATE EXCLUSIVE 锁。**这个锁和 INSERT、SELECT 不冲突，但和 VACUUM、ANALYZE、CREATE INDEX CONCURRENTLY 以及另一个汇总冲突。碰上一个很长的 VACUUM，维护任务就会一直等。下面的程序给它设了 lock_timeout，拿不到锁就跳过这一轮，反正 VACUUM 自己也会汇总。

物理顺序乱了，再怎么汇总也没用

上面的一切都建立在 “物理顺序约等于时间顺序” 上。最常见的破坏者是补传：设备离线几天，恢复后一边上报实时数据，一边补传缓存，两类数据交替写进同一批页。

实验里，表先有 11-01 到 11-07 的正常数据，11-08 当天 5 辆车实时上报，同时第 6 辆车每分钟补传一批 11-04 的数据。查一个和两类数据都无关的时段，11-06 中午的 10 分钟：

操作符类 读的页 耗时 索引大小
默认 minmax 5075 42.6 毫秒 24 kB
timestamptz_minmax_multi_ops 128 1.2 毫秒 64 kB

11-08 写入的每个范围，min 是 11-04，max 是 11-08，区间盖住了 11-06，于是那一天写入的约 39 个范围全部命中。更糟的是，这时 pg_stats 里 collected_at 的 correlation 是 0.964，看上去非常有序，统计信息完全不会提醒你。

PostgreSQL 14 加入的 minmax-multi 操作符类（13 的 BRIN 文档里没有，14 有）每个范围存多个值和区间（values_per_range 默认 32，见 BRIN 文档），能表示 “11-04 的一段加 11-08 的一段”，中间的空隙就被排除了。代价是索引更大（这里是 2.7 倍）、建索引和维护时 CPU 更多。它只能应付 “少数离群的时间段”；如果数据真的被打成随机顺序，每个范围都覆盖全部时间，换什么操作符类都救不回来。

更根本的办法是别让乱序数据进主表：补传先写进一张临时表，按时间排好序再批量插入，或者按时间分区，让补传的数据落进它自己那天的分区。另外，UPDATE 和 DELETE 只会让摘要变宽，不会变窄；大量修改过的范围可以用 brin_desummarize_range 撤掉摘要再重新汇总。

完整代码

脚本按编号顺序在一个空库里用 psql -f 执行。实验用超级用户跑，因为 00 依赖 pageinspect 直接读索引页，它只用于观察。生产环境的维护程序用有表属主权限的角色就够了，见上文 “权限和锁”。我只在 PostgreSQL 16.15 上跑过；minmax-multi 需要 14 及以上。

观察工具：还有多少范围没摘要

-- 需要超级用户：pageinspect 能直接读索引页
CREATE EXTENSION IF NOT EXISTS pageinspect;

-- 统计一个 BRIN 索引覆盖了多少个块范围、其中多少个还没有汇总。
-- 依据是 revmap：每个块范围一格，存着摘要元组的 TID。
-- 块号 0 是元数据页、4294967295 是无效块号，两者都表示这个范围没有摘要。
CREATE OR REPLACE FUNCTION brin_coverage(idx regclass)
RETURNS TABLE (ranges bigint, summarized bigint, unsummarized bigint)
LANGUAGE sql AS $$
WITH meta AS (
    SELECT m.pagesperrange, m.lastrevmappage,
           ceil((pg_relation_size(i.indrelid) / current_setting('block_size')::int)::numeric
                / m.pagesperrange)::bigint AS ranges
    FROM brin_metapage_info(get_raw_page(idx::text, 0)) AS m, pg_index AS i
    WHERE i.indexrelid = idx
),
slots AS (
    SELECT row_number() OVER (ORDER BY p, ord) - 1 AS range_no, r.pages AS tid
    FROM meta, generate_series(1, meta.lastrevmappage) AS p,
         LATERAL brin_revmap_data(get_raw_page(idx::text, p)) WITH ORDINALITY AS r(pages, ord)
)
SELECT meta.ranges,
       count(*) FILTER (WHERE (tid::text::point)[0] NOT IN (0, 4294967295)),
       meta.ranges - count(*) FILTER (WHERE (tid::text::point)[0] NOT IN (0, 4294967295))
FROM meta LEFT JOIN slots ON slots.range_no < meta.ranges
GROUP BY meta.ranges;
$$;

造数据，然后追加一天

-- 演示数据：5 辆车，每辆每秒 1 个点，先灌 14 天历史（共 604.8 万行）
DROP TABLE IF EXISTS positions;
CREATE TABLE positions (
    id           bigint GENERATED ALWAYS AS IDENTITY,
    vehicle_id   int         NOT NULL,
    collected_at timestamptz NOT NULL,
    latitude     double precision,
    longitude    double precision,
    speed        int
) WITH (autovacuum_enabled = off);  -- 演示里不让 autovacuum 插手，下面手动控制

-- 按时间顺序写入：第 n 行属于第 n/5 秒、第 n%5+1 辆车
INSERT INTO positions (vehicle_id, collected_at, latitude, longitude, speed)
SELECT n % 5 + 1,
       timestamptz '2026-11-01 00:00:00+00' + (n / 5) * interval '1 second',
       31.2 + random() / 100, 121.4 + random() / 100, (random() * 120)::int
FROM generate_series(0, 14 * 86400 * 5 - 1) AS n;

CREATE INDEX positions_at_brin ON positions USING brin (collected_at);
VACUUM ANALYZE positions;

// brinsum 定期补齐 BRIN 索引里已经不再接收追加写入、却还没有摘要的块范围。
//
// 用法：
//
//	go run . -dsn 'postgres://owner@localhost:5432/app' -index positions_at_brin -interval 5m
package main

import (
	"context"
	"errors"
	"flag"
	"log"
	"os"
	"os/signal"
	"strconv"
	"strings"
	"syscall"
	"time"

	"github.com/jackc/pgx/v5/pgconn"
	"github.com/jackc/pgx/v5/pgxpool"
)

// Options 控制一次汇总的行为。
type Options struct {
	// IncludeTail 为 true 时连当前正在写入的那个范围一起汇总（brin_summarize_new_values）。
	// 好处是最新数据也能被裁剪；代价是之后落进这个范围、又把最大值往后推的插入，
	// 都要改写这个范围的摘要。
	IncludeTail bool
	// LockTimeout 是等表上 SHARE UPDATE EXCLUSIVE 锁的上限。
	// 拿不到锁通常是 VACUUM 正在跑，而 VACUUM 自己也会汇总，这一轮跳过即可。
	LockTimeout time.Duration
	// StatementTimeout 是单次汇总的上限，防止积压太久后一次扫太多页。
	StatementTimeout time.Duration
}

// ErrSkipped 表示这一轮因为拿不到锁而跳过。
var ErrSkipped = errors.New("table is locked, skipped")

// summarizeFullRanges 对 "最后一个已分配页所在范围" 之前的每个范围调用 brin_summarize_range。
//
// 判断依据是最后一个已分配页落在哪个范围：表有 heap_pages 个页时，最后一页是
// heap_pages-1，它所在的范围及之后都不碰。恰好 128 页时最后一页还属于范围 0，
// 这时一个范围也不汇总；等第 129 页分配出来，范围 0 才算不再接收追加写入。
// 这和 autosummarize "跨进下一个范围才汇总上一个" 的时机一致，比 VACUUM 严格：
// VACUUM 只要求范围的 128 个页都已分配。
// 已经有摘要的范围只查一下 revmap 就返回 0，所以每次从 0 扫到头也很便宜。
const summarizeFullRanges = `
WITH m AS (
    SELECT coalesce((SELECT o.option_value::int
                     FROM pg_options_to_table(c.reloptions) AS o
                     WHERE o.option_name = 'pages_per_range'), 128) AS ppr,
           pg_relation_size(i.indrelid) / current_setting('block_size')::int AS heap_pages
    FROM pg_class AS c
    JOIN pg_index AS i ON i.indexrelid = c.oid
    JOIN pg_am    AS a ON a.oid = c.relam AND a.amname = 'brin'
    WHERE c.oid = $1::regclass
)
SELECT (SELECT count(*) FROM m),
       coalesce(sum(brin_summarize_range($1::regclass, r * m.ppr)), 0)
FROM m, generate_series(0, (m.heap_pages - 1) / m.ppr - 1) AS r`

// brin_summarize_new_values 自己会检查索引类型，第一列恒为 1。
const summarizeIncludingTail = `SELECT 1, brin_summarize_new_values($1::regclass)`

// ErrNotBRIN 表示传进来的名字不是一个 BRIN 索引。
var ErrNotBRIN = errors.New("not a BRIN index")

// SummarizeOnce 补齐 index 上缺失的摘要，返回新写入的摘要条数。
func SummarizeOnce(ctx context.Context, db *pgxpool.Pool, index string, opt Options) (int64, error) {
	tx, err := db.Begin(ctx)
	if err != nil {
		return 0, err
	}
	defer tx.Rollback(ctx) //nolint:errcheck // 提交之后再回滚是空操作

	// SET LOCAL 只在这个事务里生效，不会把设置留在连接池的连接上。
	// SET 不支持占位符；这里拼进去的只是整数毫秒数。
	if _, err := tx.Exec(ctx,
		"SET LOCAL lock_timeout = "+ms(opt.LockTimeout)+
			"; SET LOCAL statement_timeout = "+ms(opt.StatementTimeout)); err != nil {
		return 0, err
	}

	query := summarizeFullRanges
	if opt.IncludeTail {
		query = summarizeIncludingTail
	}
	var found, n int64
	if err := tx.QueryRow(ctx, query, index).Scan(&found, &n); err != nil {
		var pgErr *pgconn.PgError
		if errors.As(err, &pgErr) && pgErr.Code == "55P03" { // lock_not_available
			return 0, ErrSkipped
		}
		return 0, err
	}
	if found == 0 {
		return 0, ErrNotBRIN
	}
	return n, tx.Commit(ctx)
}

func ms(d time.Duration) string {
	if d <= 0 {
		return "0" // 0 表示不限制
	}
	return strconv.FormatInt(d.Milliseconds(), 10)
}

// Run 启动时先补一次，之后每隔 interval 补一次，直到 ctx 被取消。
// Ticker 在上一轮跑慢时会丢掉积压的 tick，不会几轮挤在一起连着跑。
func Run(ctx context.Context, db *pgxpool.Pool, indexes []string, interval time.Duration, opt Options) {
	tick := time.NewTicker(interval)
	defer tick.Stop()
	for {
		for _, idx := range indexes {
			start := time.Now()
			n, err := SummarizeOnce(ctx, db, idx, opt)
			switch {
			case ctx.Err() != nil:
				return
			case errors.Is(err, ErrSkipped):
				log.Printf("%s: %v", idx, err)
			case err != nil:
				log.Printf("%s: summarize failed: %v", idx, err)
			case n > 0:
				log.Printf("%s: summarized %d ranges in %s", idx, n, time.Since(start).Round(time.Millisecond))
			}
		}
		select {
		case <-ctx.Done():
			return
		case <-tick.C:
		}
	}
}

func main() {
	dsn := flag.String("dsn", os.Getenv("DATABASE_URL"), "PostgreSQL 连接串，用户必须是表的属主或属主角色的成员")
	index := flag.String("index", "", "要维护的 BRIN 索引，多个用逗号分隔")
	interval := flag.Duration("interval", 5*time.Minute, "两次汇总之间的间隔")
	tail := flag.Bool("include-tail", false, "连当前正在写入的那个范围一起汇总")
	lockTimeout := flag.Duration("lock-timeout", 5*time.Second, "等锁上限")
	stmtTimeout := flag.Duration("statement-timeout", time.Minute, "单次汇总上限")
	once := flag.Bool("once", false, "只汇总一次就退出")
	flag.Parse()
	if *dsn == "" || *index == "" {
		flag.Usage()
		os.Exit(2)
	}

	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	db, err := pgxpool.New(ctx, *dsn)
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	opt := Options{IncludeTail: *tail, LockTimeout: *lockTimeout, StatementTimeout: *stmtTimeout}
	indexes := strings.Split(*index, ",")
	if !*once {
		Run(ctx, db, indexes, *interval, opt)
		return
	}
	failed := false
	for _, idx := range indexes {
		n, err := SummarizeOnce(ctx, db, idx, opt)
		if err != nil && !errors.Is(err, ErrSkipped) {
			log.Printf("%s: %v", idx, err)
			failed = true
			continue
		}
		log.Printf("%s: summarized %d ranges (err=%v)", idx, n, err)
	}
	if failed {
		os.Exit(1)
	}
}

// isolatedPool 在 base 指向的库里新建一个唯一的 schema，返回 search_path 只含这个 schema 的连接池。
// 测试里不带 schema 的表名都落在这里，也只会在这里找。
func isolatedPool(t *testing.T, base *pgxpool.Config) *pgxpool.Pool {
	t.Helper()
	ctx := context.Background()
	admin, err := pgxpool.NewWithConfig(ctx, base.Copy())
	if err != nil {
		t.Fatal(err)
	}
	b := make([]byte, 8)
	if _, err := rand.Read(b); err != nil {
		t.Fatal(err)
	}
	schema := "brinsum_test_" + hex.EncodeToString(b)
	// 不加 IF NOT EXISTS：万一重名，宁可失败，也不往别人的 schema 里建表、更不删它。
	exec(t, admin, "CREATE SCHEMA "+schema)
	t.Cleanup(func() {
		if _, err := admin.Exec(ctx, "DROP SCHEMA "+schema+" CASCADE"); err != nil {
			t.Errorf("drop schema %s: %v", schema, err)
		}
		admin.Close()
	})

	cfg := base.Copy()
	cfg.ConnConfig.RuntimeParams["search_path"] = schema
	db, err := pgxpool.NewWithConfig(ctx, cfg)
	if err != nil {
		t.Fatal(err)
	}
	t.Cleanup(db.Close) // 后注册先执行：先关连接，再删 schema
	return db
}

func testFullRangeBoundary(t *testing.T, db *pgxpool.Pool) {
	opt := Options{LockTimeout: 5 * time.Second, StatementTimeout: time.Minute}

	exec(t, db, `CREATE TABLE edge (collected_at timestamptz NOT NULL) WITH (autovacuum_enabled = off)`)
	// 在空表上建索引时，范围 0 会得到一条（空的）摘要。先撤掉，后面才看得出谁汇总了它。
	exec(t, db, `CREATE INDEX edge_brin ON edge USING brin (collected_at)`)
	exec(t, db, fmt.Sprintf(appendUntilPages, 128))
	exec(t, db, `SELECT brin_desummarize_range('edge_brin', 0)`)

	if got := scalar(t, db, `SELECT pg_relation_size('edge') / current_setting('block_size')::int`); got != 128 {
		t.Fatalf("pages = %d, want 128", got)
	}
	// 第 128 页（编号 127）刚分配出来，只放了一行，还有很多空间。
	lastPageRows := scalar(t, db, `SELECT count(*) FROM edge WHERE (ctid::text::point)[0] = 127`)
	if lastPageRows >= 10 {
		t.Fatalf("last page already has %d rows; boundary setup is wrong", lastPageRows)
	}

	// 恰好 128 页：最后一页还在范围 0 里，默认模式一个也不汇总。
	if n := summarize(t, db, opt); n != 0 {
		t.Fatalf("at exactly 128 pages summarized %d ranges, want 0", n)
	}

	// 范围 0 确实还在接收插入：再写 10 行，页数不变，新行都落在第 128 页。
	exec(t, db, `INSERT INTO edge
		SELECT (SELECT max(collected_at) FROM edge) + n * interval '1 second' FROM generate_series(1, 10) n`)
	if got := scalar(t, db, `SELECT pg_relation_size('edge') / current_setting('block_size')::int`); got != 128 {
		t.Fatalf("pages = %d after 10 more rows, want still 128", got)
	}
	if got := scalar(t, db, `SELECT count(*) FROM edge WHERE (ctid::text::point)[0] = 127`); got != lastPageRows+10 {
		t.Fatalf("last page rows = %d, want %d", got, lastPageRows+10)
	}

	// 对照：VACUUM 只看 128 个页是否都已分配，这时就会汇总范围 0。
	exec(t, db, `VACUUM edge`)
	if got := scalar(t, db, `SELECT brin_summarize_range('edge_brin', 0)`); got != 0 {
		t.Fatalf("VACUUM left range 0 unsummarized (brin_summarize_range returned %d)", got)
	}
	exec(t, db, `SELECT brin_desummarize_range('edge_brin', 0)`)

	// 对照：-include-tail 也会汇总它。
	if n := summarize(t, db, Options{IncludeTail: true, LockTimeout: opt.LockTimeout, StatementTimeout: opt.StatementTimeout}); n != 1 {
		t.Fatalf("include-tail summarized %d ranges, want 1", n)
	}
	exec(t, db, `SELECT brin_desummarize_range('edge_brin', 0)`)

	// 第 129 页分配出来之后，追加写入已经转到范围 1，范围 0 才被默认模式汇总。
	exec(t, db, fmt.Sprintf(appendUntilPages, 129))
	if n := summarize(t, db, opt); n != 1 {
		t.Fatalf("at 129 pages summarized %d ranges, want 1", n)
	}
	if n := summarize(t, db, opt); n != 0 {
		t.Fatalf("second run summarized %d ranges, want 0", n)
	}
}

func testNotBRIN(t *testing.T, db *pgxpool.Pool) {
	exec(t, db, `CREATE TABLE not_brin (collected_at timestamptz)`)
	exec(t, db, `CREATE INDEX not_brin_btree ON not_brin (collected_at)`)
	for _, name := range []string{"not_brin", "not_brin_btree"} {
		if _, err := SummarizeOnce(context.Background(), db, name, Options{}); err != ErrNotBRIN {
			t.Errorf("%s: err = %v, want ErrNotBRIN", name, err)
		}
	}
}

// TestLeavesExistingTablesAlone 模拟读者库里已有同名的 edge 和 not_brin：
// 把它们建在另一个 schema 里，并让这个 schema 成为连接串的默认 search_path，
// 跑完上面两个测试后，原表还是原来那张（oid 不变），数据一行不少。
func TestLeavesExistingTablesAlone(t *testing.T) {
	base := baseConfig(t)
	reader := isolatedPool(t, base)
	exec(t, reader, `CREATE TABLE edge (collected_at timestamptz)`)
	exec(t, reader, `INSERT INTO edge SELECT now() FROM generate_series(1, 3)`)
	exec(t, reader, `CREATE TABLE not_brin (id int)`)
	exec(t, reader, `INSERT INTO not_brin VALUES (1), (2)`)
	const snapshot = `SELECT format('edge oid=%s rows=%s, not_brin oid=%s rows=%s',
	    'edge'::regclass::oid, (SELECT count(*) FROM edge),
	    'not_brin'::regclass::oid, (SELECT count(*) FROM not_brin))`
	before := text(t, reader, snapshot)

	schema := text(t, reader, `SELECT current_schema()`)
	readerCfg := base.Copy()
	readerCfg.ConnConfig.RuntimeParams["search_path"] = schema
	t.Run("boundary", func(t *testing.T) { testFullRangeBoundary(t, isolatedPool(t, readerCfg)) })
	t.Run("not_brin", func(t *testing.T) { testNotBRIN(t, isolatedPool(t, readerCfg)) })

	if after := text(t, reader, snapshot); after != before {
		t.Fatalf("existing tables changed: %s, want %s", after, before)
	}
	if n := scalar(t, reader, `SELECT count(*) FROM pg_indexes WHERE schemaname = current_schema()`); n != 0 {
		t.Fatalf("%d indexes appeared on the existing tables", n)
	}
}

几个设计点：

  • **默认不碰当前范围。**按最后一个已分配页所在的范围排除，而不是按 “页数够 128” 判断，所以恰好 128 页时一个范围也不汇总，避免把还在接收写入的范围汇总掉。brin_summarize_range 对已有摘要的范围直接返回 0，所以每次都从第 0 个范围扫到当前范围之前。这样不用记 “上次扫到哪”，进程重启、请求丢失、有人手动撤掉过摘要，下一轮都会补上。
  • **先确认是 BRIN 索引。**传错成表名或 B-tree 索引名时，如果表还不到一个范围大，generate_series 是空的，查询会安静地返回 0。所以查询里多返回一列 “找到几个 BRIN 索引”，为 0 就报 ErrNotBRIN。
  • **超时用 SET LOCAL。**它只在当前事务里有效，事务结束就恢复，不会把 lock_timeout 留在连接池的连接上，影响别的查询。
  • **拿不到锁算跳过，不算失败。**SQLSTATE 55P03 是 lock_not_available，通常意味着 VACUUM 在跑。
  • **用 time.Ticker。**上一轮跑慢了，Ticker 会丢掉积压的 tick，不会让几轮连在一起跑。

main_test.go 用一张临时表测这个边界：一行一行写到恰好 128 页（第 128 页只有一行），默认模式汇总 0 个范围；再写 10 行，页数仍是 128，新行都在第 128 页，说明范围 0 确实还在接收写入；对照组里 VACUUM 和 -include-tail 这时都会汇总范围 0；写到第 129 页后，默认模式汇总 1 个。把查询里的 (heap_pages - 1) / ppr 改回 heap_pages / ppr，测试会在 “恰好 128 页” 那一步失败。TestLeavesExistingTablesAlone 先在另一个 schema 里建好同名的 edge 和 not_brin 并写入数据，让它充当连接串的默认 search_path，跑完两个测试后检查原表的 oid 和行数都没变；如果测试改回直接用读者的连接、先 DROP TABLE IF EXISTS 再建表，这一步会失败。

另外手动做了这些检查：撤掉 10 个范围的摘要、再追加 3 小时数据后跑一次，补了 12 个范围，留下尾巴；加 -include-tail 再跑，尾巴也补上了；另开一个会话持有 SHARE UPDATE EXCLUSIVE 锁，-lock-timeout 500ms 时这一轮被跳过；传表名、B-tree 索引名、不存在的名字分别报 not a BRIN index、not a BRIN index、relation "nope" does not exist；用非属主账号连库报 must be owner of index；以 2 秒间隔循环运行后发 SIGINT，干净退出。

和其他做法比

**直接用 B-tree。**精确、没有汇总的问题，最新数据随写随可查。代价是大小：演示表上 67 MB 对 32 kB，而且每一行写入都要维护 B-tree。对 “查最近一段时间” 为主、表很大的时序场景，BRIN 加上本文的维护通常更划算；需要按时间点精确查少量行，或者表不大时，B-tree 更省心。

**按时间分区。**分区之后可以直接删掉过期分区，查询也能先按分区裁剪。但分区内部用的还是 BRIN 或 B-tree，正在写入的那个分区一样有没摘要的尾巴，本文的问题和做法照样适用。好处是 autovacuum 的插入阈值按分区算，分区越小越容易触发。

**调小表级 autovacuum_vacuum_insert_scale_factor。**能让 VACUUM 更频繁，顺带汇总 BRIN，还能及时更新可见性映射，对 index-only scan 有好处。但如果目的只是汇总 BRIN，为此频繁 VACUUM 整张大表是用大炮打蚊子。

**全靠 autosummarize。**多数时候够用，但它不持久、有容量上限、依赖 autovacuum 在跑。上面的实验里，一次带着积压请求的重启就留下了 4 个永远不会被汇总的范围。

小结

  • BRIN 对没有摘要的范围一律视为命中，而新写入的页默认没有摘要。时序表的新数据集中在表尾，所以查最新数据和查历史数据都要额外扫过这条尾巴。
  • VACUUM 会补摘要，但跳过页数不足 128 的最后一个范围（恰好 128 页时不跳过）；只插入的表上，autovacuum 要等新增行数超过表的 20% 才触发，表越大间隔越长。
  • autosummarize 只在跨进下一个范围时补上一个，请求存在共享内存里，满了会丢，重启也会丢。
  • 连尾巴一起汇总后，之后把最大值往后推的插入都要改写摘要，实测多 35% 耗时、多 20% WAL。只汇总尾巴之前的范围没有这个代价，尾巴最多让查询多读 1 MB。
  • 推荐 autosummarize = on，再加一个定期补齐 “最后一个已分配页所在范围之前” 的兜底任务；任务用有表属主权限的角色执行，并设 lock_timeout。
  • 物理顺序被补传打乱时，correlation 看起来依旧很高，minmax 摘要却已经失效。可以换 minmax-multi，更好的办法是别让乱序数据混进主表。
