AES-GCM 加密存库的令牌：密文搬到别的行也能解开，用 AAD 把它钉住

服务要替用户保管第三方的 OAuth access token、refresh token，或者两步验证用的 TOTP 密钥。这些东西不能像密码那样只存哈希，程序之后还要用原文，所以常见做法是加密后存库：配置里放一个密钥，用 AES-256-GCM 加密，随机 nonce 拼在密文前面，整体 base64 后加个版本前缀写进列里。

GCM 是认证加密，改一个字节都解不开，看上去已经很稳了。最近读到一段这样的代码，问题不在加密本身，而在它没告诉 GCM 这段密文属于谁：同一个密钥加密所有账号的所有字段，于是一段密文出现在别的行、别的列，照样能解开，程序毫无察觉。

这篇只讲这一件事：GCM 的附加认证数据（AAD）怎么把密文钉在“这个租户、这张表、这一列、这一行、这个用途”上，AAD 该放什么、怎么编码，旧数据怎么迁移、迁移时要注意什么，以及它管不了什么。示例是一个只依赖标准库、可独立运行的 Go 包和测试，测试全部用合成数据，验证正确的 Context 能解密、错误的 Context 会被拒绝、旧格式数据能被正确读出并重写。

测试环境：

  • Go 1.27.4（当前最新版）；示例的 go.mod 写 go 1.24（用到 1.24 新增的 crypto/hkdf 和 cipher.NewGCMWithRandomNonce），用 Go 1.24.0 也跑过测试；
  • 4 核 Intel Xeon 2.10GHz，Linux。

常见写法

下面是这类代码的典型样子（为说明问题重写的，不是原代码）。后文把它叫作“旧写入路径”，示例测试里的 legacyEncrypt 就是这个函数原样照抄，用来生成旧格式的兼容样本：

func legacyEncrypt(configKey, token string) (string, error) {
	sum := sha256.Sum256([]byte(configKey)) // 配置字符串的原始字节 → 32 字节
	block, err := aes.NewCipher(sum[:])
	if err != nil {
		return "", err
	}
	aead, err := cipher.NewGCM(block)
	if err != nil {
		return "", err
	}
	nonce := make([]byte, aead.NonceSize()) // 12 字节随机 nonce
	if _, err := io.ReadFull(rand.Reader, nonce); err != nil {
		return "", err
	}
	ct := aead.Seal(nil, nonce, []byte(token), nil) // 最后一个参数：AAD，传了 nil
	return "app-token:v1:" + base64.RawURLEncoding.EncodeToString(append(nonce, ct...)), nil
}

它做对了不少事：用的是认证加密而不是裸 CBC；nonce 每次随机；格式带版本前缀，以后能升级。问题集中在 Seal 的最后一个参数 nil 上。

GCM 认证的到底是什么

GCM 的标签（tag）覆盖四样东西：密钥、nonce、密文、AAD。解密时只要这四样和加密时一致，Open 就成功。

“这段密文原本存在哪一行”不在这四样里。密钥是全局的，nonce 和密文都在那串字符里，AAD 是空的。所以对 GCM 来说，出现在别处的同一串密文和原地的密文没有任何区别。它保证的是“这串字节是持有密钥的人造的、没被改过”，不保证“它是给这一格造的”。

具体后果有两类：一行的 refresh token 密文出现在另一行，程序会拿着别人的凭证去调第三方接口；同一行的两列内容对调，程序会把 refresh token 当 access token 用。两种情况下解密都成功，没有任何报错。TOTP 密钥同理：哪一行的 TOTP 密钥密文出现在哪一行，程序就按它校验验证码。

谁会这样做，值不值得防

先说清楚威胁模型，免得把它说得比实际更严重。

  • 能任意写库的人，往往还有更直接的路，比如把“已开启两步验证”的开关改成 false。AAD 防不住这种人。
  • 但“加密存库”本来针对的就是数据库不完全可信的情况：备份外泄、只读账号、只能改某些列的注入点、能在后台编辑部分字段的运维工具、多租户里租户管理员能改自己租户的行。在这些场景里，能动的往往是“一部分行、一部分列”。没有 AAD，“这一列的合法值只有持密钥的程序能造出来”这条保证就不成立：不用造，已有的密文就能直接用在别处。
  • 更常见、也更实际的收益是防自己的 bug。查询 JOIN 错了一行、映射结构体时两列写反、复制账号时连密文一起拷了，没有 AAD 时这些都会静默地用上别人的凭证；有了 AAD，它们变成一条解密失败的报错。

所以 AAD 不是万能锁，它是把“这段密文属于哪里”写进认证范围，让错位的密文解不开。代价下文会量：几乎为零。

修法：把位置写进 AAD

AAD 是 Seal/Open 的最后一个参数：它不加密、不存进密文，但会被标签认证。加密和解密时必须给出完全相同的 AAD，否则 Open 失败。所以思路很直接：加密时把“用途、命名空间、表、列、行标识”编码进 AAD；解密时由程序按自己要读的位置重新算一遍 AAD，而不是从密文里读。密文出现在别处，程序算出的 AAD 就变了，解不开。

这和云厂商 KMS 的 encryption context 是同一个想法：AWS KMS 的文档说它把 encryption context 用作附加认证数据（AAD），并且解密时必须提供同样的 encryption context（见文末参考）。

示例里的 Context 和编码：

type Context struct {
	Purpose   string // 例如 "oauth.refresh_token"、"totp.secret"
	Namespace string // 例如租户 ID；RowID 全局唯一时可以留空
	Table     string // 逻辑表名常量
	Column    string // 逻辑列名常量
	RowID     string
}

func (c Context) AAD() []byte {
	b := []byte("box/aad/v2")
	for _, f := range []string{c.Purpose, c.Namespace, c.Table, c.Column, c.RowID} {
		b = binary.AppendUvarint(b, uint64(len(f)))
		b = append(b, f...)
	}
	return b
}

测试 TestWrongContextIsRejected 用合成数据把同一段密文分别交给“另一行、另一租户、另一列、另一用途、另一张表、空 Context”去解，六种都返回错误。完整的包在文末，下面讲设计里的取舍和坑。

选 AAD 字段的坑

1. 行标识：不可变，且在同一张表同一列里唯一

AAD 不存进密文，解密时必须重新算出来。所以 RowID 要用不可变的行标识：主键、应用生成的 UUID。不要用邮箱、用户名、手机号：用户改了邮箱，这行的密文就再也解不开了，数据把自己锁死。

还要看它在什么范围内唯一。如果行号只在租户内唯一（比如每个租户各自从 1 编号，或者分库分表后各自自增），只放 RowID 就不够：两个租户的“第 1 行”会算出同一个 AAD，密文在它们之间照样能通用。这时要把稳定的租户 ID（不是可改的租户名）放进 Namespace。

Table、Column 建议写成代码里的逻辑名常量（如 "accounts"、"refresh_token"），而不是运行时查出来的真实表名。以后重命名表、拆表，只要逻辑名不变，就不用重新加密全表。

2. 自增主键在 INSERT 之前不知道

如果 RowID 用数据库的自增 id，加密时还不知道它。两个办法：

  • 主键改由应用生成（UUID 等），先有 id 再加密、再插入；
  • 在同一个事务里先插入一行占位（密文列为空），拿到 id 后加密再 UPDATE。

不要退回到“先用空 RowID 加密”，那等于没绑行。

3. 编码必须无歧义

最省事的写法是 strings.Join(fields, "|")。只要有一个字段可能包含分隔符，就会出现两个不同的 Context 拼出同一串 AAD：

a := Context{Purpose: "p", Table: "t", Column: "c", RowID: "acme|42"}
b := Context{Purpose: "p", Table: "t", Column: "c|acme", RowID: "42"}
// Join 之后都是 "p||t|c|acme|42"

RowID 里带租户名、用户可控的 slug 时，这不是空想。示例用“每个字段前写 uvarint 长度”的编码，测试 TestAADIsUnambiguous 验证两者不再相同。开头的 "box/aad/v2" 是域分隔标签，将来换编码方式时改版本号，新旧 AAD 永远不会相等。

4. 合法的搬家要重新加密

把账号转移到另一个租户、把行挪进归档表，这些是业务上合法的“搬动”，有了 AAD 之后它们都必须先按旧 Context 解密、再按新 Context 加密。这是 AAD 的本意，不是负担，但要在设计数据迁移脚本时记得。

5. AAD 不保密，也不防回滚

AAD 本身是明文参与计算，不要往里放机密。

更重要的一点：AAD 只能证明“这段密文是给这一格的”，证明不了“这是这一格最新的值”。同一行早先的密文（比如备份里的）Context 完全一样，照样能解开。如果回滚本身有危害（比如旧的 refresh token 已被吊销、换成了新的），要靠别的机制：服务端吊销、在别处单独记录的版本号等。

旧数据怎么迁移

线上已经有一批旧写入路径生成的 app-token:v1: 密文。常见做法和升级密码哈希一样：

  1. 新代码能读旧格式和 v2，写入一律用 v2；
  2. 读到旧格式（或旧密钥）时返回一个“需要重写”的标记，调用方按当前 Context 重新加密写回；
  3. 再跑一个后台任务把没人读到的行也批量重写；
  4. 全部迁完后，关掉旧格式解密。

旧格式要原样认出来

迁移器读旧数据，必须和旧写入路径逐字节一致：同一个前缀，同一种密钥派生。这里有两个容易出错的地方：

  • 前缀。旧路径写的是 app-token:v1:，迁移器就得认 app-token:v1:，不能自己另起一个名字。
  • 密钥的原始字节。旧路径对配置字符串的原始字节做 SHA-256；如果迁移器“顺手”做了 TrimSpace 或别的规范化，而线上配置恰好带了首尾空白或换行（从文件、环境变量里读进来时很常见），派生出的就是另一把密钥，旧数据全部解不开。示例的 LegacyAEAD 刻意不做任何处理。

示例里有两个兼容测试，都用旧写入路径本身生成样本，而不是按迁移器的预期去手工拼：

  • TestLegacyGoldenSample：一个用 legacyEncrypt 生成后写死在测试里的固定样本，配置密钥首尾带空格和换行。按原始字节派生的密钥能解开；先 TrimSpace 再派生则解不开。
  • TestLegacyFreshSample：测试运行时现场调用 legacyEncrypt 生成样本，确认能读出、能重写成 v2。

顺带一提，Go 1.24 新增的 cipher.NewGCMWithRandomNonce 生成 12 字节随机 nonce 并放在密文前面，格式正好是 nonce | 密文 | tag，和旧写入路径手工拼的一样，所以 LegacyAEAD 直接用它解旧数据，不用自己切 nonce。

写回必须带条件

第 2 步“读到就重写”看起来只是一条 UPDATE，但不能无条件地写。读出旧密文、解密、重新加密、写回，这中间有一段时间窗口；如果另一个请求恰好在这时刷新了令牌（OAuth 的 refresh token 每次刷新都可能换新），无条件的 UPDATE 会用刚读到的旧令牌覆盖掉新令牌。

所以写回要检查旧值（或版本号）仍然匹配，不匹配就放弃本次重写。还有一点同样重要：定位这一行要用完整的行键，并且和算 AAD 用的是同一组值。上文允许行号只在租户内唯一，那么行键就是 (tenant_id, id)，只按 id 定位是不够的：

  • 旧格式密文没有绑定任何上下文，同一串旧密文完全可能出现在另一个租户的同号行里（比如当初连数据一起复制过），“旧值相等”并不能证明找到的是同一行；
  • 按版本号比较时更是如此，各租户的版本号都从 1 开始，两个租户的“第 7 行、版本 3”同时存在再正常不过。

只按 id 加旧值或版本去更新，就可能把为租户 A 加密（AAD 里是租户 A）的新密文写进租户 B 的行，之后那一行谁都解不开。正确的做法是从读到写都用同一个行键：

// rewrapRefreshToken 读一行，必要时重写成当前格式。行键是 (tenantID, id)。
// rewritten 为 false 且 err 为 nil：不需要重写，或者这一格已被别人改过、放弃了本次重写。
func rewrapRefreshToken(ctx context.Context, db *sql.DB, k *box.Keyring, tenantID, id string) (rewritten bool, err error) {
	var old string
	err = db.QueryRowContext(ctx,
		`SELECT refresh_token FROM accounts WHERE tenant_id = $1 AND id = $2`,
		tenantID, id).Scan(&old)
	if err != nil {
		return false, err
	}
	// AAD 用的租户和行号，就是上面定位用的那一组。
	c := box.Context{Purpose: "oauth.refresh_token", Namespace: tenantID,
		Table: "accounts", Column: "refresh_token", RowID: id}
	plain, rewrap, err := k.Open(old, c)
	if err != nil || !rewrap {
		return false, err
	}
	res, err := db.ExecContext(ctx,
		`UPDATE accounts SET refresh_token = $1
		 WHERE tenant_id = $2 AND id = $3 AND refresh_token = $4`,
		k.Seal(plain, c), tenantID, id, old)
	if err != nil {
		return false, err
	}
	n, err := res.RowsAffected() // 0：旧值已被别人换掉，放弃本次重写
	return n == 1, err
}

这段代码只为说明定位条件，不在文末的示例包里（用的是 PostgreSQL 的 $n 占位符，和示例包放在一起能编译通过）。用版本号的写法相同，只是把最后一个条件换成 AND token_version = $4，并在同一条语句里 token_version = token_version + 1。

如果是单租户系统、id 是全局唯一的主键（不分库分表、不按租户编号），WHERE id = $id AND refresh_token = $old 就够了，Context 里的 Namespace 留空。但这个简化只在这个前提下成立；一旦行号只在某个范围内唯一，定位条件和 AAD 都要带上那个范围。

受影响行数为 0，说明这一格已经被别人改过了，什么都不用做：新值是别的写入路径用当前格式写的，下次读到时它本来就不需要重写。后台批量重写也用同样的定位和条件。

迁移窗口要尽快关

只要程序还接受旧格式，旧格式的密文就不受 Context 约束：它没有 AAD，解密时程序给什么 Context 都无从校验。哪怕某一行已经重写成了 v2，旧格式的密文出现在这一行时依然能被解开。也就是说，迁移窗口开着一天，AAD 的保护就打一天折扣。所以第 4 步不能拖：确认全表都是 v2（例如统计 LIKE 'app-token:v1:%' 的行数为 0）之后，就把旧格式解密从配置里去掉。测试 TestLegacyRejectedWhenDisabled 确认关掉之后旧格式一律被拒绝。

顺带的两件事：主密钥从哪来、怎么换

这两件不是本文的主题，但在同一段代码里，一起说。先分清两个名字：下面说的主密钥是加密用的随机密钥，放在配置或密钥管理服务里；上文 AAD 里的行标识是数据库里那一行的不可变 ID，是公开的。两者毫无关系。

主密钥派生。 把 SHA-256(配置字符串) 直接当 AES 密钥，如果配置里放的是 32 字节以上的随机值，问题不大；如果放的是人起的口令，就危险了：拿到任意一段密文的人可以离线猜口令，每猜一次只需要一次 SHA-256、一次 AES 密钥扩展和一次 GCM 校验，都是非常便宜的运算。专门的口令哈希函数（PBKDF2、scrypt、Argon2id）之所以故意做慢，就是为了让每一次猜测都昂贵；单次 SHA-256 完全没有这层保护。

示例的做法是：主密钥必须是至少 32 字节的随机值（NewKeyring 对短密钥直接报错），再用 HKDF（crypto/hkdf）派生出真正的数据密钥。HKDF 不会让弱口令变强，它的作用是从一个高熵主密钥按用途派生出互相独立的子密钥。如果真的只能用人记的口令，要换成 Argon2id、scrypt 这类专门的口令派生函数，而不是 SHA-256 或 HKDF。

密钥轮换和 nonce 上限。 随机 96 位 nonce 有碰撞概率，NIST SP 800-38D 第 8.3 节要求随机 IV 构造下同一密钥的加密调用总数不超过 2³²；Go 的 NewGCMWithRandomNonce 文档写的也是同一个数。存令牌一般远到不了这个量，但密钥总有要换的时候（泄露、合规要求）。示例格式是 box:v2:<kid>:<base64>，kid 指明用哪把密钥；新密钥上线后旧密文仍能解开，并返回“需要重写”，和上面的迁移走同一条路，写回同样要带条件。旧 kid 从配置里删掉之后，残留的旧密文就解不开了（TestRotation）。

代价

120 字节的令牌，go test -run x -bench . -benchmem -count 3，取中间值：

操作 耗时 分配
GCM Seal，不带 AAD 305 ns 1 次 / 160 B
GCM Seal，带预先算好的 AAD 327 ns 1 次 / 160 B
GCM Seal，每次现算 AAD 462 ns 5 次 / 344 B
Keyring.Seal 全流程（含 base64、拼前缀） 918 ns 9 次 / 1096 B
Keyring.Open 全流程 648 ns 7 次 / 600 B

AAD 本身多出的认证计算只有几十纳秒（这组数据里约 7%，和三次之间的波动同一量级）；现算 AAD 的编码再多一百多纳秒。整个加解密都在 1 µs 以内，和一次数据库往返比可以忽略。

  go.mod

  box/box_test.go

运行（需要 Go 1.24 或更新）：

cd aeadbox

module example.com/aeadbox

box/box.go：

// Package box 把短小的机密（令牌、TOTP 密钥）加密成一个字符串存进数据库。
// 每段密文都绑定一个 Context：它属于哪个命名空间、哪张表、哪一列、哪一行、做什么用。
package box

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/hkdf"
	"crypto/sha256"
	"encoding/base64"
	"encoding/binary"
	"errors"
	"fmt"
	"strings"
)

// Context 描述一段密文“应该待在哪里”。解密时必须给出完全相同的值。
// RowID 用不会变的行标识（主键、应用生成的 UUID），不要用邮箱、用户名这类可改的字段。
// 如果同表同列的 RowID 只在租户内唯一，把稳定的租户 ID 放进 Namespace。
type Context struct {
	Purpose   string // 例如 "oauth.refresh_token"、"totp.secret"
	Namespace string // 例如租户 ID；RowID 全局唯一时可以留空
	Table     string // 逻辑表名常量
	Column    string // 逻辑列名常量
	RowID     string
}

// AAD 把 Context 编码成附加认证数据：每个字段前面写长度，
// 这样 ("a|b","c") 和 ("a","b|c") 不会撞成同一串字节。
func (c Context) AAD() []byte {
	b := []byte("box/aad/v2")
	for _, f := range []string{c.Purpose, c.Namespace, c.Table, c.Column, c.RowID} {
		b = binary.AppendUvarint(b, uint64(len(f)))
		b = append(b, f...)
	}
	return b
}

var ErrOpen = errors.New("box: cannot open ciphertext")

const (
	// LegacyPrefix 是旧写入路径的格式：
	// "app-token:v1:" + base64url(nonce|密文|tag)，key = SHA-256(配置字符串的原始字节)，不带 AAD。
	LegacyPrefix = "app-token:v1:"
	// 新格式：box:v2:<kid>:<base64url(nonce|密文|tag)>
	prefixV2 = "box:v2:"
)

// Keyring 持有当前密钥、仍可解密的旧密钥，以及（迁移期间）旧格式的解密能力。
type Keyring struct {
	current string
	aeads   map[string]cipher.AEAD
	legacy  cipher.AEAD // nil 表示不再接受旧格式
}

// DeriveAEAD 用 HKDF 从主密钥派生 AES-256 数据密钥。
// 主密钥必须是至少 32 字节的随机值，不是人记的口令。
func DeriveAEAD(masterKey []byte) (cipher.AEAD, error) {
	if len(masterKey) < 32 {
		return nil, errors.New("box: master key must be at least 32 random bytes")
	}
	key, err := hkdf.Key(sha256.New, masterKey, nil, "box/v2 aes-256-gcm", 32)
	if err != nil {
		return nil, err
	}
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, err
	}
	// Go 1.24+：随机 96 位 nonce，Seal 时放在密文前面，Open 时取出来。
	return cipher.NewGCMWithRandomNonce(block)
}

// LegacyAEAD 复现旧写入路径的密钥：对配置字符串的原始字节做 SHA-256，
// 不做 TrimSpace 或任何规范化，否则旧数据会解不开。
// 线上格式（nonce|密文|tag）和 NewGCMWithRandomNonce 一样，可以直接复用。
func LegacyAEAD(configKey string) (cipher.AEAD, error) {
	sum := sha256.Sum256([]byte(configKey))
	block, err := aes.NewCipher(sum[:])
	if err != nil {
		return nil, err
	}
	return cipher.NewGCMWithRandomNonce(block)
}

// NewKeyring 的 masterKeys 是 kid -> 主密钥，current 必须在其中。
// legacy 为 nil 表示不接受旧格式。
func NewKeyring(current string, masterKeys map[string][]byte, legacy cipher.AEAD) (*Keyring, error) {
	k := &Keyring{current: current, aeads: map[string]cipher.AEAD{}, legacy: legacy}
	for kid, m := range masterKeys {
		if kid == "" || strings.Contains(kid, ":") {
			return nil, fmt.Errorf("box: bad kid %q", kid)
		}
		a, err := DeriveAEAD(m)
		if err != nil {
			return nil, fmt.Errorf("box: kid %q: %w", kid, err)
		}
		k.aeads[kid] = a
	}
	if k.aeads[current] == nil {
		return nil, fmt.Errorf("box: current kid %q not in keyring", current)
	}
	return k, nil
}

// Seal 用当前密钥加密，并把 ctx 绑进认证标签。
func (k *Keyring) Seal(plaintext string, ctx Context) string {
	ct := k.aeads[k.current].Seal(nil, nil, []byte(plaintext), ctx.AAD())
	return prefixV2 + k.current + ":" + base64.RawURLEncoding.EncodeToString(ct)
}

// Open 解密。rewrap 为 true 表示这段密文是旧格式或旧密钥，调用方可以用 Seal 重写，
// 但写回必须是带条件的更新（旧值或版本仍匹配才写），见文章“旧数据怎么迁移”。
func (k *Keyring) Open(s string, ctx Context) (plaintext string, rewrap bool, err error) {
	switch {
	case strings.HasPrefix(s, prefixV2):
		kid, enc, ok := strings.Cut(strings.TrimPrefix(s, prefixV2), ":")
		a := k.aeads[kid]
		if !ok || a == nil {
			return "", false, ErrOpen
		}
		raw, err := base64.RawURLEncoding.DecodeString(enc)
		if err != nil {
			return "", false, ErrOpen
		}
		pt, err := a.Open(nil, nil, raw, ctx.AAD())
		if err != nil {
			return "", false, ErrOpen
		}
		return string(pt), kid != k.current, nil
	case strings.HasPrefix(s, LegacyPrefix) && k.legacy != nil:
		raw, err := base64.RawURLEncoding.DecodeString(strings.TrimPrefix(s, LegacyPrefix))
		if err != nil {
			return "", false, ErrOpen
		}
		pt, err := k.legacy.Open(nil, nil, raw, nil) // 旧格式没有 AAD，ctx 无从校验
		if err != nil {
			return "", false, ErrOpen
		}
		return string(pt), true, nil
	}
	return "", false, ErrOpen
}

// legacyEncrypt 就是文章开头那段旧写入路径，原样保留，用来生成兼容样本。
func legacyEncrypt(configKey, token string) (string, error) {
	sum := sha256.Sum256([]byte(configKey))
	block, err := aes.NewCipher(sum[:])
	if err != nil {
		return "", err
	}
	aead, err := cipher.NewGCM(block)
	if err != nil {
		return "", err
	}
	nonce := make([]byte, aead.NonceSize())
	if _, err := io.ReadFull(rand.Reader, nonce); err != nil {
		return "", err
	}
	ct := aead.Seal(nil, nonce, []byte(token), nil)
	return "app-token:v1:" + base64.RawURLEncoding.EncodeToString(append(nonce, ct...)), nil
}

小结

用 AES-GCM 把机密加密存库时，对照这几条检查一遍：

  • Seal/Open 的 AAD 不要传 nil，至少放“用途 + 表 + 列 + 行标识”，解密时由程序按要读的位置重新计算；
  • 行标识用不可变的值；它只在租户内唯一时，把稳定的租户 ID 也放进去；表名、列名用逻辑名常量；
  • AAD 编码要无歧义（长度前缀），带一个版本标签；
  • 迁移时旧格式要和旧写入路径逐字节一致（前缀、密钥原始字节），用旧路径生成的样本做兼容测试；
  • 惰性重写和批量重写都按完整行键定位、再比较旧值或版本，不匹配就放弃，AAD 用同一组行键；迁完立刻关掉旧格式解密；
  • AAD 管“属于哪一格”，不管“是不是最新”，防回滚另想办法；
  • 主密钥用至少 32 字节的随机值，配合 HKDF 派生；格式里带密钥 ID，给轮换留路。
